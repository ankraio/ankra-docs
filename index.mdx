Running Kubernetes well usually means a pile of Helm values, a GitOps tool to babysit, a runbook per failure, and one person who knows how it all fits together. Ankra is the AI platform engineer that takes that pile off your team: you describe what a cluster should run, Ankra deploys it and keeps it in sync, and its AI reads your logs, events and deploy history to tell you why something broke and how to fix it.

It is built for platform engineers and developers who want production Kubernetes without hand-maintaining the machinery around it.

## How it fits together

<Frame>
  <img className="block w-full dark:hidden" src="/images/how-it-fits-together.svg" alt="An organisation owns clusters. Each cluster runs the Ankra agent and deploys Stacks. A Stack is made of add-ons, which are Helm charts, and manifests, which are Kubernetes YAML. A Git repository is optional and syncs with the Stack in both directions." />
  <img className="hidden w-full dark:block" src="/images/how-it-fits-together-dark.svg" alt="An organisation owns clusters. Each cluster runs the Ankra agent and deploys Stacks. A Stack is made of add-ons, which are Helm charts, and manifests, which are Kubernetes YAML. A Git repository is optional and syncs with the Stack in both directions." />
</Frame>

- An **organisation** is your team's account: members, roles, credentials and billing.
- A **cluster** is any Kubernetes cluster running the lightweight [Ankra agent](/concepts/cluster-agent). The agent connects out to Ankra, so it works behind firewalls and NAT.
- A **Stack** is what a cluster should run: [add-ons](/concepts/addons) (Helm charts) and [manifests](/concepts/stacks#manifests) (your own YAML), with [variables](/concepts/variables) for what differs between clusters.
- An **application** is your own code from a GitHub repository. Ankra Pipelines builds, checks and publishes it, and Ankra deploys it to one or more clusters - see [Applications](/concepts/applications).
- **Git is optional.** Stacks deploy straight through the agent. Connect a repository when you want every change reviewed and versioned, and edits flow both ways - see [GitOps](/concepts/gitops).

## Find your way around

After the first screen, **Skip to Home** (or **Go to Home**, once you have finished one of the four choices) takes you into the portal at `/next`.

- **Home** is **Ask Ankra**: a conversation box where you ask Ankra AI about your organisation. Below it, **Needs you** lists what waits on you, **In** *your organisation* lists what you already have, and **Starting points** lists the choices from the first screen you have not finished.
- **Needs you**, under **Find** at the top of every menu, counts what waits on you. Under it the sidebar has three groups. **Workspace** holds **Home**, **Applications**, **Clusters**, **Managed services**, **Cost** and **Security**. **Platform** folds open and holds **Infrastructure** (where **Cluster meshes** are), **Build & delivery**, **Integrations & alerts** and **Ankra AI**. **Settings and help** holds **Identity & access**, **Settings** and **Support**. An area's pages open under its row.
- A cluster's own menu opens when you open the cluster from **Clusters**. It starts with pages such as **Overview**, **Health**, **Metrics**, **Security** and **Settings**, and keeps **Stacks**, **Operations**, **Kubernetes**, **Kubectl access** and **Audit log** under **Technical details**.
- Press <kbd>⌘</kbd> + <kbd>J</kbd> (<kbd>Ctrl</kbd> + <kbd>J</kbd> on Windows and Linux) on any page to open Ask Ankra.

## Run your CI on your own clusters

Ankra CI runs a repository's tests, image builds and security scans as Kubernetes Jobs on a cluster you already connected, and reports back as a check on every pull request. [Get started with Ankra CI](/get-started/ankra-ci) moves your first repository in about 20 minutes.

## Work from your own tools

The web UI, the CLI, the MCP server and the in-product AI all use the same tools and the same permissions, so anything you can do in one you can do in the others.

<CliVersion since="0.71.0" />

<Tabs>
  <Tab title="CLI">
    ```bash
    curl -fsSL https://ankra.ai/install | sh   # installs the CLI, then signs you up or in
    ankra chat "why is the payments pod crashing?" --cluster prod
    ```

    See the [Ankra CLI](/integrations/ankra-cli) guide for Windows, Homebrew and the other ways to install.
  </Tab>
  <Tab title="AI assistants (MCP)">
    Connect Claude, Cursor or any other MCP client to Ankra's remote MCP server. For Claude Code, Cursor or Codex, one command creates a read-only token, registers the server and offers to install the Ankra skills that teach the assistant Ankra's conventions:

    ```bash
    ankra mcp connect --client claude-code
    ```

    Add `--write` when the assistant should change things, not only read. Setup for every client is in the [MCP Server](/platform/mcp-server) guide, and the [MCP Tool Reference](/platform/mcp-tools) lists every tool.
  </Tab>
  <Tab title="CI/CD">
    Your pipeline builds and pushes an image, commits the new tag to your GitOps repository, and Ankra deploys it - [Ship Your App](/guides/deliver-your-app) compares this with letting Ankra build and redeploy on every merge. Plain CI jobs can also call `ankra chat` and `ankra cluster apply` - see [Use the ankra CLI in CI](/guides/pipeline-agents).
  </Tab>
</Tabs>

<Note>
**Automating Ankra or building an agent on it?** Use the [MCP server](/platform/mcp-server) or the [CLI](/integrations/ankra-cli) rather than driving the web UI with a browser. Both use scoped tokens, and every call lands in your organisation's audit log.
</Note>
