<Warning>
**Closed beta.** Projects are in closed beta. The model is stable but the surface may still change, and projects are enabled per organisation on request. [Contact support](/platform/support) to have them turned on for your organisation. Until they are on, every organisation has exactly one invisible project, the project routes answer `404`, and nothing on this page changes what you see.
</Warning>

A **project** is a room inside an [organisation](/concepts/organisations). The organisation keeps everything that is about people and money - members, roles, invitations, billing, single sign-on, the AI provider. A project owns a slice of the resource estate: its clusters, applications, environments, stack profiles, pipeline repositories, AI tickets and automations, incidents, and the cost those produce. A member with a role in one project sees that project and nothing else; a member with a role on the organisation sees every project.

Projects exist for the organisation that holds several teams, products or stages that should not see or change each other's clusters, without splitting into several organisations and several invoices.

<Note>
A project is not a cluster group. A [cluster group](/guides/roles-and-access#cluster-groups) is a label-selected set of clusters used as an assignment scope and nothing more. A project is a tenancy boundary: a resource belongs to exactly one, listings and cost are per project, and tokens can be confined to one.
</Note>

## What lives where

| Level | Holds |
| --- | --- |
| **Organisation** | Members and invitations, role definitions, billing (customer, plan, invoices, activation), SSO, feature flags, the AI provider and AI configuration (MCP servers, custom tools, skills, playbooks), the Harbor registry project, support tickets, cluster groups |
| **Project** (always exactly one) | Clusters and everything reached through a cluster, applications, environments, stack profiles, pipeline repositories, AI tickets / automations / workspaces, incidents, cost budgets and autopilot defaults |
| **Project, or organisation-wide** | Credentials, Helm and OCI registries, backup vaults and object storage buckets, organisation variables, notification routes, DNS zones |

The third row is the shared kinds. A credential, a registry or a variable is either pinned to one project or **organisation-wide**, in which case every project sees and uses it. Reading an organisation-wide resource needs nothing beyond the ordinary read permission. Changing, revealing or deleting one needs the matching permission held **on the organisation**, not only in a project: a role assigned at project scope can edit the project's own credentials and variables, and reads past the organisation's. The refusal says so - `403 Organisation-wide resources require an organisation-level grant`.

## The default project

Every organisation carries a reserved project whose slug is `default`. It is created with the organisation, it cannot be deleted, and when projects are turned on for an organisation every existing cluster, application and other project-scoped resource is already in it. Shared kinds that existed before stay organisation-wide. So the day projects are enabled nothing moves and nobody loses sight of anything; you create further projects and move resources into them deliberately.

A project has a name (up to 128 characters), a slug (`a-z`, `0-9` and hyphens, up to 63 characters, immutable, never shaped like a UUID) and an optional description. Slugs are unique within the organisation.

## Your current project

Every request acts in one project. It is resolved once, when the request is authenticated, in this order:

1. **The token's pin.** An MCP token or a [service token](/guides/service-tokens) is minted inside a project and stays confined to it.
2. **The `X-Ankra-Project-Id` header** on a REST token call, naming a project of the current organisation by id. It is refused with `403 Project not found in this organisation` when the id is another organisation's, and refused outright on a pinned token that names a different project.
3. **Your current project** in this organisation, which `POST /api/v1/org/projects/switch` sets. Each organisation you belong to remembers its own current project.
4. **The default project.**

Switching is server-side, exactly like switching organisations: after a switch, every surface - API, MCP, portal - reads and writes in the new project. `GET /api/v1/org/projects/current` tells you where you are, and `GET /api/v1/org/projects` lists the projects you can reach, each with `is_current` and `is_default`.

<Tip>
Older CLIs, Terraform and scripts send no project header. They keep operating in the default project, and the only thing that changes for them is a resource an administrator has moved out of it.
</Tip>

## Roles at project scope

A project is the fourth [assignment scope](/guides/roles-and-access#scopes), beside the organisation, a cluster and a cluster group. A role assigned at project scope grants its resource permissions on every cluster the project holds now and later, and on the project's applications, environments, profiles, repositories and shared resources.

A project assignment can never confer the permissions that are about the organisation as a whole. Whatever role is assigned, these are dropped from a project grant: `organisation.*`, `members.*`, `billing.*`, `tokens.*`, `audit.*`, `projects.*`, `kube_access.manage`, `kube_access.policy`, `sops.manage`, `git.manage`, `security.manage`, `ai.manage`, `workspaces.manage` and `profiles.share`. An `admin` assigned to one project is the resource half of admin inside that project, and cannot invite members, see invoices or create projects.

Creating, renaming, deleting and moving between projects needs `projects.manage`, which owners and admins hold at organisation scope. Listing projects needs `projects.read`, which every built-in role holds.

## Tokens are pinned

Tokens that carry `mcp:` scopes, and every service token, are **pinned** to the project they were created in. A pinned token:

- reads and writes in that project only, however the request is phrased - `?project_id=all` on a cost route and `X-Ankra-Project-Id` naming another project are both refused;
- cannot switch organisations either, as before;
- stops authenticating, with a `403`, if its project is deleted. Mint a new one in the project that replaced it.

A personal REST token without `mcp:` scopes follows its owner's current project and accepts the header. See [API Tokens](/reference/tokens).

## Moving resources between projects

`POST /api/v1/org/projects/move` moves one resource - a cluster, an application, a stack profile, a credential, a registry, a vault, a bucket, a variable, a notification route or a DNS zone - into another project, or makes a shared kind organisation-wide. It is one transaction, audited as `move_to_project`, and it carries the rows whose project is derived from the resource: a cluster takes its DNS zones, incidents, AI tickets and the notification routes pinned to it; an application takes its connected pipeline repositories; a profile takes its drafts.

A cluster is not moved while an operation is running on it (`409`, code `operations_in_flight`), and a DNS zone bound to a cluster follows the cluster rather than moving on its own (`follows_cluster`). Cost already metered stays attributed to the project the cluster was in at the time; only hours from the move onwards count against the destination.

A project can be deleted only once nothing is in it: every cluster, application and other strictly scoped resource moved out, and no shared resource still pinned to it. The refusal lists what remains, per kind. Deleting a project retires the role assignments made at its scope, moves every member whose current project it was back to the default, and removes its budgets and autopilot defaults.

## Cost by project

Cost is metered per project from the moment projects are on, so a report for a month in which a cluster moved shows its cost split between the two projects. Every cost route and tool takes `project_id`: a project id for one project, `all` for the whole organisation, and nothing for your current project. The fleet summary gains `by_project`, with an **unattributed** bucket for spend no project can claim, such as credential-level waste; cost budgets gain a `project` scope; the cost autopilot gains per-project defaults between the organisation's policy and a cluster's own override. [Cloud Cost](/platform/cloud-cost) has the detail.

Billing does not split. The invoice stays one per organisation. `GET /api/v1/org/billing/analytics/by-project` is a read-only showback of worker vCPU-hours per project over a window, for charging teams back internally. See [Billing](/platform/billing#showback-by-project-closed-beta).

## Ankra's AI and the MCP server

The [MCP server](/platform/mcp-server) and the AI Assistant act in the current project of the token or session. `list_projects` and `get_current_project` say where a session is, and `move_cluster_to_project` / `move_application_to_project` are the moves, confirmed before they run. `get_organisation` reports the current project, and the cost tools take the same `project_id` as the routes. Portal links Ankra hands you carry `?project=` beside `?org=`, so the link opens in the right room. See [MCP Tools](/platform/mcp-tools#projects-closed-beta).

## Ankra Cloud

For organisations that also use [Ankra Cloud](/guides/ankra-cloud-clusters), the platform is the source of truth for projects and the Cloud keeps a mirror: it learns the project list and each member's reach when they sign in, and between sign-ins the platform pushes every change. Servers the platform creates for a cluster carry the project in the `platform.ankra.io/project-id` label beside the cluster label. Projects are never created, renamed or deleted from the Cloud.
