There are three ways to get a cluster into Ankra. If you already run one - EKS, GKE, AKS, k3s, on-premises, even minikube on your laptop - import it in a couple of minutes with one `helm` command. If you need a new one, Ankra can build it on your own cloud account, or create a cluster your cloud provider runs for you. A cluster you import, or one built on your own account, stays yours along with its servers: they keep running if you ever disconnect from Ankra. A [Playground](/guides/cluster-sandbox) and [Ankra Cloud](/guides/ankra-cloud-clusters) (Closed Beta) are the exceptions, because they run on servers Ankra operates.

## Which path is mine?

| You have... | You want... | Choose | Start here |
|---|---|---|---|
| A running cluster, anywhere | To manage it with Ankra | **Import** | [Connect an existing cluster](#connect-an-existing-cluster) below |
| A cloud or server account | A new cluster where Ankra installs, upgrades and operates Kubernetes for you | **Ankra Managed** | A provider guide under [Build a new cluster](#build-a-new-cluster) |
| An AWS, Google Cloud, Azure, DigitalOcean, OVHcloud, UpCloud or Scaleway (Closed Beta) account | A new cluster that your cloud provider runs (EKS, GKE, AKS, DOKS, MKS, UKS, Kapsule) | **Cloud Managed** | [Managed Kubernetes](/guides/managed-kubernetes) |
| Nothing yet | To try Ankra first | **Playground** | [Playground](/guides/cluster-sandbox) - a real cluster in about two minutes, no cloud account needed |

<Tip>
**Already running EKS, GKE or AKS?** You can connect it either way. The `helm` install below needs no cloud credential. The **Find a managed cluster** tab on the same page uses your cloud credential instead: Ankra lists the Kubernetes clusters your cloud account runs, you pick one under **Cluster to connect**, and connecting it does not change it. [Managed Kubernetes](/guides/managed-kubernetes#importing-existing-clusters) explains what such a cluster gains.
</Tip>

## Connect an existing cluster

Connecting installs the Ankra agent in your cluster. The agent only makes outbound connections to Ankra, and Ankra sends work back over that same connection, so the cluster can sit behind a firewall, NAT or a private network. Nothing is opened inbound and Ankra holds no kubeconfig.

It takes about five minutes.

### Before you start

- **A payment method on the organisation.** Without one the page shows **Add a payment method before you connect a cluster**: "Ankra connects a cluster only for an organisation with a payment method on file. Free credit does not replace it: without one, adding the cluster is refused." Add one under **Plan and billing** ([Billing](/platform/billing#credit-and-payment-method)). Only the free [playground](/guides/cluster-sandbox) runs without one.
- **A role that may add clusters, and the `agents.manage` permission** to see the install command, because the command contains the agent's access token. [Roles and access](/guides/roles-and-access) lists the permissions.
- **`helm` and `kubectl`**, with a kubeconfig whose account may create a namespace and cluster-wide roles.
- **Outbound access** from the cluster to `platform.ankra.app:443` (the Ankra API), `command.platform.ankra.app:4222` (the channel Ankra sends work over, TLS) and `registry.ankra.cloud:443` (the agent image and its chart).

<Warning>
The agent runs with full admin rights on the cluster: a ClusterRole, `ankra-agent-ankra`, that allows every verb on every resource and URL. Ankra operates the cluster through it, and the agent's chart offers no narrower role. [Agent compliance](/security/agent-compliance) describes the agent, and [agent hardening](/security/agent-hardening) lists the controls you can put around it.
</Warning>

<Steps>
  <Step title="Name the cluster">
    Open **Infrastructure → Clusters** and click **Connect a cluster** (`/next/clusters/import`). The page **Connect an existing cluster** opens on the **Install the agent** tab.

    Fill in **Cluster name** (3 to 53 lowercase letters, digits and hyphens, starting with a letter) and answer **What will this cluster run?**: **Production**, **Staging**, **Development**, **Testing**, **Local** or **Something else**. Ankra treats changes on the cluster as carefully as this answer says, and never stops a production cluster at night. Click **Get the install command**.

    **You should see** the page change to **Install the agent in my-cluster**, with a **Waiting for the agent to connect** badge.
  </Step>
  <Step title="Run the install command">
    Click **Show the install command**. The page shows two commands. Run the first to check which cluster your kubeconfig points at, because the install goes into that cluster:

    ```bash
    kubectl config current-context
    ```

    Then copy the second, **Install the Ankra agent**, exactly as shown and run it. It carries this cluster's own token and pins the agent version, and has this shape:

    ```bash
    helm upgrade --install ankra-agent oci://registry.ankra.cloud/ankra/ankra-agent \
      --version <version> \
      --set config.ankra_url=https://platform.ankra.app \
      --set config.token=<your-cluster-token> \
      --namespace=ankra --create-namespace
    ```

    **You should see** Helm report the release `ankra-agent` deployed in the namespace `ankra`.
  </Step>
  <Step title="Check it is connected">
    The page watches for the agent, which usually reports in within a minute. **Check now** looks straight away.

    **You should see** the page turn into **my-cluster is connected**: "The Ankra agent is running in the cluster and reporting to Ankra." Click **Open the cluster**. In **Infrastructure → Clusters** the cluster shows **Online**.
  </Step>
</Steps>

### From the CLI

<CliVersion since="0.79.0" />

```bash
ankra cluster connect my-cluster --environment production
```

**You should see** `Cluster 'my-cluster' is registered. Install the Ankra agent to connect it.`, then the two commands the portal shows: one that prints which cluster kubectl points at, and the `helm upgrade --install` command with this cluster's token. Run them where kubectl and Helm reach the cluster.

`--environment` takes `production`, `staging`, `development`, `testing`, `local` or a name of your own. Without it the cluster is labelled development. A name another cluster in the organisation already has is refused, and nothing is changed.

**Check:** the cluster is in `ankra cluster list`, and shows **Online** in **Infrastructure → Clusters**.

To declare Stacks, add-ons or a GitOps repository in the same step, write an [ImportCluster file](/reference/importcluster) and run `ankra cluster apply -f cluster.yaml --wait` instead. It prints the same install command. [Import clusters as code](/guides/import-clusters-as-code) covers that route.

### What the agent installs

| | |
| --- | --- |
| **In the namespace `ankra`** | One Deployment (`ankra-agent`), its Service, two service accounts and its Secret |
| **Cluster-wide** | One ClusterRole and one ClusterRoleBinding, both named `ankra-agent-ankra`. No DaemonSet, no CRDs, no webhooks |
| **Its token** | A lasting credential: it does not expire, and the agent keeps it in the Secret `ankra-identity-secret` in the namespace `ankra`. It stops working when you replace it (`ankra cluster agent token --generate`) or remove the cluster from Ankra. Run from the command line, it also lands in your shell history and in Helm's release values, where `helm get values` shows it |
| **After it connects** | Ankra reads the cluster and its metrics and keeps its own agent up to date, which you can turn off for the cluster. It deploys nothing and changes nothing else until you ask |

To see everything the chart would create without applying it:

```bash
helm template ankra-agent oci://registry.ankra.cloud/ankra/ankra-agent --namespace ankra
```

### When it does not connect

| What you see | Why | What to do |
| --- | --- | --- |
| **The cluster was not added**, with the payment sentence above | The organisation has no payment method | Add one under **Plan and billing**, then try again. [Why was I refused?](/guides/why-was-i-refused) covers each refusal |
| **Your role does not allow adding clusters.** | Your role cannot create clusters | Ask an organisation owner for a role that can |
| **Your role cannot show the install command** | The command holds the agent's token, so it needs `agents.manage` | Ask an organisation owner to show it, or to grant you the permission |
| **Waiting for the agent to connect** does not change | The agent pod is not running, or cannot reach Ankra | Run the three commands below |

```bash
kubectl get pods -n ankra -l app.kubernetes.io/name=ankra-agent
kubectl describe pod -n ankra -l app.kubernetes.io/name=ankra-agent
kubectl logs -n ankra deploy/ankra-agent
```

- The pod stays `Pending` or cannot pull its image: the `describe` output says why.
- It keeps restarting: the logs say why.
- It runs and nothing arrives: the cluster cannot reach the three addresses under [Before you start](#before-you-start).
- Helm stopped with a permissions error: the account that ran it must be allowed to create a namespace and cluster-wide roles.

[Ankra Agent](/concepts/cluster-agent) has more on the agent itself.

### Remove it again

Removing the cluster in Ankra takes away the agent's access at once and sends nothing to the cluster. The agent stays installed until you remove it:

```bash
helm uninstall ankra-agent -n ankra
kubectl delete namespace ankra
```

Check that nothing cluster-wide is left. Both lines answer `NotFound` once it is gone:

```bash
kubectl get clusterrole,clusterrolebinding ankra-agent-ankra
```

Running Kubernetes on your laptop? [Run Kubernetes locally](/guides/minikube) sets up minikube and connects it.

## Build a new cluster

### Ankra Managed

Ankra creates the servers, private network and bastion on your own account, installs Kubernetes (kubeadm with Cilium by default, or k3s), and then operates it for you: upgrades, node groups, stop and start. The provider bills you directly. Creating one needs a [payment method](/platform/billing#credit-and-payment-method) on your Ankra organisation.

### Cloud Managed

Your cloud provider runs the Kubernetes control plane; Ankra creates the cluster and its node pools through your cloud credential, connects the agent, and manages what runs on it. Start with [Managed Kubernetes](/guides/managed-kubernetes), which compares the options, or go straight to [EKS](/guides/eks-clusters), [GKE](/guides/gke-clusters), [AKS](/guides/aks-clusters), [DOKS](/guides/doks-clusters), [OVHcloud MKS](/guides/ovh-mks-clusters), [UKS](/guides/uks-clusters), [Scaleway Kapsule](/guides/managed-kubernetes#scaleway-kapsule-closed-beta) (closed beta) or [Ankra Cloud Kubernetes](/guides/ankra-cloud-kubernetes) (closed beta).
