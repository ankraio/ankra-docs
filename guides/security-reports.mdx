Ankra can email a recurring security report for a cluster: a summary of its open vulnerabilities drawn from the same data as [cluster security](/guides/cluster-security). A report runs weekly or monthly, goes to a list of addresses you choose, and can also be sent at once.

The portal has no screen for report schedules. Set them up with `ankra security report-schedule` or from Ankra AI and the MCP server, as below.

## What the report contains

The email's subject names the cluster and its open critical and high counts, for example `Security report: my-cluster - 3 actionable critical, 12 actionable high (+2 severe vs last period)`. The trend in brackets appears when the count of critical and high findings changed since the previous report.

The body has:

- **A known-exploited callout** when the cluster carries findings on the CISA Known Exploited Vulnerabilities catalogue.
- **Fix these first**: the package upgrades available right now, so the report gives actions rather than only a list of CVEs.
- **Top actionable CVEs**: each with its severity, a **KEV** marker where CISA lists it, and its EPSS exploitation probability where the platform holds one.
- **OS updates**: whether the cluster's [OS updates](/guides/os-patching#automatic-or-advisory) are automatic or advisory and why, what the last dry run found pending, the security lag, and the node package and node kernel findings still open. On a cluster Ankra patches, **Patch the nodes: next window or now** opens the cluster's OS updates, where you start the rolling run. An advisory cluster is never patched until someone does. On a cluster Ankra does not patch, the section lists the node findings and says they are fixed outside Ankra.

Accepted risks are left out of the open counts: the report is for what still needs attention.

## Before you start

- **A scanner on the cluster.** Without scanner reports there is nothing to report on. See [Turn on scanning](/guides/cluster-security#turn-on-scanning).
- **The `clusters.write` permission** to set a schedule or send a report. See [Roles and access](/guides/roles-and-access).
- **The Ankra CLI**, or an MCP client connected to Ankra. See [MCP tools](/platform/mcp-tools).

## Schedule a report

<Tabs>
  <Tab title="CLI">
    <CliVersion since="0.65.0" />

    Create or replace the schedule. `--frequency` is `weekly` or `monthly`, and `--recipient` repeats, up to 20 addresses. Recipients do not need to be Ankra users. The command asks before it saves; `--yes` skips the question.

    ```bash
    ankra security report-schedule set --cluster my-cluster --frequency weekly \
      --recipient ops@example.com --recipient security@example.com
    ```

    Add `--disabled` to store the schedule paused. At least one recipient is required while the schedule is enabled.

    Check it:

    ```bash
    ankra security report-schedule --cluster my-cluster
    ```

    The output shows the frequency, the recipients, whether it is enabled, and when it was last sent and is next due. A cluster without a schedule reads "not configured".
  </Tab>
  <Tab title="MCP">
    Ask Ankra AI, or call the tools from your MCP client:

    - `set_cluster_security_report_schedule` stores the frequency, up to 20 recipients and whether sending is enabled. It replaces the whole schedule and is confirmed before it runs.
    - `get_cluster_security_report_schedule` reads it back: whether one is configured, weekly or monthly, the recipients, enabled or paused, when it last went out and when it is next due.
  </Tab>
</Tabs>

## Send a report now

Send the current report to the schedule's recipients at once, to check delivery after setting up a schedule or to share the posture ahead of a review.

<Tabs>
  <Tab title="CLI">
    ```bash
    ankra security report-schedule send --cluster my-cluster
    ```

    The command asks first; `--yes` skips the question.
  </Tab>
  <Tab title="MCP">
    Call `send_cluster_security_report_now`. It is confirmed before it runs.
  </Tab>
</Tabs>

## Verify

Run `ankra security report-schedule --cluster my-cluster`. After a send, the time it was last sent is filled in, and each recipient has the email in their inbox.

With an API token, the same schedule is `GET` and `PUT /api/v1/org/clusters/imported/{cluster_id}/security/report-schedule`, and `POST .../report-schedule/send-now` sends one.

## What can go wrong

| Symptom | Likely cause | Fix |
|---------|--------------|-----|
| The report shows no findings | The cluster has no scanner, or it has not reported yet | Check the cluster's **Last scan** on **Infrastructure → Clusters → *your cluster* → Security**. See [Turn on scanning](/guides/cluster-security#turn-on-scanning) |
| No email arrives | The schedule is paused, or has no recipients | Run `ankra security report-schedule --cluster my-cluster`, then `set` again without `--disabled` and with at least one `--recipient` |
