[Amazon EKS](https://aws.amazon.com/eks/) is AWS's managed Kubernetes service. AWS runs the control plane; Ankra provisions the cluster, then manages everything on top - node groups, Kubernetes upgrades, addons, stacks, GitOps, and AI-assisted operations.

This page covers EKS specifically. For the shared concepts across all managed providers - live options, discovery/import, and day-2 API patterns - see [Managed Kubernetes](/guides/managed-kubernetes).

<Tip>
**Already running EKS?** You can bring it into Ankra two ways. A **managed import** uses your AWS credential: open **Infrastructure → Clusters → Connect a cluster** and choose the **Find a managed cluster** tab, or run `ankra cluster managed discover --provider eks` and `ankra cluster managed import --provider eks`. Ankra fetches the kubeconfig and installs the agent, so there is nothing to run on the cluster, and the cluster gains the same node-pool and upgrade operations as clusters Ankra created. The **Helm import** needs no cloud credential and works for any cluster: the **Install the agent** tab on the same page gives you the command - see [Import an existing cluster](/guides/import-cluster).
</Tip>

## Why EKS with Ankra

- **Automatic IAM setup** - Ankra creates the required IAM roles for the cluster and node groups, so you do not have to wire them by hand.
- **Bring your own network, or don't** - pick a VPC, specify `subnet_ids` and `security_group_ids`, or let Ankra use your default VPC subnets.
- **Live pricing and options** - regions, Kubernetes versions, and EC2 instance types are fetched live with your AWS credential, including spot capacity and autoscaling.

## Before you start

- An **AWS credential** stored in Ankra (access keys or an IAM role) with permissions for **EKS**, **EC2**, and **IAM role management**. The IAM-role wizard's **Provisioning (EKS clusters)** access level creates a correctly scoped role for you. See [AWS Credentials](/platform/credentials/aws). If you have none, the create form shows **Add an Amazon EKS credential first** with an **Add a credential** button.
- A **payment method** on the organisation. Without one the review step warns "A payment method is required to create this cluster." and the create is refused - see [Billing](/platform/billing).
- A role with the `clusters.create` permission. Without it **Add a cluster** reads "Your role does not allow creating clusters."

GitOps is optional: connect a repository at creation and Ankra commits the cluster's stack definitions to Git.

## Creating an EKS cluster

<Tabs>
  <Tab title="Portal">
    The portal takes a VPC but not subnets, security groups or control-plane logging. Set those through the API.

    <Steps>
      <Step title="Choose AWS, run by AWS">
        Open **Infrastructure → Clusters → Add a cluster** (`/next/clusters/new`). Choose **AWS** as the provider, then **Provider managed** under **Who runs Kubernetes on AWS?**. The page now reads **Add an Amazon EKS cluster**.
      </Step>
      <Step title="Name and purpose">
        Enter a **Cluster name** (EKS allows letters, digits and hyphens) and answer **What will this cluster run?**. The answer is required before you can review.
      </Step>
      <Step title="Where it runs">
        Pick the **Amazon EKS credential** and a **Region** (for example `eu-west-1`). Regions load live from AWS. Then pick the **VPC** the cluster runs in.
      </Step>
      <Step title="Worker nodes">
        Each node group has a **Group name**, a number of **Nodes**, a **Size for** the group (instance types with live pricing) and **Scale this group automatically** with **At least** and **At most**. **Add a node group** adds another. **Placement, labels and taints** holds node labels and taints, and **Use spot capacity** with an optional **Maximum spot price per hour**.
      </Step>
      <Step title="Kubernetes and Git">
        Pick a **Kubernetes version** or keep **Provider default**. Under **Cluster configuration in Git**, optionally choose a **Git connection**, **Repository** and **Branch**.
      </Step>
      <Step title="Review and create">
        Click **Review cluster**, check the settings and the **Checks before creating**, then click **Create cluster**. Ankra creates the IAM roles, provisions the cluster, retrieves the kubeconfig and installs the Ankra agent. The page reads **Your cluster is ready** when it is done.
      </Step>
    </Steps>
  </Tab>
  <Tab title="CLI">

    <CliVersion since="0.5.1" />

    ```bash
    ankra cluster managed create \
      --provider eks \
      --name my-eks-cluster \
      --credential-id <aws-credential-id> \
      --location eu-west-1 \
      --node-pool-name workers \
      --node-pool-size m5.large \
      --node-pool-count 2
    ```

    The VPC, subnets, security groups and control-plane logging have no CLI flags: set them through the API, or the VPC in the portal. Node-group autoscaling bounds take `--autoscaling --autoscaling-min <n> --autoscaling-max <n>` (CLI v0.9.0 or later).
  </Tab>
  <Tab title="API">
    ```bash
    curl -X POST https://platform.ankra.app/api/v1/clusters/managed/eks \
      -H "Authorization: Bearer $ANKRA_API_TOKEN" \
      -H "Content-Type: application/json" \
      -d '{
        "name": "my-eks-cluster",
        "credential_id": "<aws-credential-id>",
        "location": "eu-west-1",
        "kubernetes_version": "1.32",
        "node_pools": [
          {
            "name": "workers",
            "size": "m5.large",
            "count": 2,
            "autoscaling": {"enabled": true, "min_count": 2, "max_count": 5}
          }
        ],
        "eks": {"enable_control_plane_logging": true}
      }'
    ```
  </Tab>

### EKS options

| Field | Description |
|-------|-------------|
| `eks.vpc_id` | VPC to place the cluster in; Ankra uses its subnets. The portal's **VPC** field sets it |
| `eks.subnet_ids` | Subnets to place the cluster in (defaults to your default VPC subnets) |
| `eks.security_group_ids` | Security groups to attach |
| `eks.enable_control_plane_logging` | Enable EKS control-plane logging |

<Note>
EKS creates the IAM roles for the cluster and node groups automatically and uses your default VPC subnets when `subnet_ids` is omitted. Control planes routinely take 10-15 minutes to provision; node groups follow after.
</Note>

## Verify

The create progress view follows the control plane, the node pools, kubeconfig retrieval and the Ankra Agent install. The cluster shows **Online** once the agent has connected. Then point `kubectl` at it through Ankra - this needs a [Cluster Access](/guides/cluster-access) grant - and check that every node is `Ready`:

```bash
ankra cluster kubeconfig add <cluster-name> --use
kubectl get nodes
```

See [Accessing Clusters with kubectl](/guides/kubeconfig).

## Day-2 operations

Node groups, upgrades, and deletion work from the portal, the CLI or the API. The CLI examples use `--provider eks`:

```bash
# scale a pool to a fixed count
ankra cluster managed node-pool scale <cluster_id> workers --provider eks --count 5

# upgrade the cluster
ankra cluster managed upgrade <cluster_id> --provider eks --version 1.32

# delete the cluster
ankra cluster managed delete <cluster_id> --provider eks
```

In the portal, node pools are under **Infrastructure → Clusters → &lt;your cluster&gt; → Kubernetes → Nodes → Manage nodes and groups**, upgrades under **Settings → Upgrades and maintenance**, and disconnect and delete under **Settings → Terminate or remove**. EKS clusters cannot be stopped and started. Autoscaling bounds are set from the portal (**Change autoscaling** on a pool), with `ankra cluster managed node-pool update --autoscaling --autoscaling-min <n> --autoscaling-max <n>`, or with the `PATCH .../node-pools/{name}` endpoint. See [Managed Kubernetes - day-2 operations](/guides/managed-kubernetes#day-2-operations) for the shared mechanics.

## Importing an existing EKS cluster

Already running EKS? Discover clusters in your AWS account and adopt them into Ankra. Discovery and import run from the portal (**Infrastructure → Clusters → Connect a cluster → Find a managed cluster**), the CLI (`ankra cluster managed discover --provider eks`, then `ankra cluster managed import --provider eks`) or the API - see [Managed Kubernetes - importing existing clusters](/guides/managed-kubernetes#importing-existing-clusters).

### What a managed import changes on your cluster

By default, Amazon EKS gives Kubernetes access only to the identity that created a cluster, so the AWS role you connected to Ankra starts with none. To install the agent, Ankra gives that role access for the length of the install:

1. Ankra creates an [access entry](https://docs.aws.amazon.com/eks/latest/userguide/access-entries.html) for the role, tagged `managed-by=ankra-agent-install`, and associates `AmazonEKSClusterAdminPolicy` at cluster scope.
2. Ankra installs the agent.
3. Ankra deletes the access entry, whether the install worked or not. If AWS refuses the delete, or the install is cut off, the step fails and says so, and Ankra tries again until the entry is gone. An agent that did install keeps running in the meantime. If you disconnect the cluster from Ankra before that retry, the entry stays: delete the role's access entry tagged `managed-by=ankra-agent-install` in the EKS console.

The agent then runs under its own Kubernetes service account, so Ankra needs no Kubernetes access through your AWS role after the install. To avoid the access entry altogether, use a [Helm import](/guides/import-cluster) (the **Install the agent** tab), which needs no AWS credential.

- **The role needs to manage access entries.** The Ankra CloudFormation template already allows this with `eks:*`. A role you wrote yourself needs `eks:CreateAccessEntry`, `eks:DescribeAccessEntry`, `eks:AssociateAccessPolicy` and `eks:DeleteAccessEntry`.
- **An access entry you already made is yours.** If the role already has an entry that Ankra didn't tag, Ankra leaves it exactly as it is and doesn't delete it.
- **Clusters on the `CONFIG_MAP` authentication mode have no access entries.** Ankra never changes the authentication mode. Map the role in the `aws-auth` ConfigMap, or switch the cluster to `API_AND_CONFIG_MAP`, which AWS doesn't let you undo. If the cluster refuses the role, the setup page says what to change.
