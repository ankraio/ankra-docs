[Azure Kubernetes Service (AKS)](https://azure.microsoft.com/en-us/products/kubernetes-service) is Microsoft Azure's managed Kubernetes service. Azure runs the control plane; Ankra provisions the cluster, then manages everything on top - node pools, Kubernetes upgrades, add-ons, Stacks, GitOps, and AI-assisted operations.

This page covers AKS specifically. For the shared concepts across all managed providers - live options, discovery/import, and day-2 API patterns - see [Managed Kubernetes](/guides/managed-kubernetes).

<Tip>
**Already running AKS?** You can bring it into Ankra two ways. A **managed import** uses your Azure credential: open **Infrastructure → Clusters → Connect a cluster** and choose the **Find a managed cluster** tab, or run `ankra cluster managed discover --provider aks` and `ankra cluster managed import --provider aks`. Ankra fetches the kubeconfig and installs the agent, so there is nothing to run on the cluster, and the cluster gains the same node-pool and upgrade operations as clusters Ankra created. The **Helm import** needs no cloud credential and works for any cluster: the **Install the agent** tab on the same page gives you the command - see [Import an existing cluster](/guides/import-cluster).
</Tip>

## Why AKS with Ankra

- **A catalogue for the location you pick** - Kubernetes versions, VM sizes, availability zones, subnets and prices are read for the selected Azure location, and sizes your subscription cannot launch there are left out.
- **Spot node pools, zones and OS disks** - run a User pool on spot capacity with an optional price cap, spread a pool across availability zones, and choose a managed or ephemeral OS disk per pool.
- **Bring your own network** - place every node pool in an existing virtual network subnet, or let AKS create its VNet.
- **Planned maintenance** - pin the weekly window in which Azure may run control-plane upgrades and node reboots.
- **Stop and start** - AKS is the only managed provider with native cluster stop/start, exposed in the portal, CLI, API and MCP.
- **Retention-aware deletion** - keep or delete the resource group Ankra created for the cluster; a resource group you brought is never deleted.

## Before you start

- An **Azure service principal** stored in Ankra with the roles described in [Azure Credentials](/platform/credentials/azure). Store it from the portal or with `ankra credentials azure create`. If you have none, the create form shows **Add an Azure Kubernetes Service credential first** with an **Add a credential** button.
- A **payment method** on the organisation. Without one the review step warns "A payment method is required to create this cluster." and the create is refused - see [Billing](/platform/billing).
- A role with the `clusters.create` permission. Without it **Add a cluster** reads "Your role does not allow creating clusters."

GitOps is optional: connect a repository at creation and Ankra commits the cluster's Stack definitions to Git.

## Creating an AKS cluster

<Tabs>
  <Tab title="Portal">
    <Steps>
      <Step title="Choose Azure, run by Azure">
        Open **Infrastructure → Clusters → Add a cluster** (`/next/clusters/new`). Choose **Microsoft Azure** as the provider, then **Provider managed** under **Who runs Kubernetes on Microsoft Azure?**. The page now reads **Add an Azure Kubernetes Service cluster**.
      </Step>
      <Step title="Name and purpose">
        Enter a **Cluster name** (Azure allows letters, digits, hyphens and underscores) and answer **What will this cluster run?** (**Production**, **Staging**, **Development**, **Testing**, **Local** or **Something else**). The answer is required before you can review.
      </Step>
      <Step title="Where it runs">
        Pick the **Azure Kubernetes Service credential** and a **Region** (for example `westeurope`), then the **Network plugin**: **Azure CNI** (the default) or **kubenet**. Sizes and versions load for that region; the **Estimated monthly cost** panel fills in.
      </Step>
      <Step title="Worker nodes">
        Each node group has a **Group name**, a number of **Nodes** and a **Size for** the group, and **Scale this group automatically** with **At least** and **At most**. **Add a node group** adds another. Open **Placement, labels and taints** on a group for node labels, taints, **Pool zones**, **Node disk type**, **Node disk size in GB** and **Use spot capacity** with an optional **Maximum spot price per hour**. Spot is disabled on the first group: "The first AKS pool runs system workloads and requires regular capacity."
      </Step>
      <Step title="Kubernetes and Git">
        Pick a **Kubernetes version** or keep **Provider default**. Under **Cluster configuration in Git**, optionally choose a **Git connection**, **Repository** and **Branch**.
      </Step>
      <Step title="Advanced configuration">
        Open **Advanced configuration** for **Azure cluster settings**: an **Existing resource group** to adopt (leave it empty and Ankra creates one), the **AKS service tier** (**Free**, **Standard** or **Premium**), **Use a private Kubernetes API endpoint**, the **Azure subnet** (**Create a network with the cluster**, or a subnet in the region), and **Schedule planned maintenance** with **Maintenance day (UTC)**, **Start hour (UTC)** and **Maintenance duration in hours** (between 4 and 24).
      </Step>
      <Step title="Review and create">
        Click **Review cluster**. The review page lists the settings and runs **Checks before creating** (the AKS preflight: credential, location, version, name, size availability, zones, OS disk support, vCPU quota, subnet). When they pass, click **Create cluster**. Ankra submits the cluster, follows it while Azure provisions it, retrieves the kubeconfig and installs the Ankra agent. The page reads **Your cluster is ready** when it is done.
      </Step>
    </Steps>
  </Tab>

    ankra cluster managed create \

### AKS options

| Field | Description |
|-------|-------------|
| `aks.resource_group` | Existing resource group to adopt. Omit it and Ankra creates `ankra-<name>`, tags it as Ankra-owned, and deletes it with the cluster. An adopted group is never modified or deleted. |
| `aks.network_plugin` | `azure` (default; pods get VNet addresses, required with a customer subnet) or `kubenet` |
| `aks.sku_tier` | `Free` (default, no control-plane fee), `Standard` (uptime SLA, about $73 per month) or `Premium` |
| `aks.private_cluster` | Private API server endpoint |
| `aks.vnet_subnet_id` | ARM id of the subnet every node pool joins; pick one from the catalogue's `private_networks`. Omit for an AKS-managed VNet. |
| `aks.maintenance_window` | `{day, start_hour, duration_hours}` - an English weekday, a 0-23 UTC hour and 4-24 hours |

### Node pool options

| Field | Description |
|-------|-------------|
| `zone` | Availability zone(s) from the catalogue's `zones`, comma-separated to spread the pool (`"1,2,3"`). Omit for a regional pool. |
| `root_volume_type` | OS disk type, `Managed` or `Ephemeral`. Ephemeral needs a VM size that supports it; preflight checks. |
| `root_volume_size_gb` | OS disk size, at least 30 GB |
| `spot` | `{"enabled": true, "max_price": <hourly-cap>}` - spot capacity with an optional cap in USD per hour; omit `max_price` to pay up to the on-demand price. Refused on the first pool. |

<Note>
AKS node pool names are lowercase alphanumeric, start with a letter and are at most 12 characters; cluster names are at most 63 characters. The first pool is the cluster's System pool: AKS requires at least one System pool, so Ankra refuses to delete the only one and refuses spot on it.
</Note>

### Preflight

Every create runs a preflight you can also call on its own (`POST .../managed/aks/preflight` with the create body). It checks the service principal, pool names, the location and version, a name collision in the resource group, that each VM size is available to your subscription in that location and offered in the requested zones, ephemeral OS disk support, the subscription's regional and per-family vCPU quota against the pools' maximum node counts (and the separate regional spot vCPU quota for spot pools), the subnet, and the maintenance window. Catalogue reads the service principal lacks permission for become warnings; a failing item blocks the create.

## Verify

The create progress view follows the control plane, the node pools, kubeconfig retrieval and the Ankra Agent install. The cluster shows **Online** once the agent has connected. Then point `kubectl` at it through Ankra - this needs a [Cluster Access](/guides/cluster-access) grant - and check that every node is `Ready`:

```bash
ankra cluster kubeconfig add <cluster-name> --use
kubectl get nodes
```

See [Accessing Clusters with kubectl](/guides/kubeconfig).

## Day-2 operations

Node pools, upgrades, stop/start and deletion work from the portal, the CLI or the API. The CLI examples use `--provider aks`:

```bash
# add a spot pool spread over two zones
ankra cluster managed node-pool add <cluster-id> --provider aks \
  --name batch --size Standard_E4s_v5 --count 3 --zone 1,2 \
  --spot --spot-max-price 0.05 --autoscaling --autoscaling-min 1 --autoscaling-max 10

# scale a pool to a fixed count
ankra cluster managed node-pool scale <cluster-id> batch --provider aks --count 5

# turn autoscaling off again
ankra cluster managed node-pool update <cluster-id> batch --provider aks --autoscaling=false --count 3

# upgrade the cluster
ankra cluster managed upgrade <cluster-id> --provider aks --version 1.32.3

# delete the cluster
ankra cluster managed delete <cluster-id> --provider aks
```

In the portal, open **Clusters → &lt;your cluster&gt; → Kubernetes → Nodes** and click **Manage nodes and groups**. The **Node pools** section lists every pool with its size, node count and autoscaling state. **Add node pool** adds one; **Inspect and edit** on a pool shows its zone, root volume and upgrade policy and offers **Change node count**, **Change autoscaling** and **Delete node pool**. Each change ends with **Review change** and **Confirm change**. A pool's instance type, labels and taints cannot be changed in place: add a replacement pool instead.

### Upgrades

An upgrade moves the control plane **and every node pool** to the target version in one operation - the same request `az aks upgrade` sends. AKS refuses a control plane more than two minor versions ahead of a pool, so Ankra never leaves pools behind. Available targets come from Azure's upgrade profile; preview versions are skipped.

In the portal, open **Clusters → &lt;your cluster&gt; → Settings → Upgrades and maintenance**, pick the **Version to upgrade to** under **Kubernetes version**, click **Review upgrade** and confirm **Upgrade to &lt;version&gt;**.

### Stopping and starting

AKS is the only managed provider with native cluster stop/start, and Ankra exposes it in the portal, the CLI, the API and MCP (`stop_managed_cluster`, `start_managed_cluster`). Stopping deallocates the control plane and agent pools (Azure stops billing for compute) while keeping all configuration; starting brings the same cluster back.

In the portal, open **Clusters → &lt;your cluster&gt; → Settings → Stop, start and schedules**. Under **Stop or start now**, click **Stop cluster** (or **Start cluster** on a stopped one) and confirm. The section shows the **State in Ankra** and the **Status at Microsoft Azure**. Schedules are not offered for managed clusters: "Schedules are only for clusters Ankra built on servers it provisions."

```bash
ankra cluster managed stop <cluster-id> --provider aks
ankra cluster managed start <cluster-id> --provider aks
```

Both operations are asynchronous on Azure's side - the cluster shows `stopped` or `running` once Azure completes the transition. Ankra advertises the capability per provider as `supports_stop_start`.

## Importing an existing AKS cluster

Discover the clusters in your subscription and adopt one into Ankra without touching it - discovery and import run from the portal (**Infrastructure → Clusters → Connect a cluster → Find a managed cluster**), the CLI (`ankra cluster managed discover --provider aks`, then `ankra cluster managed import --provider aks`) or the API (see [Managed Kubernetes - importing existing clusters](/guides/managed-kubernetes#importing-existing-clusters)). Import brings the cluster's node pools, their zones, OS disks, spot settings, labels and taints into Ankra, and records the subnet the pools use.

<Warning>
Ankra needs the cluster's admin kubeconfig, which Azure only issues while **local accounts** are enabled. A cluster configured for Microsoft Entra ID only (`disableLocalAccounts: true`) is refused at import with an explanation; enable local accounts (`az aks update --enable-local-accounts`) before importing it.
</Warning>

## Deleting, disconnecting and retention

These operations are deliberately different. Both are under **Clusters → &lt;your cluster&gt; → Settings → Terminate or remove**, and both ask you to type the cluster's name to confirm:

- **Disconnect from Ankra** (button **Disconnect cluster**) removes the Ankra integration and cluster-local privileged material but never calls Azure. The AKS cluster keeps running, and Azure keeps charging for it. Use it for imported clusters.
- **Delete the AKS cluster at Microsoft Azure** (button **Delete at Microsoft Azure**) deletes the AKS cluster (Azure removes its `MC_` node resource group with it) and then removes the Ankra integration. **Continue past cleanup errors** finishes even when Ankra cannot clean up everything. The portal offers this only for clusters Ankra created; for an imported cluster it says "Ankra did not create this cluster at Microsoft Azure, so it does not delete it there." Through the API an imported cluster can be deleted with the explicit force option.

With `retention_policy=delete` (the default) Ankra also deletes the resource group it created for the cluster. With `retention_policy=retain` that group survives and is reported in `retained_resources`; the portal sends `delete` and the CLI takes the default, so `retain` is an API parameter only. A resource group you named at creation is adopted: Ankra never deletes it and always reports it as retained.

<Warning>
A deleted resource group takes every resource in it with it. Keep other workloads out of the `ankra-<name>` group Ankra creates, or adopt a group of your own.
</Warning>

## Troubleshooting

- **403 on the resource group or subscription** - the service principal lacks a role listed in [Azure Credentials](/platform/credentials/azure). Catalogue reads need `Reader` at the subscription; creating clusters needs the AKS and network roles on the resource group.
- **Preflight fails on `quota` or `quota.spot`** - the pools' maximum node counts exceed the free regular or per-family vCPUs, or the spot pools exceed the regional spot (low-priority) vCPU quota, which Azure sizes separately and often at only a few vCPUs on new subscriptions. Request a quota increase for that location or pick smaller sizes.
- **VM size "not available to this subscription"** - Azure restricts the SKU in that location for your subscription. The catalogue already omits such sizes; a size typed by hand is caught at preflight.
- **"cannot run on spot capacity"** - spot was requested on the first pool. Put spot workloads in a later pool.
- **Import refused with "local accounts disabled"** - see the warning under importing.
- **Upgrade refused by Azure** - a pool is more than two minor versions behind the target. Upgrade in steps of one minor version.
