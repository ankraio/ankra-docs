Your cluster is running and now it needs to change: more workers, a bigger instance type, a new Kubernetes version, a pause overnight, or a clean teardown. This page covers those tasks for every cluster Ankra builds on your own account - the clusters you create as **Ankra managed** under **Add a cluster**, on Hetzner, OVHcloud, UpCloud, DigitalOcean, Scaleway, AWS EC2, Ankra Cloud, Proxmox VE and HPE Morpheus. Where a provider behaves differently, the table in each section says so, and the provider's own guide carries the details.

<Note>
Clusters whose control plane your cloud runs (EKS, GKE, AKS, DOKS, UKS, OVHcloud MKS, Kapsule, Ankra Cloud Kubernetes) are **Provider managed**; their node pools, upgrades and deletion are on [Managed Kubernetes](/guides/managed-kubernetes#day-2-operations).
</Note>

## Before you start

- The cluster shows **Online** and no operation is running on it. Day-2 changes are queued one at a time; follow them under **Infrastructure → Clusters → &lt;your cluster&gt; → Operations** or with `ankra cluster operations list`.
- In the portal, the node controls are on the **Node management** page: open **Infrastructure → Clusters → &lt;your cluster&gt; → Kubernetes → Nodes** and click **Manage nodes and groups** (`/next/clusters/<cluster-id>/node-groups`). It has three sections: **Node groups**, **Control plane** and **Provider machines** (workers, control planes and bastions). Each change ends with **Review change** and **Confirm change**. Everything else is under **Infrastructure → Clusters → &lt;your cluster&gt; → Settings**, one page per area. [Nodes](/platform/cluster-nodes) describes the Nodes page.
- Changing nodes needs the `clusters.write` permission on the cluster, deleting a node group `clusters.delete`, and restarting a machine `clusters.operate`. Without it the page says "This action requires clusters.write for this cluster."
- On the CLI, most commands find the provider from the cluster, so they are the same everywhere. The rest take the provider name: `hetzner`, `ovh`, `upcloud`, `digitalocean`, `scaleway`, `aws`, `proxmox`, `morpheus` or `ankracloud`. The Ankra Cloud commands need CLI v0.21.0 or later; [`ankra cluster ankracloud`](/reference/cli/cluster#ankra-cluster-ankracloud) lists them.
- Every command has an API equivalent under `/api/v1/clusters/{provider}/{cluster_id}/...` - see the API reference. Writes answer `202 Accepted` and run in the background. The `node-group` commands and `bastion resize` take `--wait` to block until the change finishes; follow every other write (stop, start, control plane, restart, upgrade, deprovision) with `ankra cluster operations list <cluster>`.

| Hetzner | `hetzner` | Portal, CLI | Portal, CLI | Portal, CLI |

## Node groups

A node group is a set of workers with one instance type, a count, and optional labels and taints. Each group scales, changes type and carries its labels independently. A group holds 0 to 100 nodes; scaling a group to 0 keeps its definition and removes its servers.

**In the portal:** on **Node management**, the **Node groups** section lists each group with its instance type, node count and autoscaling state. **Add node group** opens the size picker with live prices. **Inspect and edit** on a group shows its current settings and offers **Change node count**, **Change autoscaling**, **Change instance type**, **Edit labels**, **Edit taints** and **Delete node group**. The portal has no control that sizes a group to the room left in your cloud account.

**On the CLI:**

<CliVersion since="0.72.0" command="cluster node-group remove-node" />

```bash
ankra cluster node-group list <cluster>
ankra cluster node-group add <cluster> --name workers-large --instance-type <instance-type> --count 2
ankra cluster node-group scale <cluster> workers-large 4
ankra cluster node-group remove-node <cluster> workers-large <node>
ankra cluster node-group upgrade <cluster> workers-large <larger-instance-type>
ankra cluster node-group labels <cluster> workers-large --labels env=production,tier=backend
ankra cluster node-group taints <cluster> workers-large --taints dedicated=ml:NoSchedule
ankra cluster node-group delete <cluster> workers-large
```

- **Instance type changes go one way.** A group moves to an equal or larger type only; to get smaller nodes, add a new group with the smaller type and delete the old one. How the change is applied depends on the provider - most power each node off, resize it and power it on again, while AWS replaces each node - so check the provider guide before you resize a group that runs stateful workloads.
- **Labels and taints** apply to every node in the group. `--clear` removes them all; a taint without an effect gets `NoSchedule`.
- **Removing nodes drains them first.** A scale-down, a group delete and a replacement drain each node, honouring PodDisruptionBudgets. A scale-down picks the nodes it removes itself; `remove-node` retires one chosen worker instead, named by its server id, server name, Kubernetes node name or providerID, and prints the operation that drains it and deletes its server. A node whose drain is refused is kept in service, and `--force-drain` removes it anyway. The last node of a group is not removed that way (scale the group to 0 or delete it), and a stopped cluster's nodes are not removed.
- **Deleting a group removes all its servers.** Workloads on them are evicted.
- **Zones.** On OVHcloud 3-AZ regions (`--availability-zone`), UpCloud zone pools (`--zone`) and multi-zone AWS clusters, a group can be pinned to one zone - do that for groups that run zonal storage.
- **Autoscaling and first-boot scripts.** Set a group's autoscaling range with `ankra cluster node-group autoscaling set` - see [Cluster Autoscaling](/guides/cluster-autoscaling). OVHcloud groups can carry a cloud-init document - see [Node Group Cloud-init User Data](/guides/node-group-user-data).
- **A stopped cluster.** Adding or changing a node group on a stopped cluster brings its infrastructure back first, so the cluster comes online. Use **Start cluster** when you want the full saved topology back.

### Legacy worker scaling

Clusters also keep a single default worker pool that predates node groups. `ankra cluster scale <cluster> <count>` sets its size, and `ankra cluster <provider> workers <cluster>` shows it. Prefer node groups for anything new.

## Control plane

**In the portal:** on **Node management**, the **Control plane** section shows the controller count and instance type. **Inspect control-plane settings** offers **Change control-plane count** and **Resize control plane**.

- **Growing the count is live.** Going from 1 to 3 controllers (3 to 5 on Proxmox VE) provisions the new controllers and joins them to the running cluster.
- **Reducing the count is offline.** Stop the cluster (its state is kept and restored on start), apply the change, then start it.
- **The instance type** changes in one of three ways, described below. `control-plane get` says which one applies to your cluster right now.
- A cluster spread across several zones or hosts keeps at least three controllers.

```bash
ankra cluster <provider> control-plane get <cluster>
ankra cluster <provider> control-plane set-count <cluster> 3
ankra cluster <provider> control-plane set-instance-type <cluster> <instance-type>
```

### Change the control plane instance type

How Ankra changes the instance type depends on how many controllers the cluster has and whether it is running:

| Mode | When it applies | What happens |
|---|---|---|
| `rolling` | A running cluster with three or more controllers, on any provider | Ankra drains and resizes one controller at a time and waits for each to be healthy before the next. The Kubernetes API stays up. |
| `live_with_api_downtime` | A running Hetzner cluster with one controller | Ankra resizes the only controller in place. The Kubernetes API is down for a few minutes while that server reboots on the new type. You have to accept the downtime first. |
| `offline` | A stopped cluster, on any provider | On a paused Hetzner, UpCloud or DigitalOcean k3s cluster the change is refused. Otherwise Ankra saves the new type for the next start. A default stop on Hetzner, OVHcloud, UpCloud, DigitalOcean, Proxmox VE or HPE Morpheus deletes the servers, so the start creates every server again, the controllers on the new type. AWS EC2, Scaleway and Ankra Cloud keep the servers powered off: the start powers those same servers back on with the type they had, so the saved type is not applied to them (see Stop and start below). |

A running cluster with one controller on any other provider cannot change its instance type live. Either grow it to three controllers first and then resize it with no downtime, or stop it and change the type offline.

#### What the API downtime means

While the only controller reboots, the Kubernetes API is not available:

- Pods that are already running on the workers keep running.
- `kubectl`, deployments, Stack and add-on changes, controllers and operators, and the Ankra agent pause until the API is back. Anything that needs the API, such as scaling a Deployment or rescheduling a pod, waits until then.
- Before it changes the server, Ankra takes an etcd snapshot on the node and drains it. Hetzner changes the server type and keeps its disk and IP address, so the node comes back as the same machine with the same cluster state. Ankra then waits for the node to be Ready again. When the new type has a larger disk, the disk grows with it, and Hetzner cannot shrink it again, so the controller cannot move back to a type with a smaller disk.

In a test on 2026-10-28, a Hetzner cluster resized from `cpx22` to `cpx32` finished the whole step in about two and a half minutes, and the workloads on the workers were not restarted. Plan for a few minutes of API downtime. To avoid any downtime, grow the cluster to three controllers first.

Ankra does not start the resize while another change is running on the cluster, for example a [scheduled Cluster State Snapshot](/guides/kubernetes-upgrades#scheduled-cluster-state-snapshots). Start it again when that change has finished.

#### Resize the only controller

**In the portal:** open **Inspect control-plane settings**, choose **Resize control plane** and pick the new type. The review dialog is titled **Resize the only control plane**; **Resize with API downtime** accepts the downtime and starts the resize.

**On the CLI:** `control-plane get` shows the change as `Change type: yes - live with a few minutes of API downtime (single controller)`. `set-instance-type` refuses the change unless you pass `--accept-api-downtime`:

<CliVersion since="0.49.0" command="cluster hetzner control-plane set-instance-type --accept-api-downtime" />

```bash
ankra cluster hetzner control-plane get <cluster>
ankra cluster hetzner control-plane set-instance-type <cluster> cpx32 --accept-api-downtime
ankra cluster operations list <operation-id>    # show the resize operation the command printed
```

**From the AI or MCP:** the `change_control_plane` tool takes `accept_api_downtime`. The AI tells you about the downtime and sets it only after you have accepted it.

**On the API:** send `accept_api_downtime: true` with the new type. Without it, the request is refused with `409 Conflict` and a message that describes the downtime.

```bash
curl -X PUT https://platform.ankra.app/api/v1/clusters/hetzner/<cluster-id>/control-plane/instance-type \
  -H "Authorization: Bearer $ANKRA_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"instance_type": "cpx32", "accept_api_downtime": true}'
```

Sending the type the controller already has changes nothing and needs no acceptance.

## Restart a node

Restart one node - a control plane, a worker or the bastion - without waiting for a reconciliation. The restart is a tracked operation, and workloads on the node are briefly unavailable while it reboots.

**In the portal:** on **Node management**, find the machine under **Provider machines**, click **Inspect machine** and choose **Restart machine**. The review says "This restarts the provider machine. It does not drain its workloads first." Restarting needs the `clusters.operate` permission.

**On the CLI:** find the node ID, restart it, and follow the operation:

```bash
ankra cluster <provider> nodes list <cluster>
ankra cluster <provider> nodes get <cluster> <node-id>
ankra cluster <provider> nodes restart <cluster> <node-id>
ankra cluster operations list <operation-id>
```

The node must be `up` with no restart already in flight. If a node never joined, `ankra cluster <provider> nodes cloud-init-log <cluster> <node-id>` shows its cloud-init status and the end of its log, read over the bastion (not on Proxmox VE or HPE Morpheus). You can also ask Ankra AI, for example "restart worker-2 on my-cluster".

### Diagnose a node

When a node is `NotReady` or its kubelet stopped posting status, `nodes diagnose` runs a read-only job over the bastion and reports the node's OS-level state: the Kubernetes service unit and its journal, disk, memory, uptime, the kernel log and the firewall path to the API server, with the symptoms it finds. Nothing on the node changes. It needs the `clusters.operate` permission. The portal has no diagnose action; use the CLI.

<CliVersion since="0.52.0" command="cluster hetzner nodes diagnose" />

```bash
ankra cluster hetzner nodes diagnose <cluster> <node-id>
```

The platform waits up to two minutes for the job; a slower run hands back the operation id to follow with `ankra cluster operations list`. The command exists on Hetzner, OVHcloud, UpCloud, DigitalOcean, Scaleway, AWS EC2 and Ankra Cloud (`ankra cluster ovh nodes diagnose`, and so on), not on Proxmox VE or HPE Morpheus.

### Remove a dead control plane's etcd member

A control-plane node that died leaves its etcd member behind, which can stop its replacement from joining. On Hetzner, OVHcloud, UpCloud, DigitalOcean, Scaleway, AWS EC2 and Ankra Cloud, read the membership from a healthy control-plane node, then remove the stale member by the id it reported:

<CliVersion since="0.73.0" command="cluster hetzner etcd remove" />

```bash
ankra cluster hetzner etcd members <cluster> <healthy-node-id>
ankra cluster hetzner etcd remove <cluster> <healthy-node-id> <member-id>
```

<Warning>
`etcd remove` cannot be undone. The platform re-reads the live membership first and refuses a healthy member, a member whose health it cannot read, the node's own member, an ambiguous id and any removal that would break quorum. Both commands need `clusters.operate`.
</Warning>

### Automatic node restarts

Ankra can restart a node that stays `NotReady`, through your cloud provider, so a hung machine comes back without you. Automatic restarts are being introduced gradually and may not be active for your organisation yet: ask [Ankra support](/platform/support) before you rely on them, and restart a hung node yourself with `ankra cluster <provider> nodes restart` in the meantime. Where they are active, a restart follows these rules:

- **Workers:** only a worker that has stayed `NotReady` for several minutes while every control plane is `Ready`, one worker of a cluster at a time and at most once per node per day. When the restart does not bring it back, the cluster's notifications name the node.
- **Control planes:** only a control-plane node that has stayed `NotReady` for several minutes, while every other control plane is `Ready` and etcd keeps quorum without it.

Neither stops, scales or deletes anything. Both switches are per cluster and on by default. The portal has no switch for them; use the CLI, with the `clusters.write` permission:

<CliVersion since="0.74.0" command="cluster worker-heal set" />

```bash
ankra cluster worker-heal get --cluster my-cluster
ankra cluster worker-heal set --enabled=false --cluster my-cluster
ankra cluster control-plane-heal get --cluster my-cluster
ankra cluster control-plane-heal set --enabled=false --cluster my-cluster
```

`get` shows the switch and the latest episode: which node, and how it ended or why Ankra has not restarted it. Turning a switch off stops the restart only; the cluster still shows the `NotReady` node.

## Bastion

The bastion is the machine Ankra and you reach the cluster through: every SSH hop into the private network goes via it. On most providers it carries no workload traffic, so workloads keep running while it is down, but Ankra cannot provision, scale, upgrade or reconcile the cluster until it is back.

**In the portal:** on **Node management**, the bastion is listed under **Provider machines**. **Inspect machine** on it offers **Resize bastion or gateway** and, where the provider supports it, **Restart machine**. The portal has no bastion health check; use `bastion status` and `bastion diagnose` on the CLI.

```bash
ankra cluster <provider> bastion status <cluster>                     # last health verdict, without probing
ankra cluster <provider> bastion diagnose <cluster>                   # probe it now, as an operation (not Scaleway)
ankra cluster <provider> bastion resize <cluster> <instance-type>     # every provider: a gateway type on Scaleway, a size preset on Proxmox VE, a numeric plan id on HPE Morpheus
```

A resize powers the bastion off, changes its type and powers it on again, so SSH access is interrupted briefly. Where the bastion is also the NAT for the nodes (AWS `bastion_nat` egress), node egress stops until it is back.

### Restrict who can reach the bastion over SSH

On Hetzner, OVHcloud, UpCloud and DigitalOcean the bastion accepts key-only SSH from anywhere unless you restrict it. `bastion allowed-ips` replaces that with an allowlist: only the IPv4 addresses or CIDRs you list, the platform's own egress addresses and private network sources can reach port 22. The platform always adds its own egress, so it cannot be locked out. The portal has no page for this on a running cluster; use the CLI:

<CliVersion since="0.31.0" command="cluster hetzner bastion allowed-ips" />

```bash
ankra cluster hetzner bastion allowed-ips <cluster> 203.0.113.7 198.51.100.0/24
ankra cluster hetzner bastion allowed-ips <cluster> --clear     # reachable from anywhere again
```

The list you give is the complete new list. IPv6 entries and `0.0.0.0/0` are refused, and the list holds at most 64 entries. The change runs as a bastion update operation; follow it with `ankra cluster operations list`.

### SSH access and keys

**Infrastructure → Clusters → &lt;your cluster&gt; → Settings → SSH access** shows copy-paste SSH commands through the bastion for the cluster's own addresses under **Connect with SSH**, and the SSH key credentials on the cluster's servers under **SSH keys**, where you can change them. On the CLI:

```bash
ankra cluster ssh-keys get <cluster>
ankra cluster ssh-keys set <cluster> --ssh-key-credential-ids <key-id-1>,<key-id-2>
ankra cluster ssh-keys resync <cluster>
```

The new keys are written to every node on the next reconciliation; `resync` forces it. The key Ankra itself uses is never removed. For everyday `kubectl` you need no SSH at all - see [Accessing Clusters with kubectl](/guides/kubeconfig).

## Upgrade Kubernetes

**In the portal:** open **Infrastructure → Clusters → &lt;your cluster&gt; → Settings → Upgrades and maintenance**. Under **Kubernetes version**, pick the **Version to upgrade to**, click **Review upgrade** and confirm **Upgrade to &lt;version&gt;**.

Automatic patch upgrades, which move a cluster to the newest patch of its current minor version on their own, are off by default, and the portal, the CLI and the `/api/v1` API have no switch for them. Minor versions are never upgraded automatically.

**On the CLI:**

```bash
ankra cluster <provider> k8s-version <cluster>     # current version and distribution
ankra cluster kubeadm-versions                     # or: ankra cluster k3s-versions
ankra cluster upgrade <cluster> v1.33.2            # kubeadm: a plain upstream tag
ankra cluster upgrade <cluster> v1.33.2+k3s1       # k3s
```

- Nodes upgrade one at a time, control plane first, then workers. Each node is cordoned, drained honouring PodDisruptionBudgets, upgraded, and must be `Ready` at the target version before the next one starts.
- An etcd snapshot is taken before the control plane upgrade. With external etcd, the dedicated etcd members are upgraded first, one at a time, each saving a snapshot.
- A drain blocked by a PodDisruptionBudget stops the rollout; `--force` proceeds anyway.
- One minor version at a time (1.33 to 1.34, not 1.33 to 1.35), and no downgrades.

Restore points, the pre-upgrade checklist and what to do when a hop stops are in [Upgrade Kubernetes on a Cluster](/guides/kubernetes-upgrades).

## Stop and start

Stopping releases the cluster's compute and keeps its configuration, stacks and credentials in Ankra, which is how you park a cluster you do not need right now. Starting re-provisions it and reconciles it back to running. What a stop does to the servers depends on the provider:

| Provider | What a stop does |
|---|---|
| Hetzner, UpCloud, DigitalOcean | Captures an encrypted etcd snapshot, then deletes the servers; the start restores the snapshot. k3s clusters can **Pause** instead: the servers are powered off and kept with their disks, and keep billing. |
| OVHcloud, Proxmox VE, HPE Morpheus | Captures an encrypted etcd snapshot, then deletes the servers; the start restores the snapshot. |
| AWS EC2, Scaleway, Ankra Cloud | Powers the servers off and keeps them with their disks, so the cluster comes back with its state. |

[Stop, start and schedules](/platform/cluster-power-schedules) explains the snapshot, the pause mode and the restore in full.

**In the portal:** open **Infrastructure → Clusters → &lt;your cluster&gt; → Settings → Stop, start and schedules**. Under **Stop or start now**, click **Stop cluster**; the dialog has **Keep cluster state (recommended)** ticked, and **Stop &lt;cluster&gt;** confirms. A stopped cluster shows **Start cluster** instead. The same page runs stops and starts on a timetable. The portal has no pause choice; use `--mode pause` on the CLI.

<CliVersion since="0.18.0" command="cluster &lt;provider&gt; stop --mode pause" />

```bash
ankra cluster <provider> stop <cluster>
ankra cluster <provider> stop <cluster> --mode pause               # Hetzner, UpCloud, DigitalOcean k3s clusters
ankra cluster <provider> stop <cluster> --preserve-state=false     # tear down without a snapshot
ankra cluster <provider> stop <cluster> --force                    # cancel in-flight operations and stop now
ankra cluster <provider> start <cluster>                           # the whole cluster
ankra cluster <provider> start <cluster> --scope control_plane     # only the control plane, to inspect or repair it
ankra cluster <provider> start <cluster> --restore-state=false     # start fresh instead of restoring the snapshot
ankra cluster <provider> start <cluster> --restore-snapshot-id <id>  # restore the snapshot you name
```

<CliVersion since="0.71.0" command="cluster &lt;provider&gt; start --restore-snapshot-id" />

A start restores the newest snapshot captured after the cluster's last start by itself. When there is none but older snapshots exist, the start is refused and the refusal names the newest; `ankra cluster state-snapshots latest` shows it, and `--restore-snapshot-id <id>` restores it. On AWS EC2, Scaleway and Ankra Cloud, whose stop keeps the servers, a start restores nothing by itself; when the control-plane machines are lost, add `--restore-over-kept-etcd` to the named restore. [Restore a named snapshot](/guides/kubernetes-upgrades#restore-a-named-snapshot) has the detail.

- A stop never deletes the volumes your workloads provisioned through the CSI driver, forced or not; at a cloud provider they keep billing while the cluster is stopped. HPE Morpheus clusters have no CSI volumes. `--force` also deletes the cluster's load balancers, and never captures a snapshot.
- Stop and start run in the background. A start is refused with `409` while a stop or terminate is still running.
- While the cluster is stopped, `ankra cluster <provider> nodes list` still shows the saved machines that the next start re-provisions.

## Terminate a cluster

Terminating deletes the cluster's servers and the network Ankra created, then removes the cluster from Ankra. It cannot be undone.

**In the portal:** open **Infrastructure → Clusters → &lt;your cluster&gt; → Settings → Terminate or remove** and click **Terminate cluster** under **Terminate the cluster**. Type the cluster's name to confirm. When persistent volumes will be deleted, the dialog lists them and asks you to type `DELETE VOLUME DATA` as well. Terminating needs the `clusters.delete` permission.

<CliVersion since="0.19.0" command="cluster deprovision --accept-volume-data-loss" />

```bash
ankra cluster deprovision <cluster>                            # names the volumes and asks
ankra cluster deprovision <cluster> --accept-volume-data-loss  # for scripts
```

- **Volumes are deleted only once you accept it.** `--yes` skips the teardown confirmation but never the volume one. The API lists the volumes with `GET .../deprovision-volumes` and needs `?accept_volume_data_loss=true` on the `DELETE`; without it the answer is `409` naming them.
- **`--force`** deletes leftover load balancers and tolerates infrastructure that no longer answers. It never stands in for accepting the volume loss. On Proxmox VE it finishes the teardown when the host or jumphost is unreachable, leaving the VMs behind.
- **A stopped cluster** can be terminated too: the volumes recorded at stop time are still known and named.

| Provider | What happens to persistent volumes |
|---|---|
| Hetzner, OVHcloud, UpCloud, DigitalOcean | Deleted with the cluster once you accept it. On Hetzner a volume labelled `ankra-retain` is kept. |
| AWS EC2, Scaleway, Ankra Cloud | Follow the cluster's `retention_policy`: `retain` (the default) keeps them in your account, where they keep billing; `delete` removes them once you accept it. |
| Proxmox VE | Deleted from your Proxmox storage with the cluster once you accept it. The VMs Ankra created are deleted; your Proxmox nodes, storage and bridges are left untouched. |
| HPE Morpheus | No volume step: the disks go with the instances. The VMs Ankra created are deleted; your Morpheus groups, clouds and networks are left untouched. |

[Cluster Settings](/platform/cluster-settings) covers the **Terminate or remove** page.

## Choices fixed at create time

A few choices cannot be changed on a running cluster. They are made in the create form (the **Kubernetes** section and **Advanced configuration**) or in the create request, and they shape the upgrade and networking tasks above.

- **Distribution.** `kubeadm` (the default everywhere: portal, CLI and API) is upstream Kubernetes with containerd; its versions are plain tags such as `v1.33.2`. `k3s` is a single-binary distribution; its versions look like `v1.33.2+k3s1`.
- **CNI** (`cni`). kubeadm clusters always run Cilium. k3s clusters choose `flannel` (the default), `calico` or `cilium`; AWS defaults to Cilium for both distributions. The CNI cannot be changed later.
- **CNI features** (`cni_features`). Cilium offers `kube_proxy_replacement`, `hubble` and `wireguard_encryption`; Calico offers `ebpf_dataplane`; flannel takes none. On k3s, `kube_proxy_replacement` and `ebpf_dataplane` need a single control plane.
- **etcd topology** (kubeadm only). `stacked` (the default) runs etcd on the control plane nodes. `external` runs it on 3 or 5 dedicated machines (`etcd_node_count`), sized by a provider-specific field:

| Provider | Field that sizes the etcd machines |
|---|---|
| Hetzner | `etcd_server_type` |
| OVHcloud | `etcd_flavor_id` |
| UpCloud | `etcd_plan` |
| DigitalOcean | `etcd_size` |
| Scaleway, AWS EC2 | `etcd_type` |
| Proxmox VE | `etcd_instance_type` |
| HPE Morpheus | `etcd_plan_id` |
| Ankra Cloud | `etcd_plan` |
