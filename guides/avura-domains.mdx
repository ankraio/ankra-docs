If your domains live in Avura, Ankra can use them directly: clusters publish Ingress hostnames into them, you edit their records in Ankra, and one of them can become the root every generated cluster domain nests under. You connect once and choose, domain by domain, which ones Ankra may touch.

Everything on the Ankra side is on **Infrastructure → Domains** (`/next/organisation/domains`). For any other DNS provider, see [Use your own domain](/guides/use-your-own-domain).

## Before you start

- **One login for both.** You sign in to Avura with **Continue with Ankra**, using the same account you use for Ankra. If you already have an Avura password account, link Ankra to it from **Settings** → **Security** → **Link Ankra account** in Avura. The Ankra email has to match your Avura email, and both have to be verified.
- **An Avura workspace linked to the Ankra organisation.** When an Ankra organisation owner or admin signs in to Avura with Ankra for the first time, Avura creates a workspace for each organisation they administer and links it. An existing workspace is linked by its Avura owner from **Admin** → **General** → **Ankra Platform organisation**, which lists the Ankra organisations you administer that are not linked anywhere else. One workspace links to one organisation.
- **Admin rights on both sides.** Connecting, disconnecting and changing records needs an Avura owner or admin and an Ankra organisation owner or admin. A custom role that holds `organisation.manage` is not enough. Adding a domain for every cluster needs `credentials.write`; adding it for picked clusters needs `clusters.write`. Any member can view the page; a role that cannot change it sees "Your role can look at these settings but not change them. An organisation admin can." See [Roles and access](/guides/roles-and-access).

## Connect Avura

Connect from either side. Both store the same connection.

<Tabs>
  <Tab title="From Avura">
    <Steps>
      <Step title="Open the Ankra Platform card">
        In Avura, go to **Admin** → **General** → **Ankra Platform**. The card shows which Ankra organisation the workspace is linked to.
      </Step>
      <Step title="Connect">
        Click **Connect**. Avura creates a platform token for the workspace and hands it to the linked Ankra organisation, which checks it against Avura before saving it. If Ankra refuses, Avura discards the new token and shows why; a connection that was already working is left as it was.
      </Step>
    </Steps>
  </Tab>
  <Tab title="From Ankra">
    <Steps>
      <Step title="Get the organization ID and a platform token from Avura">
        You need two values from Avura: the organization ID, which is under your organization's settings, and a platform token from your Avura organization. Platform tokens start with `avk_`.
      </Step>
      <Step title="Open the Avura row">
        In Ankra, go to **Infrastructure → Domains**. Under **DNS providers**, the **Avura** row reads "Not connected. Records already there stay." Click **Connect**.
      </Step>
      <Step title="Paste and connect">
        In **Connect Avura**, fill in **Avura organization ID** and **Platform token**, then click **Connect**. Ankra checks the token with Avura, keeps it encrypted and never shows it again.
      </Step>
    </Steps>
  </Tab>
</Tabs>

**Check it.** On **Infrastructure → Domains**, the **Avura** row under **DNS providers** carries the badge **Connected** and the line "Shares *your domains* with Ankra." Until you share a domain it reads "Shares no domain with Ankra yet. Turn on Use with Ankra Platform for a domain in Avura."

**Rotate connection** on Avura's **Ankra Platform** card replaces the platform token. Clusters already publishing through the connection keep working through a rotation. When Avura refuses the token Ankra holds, the Ankra row shows **Token refused** and offers **Connect again**.

## Choose which domains Ankra can use

Connecting shares nothing on its own. Every domain starts closed, and an Avura owner or admin opens each one:

- In Avura's **Domains** list, turn on the **Ankra Platform** switch for the domain, or open the domain and use the **Use with Ankra Platform** card on its **Overview** tab.
- Subdomains inherit the setting from the nearest parent that has it on, and show it as locked on.
- Turning a domain off cuts Ankra off on its very next request, including the tokens clusters are already using to publish records in it. Anything in Ankra that relies on that domain stops updating until you turn it back on.
- Moving a domain to another Avura organisation turns the setting off, so it never arrives already shared with that organisation's Ankra.

**Check it.** Reload **Infrastructure → Domains**: the domain is named on the **Avura** row.

## What Ankra can and cannot do

The platform token Avura issues belongs to the workspace, not to a person. It holds no Avura role, so it keeps working when the admin who connected leaves, and it never appears in anyone's token list.

On the domains you opened, and their subdomains, Ankra can:

- list the domains and read their records
- create, edit and delete records, and ask Avura to re-sync a zone
- create subzones, and delete any subzone inside a shared domain (but never the shared domain itself)
- mint tokens pinned to a single shared domain, which is what a cluster's external-dns receives

Ankra cannot see any domain you did not open, delete a shared domain itself, add root domains, change a domain's sharing, or reach grants, mail, DNSSEC or Avura's own settings.

The platform token itself stays in Ankra's secret store and is never sent to a cluster. Clusters receive tokens pinned to one domain: a domain you serve from a single cluster gets a token for that cluster, and a domain declared for the whole organisation gets one token shared by every cluster that serves it. Revoking the connection revokes every token minted from it.

## Serve an Avura domain from your clusters

A shared Avura domain works as a [custom DNS zone](/concepts/applications#serving-a-zone-in-your-own-dns-account-from-every-cluster): Ankra runs an external-dns pinned to that zone on each cluster that serves it, and an Ingress on a hostname under it is published by that cluster. The certificate follows once the name resolves.

<Tabs>
  <Tab title="Portal">
    <Steps>
      <Step title="Add the domain">
        On **Infrastructure → Domains**, click **Add your own domain**.
      </Step>
      <Step title="Pick Avura">
        Under **Where does its DNS live?**, choose **Avura**. Its card reads "Connected. Ankra writes the records for you." Pick the domain from **Domain**, which lists the domains Avura shares with Ankra.
      </Step>
      <Step title="Choose the clusters">
        Under **Clusters that serve it**, choose **Every cluster, new ones too**, or **Only the clusters I pick** and tick them under **Which clusters**. Click **Add domain**.
      </Step>
    </Steps>
  </Tab>
  <Tab title="CLI">
    The connection's credential is always named `avura`.

    <CliVersion since="0.13.0" />

    ```bash
    ankra org custom-dns-zones add --zone example.dev --credential avura
    ankra cluster custom-dns-zones add my-cluster --zone example.dev --credential avura
    ```

    The first line serves the zone from every cluster, the second from one.
  </Tab>
</Tabs>

**Check it.** The domain appears under **Your own domains** with a badge. **Working** means "Records answer and reach the cluster. Certificates renew on their own." **Waiting for DNS** comes with the one sentence that says what is left; click **Check now** to ask public DNS again.

A zone that Avura does not share with Ankra is refused, and so is a zone that overlaps the organisation's Custom Ankra domain (use a domain either as a custom DNS zone or as the root below, not both). **Remove…** in the domain row's options menu (or `ankra org custom-dns-zones remove --zone example.dev`) withdraws the zone and revokes the token its clusters used. The records already in the zone are yours and stay where they are.

## Manage records

On **Infrastructure → Domains**, **Records at your DNS providers** shows the records inside the domains Avura shares with Ankra (and those your Cloudflare tokens reach).

1. Pick the domain in **Domain**. Its records are listed.
2. Click **Add record**, or open a record's options menu and choose **Change…** or **Delete…**.
3. Fill in **Name** (the part before the domain; use `@` for the domain itself), **Type**, **Value** and **Time to live**, then click **Add record** or **Save**.

A record's name and type are fixed once it exists, so changing it changes its value and time to live only. **Time to live** offers **The domain's default**, 1 minute, 5 minutes, 30 minutes, 1 hour and 1 day. If Avura refuses a change (a conflicting record, or Avura being briefly unavailable), the dialog stays open with the reason so you can fix it or retry.

**Check it.** The change is made in Avura and answers within a few minutes; Avura's own record list shows it straight away.

## Root generated cluster domains on an Avura domain

Every hostname Ankra generates, including each cluster's domain and the preview URLs built from it, nests under the organisation's [Custom Ankra domain](/platform/ai-workspaces#custom-ankra-domain), which is `ankra.cc` until you set one. A domain Avura shares with Ankra can be that root.

<Tabs>
  <Tab title="Portal">
    Go to **Ankra AI → AI workspaces**. Under **Domains for previews**, type the domain into **Custom Ankra domain** and click **Save changes**. The field does not list your Avura domains; type the one you shared.
  </Tab>
  <Tab title="CLI">
    ```bash
    ankra org domain set example.dev
    ```
  </Tab>
</Tabs>

Ankra first asks your Avura organisation whether it shares the domain. When it does, Ankra provisions the organisation's zone and every cluster's zone in your Avura account, with your connection, and skips the nameserver check a root hosted by Ankra needs: Avura's own listing is the proof you hold the domain. When Avura does not share the domain, it is treated as an ordinary custom Ankra domain and has to be delegated to Ankra's nameservers.

- Ankra adopts the domain as the zone apex and never creates or deletes it. It creates a subzone per cluster under it and deletes only those subzones when a cluster domain is removed.
- If Avura cannot be asked at that moment (it is unreachable, or the connection token was rejected), the change is refused and nothing is saved. Try again once the **Avura** row shows **Connected**.
- Switching from one root to another needs the organisation's cluster DNS zones and DNS records removed first. See [the preview URL](/concepts/applications#the-preview-url) for the procedure. Zones under the old root are torn down in the account that created them.

## Disconnect

You can disconnect from either side.

- In Avura, **Disconnect** on the **Ankra Platform** card asks Ankra to drop the connection and then revokes the platform token and every token minted from it.
- In Ankra, on **Infrastructure → Domains**, click **Disconnect** on the **Avura** row. The dialog **Disconnect Avura?** names any of your own domains that use it. Click **Disconnect** to confirm, or **Stay connected**.

Ankra refuses to disconnect while something still depends on the connection, and says which:

- "Custom DNS zones still use the Avura connection. Remove them first, then disconnect." Remove those domains under **Your own domains** first.
- "The organisation's generated cluster domains are rooted on a domain from this Avura connection. Change the Custom Ankra domain (dns_root_domain) first, then disconnect."

The same rule refuses reconnecting the organisation to a *different* Avura organisation while custom DNS zones use the connection; rotating the token within the same Avura organisation is always allowed.

<Warning>
When Ankra refuses or cannot be reached, Avura keeps the connection working and offers **Revoke anyway**. That revokes every platform token in Avura immediately, whatever Ankra says. Clusters stop publishing to your Avura domains and generated cluster domains on an Avura root stop updating until you connect again. Use it when you need to cut Ankra off now, not as the normal way out.
</Warning>

Unlinking the workspace from its Ankra organisation also revokes the platform tokens first.

<Note>
Deleting the `avura` credential with `ankra credentials delete` or through Ankra AI is the same as **Disconnect**: it runs the checks above and is refused with the same message while something still depends on the connection.
</Note>

**Check it.** The **Avura** row reads "Not connected. Records already there stay."

## What can go wrong

**Avura says your Ankra session expired.** Avura connects and disconnects with the Ankra sign-in stored from your last **Continue with Ankra**, and that sign-in expires. Sign out of Avura, sign in again with **Continue with Ankra**, and retry.

**Avura refuses with a permission error, or the Ankra organisation is not offered.** You have to be an admin (or owner) of the linked Ankra organisation, and the membership has to be active. Ankra also refuses when your organisation requires multi-factor authentication and your account has not enrolled. Check the organisation on the **Ankra Platform organisation** card is the one you administer; linking an existing workspace lists only organisations where you are owner or admin and that are not linked to another workspace.

**Link Ankra account fails.** The Ankra email and the Avura email must be the same address, and both must be verified. If signing in with Ankra sends you back with "an account already exists", sign in with your Avura password and link Ankra from **Settings** → **Security**.

**Connect Avura in Ankra refuses the token.** "That does not look like an Avura API token (avk_...)" means the value is not a platform token. "Avura rejected that platform token. Connect again from Avura." means Avura no longer accepts it: create a new one, or connect from Avura's card.

**The Avura row shows Token refused.** The platform token was revoked in Avura, or the workspace was unlinked. Click **Connect again**, or connect from Avura's **Ankra Platform** card.

**The Avura row shows Not answering.** Ankra could not reach Avura. Nothing is changed while it is unreachable: record changes and root domain changes are refused rather than half applied. When a record change reports that Avura's DNS server is unavailable, Ankra has already asked for a zone re-sync; refresh the page before retrying.

**Avura says the Ankra Platform is unavailable.** Avura could not reach Ankra within its time limit. The previous connection state is kept, so retry later.

**A domain is missing from the Avura list in Ankra.** Only domains with **Use with Ankra Platform** turned on are shared. Turn it on in Avura and reload the page.
