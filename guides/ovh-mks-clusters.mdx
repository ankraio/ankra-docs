[OVHcloud Managed Kubernetes (MKS)](https://www.ovhcloud.com/en/public-cloud/kubernetes/) runs on OVHcloud Public Cloud. OVHcloud runs the control plane; Ankra provisions the cluster, then manages everything on top - node pools, Kubernetes upgrades, addons, stacks, GitOps, and AI-assisted operations.

This page covers OVHcloud MKS specifically. For the shared concepts across all managed providers - live options, discovery/import, and day-2 API patterns - see [Managed Kubernetes](/guides/managed-kubernetes).

## Why OVHcloud MKS with Ankra

- **Free or standard control plane** - pick the OVHcloud control-plane plan that fits the workload.
- **Private networking and anti-affinity** - through the API, attach a private network and spread nodes with anti-affinity where supported.
- **Live pricing and options** - regions, Kubernetes versions, and node flavours are fetched live with your OVHcloud credential.

## Before you start

- **OVHcloud application keys** with a Public Cloud project (`project_id`), stored in Ankra. See [OVH API Credentials](/platform/credentials/ovh). If you have none, the create form shows **Add an OVHcloud Managed Kubernetes credential first** with an **Add a credential** button.
- A **payment method** on the organisation. Without one the review step warns "A payment method is required to create this cluster." and the create is refused - see [Billing](/platform/billing).
- A role with the `clusters.create` permission. Without it **Add a cluster** reads "Your role does not allow creating clusters."

GitOps is optional: connect a repository at creation and Ankra commits the cluster's stack definitions to Git.

## Creating an OVHcloud MKS cluster

<Tabs>
  <Tab title="Portal">
    The portal takes the control-plane plan but not the private network, anti-affinity, monthly billing or update policy. Set those through the API.

    <Steps>
      <Step title="Choose OVHcloud, run by OVHcloud">
        Open **Infrastructure → Clusters → Add a cluster** (`/next/clusters/new`). Choose **OVHcloud** as the provider, then **Provider managed** under **Who runs Kubernetes on OVHcloud?**. The page now reads **Add an OVHcloud Managed Kubernetes cluster**.
      </Step>
      <Step title="Name and purpose">
        Enter a **Cluster name** (at most 32 characters; OVHcloud allows letters, digits and hyphens) and answer **What will this cluster run?**. The answer is required before you can review.
      </Step>
      <Step title="Where it runs">
        Pick the **OVHcloud Managed Kubernetes credential** and a **Region** (for example `GRA9`). Regions load live from OVHcloud. When the platform prices every plan, choose the **Control plane plan**: **Free** (the default) or a paid plan with its monthly price. "OVHcloud bills the Standard plan's control plane by the hour; the Free plan's control plane costs nothing."
      </Step>
      <Step title="Worker nodes">
        Each node group has a **Group name**, a number of **Nodes**, a **Size for** the group (flavours with live pricing) and **Scale this group automatically** with **At least** and **At most**. **Add a node group** adds another; **Placement, labels and taints** holds node labels and taints.
      </Step>
      <Step title="Kubernetes and Git">
        Pick a **Kubernetes version** or keep **Provider default**. Under **Cluster configuration in Git**, optionally choose a **Git connection**, **Repository** and **Branch**.
      </Step>
      <Step title="Review and create">
        Click **Review cluster**, check the settings and the **Checks before creating**, then click **Create cluster**. Ankra provisions the cluster, retrieves the kubeconfig and installs the Ankra agent. The page reads **Your cluster is ready** when it is done.
      </Step>
    </Steps>
  </Tab>
  <Tab title="CLI">

    <CliVersion since="0.5.1" />

    ```bash
    ankra cluster managed create \
      --provider ovh_mks \
      --name my-ovh-cluster \
      --credential-id <ovh-credential-id> \
      --location GRA9 \
      --node-pool-name workers \
      --node-pool-size b2-7 \
      --node-pool-count 2
    ```

    Plan, private network, anti-affinity and update policy have no CLI flags: set them through the API, or the plan in the portal. `--autoscaling` with `--autoscaling-min` and `--autoscaling-max` sets the initial pool's bounds. The CLI accepts `ovh_mks` (and the `ovh-mks` and `mks` aliases).
  </Tab>
  <Tab title="API">
    ```bash
    curl -X POST https://platform.ankra.app/org/clusters/managed/ovh_mks \
      -H "Authorization: Bearer $ANKRA_API_TOKEN" \
      -H "Content-Type: application/json" \
      -d '{
        "name": "my-ovh-cluster",
        "credential_id": "<ovh-credential-id>",
        "location": "GRA9",
        "kubernetes_version": "1.32",
        "node_pools": [
          {"name": "workers", "size": "b2-7", "count": 2}
        ],
        "ovh_mks": {"plan": "free", "anti_affinity": false, "monthly_billed": false}
      }'
    ```

### OVHcloud MKS options

| Field | Description |
|-------|-------------|
| `ovh_mks.plan` | Control-plane plan (`free` or `standard`) |
| `ovh_mks.private_network_id` | Attach the cluster to a private network |
| `ovh_mks.anti_affinity` | Spread nodes with anti-affinity |
| `ovh_mks.monthly_billed` | Bill nodes monthly instead of hourly |
| `ovh_mks.update_policy` | Node update policy |

## Verify

The create progress view follows the control plane, the node pools, kubeconfig retrieval and the Ankra Agent install. The cluster shows **Online** once the agent has connected. Then point `kubectl` at it through Ankra - this needs a [Cluster Access](/guides/cluster-access) grant - and check that every node is `Ready`:

```bash
ankra cluster kubeconfig add <cluster-name> --use
kubectl get nodes
```

See [Accessing Clusters with kubectl](/guides/kubeconfig).

## Day-2 operations

Node pools, upgrades, and deletion work from the portal, the CLI or the API. The CLI examples use `--provider ovh_mks`:

```bash
# scale a pool to a fixed count
ankra cluster managed node-pool scale <cluster_id> workers --provider ovh_mks --count 5

# upgrade the cluster
ankra cluster managed upgrade <cluster_id> --provider ovh_mks --version 1.32

# delete the cluster
ankra cluster managed delete <cluster_id> --provider ovh_mks
```

In the portal, node pools are under **Clusters → &lt;your cluster&gt; → Kubernetes → Nodes → Manage nodes and groups**, upgrades under **Settings → Upgrades and maintenance**, and disconnect and delete under **Settings → Terminate or remove**. OVHcloud MKS clusters cannot be stopped and started. Autoscaling bounds are set from the portal (**Change autoscaling** on a pool), with `ankra cluster managed node-pool update --autoscaling --autoscaling-min <n> --autoscaling-max <n>`, or with the `PATCH .../node-pools/{name}` endpoint. See [Managed Kubernetes - day-2 operations](/guides/managed-kubernetes#day-2-operations) for the shared mechanics.

## Importing an existing MKS cluster

Already running OVHcloud MKS? Discover clusters in your Public Cloud project and adopt them into Ankra without touching them. Discovery and import run from the portal (**Infrastructure → Clusters → Connect a cluster → Find a managed cluster**), the CLI (`ankra cluster managed discover --provider ovh_mks`, then `ankra cluster managed import --provider ovh_mks`) or the API - see [Managed Kubernetes - importing existing clusters](/guides/managed-kubernetes#importing-existing-clusters).
