Find the symptom, then the fix. Most first-week problems are one of these, and the run usually names the cause itself: a failed or waiting step carries a **diagnosis** with what happened and what to do, shown above the steps on the run page and in `ankra pipeline get <run-id>`.

<CliVersion since="0.74.0" note="Most commands here work from v0.16.0; pipeline authority needs v0.74.0." />

```bash
ankra pipeline list --repository <repository-id>
ankra pipeline get <run-id> --repository <repository-id>
ankra pipeline logs <run-id> --repository <repository-id> --step <step>
```

Inside a checkout of an [Ankra application](/concepts/applications)'s repository you can leave out `--repository`: the CLI finds the application from your `origin` remote.

## A push or pull request started no run

Work down this list - each line is a reason Ankra records for an event that did not start a run.

| Check | Fix |
| --- | --- |
| Is the repository connected? `ankra pipeline repositories list` | Connect it - [step 3 of Get started](/get-started/ankra-ci#3-connect-the-repository) |
| Does it have a definition? `ankra pipeline definition get --repository <repository-id>` | Store one: `ankra pipeline definition put .ankra/pipeline.yaml --repository <repository-id>`. Connecting only reads the file when it is already on the default branch. |
| Is there a pipeline cluster? `ankra org ci-settings get` | Choose one in **Build & delivery → Builds and clusters**, under **Where pipelines run**, or `ankra org ci-settings set --cluster <cluster-name>`. Without one, Ankra uses the organisation's AI staging cluster, a cluster someone confirmed as non-production, or the organisation's playground; with none of them, the push gets a check titled **Choose a CI cluster for this organisation** and no run starts. See [Where your pipeline runs](/pipelines/where-pipelines-run). |
| Are pipelines paused for billing? | The run shows **Run did not start: add a payment method** and its check reads action required. Choose **Open billing**, or go to **Settings → Plan and billing**, and add a payment method. Then push again or re-run. |
| Does `on:` match the event? | `on.push.branches` is the branch you pushed. `on.pull_request.branches` is the pull request's **base** branch, the one it merges into. |
| Did a path filter exclude it? | A push that changed no file under `paths` starts nothing. The run list shows it as concluded `skipped` with the reason. |

`ankra pipeline list` shows runs that were recorded as skipped, with the reason.

### No check appears on GitHub, but the run is there

The Ankra GitHub App needs the **Checks: write** permission to post the `Ankra pipeline` check. Without it, Ankra reports the run in its status comment on the pull request instead, and the comment says which permission is missing. Grant it in the App's settings on GitHub.

## "No trigger this pipeline declares matches this event"

`ankra pipeline run`, and the portal's **Run pipeline** button, answer this when the pipeline does not declare manual runs. Add it to `on:`:

```yaml
on:
  push:
    branches: ["main"]
  pull_request:
    branches: ["main"]
  manual: {}
```

## The check says "Awaiting authority approval"

The pipeline asks for a protected setting that no administrator has approved yet, and the check lists which. On a repository's first pipeline this is expected: the pull request trigger's `fork_policy: read_only` is one of them.

An application created from the portal by a person with pipeline management access does not reach this state: Ankra approves the pipeline it generated in that person's name. It still appears for an application added with the CLI, an API token or the AI Assistant, for a repository connected on its own, and whenever a later change edits a protected setting.

The steps still run, but the check stays in progress until a person approves. An AI agent or a service token cannot approve. Approve once:

<Tabs>
  <Tab title="Portal">
    Open **Build & delivery → Builds and clusters** (`/next/organisation/pipelines`). Under **Pipeline settings waiting for approval**, open the repository's request, read what it asks for, and choose **Approve these settings**. When nothing is left, the card reads **Nothing waits for approval**.
  </Tab>
  <Tab title="CLI">
    <CliVersion since="0.74.0" command="pipeline authority list" />

    ```bash
    ankra pipeline authority list
    ankra pipeline definitions approve <definition-id>
    ```

    The pull request comment prints the approve command with the definition id. To decline a request instead, with a reason the run's check shows: `ankra pipeline authority dismiss <request-id>`.
  </Tab>
</Tabs>

The check then settles. A dismissed request leaves the pipeline running without those settings. See [Approve the pipeline once](/get-started/ankra-ci#7-approve-the-pipeline-once).

## A setting in the file has no effect

Secrets, credentials, caches, CPU and memory, a stage's timeout, services, a network tier above `egress-https` and step placement are **protected**. A run takes them only from the version of the pipeline on the default branch, and only once an administrator has approved it. Until then the run behaves as if they were not set - a cache does not restore, a memory limit stays at 1Gi, a secret's file is missing.

`ankra pipeline validate` names every protected setting that will not apply yet, and prints the command to approve it:

```bash
ankra pipeline validate .ankra/pipeline.yaml --repository <repository-id>
```

Merge the change to the default branch, then approve it. The runs that waited re-run on their own.

## A step waits and does not start

The run page and `ankra pipeline get` say why a step is waiting. The common reasons:

| What it says | What to do |
| --- | --- |
| Waiting for a CI slot, or `waiting_on_ci_workers` | The cluster's agent has no free pipeline worker. A cluster can start with none at all ([Before your first run](/guides/ankra-pipelines#before-your-first-run) says which ones start with two): `ankra cluster agent ci set --workers 2 --cluster <cluster-name>`, or **Enable build execution** on the application's **Pipelines** view, which applies at least one worker and restarts the cluster's agent. Otherwise raise the count. |
| `scale_up_in_progress` | A node is being added for the step. It usually joins in one to three minutes. |
| `node_group_at_max` | Every node group that could run the step is at its maximum. Raise the maximum, or add another cluster to the CI pool. |
| `no_node_group_fits`, `stage_exceeds_node_size` | No node is big enough for what the stage asks for. Lower its `resources`, or add a node group with bigger nodes. |
| `provider_quota_exceeded` | Your cloud provider refused a new node for a quota. Raise the quota with the provider. |
| `provider_server_type_unavailable` | Your cloud provider no longer sells the node group's server type in its location. Move the group to a type the location sells. |
| `image_pull_auth`, `image_pull_failed` | The cluster cannot pull the step's image. Check the name and tag, and that the registry is reachable, or add the registry's credential to the organisation. |

A step that never starts is eventually concluded with a message pointing at the cluster's agent and its worker count, so a run never stays open forever. [Diagnosis codes](/guides/ankra-pipelines#diagnosis-codes) lists every code.

## The step cannot reach the network

A package install fails on a DNS lookup or a connection:

```text
npm error code EAI_AGAIN
npm error request to https://registry.npmjs.org/... failed, reason: getaddrinfo EAI_AGAIN registry.npmjs.org
```

pip, Go, Cargo and curl report the same thing as `Temporary failure in name resolution`, `bad address` or `Could not resolve host`. A `run` stage has **no network by default**. Give it HTTPS to the public internet:

```yaml
defaults:
  network: "egress-https"
```

Or set `network: "egress-https"` on the one stage that needs it. Two more cases:

- **A host on a private address**, such as an internal package mirror, stays out of reach on `egress-https`. An administrator can allow its range for every pipeline: `ankra org ci-settings set --egress-allowed-cidr 10.20.0.0/16`.
- **A stage on `network: "services"`** reaches its sidecar services and nothing else. Install dependencies in an earlier stage on `egress-https`, and reuse them from `/workspace`.

## "Read-only file system" or "permission denied"

A step runs as a non-root user (uid 65532) on a read-only root filesystem. It can write to three places:

| Path | What it is |
| --- | --- |
| `/workspace` | The run's shared volume, on disk. The checkout lives here. Put caches, virtual environments and build output here. |
| `/tmp` | Private to the step, 256 MiB, held in memory. `HOME` points here. |
| `/dev/shm` | 64 MiB unless the stage sets `shm_size`. |

The usual fixes:

- **`corepack enable` fails with `EROFS`** - call the package manager through corepack instead: `corepack pnpm install`, `corepack yarn install`.
- **`pip install` cannot write to `site-packages`** - create a virtual environment in the workspace first: `python -m venv /workspace/.ankra-venv`.
- **`apt-get install`, `apk add` fail** - a step cannot install system packages. Use an image that already contains the tools, such as `mcr.microsoft.com/playwright` for browser tests.
- **A compiler or test runner reports `No space left on device`** - it is filling `/tmp`. Point its temporary files into the workspace: `export TMPDIR=/workspace/.tmp && mkdir -p "$TMPDIR"` at the top of the `run` script.

## git: "detected dubious ownership in repository"

The checkout belongs to a different user than the one later steps run as, so git refuses to work in it:

```text
fatal: detected dubious ownership in repository at '/workspace'
```

Trust the workspace on the command itself:

```bash
git -c safe.directory=/workspace rev-parse HEAD
```

Go builds hit the same thing when they stamp version information. Add `GOFLAGS: "-buildvcs=false"` to the stage's `env`, as the [Go starter](/guides/ankra-ci-starter-pipelines#test-pipelines-by-toolchain) does. The commit being built is in `$ANKRA_HEAD_SHA` if that is all you needed git for.

## The step was killed: `out_of_memory`

The step used more memory than it asked for - 1Gi unless the stage says otherwise. Large JavaScript installs and TypeScript builds commonly need more. Raise it on the stage:

```yaml
    resources:
      cpu: "2"
      memory: "4Gi"
```

`resources` is protected, so merge and approve it. `ankra pipeline get <run-id>` prints each step's memory peak against what it asked for, which tells you how much to ask for.

## The secret file is missing

```text
cat: can't open '/run/agent-secrets/npm_token': No such file or directory
```

Check, in order:

1. The pipeline declares it in the top-level `secrets` list, **and** the stage lists its name under `secrets`.
2. The declaration is on the default branch and approved. A pull request that adds a secret runs without it until then.
3. The run is not from a fork. Pull requests from forks get no secrets.
4. The value exists: `ankra org variables get <NAME>` for an organisation variable.

## The cache never restores

The step's **CACHE** column in `ankra pipeline get` says what happened:

- **Nothing shown, or the cache is ignored** - `cache` is protected. Merge and approve it.
- **`miss` every time** - the key changes on every run, often because `hashFiles` matched nothing. Check the lock file name and that it is committed.
- **`disabled`** - the cluster has no StorageClass to back the cache. Give the pipeline cluster a default StorageClass.

Pull requests from forks and tag runs never share caches, by design.

## Node-local storage is not ready

`node_local_storage_not_ready` means the cluster has no StorageClass Ankra may use that creates volumes, so Ankra keeps each run's workspace on the disk of its node, and the agent could not set that up. Nothing ran. The step's `detail` names the cause, and its `next_step` the way out. The ones you are most likely to meet:

| What the step says | What to do |
|--------------------|------------|
| The provisioner did not become ready within 120 seconds | Wait a minute, then run the pipeline again. The provisioner goes on starting after the step fails, and a later run uses it once it is ready. A run started within a minute of the failure fails at once with the same message. If it still fails after that, read the provisioner's pod in namespace `ankra-ci-node-local` |
| The cluster does not serve ValidatingAdmissionPolicy | Upgrade the cluster to Kubernetes 1.30 or later, or name a StorageClass |
| Namespace `ankra-ci-node-local`, or another object under that name, exists and Ankra did not create it | Delete the namespace if nothing in it is yours, or remove or rename the object the detail names. An empty namespace of that name is left by an install that was interrupted and can be deleted |
| Claims outside the pipeline namespaces already name StorageClass `ankra-ci-node-local` | Delete the claims the detail names |
| An admission policy refuses the provisioner's pod or its helper pod | Allow them in namespace `ankra-ci-node-local`. The helper pod runs as root and mounts `/var/lib/ankra-ci-node-local` |
| The cluster cannot pull the provisioner's image | Let the cluster pull it, or set the agent chart value `ci_node_local_provisioner_image` or `ci_node_local_helper_image` to a copy it can pull |
| A pipeline namespace enforces a Pod Security profile below the one pipelines need | Give the namespace the profile the detail names |
| Ankra could not see its admission policy refuse a trial claim | Run the pipeline again. If it fails the same way, read ValidatingAdmissionPolicy `ankra-ci-node-local-claims` and what the detail names |

Whatever the cause, there is one more way out: name a StorageClass whose provisioner creates volumes, and new runs on that cluster use it instead of the nodes' disks.

```bash
ankra cluster agent ci set --cluster my-cluster --storage-class <class>
```

For what node-local storage is and when it applies, see [Workspace storage](/guides/ankra-pipelines#workspace-storage).

## The build step fails before the Dockerfile is read

`build_runtime_confined` means the cluster's nodes stop the rootless image builder from starting - common with AppArmor on Ubuntu or k3s nodes. The build step's log ends in a rootlesskit error such as:

```text
[rootlesskit:child ] error: failed to share mount point: /: permission denied
```

The build pod names no AppArmor profile of its own, so the container runtime applies its default one. containerd's default profile (`cri-containerd.apparmor.d`) denies `mount`, and rootlesskit needs it to set up the builder's own user namespace. The `ankra-ci-build` namespace enforces Pod Security Baseline, which forbids an `Unconfined` profile but admits a `Localhost` one: a profile loaded on the node by name. So the way to keep builds in your cluster is to run the builder under an AppArmor profile that allows `mount`, `pivot_root` and `userns`. There are three ways out, in this order of preference:

1. [Let Ankra load the profile](#let-ankra-load-the-apparmor-profile) on your nodes.
2. [Install the profile yourself](#install-the-apparmor-profile-yourself), when you want to own its text.
3. [Build on Ankra instead](#build-on-ankra-instead), on Ankra's own build cluster.

### Let Ankra load the AppArmor profile

```bash
ankra cluster agent ci set --build-apparmor-profile ankra-managed --cluster <cluster>
```

With `ankra-managed`, Ankra ships the profile, loads it and sends builds only where it is loaded:

- **The profile.** The agent carries a profile named `ankra-managed-rootless-buildkit`. Its rules are exactly those of the [profile you can install yourself](#install-the-apparmor-profile-yourself), under its own name. Its version is the first 12 characters of the sha256 of its text, so an agent release that changes the profile reloads it on every node.
- **Loading it.** The agent runs a DaemonSet, `ankra-ci-apparmor-loader`, with the profile in the ConfigMap `ankra-ci-apparmor-profile`. With a required [step placement](/guides/ankra-pipelines#step-placement), it runs on the nodes the placement's node selector picks. Otherwise it runs on every node, control plane included, because a single-node or untainted k3s server runs builds on its control plane. Either way it tolerates every taint and covers nodes the autoscaler adds later. It loads the profile with each node's own `apparmor_parser` and checks that it is enforced.
- **Routing builds.** Each node where the profile is loaded gets the label `apparmor.ankra.io/ankra-managed-rootless-buildkit=<version>`, and a build pod only schedules on a node with that label. A build waits until a node it can run on has the label. On a node with AppArmor disabled the profile cannot be loaded, so it never gets the label, and the per-node report says `AppArmor is not enabled on <node>`. A node with AppArmor 3, such as Ubuntu 22.04 or Debian 12, cannot parse the profile, so it never gets the label either, and the report says loading failed, with the parser's error.

The agent starts the loader with the first build after you set it, so that build can wait while the nodes load the profile. That build is also tried in your cluster again, even if the cluster was known to confine the builder.

It needs an agent that advertises managed AppArmor. Until the agent does, Ankra sends it no profile, and builds run as if none was set. To read the state, run:

```bash
ankra cluster agent ci get --cluster <cluster>
```

```text
  Build AppArmor:        ankra-managed (ankra-managed-rootless-buildkit 79142a0eefe6)
  AppArmor support:      advertised
  Managed AppArmor:      advertised
  Profile loaded on:     <loaded> of <nodes> nodes (last build's report, <time> ago)
```

`AppArmor support` and `Managed AppArmor` say whether the agent advertises a build profile and the managed one; `not advertised` on either means upgrade the agent. `Profile loaded on` is what the last build that ran with the setting reported, followed by one line for each node where the profile is not loaded, with the reason. Until a build has reported, it reads `not reported yet (the next build reports it)`. `-o json` carries the raw fields, `supports_build_apparmor_managed` and `build_apparmor_managed_status`.

To turn it off, clear the setting. When the next build reaches the agent, it removes the DaemonSet, the ConfigMap and the node label. Until then they stay. The profile file left on the nodes is inert, because nothing names it.

```bash
ankra cluster agent ci set --build-apparmor-profile '' --cluster <cluster>
```

### Install the AppArmor profile yourself

Use this when you want to own the profile text, or while your agent does not advertise managed AppArmor yet. Ankra runs this exact profile on its own Ubuntu 24.04 and Debian 13 build nodes. It is containerd's default container profile with two changes: `deny mount,` becomes `mount,` and `pivot_root,`, and `userns,` is added. Every `/proc` and `/sys` deny of the default profile is kept.

- **Ubuntu 24.04** needs no sysctl change. `kernel.apparmor_restrict_unprivileged_userns=1` only restricts unconfined processes, and the builder is confined by this profile. `userns,` changes nothing there, because a profile with no `abi` rule is compiled without user namespace mediation.
- **Debian 13** pins the AppArmor 4 feature set, which mediates creating a user namespace. Without `userns,` the builder fails with `[rootlesskit:parent] error: failed to start the child: fork/exec /proc/self/exe: permission denied`. Keep the rule.
- **Ubuntu 22.04 and Debian 12** run AppArmor 3, whose parser does not know `userns,` and refuses the whole profile with `syntax error, unexpected TOK_END_OF_RULE, expecting TOK_MODE`. On those nodes, [build on Ankra instead](#build-on-ankra-instead).
- **`mount,` is not narrowed** to a list of filesystem types. Inside its own unprivileged user namespace, the builder makes `/` private, bind-mounts, mounts proc, sysfs, tmpfs and overlay for each `RUN`, remounts read-only and pivots into each build container's root. The kernel's user namespace rules already bound all of that: the builder runs as uid 1000 with only `SETUID` and `SETGID`, so it cannot mount in any namespace it does not own. A per-type list would break on a BuildKit release that mounts something new.

<Steps>
<Step title="Add the profile and its loader to a Stack">
Save these two manifests next to your cluster's ImportCluster file. The ConfigMap holds the profile, and the DaemonSet loads it on every node except the control plane, including nodes that join later. If builds can run on a control-plane node, as on a single-node or untainted k3s server, delete the loader's `affinity` block so it loads the profile there too.

```yaml manifests/rootless-buildkit-apparmor-profile.yaml
# The AppArmor profile Ankra's rootless image builder runs under. The loader
# DaemonSet beside it writes it to /etc/apparmor.d on every worker node and
# loads it.
#
# The unscoped `mount,` is safe because of what the build pod is given: the
# builder runs as uid 1000 with only SETUID and SETGID in its bounding set, so
# the only mounts the kernel lets it make are inside its own unprivileged user
# namespace. Do not reuse this profile for a pod granted CAP_SYS_ADMIN.
#
# When you change the profile text, set the loader's ankra.io/profile-sha256
# annotation to the sha256 of the new ankra-rootless-buildkit value, or the
# loader pods are not restarted and the nodes keep the old profile.
apiVersion: v1
kind: ConfigMap
metadata:
  name: rootless-buildkit-apparmor
  namespace: kube-system
  labels:
    app.kubernetes.io/name: rootless-buildkit-apparmor
    app.kubernetes.io/part-of: ankra-pipelines
data:
  ankra-rootless-buildkit: |
    # ankra-rootless-buildkit: the AppArmor profile Ankra's rootless image builder
    # runs under. It is containerd 2.2's default container profile
    # (cri-containerd.apparmor.d) with two changes. `deny mount,` is replaced by
    # `mount,` and `pivot_root,`, so rootlesskit can make its mount namespace
    # private and runc can pivot into a build container's rootfs inside the
    # builder's own unprivileged user namespace. `userns,` lets rootlesskit create
    # that user namespace where the policy mediates it (AppArmor 4 feature sets,
    # as on Debian 13). Every /proc and /sys deny of the default profile is kept.
    #include <tunables/global>

    profile ankra-rootless-buildkit flags=(attach_disconnected,mediate_deleted) {
      #include <abstractions/base>

      network,
      capability,
      file,
      umount,
      mount,
      pivot_root,
      userns,
      signal (receive) peer=unconfined,
      signal (receive) peer=runc,
      signal (receive) peer=crun,
      signal (send,receive) peer=ankra-rootless-buildkit,

      deny @{PROC}/* w,
      deny @{PROC}/{[^1-9],[^1-9][^0-9],[^1-9s][^0-9y][^0-9s],[^1-9][^0-9][^0-9][^0-9]*}/** w,
      deny @{PROC}/sys/[^k]** w,
      deny @{PROC}/sys/kernel/{?,??,[^s][^h][^m]**} w,
      deny @{PROC}/sysrq-trigger rwklx,
      deny @{PROC}/mem rwklx,
      deny @{PROC}/kmem rwklx,
      deny @{PROC}/kcore rwklx,

      deny /sys/[^f]*/** wklx,
      deny /sys/f[^s]*/** wklx,
      deny /sys/fs/[^c]*/** wklx,
      deny /sys/fs/c[^g]*/** wklx,
      deny /sys/fs/cg[^r]*/** wklx,
      deny /sys/firmware/** rwklx,
      deny /sys/devices/virtual/powercap/** rwklx,
      deny /sys/kernel/security/** rwklx,

      ptrace (trace,tracedby,read,readby) peer=ankra-rootless-buildkit,
    }
```

```yaml manifests/rootless-buildkit-apparmor-loader.yaml
# Loads the ankra-rootless-buildkit AppArmor profile on every worker node
# (every node that is not a control plane, including nodes that join later).
#
# An init container writes the profile from the ConfigMap to
# /etc/apparmor.d/ankra-rootless-buildkit on the host and loads it with the
# host's own apparmor_parser (chroot /host), so the parser always matches the
# node's kernel and AppArmor features. A pause container then keeps the pod
# Running. The node's apparmor.service also loads the file at every boot.
#
# Only the init container is privileged, and only while the load runs. It
# mounts the host root because it runs the host's apparmor_parser in a chroot.
# kube-system is used because a namespace that enforces Pod Security baseline
# or restricted refuses a privileged pod with a host path.
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: rootless-buildkit-apparmor-loader
  namespace: kube-system
  labels:
    app.kubernetes.io/name: rootless-buildkit-apparmor-loader
    app.kubernetes.io/part-of: ankra-pipelines
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: rootless-buildkit-apparmor-loader
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 25%
  template:
    metadata:
      labels:
        app.kubernetes.io/name: rootless-buildkit-apparmor-loader
        app.kubernetes.io/part-of: ankra-pipelines
      annotations:
        # sha256 of the ConfigMap's ankra-rootless-buildkit value. Change it
        # with the profile so every node reloads it.
        ankra.io/profile-sha256: "1b6081e090fdfb759b85fb86d7d0f44a02d1f57eb40ad17fde1432b0724745aa"
    spec:
      # Scheduled ahead of everything else on a node that just joined: a build
      # pod on a node without the profile waits until it is loaded.
      priorityClassName: system-node-critical
      # Every node but the control plane. A build pod can land on any worker
      # node its run reaches, so every worker needs the profile. Where builds
      # also run on a control-plane node (a single-node or untainted k3s
      # server), delete this affinity block.
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: node-role.kubernetes.io/control-plane
                    operator: DoesNotExist
      # Tolerating every taint keeps the loader on any worker a build pod could
      # reach; the affinity alone decides where it runs.
      tolerations:
        - operator: Exists
      automountServiceAccountToken: false
      enableServiceLinks: false
      terminationGracePeriodSeconds: 0
      initContainers:
        - name: load-profile
          image: busybox:1.37.0@sha256:bdf57e528e45e4433820e045b29b4597825a1c9e38353532d90a01445013f82e
          imagePullPolicy: IfNotPresent
          command: ["/bin/sh", "-c"]
          args:
            - |
              set -eu
              name=ankra-rootless-buildkit
              target="/host/etc/apparmor.d/${name}"
              if ! cmp -s "/profiles/${name}" "${target}"; then
                cp "/profiles/${name}" "${target}.tmp"
                mv "${target}.tmp" "${target}"
              fi
              chroot /host apparmor_parser -r "/etc/apparmor.d/${name}"
              grep -q "^${name} (enforce)" /host/sys/kernel/security/apparmor/profiles
              echo "loaded ${name} on ${NODE_NAME}"

          env:
            - name: NODE_NAME
              valueFrom:
                fieldRef:
                  fieldPath: spec.nodeName
          securityContext:
            privileged: true
          resources:
            requests:
              cpu: 10m
              memory: 16Mi
            limits:
              memory: 64Mi
          volumeMounts:
            - name: host
              mountPath: /host
              mountPropagation: HostToContainer
            - name: profiles
              mountPath: /profiles
              readOnly: true
      containers:
        - name: pause
          image: registry.k8s.io/pause:3.10.2@sha256:f548e0e8e3dc1896ca956272154dde3314e8cc4fde0a57577ee9fa1c63f5baf4
          imagePullPolicy: IfNotPresent
          securityContext:
            runAsNonRoot: true
            runAsUser: 65535
            runAsGroup: 65535
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
            seccompProfile:
              type: RuntimeDefault
          resources:
            requests:
              cpu: 1m
              memory: 8Mi
            limits:
              memory: 16Mi
      volumes:
        - name: host
          hostPath:
            path: /
            type: Directory
        - name: profiles
          configMap:
            name: rootless-buildkit-apparmor
```

Both run in `kube-system`: the loader's init container is privileged and mounts the host root, so that it can run the node's own `apparmor_parser`, and a namespace that enforces Pod Security Baseline or Restricted refuses it. The long-running container is an unprivileged pause. The images are `busybox` and `registry.k8s.io/pause`, pinned by digest; mirror them if your nodes cannot pull from Docker Hub and registry.k8s.io.

Then declare a Stack with both manifests, the loader after the profile:

```yaml
apiVersion: v1
kind: ImportCluster
metadata:
  name: my-cluster
spec:
  stacks:
  - name: ci-build-apparmor
    manifests:
    - name: rootless-buildkit-apparmor-profile
      from_file: manifests/rootless-buildkit-apparmor-profile.yaml
    - name: rootless-buildkit-apparmor-loader
      from_file: manifests/rootless-buildkit-apparmor-loader.yaml
      parents:
      - name: rootless-buildkit-apparmor-profile
        kind: manifest
```

Commit it to the cluster's GitOps repository and let Ankra sync it, or apply it:

```bash
ankra cluster apply -f my-cluster.yaml
```

[Create and change a Stack](/guides/create-and-change-a-stack) covers staging it as a draft first.
</Step>
<Step title="Check the profile is loaded on every node">
A loader pod runs on every node except the control plane:

```bash
ankra cluster get pods -n kube-system --name rootless-buildkit-apparmor-loader
```

Each pod's init container logs `loaded ankra-rootless-buildkit on <node>`:

```bash
ankra cluster logs -n kube-system -l app.kubernetes.io/name=rootless-buildkit-apparmor-loader -c load-profile --follow=false
```

A pod that does not get past `Init` names the reason in that log (add `--previous` once it has restarted), for example a node without `apparmor_parser`. A build that lands on that node waits until the profile is loaded there.
</Step>
<Step title="Name the profile">
`ankra cluster agent ci get` must show `AppArmor support: advertised`, then:

```bash
ankra cluster agent ci set --build-apparmor-profile ankra-rootless-buildkit --cluster <cluster>
```

It applies to the next build dispatched, with no agent restart, and that build is tried in your cluster again even if the cluster was known to confine the builder.
</Step>
</Steps>

To change the profile, edit the ConfigMap and set the DaemonSet's `ankra.io/profile-sha256` annotation to the sha256 of the new `ankra-rootless-buildkit` value. Without a new annotation the loader pods do not restart and the nodes keep the old text.

To back out, clear the setting with `--build-apparmor-profile ''`, then remove the Stack if you like. The profile stays loaded on the nodes that had it, which is harmless while nothing names it, until the node is replaced. To move to [the profile Ankra loads](#let-ankra-load-the-apparmor-profile), set `ankra-managed`, and remove your Stack once `Profile loaded on` covers your nodes and a build has passed. The two profiles have different names, so both can be loaded at once.

### Build on Ankra instead

Ankra can build the image on its own build cluster instead, and the scan, gate and publish still run as usual. Two things must both hold: the organisation's build fallback is on (**Build on Ankra when your cluster cannot**, under **Build rules** in **Build & delivery → Builds and clusters**, or `ankra org ci-settings set --build-fallback platform_builders`), and Ankra has enabled platform builds for the organisation. `ankra org ci-settings get` shows both. Only Ankra can enable platform builds: if it says no, [contact support](/platform/support). What leaves your cluster when this happens is on [Where your pipeline runs](/pipelines/where-pipelines-run).

## The check says `action_required`

The run failed because of Ankra or the cluster, not your code: an agent that went offline, a volume that would not attach, an image that could not be pulled. Ankra retries these once by itself. A run that did not start because pipelines are paused for billing also reads action required; re-running does not help until a payment method is added (see [A push or pull request started no run](#a-push-or-pull-request-started-no-run)). If the retry fails too, the check names the cause. Fix it if it is on your side, then press **Re-run** on the check, or:

```bash
ankra pipeline rerun <run-id> --repository <repository-id> --failed-only
```

## Still stuck

Ask Ankra's AI in the portal chat - "why did run #12 of my-repo fail?" - and it reads the run, the step logs and the cluster's events. Or [contact support](/platform/support) with the run's link from the check.
