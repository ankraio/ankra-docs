A branch preview runs a branch's already-built container image in its own temporary namespace on your organisation's staging cluster, and Ankra removes it when its lifetime ends. Use it to show work in progress, reproduce a bug against one build, or hand a reviewer a live address instead of a screenshot.

Pull requests get [previews automatically](/guides/pr-preview-environments) once you turn them on. This guide covers the manual path: **New preview** in an application's **Ship** view, and the same step in the CLI and MCP.

## Before you start

- **A connected application.** The branch must belong to an [application](/concepts/applications) whose setup has run.
- **A staging cluster for previews.** An organisation admin chooses it under **Ankra AI → AI workspaces**, in **Where workspaces and previews run** → **Staging cluster** (`/next/organisation/ai-workspaces#staging`). Without one, the **Previews** section reads **Choose where previews run.** and **New preview** is disabled. The cluster's agent must be online too: otherwise the section reads **The preview cluster is offline.**
- **A role that can deploy.** Starting and stopping previews needs the `applications.deploy` permission. Without it the section says "Only people who can deploy can start previews. Ask an admin."
- **A published build of the branch.** A preview deploys an image; it does not build one. See [Which image a preview finds](#which-image-a-preview-finds).

## Start a preview

<Steps>
  <Step title="Open the Previews section">
    Go to **Applications → your application → Ship** and scroll to **Previews**.

    Check: beside the **Cluster online** badge you see the staging cluster's name and **Maximum lifetime** in hours. That maximum is the cap your role has, set by an admin under **Ankra AI → AI workspaces**.
  </Step>
  <Step title="Choose the branch and lifetime">
    Select **New preview**. In the **New preview** dialog, pick the **Branch** and set **Lifetime (hours)**. The lifetime starts at the organisation's default and cannot go above your maximum.

    Check: as soon as you pick a branch, Ankra checks the registry and a note under the fields reads `Published image: <tag>`. If it reads anything else, see [No published image for the branch](#no-published-image-for-the-branch).
  </Step>
  <Step title="Review and launch">
    Select **Review preview**. The review lists the **Branch**, the **Destination** cluster, the **Lifetime** and the **Published image**. Select **Launch preview**.

    Check: the dialog reads **Preview launch accepted.** Select **Done**. A card for the branch appears under **Previews** with its status.
  </Step>
</Steps>

The preview starts from the application's preview configuration: its variables, login, database and what it is built from. You set those once, under [Set what every preview starts with](#set-what-every-preview-starts-with), not in this dialog.

## Verify

Each preview card shows **Started**, **Version** (the image it runs), **Ends automatically** and **Data** (**Throwaway database** or **Application defaults**). When the preview is ready and its address is confirmed, the card offers **Open preview**. Select it and your branch's build opens in a new tab.

From the CLI, list the application's previews and read their addresses:

<CliVersion since="0.14.0" />

```bash
ankra application demo list <application-id>
```

## Which image a preview finds

Ankra looks in the application's registry repository for these tags, in this order, and deploys the first one it finds:

1. `sha-<7>`: the first seven characters of the branch's head commit, the only tag that is provably this head's build.
2. For each open pull request from the branch, `sha-<7>` of its merge commit, then `pr-<number>`.
3. The branch name, with every character other than letters, digits, `.`, `_` and `-` replaced by `-` (`feature/login` becomes `feature-login`).

A pull request tag is built from merging the branch into its base, not from the branch head.

What publishes these tags depends on what builds the application (see [Ship your app](/guides/deliver-your-app#where-the-image-is-built)):

| Builder | Tags it publishes |
|---|---|
| Ankra Pipelines, as generated | `sha-<7>` for commits on the tracked branch only: the `publish` stage runs on a push to that branch, not on a pull request |
| Generated GitHub Actions workflow | `sha-<7>` and the branch name for commits on the tracked branch only. A pull request is built and scanned but never pushed |
| Your own workflow | Whatever it pushes |
| Ankra platform builders | `sha-<7>` of any commit you ask for, where Ankra has enabled platform builders for your organisation |

So a preview of any branch other than the tracked one needs an image from somewhere else. Build the branch's head on Ankra platform builders:

```bash
ankra application build start <application-id> --commit <full-sha> --ref feature/login --reason demo --wait
```

Or push a `sha-<7>` tag from your own CI.

## Set what every preview starts with

Everything a preview needs beside the image is configured once per application, under **Applications → your application → Settings → Deploys** (`/next/applications/<application-id>?view=settings&section=deploys`). Changing it needs a role that can configure the application. Existing previews keep what they were launched with; the settings apply to the next preview.

**Preview defaults** holds:

- **Add preview variable**: a **Variable name**, a **New value**, and **Store as a secret** for a value that should stay hidden. Values stay hidden once saved. A secret value is mounted into the preview from a Kubernetes Secret.
- **Preview database**: **Enable preview database** creates a temporary PostgreSQL database for each new preview, inside its namespace, with its own random password. It is removed with the preview.
- **Preview login**: protects previews with a login. Ankra keeps the password, so you can copy it from here with **Copy password** whenever you need it. Rotating it leaves running previews on the old password until they next redeploy.

Nothing from the preview database is injected on its own, because every codebase names its configuration differently. Reference these placeholders in your preview variables' values instead:

| Placeholder | Resolves to |
|---|---|
| `${{ ankra.demo_database.url }}` | Full `postgresql://` connection string |
| `${{ ankra.demo_database.host }}` | In-namespace service host |
| `${{ ankra.demo_database.port }}` | `5432` |
| `${{ ankra.demo_database.name }}` | Database name |
| `${{ ankra.demo_database.user }}` | Database user |
| `${{ ankra.demo_database.password }}` | The per-preview random password |

**What a preview starts with** holds:

- **Built from**: by default **This app alone**. **Choose a profile** attaches a [stack profile](/guides/stack-profile-demos) (a **Version**, or blank for the latest), so every preview also starts that profile's add-ons and manifests in the same namespace and removes them with it.
- **Shared services**: **Choose shared services** lets every preview use one set of supporting services, such as a database or a cache. **Stop sharing services** detaches them without deleting them.
- **Database provisioning**: a **Migration command** that runs through `sh -c` in the application image once a fresh preview database is ready, and **Database extensions (comma separated, lowercase)** such as `vector`.

The same defaults are in the CLI:

```bash
ankra application demo config get <application-id>
ankra application demo config set <application-id> --database=true --env DATABASE_URL='${{ ankra.demo_database.url }}'
ankra application demo config set <application-id> --migrate-command 'pnpm run db:migrate' --database-extension vector
```

## Resource limits

Each preview namespace carries its own hard `ResourceQuota`, so one preview cannot exhaust the staging cluster:

| Preview | Pods | CPU requests | CPU limit | Memory requests | Memory limit |
|---|---|---|---|---|---|
| The application alone | 5 | 1 | 2 | 1 Gi | 2 Gi |
| Built from a stack profile | 20 | 4 | 8 | 8 Gi | 16 Gi |

## Options the portal form does not have

The **New preview** dialog asks only for the branch and the lifetime. For anything else, use the CLI:

| You want | Use |
|---|---|
| A specific image tag rather than the one Ankra resolves | `--image-tag <tag>` |
| A different container port | `--container-port <port>` |
| Some components of a monorepo, not all of them | `--component <name>` (repeat it). Every component deploys by default |
| One component's tag, port or path | `--component-tag NAME=TAG`, `--component-port NAME=PORT`, `--component-path NAME=/prefix` |
| A different component on the address's root path | `--entry-component <name>` |

```bash
ankra application demo deploy <application-id> --branch feature/login --ttl-hours 8
ankra application demo deploy <application-id> --branch main \
  --component web --component api \
  --component-port api=8090 --component-path api=/api \
  --entry-component web
```

An override may only name a component that `--component` selects: to tune one component of a full launch, list them all.

## Reach the running preview

How a preview is reached depends on the organisation's preview domain, set by an admin under **Ankra AI → AI workspaces → Domains for previews**:

1. **A Preview domain**, if configured, wins: previews get addresses under that wildcard zone, with its **Ingress class** and **TLS secret**.
2. **Otherwise the staging cluster's own Ankra subdomain**, when the cluster has DNS turned on.
3. **Otherwise inside the cluster only.** The preview still runs. Use `ankra application demo detail` for its namespace and services.

The full order is under [the preview URL](/concepts/applications#the-preview-url). The card offers **Open preview** only for an HTTPS address. For any other address it reads **No public address yet.**, and the address is in the `preview_url` field of `ankra application demo list <application-id> -o json`. While Ankra waits for DNS the card reads **Address is awaiting DNS verification.**

## Update a branch preview's image

A branch preview's card has **Update image**. Pick the **New image** (the branch's latest build or a published version) and a **Lifetime (hours)**. Redeploying restarts the timer. Pull request previews have no **Update image**: a push to the pull request redeploys them.

## Stop a preview

A preview stops itself when its lifetime ends: the namespace is deleted, with its database. To stop one early:

<Tabs>
  <Tab title="Portal">
    On the preview's card, select **Stop preview**, then **Stop this preview**. The dialog reads **Preview teardown accepted.**
  </Tab>
  <Tab title="CLI">
    ```bash
    ankra application demo list <application-id>
    ankra application demo stop <application-id> <workspace-id>
    ```
  </Tab>
  <Tab title="MCP">
    Call `demo_stop` with the preview's namespace or pull request number.
  </Tab>
</Tabs>

<Warning>
Preview namespaces are temporary. The preview database starts empty on every deploy and is removed with the namespace. Run your migrations on boot, or set a **Migration command**, and never point a preview at data you care about.
</Warning>

## From the CLI and MCP

<Tabs>
  <Tab title="CLI">
    ```bash
    # Check that a branch has a published image
    ankra application demo build <application-id> --branch feature/login

    # Start a preview of the branch
    ankra application demo deploy <application-id> --branch feature/login --ttl-hours 8

    # Read its components, provisioning steps and failure detail, then its logs
    ankra application demo detail <application-id> <workspace-id>
    ankra application demo logs <application-id> <workspace-id> --tail 500
    ```
    The deploy answer includes `preview_url` when Ankra resolved a public address.
  </Tab>
  <Tab title="MCP">
    `deploy_pr_demo` starts a preview of a pull request's build: pass `application_id`, `pr_number` and `image_tag`. It also takes `env` (variables for this launch, which win by name over the preview defaults) and `database`. Ankra AI may run it in **Ask** mode, because a preview is isolated and removes itself. Stop it with `demo_stop`, and read a failed one with `get_demo_diagnostics`. MCP has no tool that starts a preview of a branch without a pull request: use the portal or the CLI.
  </Tab>
</Tabs>

## No published image for the branch

When the registry holds nothing for the branch, the note in the **New preview** dialog says what Ankra found and **Review preview** stays disabled. Without more detail it reads "Build and publish this branch before launching a preview."

The portal has no button that fixes a missing build. Use the CLI: Ankra applies its own fixes first (publish readiness, a rerun of a failed run, a retry of a failed setup) and, when those cannot produce an image, dispatches an agent that investigates the repository and opens a pull request with the fix.

```bash
ankra application demo fix-build <application-id> --branch feature/login
```

The answer names the agent run to follow.

## What can go wrong

| Symptom | What to check |
|---|---|
| **New preview** is disabled | The section says why: "Only people who can deploy can start previews. Ask an admin.", "Ankra does not allow starting previews of this application right now.", **Choose where previews run.** or **The preview cluster is offline.** |
| **Review preview** is disabled | No branch is picked, the branch has no published image, the image could not be checked, or the lifetime is not a whole number between 1 and your maximum. |
| "Repository branches could not be read. Check the source connection." | The application's Git connection can no longer read the repository. Repair the connection, then open the dialog again. |
| The card shows an error | Select **See its pods** beside the error to open the preview's pods on the staging cluster. The preview runs *your* image, so a crash on boot is in the application. If it refuses to start without configuration, add the missing variables under **Preview defaults**, or run `ankra application demo fix <application-id> <workspace-id>` to send Ankra AI to work them out. See [pre-setup when a preview crashes](/concepts/applications#automatic-pre-setup-when-a-demo-crashes). |
| Pods stay `Pending` | The namespace quota or the cluster is full. Read the preview's events with `ankra application demo detail <application-id> <workspace-id> -o json`, and stop previews you no longer need. |
| **No public address yet.** | The staging cluster needs DNS turned on, or the organisation needs a **Preview domain**. Without either, the preview is reachable inside the cluster only. |
| A variable did not reach the container | Defaults apply to new previews only. Start a new preview after you change them. |
