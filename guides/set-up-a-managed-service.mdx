description: Add a database, cache or queue to an application, place it on one of your clusters, size it and confirm the reviewed plan, then follow the installation.
---

import { CliVersion } from "/snippets/cli-version.jsx";

Setting up a managed service takes four steps: **Connect**, **Place**, **Configure** and **Review**. The last step shows the plan Ankra prepared from your choices, and nothing is installed until you confirm it. At the end you have a service running on one of your clusters, and the application environments you chose receive its connection.

The quickest way in is from the application that will use the service: [Start from your application](#start-from-your-application) opens the same four steps with the application and its environment already chosen, and brings you back to the application when you are done. You can also start from the catalogue.

---

## Before you start

- **The service cluster uses the native deployment engine.** Services generate their credentials in the cluster, which only the [native engine](/concepts/deployment-engines) supports. New clusters use it by default. A cluster that still deploys with ArgoCD can be [migrated](/concepts/deployment-engines#migrating-a-cluster-to-the-native-engine).
- **For PostgreSQL, the service cluster runs Kubernetes 1.30 or later.** A PostgreSQL service gets a TLS certificate of its own, and an admission policy in the cluster keeps that certificate from being switched under the running database. Kubernetes serves that policy from 1.30.
- **The service cluster has a default StorageClass.** Every service keeps its data on persistent volumes from the cluster's default StorageClass.
- **The application is deployed, or you start from its deploy form.** Setup offers the environments an application is deployed to, each one a namespace on a cluster. Started from the deploy form, it also offers the environment that deploy will run in, marked **Not deployed yet**. All environments that one service connects must be in the same data boundary.
- **To be connected for you, the application runs on the service cluster.** Setup also accepts environments on other clusters, but Ankra delivers the service's connection only to environments on the cluster the service runs on. See [How your application receives the connection](/guides/connect-to-a-managed-service#how-your-application-receives-the-connection).
- **Your role allows it:**

| Permission | Needed to |
|------------|-----------|
| `applications.deploy` and `profiles.read` | Set up a service at all |
| `clusters.operate` on each cluster involved | Connect an environment on that cluster, or place the service on it |
| `clusters.write` on a cluster | Declare or change its data policy |
| `applications.read` | See **My services** |

The built-in `owner`, `admin` and `operator` roles hold all of them. See [Roles and access](/guides/roles-and-access). Without the first two, the setup page says `Your role cannot set up managed services.`

## Declare a data policy

A data policy says where a cluster keeps data. It is optional: a cluster without one takes services in the default location, and environments on clusters without a policy connect to each other freely. Declare one when services must keep data within a boundary; see [Data policies](/concepts/managed-services#data-policies) for what it then restricts.

<Tabs>
  <Tab title="Portal">
    <Steps>
      <Step title="Open the cluster's data policy">
        Go to **Infrastructure → Clusters → *your cluster* → Settings → Logs and data** (`/next/clusters/<cluster-id>/settings/logs`). The **Data policy** card, marked **Optional**, reads **None declared.** until a policy exists.
      </Step>
      <Step title="Open the policy">
        Choose **Declare data policy**, or **Change data policy** when the cluster already has one. A dialog opens.
      </Step>
      <Step title="Enter the region and data boundary">
        Enter a **Region**, such as `eu-north`, and a **Data boundary**, such as `eu`. Both take lowercase letters, digits and single hyphens, start with a letter, and are at most 63 characters. **Review policy** stays disabled until both are valid.
      </Step>
      <Step title="Choose whether services must stay on this cluster">
        Tick **Services bound to this cluster must run on this cluster only** if an application on this cluster may only use services running on the same cluster.
      </Step>
      <Step title="Review and confirm">
        Choose **Review policy**, read the summary, then **Confirm data policy**. The card now lists the **Region**, **Data boundary**, **Placement** and **Declared** revision.
      </Step>
    </Steps>
  </Tab>
  <Tab title="CLI">
    <CliVersion since="0.27.0" />

    ```bash
    ankra services policy set --cluster my-cluster --region eu-north --data-boundary eu
    ```

    Add `--local-only` if services on the cluster may serve only consumers on the same cluster. To replace an existing policy, add `--revision` with the revision that `ankra services policy get --cluster my-cluster` shows. Run `ankra services policy get --cluster my-cluster` to check the result.
  </Tab>
  <Tab title="MCP">
    `set_service_cluster_policy` declares the policy, and `get_service_cluster_policy` reads it back.
  </Tab>
</Tabs>

The policy is your organisation's declaration. Ankra records who made it and when, and does not verify the location. A service already reviewed against an earlier policy needs a new review.

## Start from your application

Open the application from **Applications**. Its **Overview** has a **Services** card listing the managed services the application uses: each one's name, kind and package, which of the application's environments it serves, and how it is doing (deployment progress until it finishes, then its health and readiness). Services that need a look come first, and **My services** in the card's header opens the full list for this application. An application without a service shows **No managed services yet.** and **Browse all services** instead.

<Steps>
  <Step title="Choose what to add">
    Choose one of the tiles, such as **Database** or **Cache**, to go straight to setting up the newest package of that kind, or **Browse all services** to pick from the whole catalogue. The card offers a tile only for a kind the catalogue has a package for that can be set up. Once the application uses a service, the tiles sit under **Add a service** below the list.
  </Step>
  <Step title="Set it up for the application">
    The setup page opens with **Connect**, and that environment's namespace is already ticked. Continue with the [four steps](#set-up-the-service) below. If the application is not deployed to that environment yet, Connect says `<application> is not deployed to <environment> yet.` and links to its deploy form: choose **Add a managed service** there, and Ankra sets the service up for where the deploy will run and connects it on the first deploy.
  </Step>
  <Step title="Deploy the application">
    After you confirm, the service's page follows its deployment. Once the service is ready, Ankra copies its connection into the application's namespace by itself while none of the application's running pods references it, without a redeploy. Workloads deployed before the service was connected read the connection only after the application's next deploy adds the reference to it, so once the service is running, deploy the application to that environment: its containers then read the connection as environment variables such as `DATABASE_URL`. See [How your application receives the connection](/guides/connect-to-a-managed-service#how-your-application-receives-the-connection).
  </Step>
</Steps>

The application's other pages lead into the same flow, with the application and environment chosen:

- **Variables** offers **Connect a managed service**.
- The deploy form (**Environments → Deploy a version**) offers **Add a managed service** under its secrets and dependencies. It opens in a new tab, so the deployment you are preparing stays open.

Every one of these opens the same setup page, with the application and environment in its address (`?application=<application-id>&environment=<environment-id>`). The card and the links appear only where managed services are offered to your organisation. The card's tiles and **Connect a managed service** also need a role that may set one up: without it, a card with no services reads `Ask someone who can deploy applications to add one.`

## Set up the service

<Tabs>
  <Tab title="Portal">
    <Steps>
      <Step title="Open the package">
        From an application, a tile or **Browse all services** brings you here: see [Start from your application](#start-from-your-application). From **Infrastructure → Managed services**, open the **Catalogue** tab, choose the service and choose **Set up**. Catalogue cards also carry a **Set up** button. The setup page opens on **Connect**.
      </Step>
      <Step title="Connect: choose the application environments">
        Choose an **Application** and tick the environments that will use the service. Each environment is listed as a namespace on a cluster, together with that cluster's data policy when it declares one. You can add environments from several applications, up to 100: those already ticked stay listed under **Also chosen from other applications**. They all use this one service and share its credentials, so to keep data apart, for example production from staging, set up a separate service for each. When you came from an application, its environment is already ticked.

        **Continue** stays disabled while the chosen environments keep data in different boundaries (`These environments cannot share one service.`), including a cluster that declares a policy beside one that does not, or while your role cannot operate one of their clusters. The line beside it says how many environments will use the service once you can continue.
      </Step>
      <Step title="Place: choose who runs it and where">
        Under **Who operates it**, **Your infrastructure** means Ankra installs the service on one of your clusters, and your team operates it. A package can also offer **An existing service**: Ankra connects a service you already run, without taking it over. A package that declares **Ankra-hosted** shows it, but it cannot be chosen.

        Choose the **Service cluster** from the clusters your environments run on. When the cluster declares a data policy, the page shows its **Region** and **Data boundary**. An environment that cannot use a service on the chosen cluster is listed under `Some environments cannot use a service on this cluster.` with the reason. The usual reasons are a different data boundary, or a cluster that keeps its services local. **Continue** is enabled once nothing is listed there.

        <Tip>
        A service's addresses resolve only inside its own cluster, and Ankra connects only the environments on that cluster. Place it on the cluster your environments run on. An environment on another cluster needs a network path you provide and the values set by hand: see [Connect from another cluster](/guides/connect-to-a-managed-service#connect-from-another-cluster).
        </Tip>
      </Step>
      <Step title="Configure: name it and size it">
        **Service name** is suggested from the application and the package, for example `storefront-postgresql`. It must follow the [name rules](#service-name-rules).

        Each setting shows its range and default. A package with more than three settings keeps the rest under **More settings**. [Managed Service Settings](/reference/managed-services) explains each one.

        Choose **Review setup**. This records the chosen environments as consumers of managed services and asks Ankra to prepare a plan. It installs nothing. The button reads **Preparing your review…** until the plan is ready.
      </Step>
      <Step title="Review: confirm the plan">
        **Review and connect** lists the plan: the **Service name**, the **Package** and version, who it is **Operated by**, the **Service cluster** with its region and data boundary, every setting, and the **Connected environments**.

        Choose **Confirm setup** before the review window ends, **10 minutes** after the plan was prepared. The page shows when that is. **Change choices** takes you back. If the window passes, the page says `This review has expired.` and **Review again** prepares a fresh plan with the same choices.

        Confirming opens the service's page, headed **Setting up *your service***.
      </Step>
    </Steps>

    A review waiting for confirmation is also listed under the **My reviews** tab of **Managed services**, where you can confirm it within its window. Each person can hold at most 20 reviews waiting for confirmation, and each organisation 100.
  </Tab>
  <Tab title="CLI">
    <CliVersion since="0.27.0" />

    Find the package, bind the application namespace that will use the service, then prepare and confirm the setup:

    ```bash
    ankra services packages list
    ankra services consumers bind --application my-app --cluster my-cluster --namespace my-app
    ankra services setup my-app-postgresql --package postgresql --cluster my-cluster --consumer <consumer-id>
    ```

    `consumers bind` prints the consumer id that `setup` takes; repeat `--consumer` for each environment. Add `--allow-planned` to bind a namespace the application is not installed in yet. `setup` prints the plan and asks before it confirms. Set a package setting with `--param name=value`: `ankra services packages get postgresql` lists them with their bounds. `--review-only` stops after the review and prints the `ankra services reviews confirm` command that confirms it, for a person or a pipeline that approves separately.

    Follow the installation with:

    ```bash
    ankra services get my-app-postgresql
    ```
  </Tab>
  <Tab title="MCP">
    `list_service_packages` and `get_service_package` find the package, `get_service_setup_eligibility` says which services an environment can set up, `bind_service_consumer` binds the namespace, `prepare_service_setup` returns the plan, and `confirm_service_setup` confirms it. `get_service_instance` follows the installation.
  </Tab>
</Tabs>

### Service name rules

The name becomes the service's namespace and its stack name on the service cluster. It must:

- be a DNS label: lowercase letters, digits and single hyphens, starting with a letter;
- be at most **36 characters**;
- not be `default`, and not start with `kube-`, `ankra`, `cnpg-system`, `cert-manager`, `ingress-nginx`, `argocd` or `flux-system`;
- not already be used on that cluster, by a stack or by another service. A name stays taken from the moment its setup is confirmed, even if the installation then fails, until that service is [deleted](/guides/delete-a-managed-service).

The form checks the characters as you type. The platform checks the rest when it prepares and confirms the review. A name another service on the cluster holds is refused at both points: the page says `Another service on the service cluster already uses this name.` and flags the name until you change it. A stack of that name that no service holds is found only when Ankra installs the service, after you confirm, and the installation then needs attention.

### What confirming does

Confirming asks Ankra to install the service. It does not verify that the service is ready or that your applications can reach it. After you confirm:

1. The service appears in **My services** and on the **Services** card of each application it serves. Its page opens with **Setting up *your service***: `Ankra is deploying it now. This page follows each step and tells you when it is ready.` Opening the confirmed review again says `This setup is already confirmed.` with **View the service**.
2. For PostgreSQL, Ankra makes sure the cluster runs the CloudNativePG operator. It is installed once per cluster, as its own stack `cloudnative-pg` in the `cnpg-system` namespace. A cluster that already runs CloudNativePG, installed by Ankra or any other way, keeps its operator. The operator is shared by every PostgreSQL service on the cluster, so leave it in place while any of them run.
3. Ankra deploys the service as a stack named after the service, into a namespace of the same name.
4. Each environment on the service cluster receives the service's connection once the service is ready. Ankra writes it into the application's namespace without a redeploy while none of the application's running pods references it, and leaves it to the application's next deploy otherwise. Workloads deployed before the service was connected read it after their next deploy. When Ankra leaves an environment's connection to a deploy, the service's page offers to deploy it; see [How your application receives the connection](/guides/connect-to-a-managed-service#how-your-application-receives-the-connection) for what each environment's state means.

The first PostgreSQL service on a cluster can take a few minutes longer while its operator comes up.

## Follow the installation

Open **Infrastructure → Managed services**, stay on **My services** and choose the service. **Deployment progress** shows where it stands, and **Operation details** opens its deployment operation (or **View cluster operations** the cluster's list when Ankra has no single operation to show). Once Ankra has observed the deployed service, it also carries a **Health** badge in **My services**, and its page's **Service health** section shows what was observed: see [Health](/concepts/managed-services#health).

| Status | Meaning |
|--------|---------|
| **Installation requested** | Your request is saved. Deployment has not been confirmed yet. |
| **Deployment in progress** | The deployment operation has not finished. |
| **Verification needed** | The deployment finished. A working connection from your application has not been verified, and either Ankra does not observe the service serving or its readiness reads **Not ready** or **Not checked recently**. |
| **Running** | The deployment finished and Ankra observes the service serving in its cluster. Its readiness check has not passed yet, or has not run. |
| **Deployed** | The deployment finished and the service passed its last readiness check: a client could connect. |
| **Installation needs attention** | The installation request did not complete. Check the cluster's operations before trying again. |
| **Deployment needs attention** | The deployment did not complete successfully. Check its operation for the next step. |
| **Progress unavailable** | Ankra does not have enough current operation records to report progress. Your request is still saved. |
| **Retired** | The service was [deleted](/guides/delete-a-managed-service) and its name released. The record is kept as history. |
| **Deleted, data may remain** | The service was deleted and its name released, but Ankra cannot show that its data is gone. Its page lists the volumes that may still hold it: see [When data may remain](/guides/delete-a-managed-service#when-data-may-remain). |

While a deletion runs, **My services** shows the service as **Deleting** instead.

### Verify that the service answers

A finished deployment does not show that your application can connect. The service's page has a **Readiness** section, whose badge reads **Not verified** or **Verifying** until Ankra's check has connected with the service's credentials, and **Ready**, with when the check last passed, once it has. Check that the service answers before you rely on it: see [Check that the service answers](/guides/connect-to-a-managed-service#check-that-the-service-answers).

### See the services an application uses

The application's **Services** card lists them, and **My services** in its header opens the full list for that application. From the command line, give the application's name or id:

<CliVersion since="0.27.0" />

```bash
ankra services list --application my-app
```

A service is listed when its reviewed plan names one of the application's namespaces as a consumer. The **Used by** column says which of the application's environments it serves, or the namespace where the application is not deployed yet. Retired services are left out unless you add `--include-released`.

## Troubleshooting

| What you see | Cause | Remedy |
|--------------|-------|--------|
| `Managed services are not available to your organisation yet.` | Managed services are not turned on for your organisation | **Contact support** |
| `Your role cannot set up managed services.` | Your role lacks `applications.deploy` or `profiles.read` | Ask an administrator for a role that holds both |
| `<application> is not deployed to <environment> yet.` | You came from an application whose environment has no deployment yet | Open its deploy form from the link, choose **Add a managed service** there, and deploy |
| `The environment this link names is not one of <application>'s environments now.` | The link names an environment the application no longer has | Choose an environment in **Connect** |
| `These environments cannot share one service.` | The chosen environments sit in more than one data boundary, or one cluster declares a data policy and another does not | Set up one service per data boundary, or declare the same boundary on each cluster |
| `Services it uses must run on <cluster> itself.` | That environment's cluster keeps its services local | Place the service on that cluster, or set up a separate service for it |
| `Your role cannot operate <cluster>.` | You lack `clusters.operate` on that cluster | Remove the environment, or ask an administrator for access |
| `This service runs in a namespace named after it. Choose a name of at most 36 characters that is not a system namespace, such as kube-system.` | The service name breaks a [name rule](#service-name-rules) | Shorten or change the name, and review again |
| `The platform refused these choices.` | A setting is out of range, or an environment is outside the service cluster's data boundary | Check the settings and the environments, and review again |
| `This service needs the Ankra native deployment engine, and the service cluster deploys new stacks through Argo CD.` | The service cluster deploys new stacks through ArgoCD | [Migrate the cluster to the native engine](/concepts/deployment-engines#migrating-a-cluster-to-the-native-engine), or choose a native-engine cluster |
| `Delivering credential grants into a deployed stack is not available yet; this package's secret inputs cannot be installed` | The package version declares secret inputs for that way of running it. Ankra refuses it when it checks the choices and when it prepares the review, before any name is reserved | Choose a package version, or a mode, that declares no secret inputs |
| `Another service on the service cluster already uses this name.` | A service that has not been deleted holds the name on the service cluster | Choose another name in **Configure** (when confirming, **Choose another name** takes you there) and review again, or [delete the other service](/guides/delete-a-managed-service) first |
| `This setup changed after you reviewed it.` | Something in the plan changed after it was prepared | **Review again** to see the current plan |
| `This review expired before it was confirmed.` | The 10-minute window passed | **Review again** |
| `You have too many setup reviews waiting.` | 20 reviews of yours, or 100 in the organisation, are waiting | Confirm one in **My reviews**, or let them expire after 10 minutes |
| `An application is no longer deployed in one of the chosen environments.` | The application was removed from that namespace | Remove the environment, or deploy the application again |
| A PostgreSQL service's deployment fails, and the failed `pg-tls` add-on reads `this cluster does not serve ValidatingAdmissionPolicy (admissionregistration.k8s.io/v1, Kubernetes 1.30 and later)` | The service cluster runs a Kubernetes version older than 1.30 | [Upgrade the cluster](/guides/kubernetes-upgrades) to 1.30 or later and choose **Retry deployment**, or [delete the service](/guides/delete-a-managed-service) and set it up on another cluster |
| **Installation needs attention**, with `Ankra cannot currently tell whether the selected cluster runs this service's shared operator` | Ankra could not see whether the cluster runs CloudNativePG, so it did not risk installing a second operator | Make sure the cluster's agent is online and reporting. Then set the service up again under a new name, or [delete the service](/guides/delete-a-managed-service) to release its name and set it up again under the same one |
