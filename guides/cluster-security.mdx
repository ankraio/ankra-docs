Ankra collects what scanners find on your clusters, ranks it by how likely it is to be used by attackers, prepares the fixes it can run, and records what your team decides about the rest. This page explains where each part lives and how it works. To fix one vulnerability end to end, follow [Fix a vulnerable image with a pull request](/guides/fix-a-vulnerable-image).

## What Security looks at

Four sources write findings. The **Vulnerabilities** view can show each one alone:

| Choice in the portal | What it checks |
|---|---|
| **Image vulnerabilities (Trivy)** | The packages inside the container images your clusters run |
| **Node kernel vulnerabilities** | The kernel each node runs |
| **Node package vulnerabilities** | The operating system packages installed on each node |
| **Endpoint checks (Samma)** | The public addresses your Ingresses serve: certificate and TLS, security headers, the HTTP to HTTPS redirect, DNS records and the domain's registration |

Container images are scanned inside each cluster by [Trivy Operator](https://aquasecurity.github.io/trivy-operator/latest/), which the security baseline installs. The platform reads the operator's reports through the Ankra agent. The Samma endpoint checks also run from inside the cluster.

Images are also scanned in two places outside the scanner on your clusters:

- Before Ankra proposes an add-on upgrade as a fix, it pulls the new release's image through the platform's registry cache and scans it there, so the proposal can say whether the upgrade clears the finding.
- An application image built by [Ankra Pipelines](/get-started/ankra-ci) is scanned in the pipeline. A version no cluster runs yet is judged from that scan.

### Node package findings

**Node package vulnerabilities** are the operating system packages installed on each node, such as OpenSSH, sudo and OpenSSL, matched against the Ubuntu and Debian security advisories. Each advisory that applies is one occurrence on that node, and **Vulnerabilities** counts these occurrences as **Nodes**. The kernel is not part of it: **Node kernel vulnerabilities** covers the kernel.

- **What is reported.** An advisory that CISA lists as known exploited, or a critical or high one for which the distribution has published a fixed package. A critical or high advisory with no published fix that nobody is known to exploit is not reported, and neither is a medium or low one that is not on CISA's list.
- **Where the package list comes from.** The dry run of [OS patching](/guides/os-patching) records each node's installed packages, and so does a patch run. Ankra starts a dry run itself once a day on every running cluster covered below, so you do not have to; a dry run changes nothing on the nodes. When that dry run fails on a cluster, Ankra tries it again a week later.
- **How fresh it must be.** A package list older than 48 hours no longer counts. The node then reports nothing new, and the findings it already had stay open until a fresh list says otherwise.
- **Which clusters are covered.** Clusters Ankra built on Ankra Cloud, AWS, DigitalOcean, Hetzner, OVHcloud, Scaleway or UpCloud, for nodes that run Ubuntu or Debian. Imported clusters, Proxmox VE and HPE Morpheus clusters, playgrounds and nodes on another operating system get no node package findings, and the bastion's packages are not matched.

A node with no recent package list has not been checked. It shows no finding, which does not mean its packages are clean.

## Before you start

- **A scanner on the cluster.** A cluster without one reads **Never** under **Last scan** and nothing on it is counted. See [Turn on scanning](#turn-on-scanning).
- **The right permission.** Built-in roles carry these by default; a [custom role](/guides/roles-and-access) can grant them:

| Permission | Built-in roles | What it allows |
|---|---|---|
| `security.read` | Viewer and above | Open **Security** and a cluster's **Security** page |
| `security.triage` | Operator, admin, owner | **Acknowledge** an issue, and turn on scanning |
| `security.manage` | Admin, owner | **Accept the risk**, change or revoke a decision, open fix pull requests |

The platform checks every permission itself; the portal only greys out what you cannot do and says why ("Accepting a risk needs the security.manage permission.").

## Where to work

| Where | Address | What it answers |
|---|---|---|
| **Security** in the main menu | `/next/security` | The organisation's view: what to fix first, every finding, fixes in progress, coverage, evidence and decisions |
| **Infrastructure → Clusters → *your cluster* → Security** | `/next/clusters/<cluster-id>/security` | What needs fixing on this one cluster, and the button for each fix |
| An advisory page | `/next/security/advisories/<cve-id>` | One CVE: what the public record says and where it is in your organisation |

### The Security menu

Opening **Security** swaps the sidebar to its own menu. Each row is a view:

| View | What it is for |
|---|---|
| **Overview** | Prioritise what needs a decision, then follow each fix to fresh evidence. The fixes Ankra prepared, ranked, with the button that opens each one |
| **Resources** | Focus on a pod, deployment source, namespace, stack or application, then expand to the fleet |
| **Vulnerabilities** | Every issue a scanner found in what runs, the ones attackers use first, then by the chance of use |
| **Exposure** | Every public address your clusters scan: what fails and what to change, what each scan saw, and when it runs next. Shown only in an organisation where a cluster runs the Samma endpoint scanner |
| **Fix activity** | Follow pull requests, builds and rescans. A started fix is still an open issue |
| **Coverage** | See where the picture is current and which clusters need a fresh report |
| **Evidence** | Framework observations (compliance) and the software inventory (bills of materials), with downloads |
| **Accepted risks** | Who accepted each risk or acknowledged each issue, why, and when the decision comes back |
| **Software lifecycle** | Source checks, image versions, release gates and deployed evidence, per application |

### The Overview

The Overview opens with two numbers: how many issues are open, and how many of them are **used by attackers**. Each opens **Vulnerabilities** with that filter. Below them are the fixes that need you, one row each, with one button: **Review fix**, **See the next step** for a fix already under way, or **See what happened** for a fix you started that went wrong. A fix Ankra cannot run is listed under **with no fix Ankra can run** with **See the issue** and **Ask Ankra where it is declared**. Fixes that carry on without you are under **In progress**, and fixes you set aside are under **Set aside**: Ankra does not offer those again until you bring them back.

An issue in an image that came with a k3s cluster is listed apart, under ***n* in images that came with the cluster**, with the badge **Came with the cluster**. It is not counted in the changes that are yours to make. See [When there is no fix](#how-fixes-work).

A cluster that has sent no scan report is offered in one line, "*cluster* has no scan report. Ankra can install a read-only scanner on it.", with **Review and turn on**. The offer is not a fix and is not counted as one. See [Turn on scanning](#turn-on-scanning).

Two folds at the bottom explain the page. **Issues that are in no plan** points at the issues no fix covers. **How Security decides** gives the order (fixes for issues used by attackers first, then the upgrades that close the most with one change), what "used by attackers" means, what counts as fixed, and which clusters have no current report.

### A cluster's Security page

**Infrastructure → Clusters → *your cluster* → Security** answers three questions in order: is this cluster safe, what do I do about it, and where are the issues.

- **A one-line verdict** at the top, for example "Nothing needs you. The last scan found no open issues."
- **Four numbers**: **Issues found**, **Known to be used by attackers**, **Fixes ready** (waiting for your review) and **Last scan** (**Up to date**, **Out of date**, or **Never** for a cluster with no scanner). The first two count each issue once on the cluster, however many occurrences it has there, as the cluster's row in **Security → Coverage** does.
- **Needs you**: every fix Ankra prepared for the cluster. Each row says what kind of change it is (**Add-on upgrade**, **Image rebuild** or **Fix plan**), whether it also changes other clusters, and has the button that opens its review. Add-on security updates for this cluster are listed here too. A fix with a published version that Ankra cannot apply is listed under **fixes you apply yourself**, with **See details** and **Ask Ankra where it is set**. Issues in images that came with a k3s cluster have their own section directly below **Needs you**. When the scanner stopped reporting, **The vulnerability scanner stopped reporting** offers **Check the scanner add-on** and **Ask Ankra why**.
- **Where the issues are**: one row per Stack with its **Open occurrences** by severity (one for each container an issue is in), **Used by attackers**, **Containers scanned** and **Containers with SBOM**. **Containers scanned** says how many of the Stack's containers have a current report on the image they run, such as **All** or **3 of 5**; a container without one is unknown, not clean. Open a Stack to see its add-ons, pods and images. Pods outside any Stack are counted below the table with **See them by namespace**.
- **Look deeper**: links into the organisation's **Security**, focused on this cluster: every vulnerability on the cluster, issues by namespace and pod, the risks your team accepted, and fixes in progress.

Nothing on this page runs until you approve it: each row opens the review of its fix, and closing the review brings you back here. Fix pull requests are the one thing Ankra can start on its own, as an application's **Keep it safe** setting allows (see [What counts as fixed](#how-fixes-work)).

## Turn on scanning

A cluster that has sent no scan report shows **Turn on vulnerability scanning** on its Security page: "Ankra installs a read-only scanner that reports within about 15 minutes. Nothing on this cluster is checked until then." The **Overview** offers the same in one line, and **Security → Coverage** lists every cluster that **sent no scanner report**.

1. Select **Review and turn on** in any of the three places. The plan opens, headed **A change Ankra prepared**. It installs the Ankra security baseline (Trivy Operator with conservative defaults) on the clusters with no scan report and shows the exact change.
2. Select **Enable the baseline on *your cluster***. This needs `security.triage`.

The offer is not a fix. Until someone approves it, it is not counted beside **Security** in the main menu or in a cluster's **Fixes ready**, and [**Needs you**](/platform/activity-inbox#needs-you) does not list it. On a cluster's Security page with nothing else to show, the section is headed **Nothing is checked yet**. Once approved, it is a change in progress. You can also set it aside, and Ankra does not offer it again until someone brings it back.

When there is no offer to open, for example because someone already approved it, the card's button reads **Turn on scanning** and opens **Security → Coverage**.

The first reports arrive within about 15 minutes of each install. The cluster's **Last scan** then reads **Up to date** and its row in **Coverage** moves out of the gap.

```bash
ankra security enable-baseline --cluster my-cluster   # publish the baseline Stack on a cluster that has none
ankra security clusters                               # every cluster's scanner freshness and counts
```

From chat or the MCP server the tool is `enable_security_baseline`, confirmed before it runs.

### The security baseline

`ankra-security-baseline` is the public stack profile the platform installs on every cluster it provisions, unless the organisation turned off **Security baseline on new clusters** under **Identity & access → Sign-in and security → New clusters**, and the one **Enable the baseline** installs on an imported cluster. Like every profile it is a catalogue entry you can open, copy and fork. It carries:

- **Trivy Operator** for image vulnerabilities, sized for a small cluster by default. Its workload configuration audit, RBAC assessment, CIS compliance report and CIS node assessment are off by default, because each of them loads the control plane. Turn them on per cluster with the profile inputs `trivy_config_audit_enabled`, `trivy_rbac_assessment_enabled`, `trivy_cluster_compliance_enabled` and `trivy_infra_assessment_enabled`.
- **Pod Security Standards, enforced by Kubernetes itself.** The profile ships an `ankra-pod-security` ConfigMap declaring the standard (`baseline` or `restricted`), the policy mode and the exempt namespaces. The Ankra agent labels every other namespace for [Pod Security Admission](https://kubernetes.io/docs/concepts/security/pod-security-admission/), the admission controller built into every API server: `pod-security.kubernetes.io/audit` and `/warn` at the standard in Audit mode, and `/enforce` as well once you switch the cluster to Enforce. Labels are only ever raised, so a namespace you hold at a stricter level keeps it, and the agent records what it set so switching back to Audit restores the previous state.
- **A guard for the enforce label.** A ValidatingAdmissionPolicy (Kubernetes 1.30 or newer) refuses lowering the enforce label of a managed namespace below the declared floor for anyone but the agent. It fails open: an admission it cannot evaluate is admitted.

The baseline adds no policy engine: the API server itself evaluates the namespace labels and the guard, with no admission webhook and no extra pod. A cluster that installed the baseline while it still carried Kyverno keeps those Kyverno add-ons, and the policy mode then sets both. Kyverno is available as the opt-in `ankra-policy-engine` profile, for image-signature verification and policies of your own.

<Warning>
`ankra security policy-mode off --cluster my-cluster` permanently uninstalls every Kyverno add-on on the cluster (charts `kyverno` and `kyverno-policies`), whether an older baseline, the `ankra-policy-engine` profile or you installed it, and leaves Pod Security Admission in Audit. Switching back to `audit` or `enforce` does not reinstall Kyverno.
</Warning>

**Sizing.** The platform sizes the baseline from the cluster's shape. A control plane below **8 GB** of memory, or one whose size the platform cannot determine, gets the **lite** shape: one image scan at a time, and the cluster carries a notification saying so. A control plane of 8 GB or more gets the standard shape, and three or more workers let two scans run at once.

| Input | Default | Meaning |
|---|---|---|
| `pod_security_standard` | `baseline` | The standard every managed namespace is labelled with; `restricted` flags most off-the-shelf charts |
| `policy_mode` | `Audit` | Audit reports and warns and never blocks; Enforce makes the API server refuse pods that violate the standard |
| `pod_security_exempt_namespaces` | `kube-system`, `kube-public`, `kube-node-lease`, `kyverno`, `trivy-system`, `ankra`, `argocd`, `hcloud`, `calico-system`, `tigera-operator`, `cert-manager` | Namespaces the standard is never applied to. `kube-system`, `kube-public`, `kube-node-lease`, `ankra` and the agent's own namespace stay exempt whatever the list says; a single `-` exempts nothing else |
| `trivy_scan_concurrency` | `1` | Image scans that run at once |
| `trivy_scan_job_timeout` | `10m` | How long one image scan may run |
| `trivy_infra_assessment_enabled` | `false` | The CIS node assessment |
| `trivy_sbom_generation_enabled` | `false` | A bill of materials per image (see [Bills of materials](#bills-of-materials)) |

The portal has no switch for the policy mode. Use `ankra security policy-mode audit|enforce --cluster my-cluster` (both directions ask first; `--yes` skips the question), and read the posture with `ankra security violations --cluster my-cluster`. From chat or the MCP server the tools are `set_cluster_security_policy_mode` and `get_cluster_policy_violations`.

## How fixes work

Ankra prepares a fix wherever it can run one, and lists it on the Overview and on the cluster's Security page. A fix that opens pull requests in an application's repository is also listed under **What needs you** on that application's [**Security** view](/platform/application-page#security), with **Review fix**. Every fix opens a review with **The exact change**, **Rollout and proof** (the risk, how to undo it, and what proves it worked) and, once it has started, **What happened so far**. Nothing you start here runs until you approve it.

| Kind | What Ankra does | The button |
|---|---|---|
| **Add-on upgrade** | Moves an add-on to a release whose image Ankra scanned and found clear of the issue. A fleet upgrade rolls in steps: each later step waits until the one before reports healthy, and for your yes. You can also approve every remaining cluster at once (**All *n* clusters at once**) | **Upgrade *add-on* on *cluster*** |
| **Image rebuild** | Opens one pull request per application repository that moves the Dockerfile base image to the fixed version. Only `FROM` lines change, on a new branch | **Open *n* pull requests** |
| An upgrade Ankra AI prepares | Hands the upgrade to Ankra AI, which shows the exact release and changelog before anything rolls | **Prepare the upgrade with Ankra** |

Installing the scanner on a cluster with no scan report opens the same kind of review, but it is an offer, not a fix: see [Turn on scanning](#turn-on-scanning).

**The order of a staged upgrade is held by the platform.** A later step of a fleet add-on upgrade cannot be approved or run until every cluster of the earlier steps has the new chart version and reports it healthy. The platform checks this itself, not only the page, so a step approved through the API or from a page left open is refused the same way. A refused step is not approved and stays as it was, and the refusal names the cluster it waits for, for example "*cluster* is still rolling *add-on version*. This step unlocks when it reports healthy." **All *n* clusters at once** is refused too while a cluster that already has the new version has not reported it healthy. The fix page then disables the button and says why beside it, for example "*cluster* already runs *version* and reports Degraded. All at once is available once it reports healthy." A step of its own can still be approved.

A step whose cluster reports the new release unhealthy holds the sequence: "*cluster* reports Degraded on *version*. The sequence holds here until you look." After it, **Open *add-on* on *cluster*** opens the add-on's page on that cluster, with its health, its workloads and its configuration.

A stopped cluster is never a fix target. An add-on upgrade skips the add-ons of a stopped cluster and names them in the plan ("*add-on* is stopped on *cluster*"); they come back into the plan on the first read after the cluster runs again. A cluster stopped after the plan was read is refused when its step runs, and the step says "The cluster is stopped, so this add-on cannot change. Start the cluster first." An add-on upgrade or rollback through the API answers the same, with `409` and `error_code` `ADDON_CLUSTER_STOPPED`.

An offline cluster, one whose Ankra agent is not connected, is never a fix target either, even when its stack already declares the new version. The plan names it ("*cluster* is offline, so Ankra cannot reach it to upgrade *add-on* until it is back online"), no later step waits for it, and a change that did not complete there before it went offline does not mark the fix as failed. It comes back into the plan once its agent connects again.

**A deployment that did not complete.** When an add-on upgrade's deployment does not complete on a cluster, the cluster's line reads **Did not complete** with the platform's error, the fix is listed with the fixes that need you, and Ankra tries the deployment again by itself. Once a later run of Ankra deploys the chart the fix asked for, and the stack still declares that chart, the line reads as deployed and the fix no longer needs you. A later run that only saved settings, removed the add-on or moved it back to the earlier chart does not count. **What happened so far** still lists the attempt that did not complete.

A cluster Ankra could not read on one pass keeps its place in the order, and no step after it can be approved until it reads again. Its step says "*cluster* could not be read just now. Later steps stay locked until it can be read." **All *n* clusters at once** waits for it too, and also while a step you just approved is still rolling: "*cluster* is still rolling the release. All at once is available once it reports healthy." While Ankra cannot read which of your clusters are online, no add-on upgrade can be approved, and its plan says so.

Ankra reads your clusters again before it runs anything you approve. If one read of your clusters leaves out a plan you have open, the review keeps it, with its button locked, and reads again a few seconds later. If the read made when you press cannot find the plan, Ankra reads once more; only when that read cannot find it either is the plan no longer offered, and nothing was approved.

**What counts as fixed.** A pull request, a passing build and a deployment are separate steps. An issue stays open until a new scan of the clusters it was on says it is gone. **Security → Fix activity** follows every started fix through those steps: **Fix in progress**, **Waiting for rescan**, and **Fixed** only once a rescan of every affected cluster finds nothing left. A pull request that fixes several of one application's issues at once, such as a base-image fix or a dependency bump, is one row in **Fix activity**, and opening it goes to the application's **Security** view, which follows the pull request and its checks. An application's **Keep it safe** setting decides how far Ankra goes with fix pull requests on its own. At **Together**, the default, Ankra opens them and keeps them green, and you approve each merge. At **Ankra runs it** it also merges them, once their checks and review pass. At **You run it** it only suggests. Ankra never accepts a risk for you.

**When there is no fix.** A finding with no published fix, or one Ankra cannot apply (no application of yours builds the image), is yours to decide: fix it where the image is declared, or record a decision as described below.

**Images that came with the cluster.** An issue in an image k3s itself ships is not yours to apply. It is badged **Came with the cluster** and reads "This image is part of k3s, the Kubernetes this cluster runs. It is updated by moving the cluster to a k3s version that ships a newer one." Ankra says this only when every container the issue is in runs in `kube-system` from an image on k3s's own list, and every node of each cluster it runs on reports a k3s version. When any of that cannot be confirmed, the issue stays yours to apply. The count of open issues does not change either way.

### Security header and redirect checks

An endpoint check on a security header or on the HTTP to HTTPS redirect says, under **How a check like this gets fixed**, who sends what the check reads and what makes it pass. The next scan clears the check once it passes.

| Check | Who sends it |
|---|---|
| HTTP to HTTPS redirect, `Strict-Transport-Security`, `X-Content-Type-Options` | Ankra, for an application it deploys on a hostname Ankra gave it, through the Ingress it generates, from the application's next deploy. The [`ingress_https_redirect`](/reference/application-descriptor#default-options) option describes the main cases where it does not. Otherwise your application, your own Ingress or the proxy in front of the cluster |
| `Content-Security-Policy`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy` | Your application. Ankra leaves these to it, so a policy the application sets is never replaced. A starter website generated from 27 November 2026 sends its own |
| A version in `Server` or `X-Powered-By`, `X-XSS-Protection`, cookie flags | Your application or its web server |

Only an enforced `Content-Security-Policy` header passes its check: `Content-Security-Policy-Report-Only` is a way to try a policy first, and the check stays open while only that one is sent. A `Content-Security-Policy` with a `frame-ancestors` directive also passes the `X-Frame-Options` check.

## Open issues and decisions

The tabs of **Security → Vulnerabilities** sort issues by what was decided about them. They overlap: an acknowledged issue is also in **Open**, and an issue accepted in some containers is also in **Open** where other containers have it undecided.

| Tab | Means |
|---|---|
| **Open** | Nobody decided about it, or it is acknowledged. Open issues are what every count, alert and report uses |
| **Acknowledged** | Your team has seen it. It stays open and stays counted |
| **Accepted** | The risk is accepted until a review date. It leaves the open count but stays visible |
| **Resolved** | No cluster's newest scan finds it any more |

An occurrence is one container (or node, or endpoint) holding the issue. A finding the scanner no longer reports moves to **Resolved** only after it has been missing from two consecutive full resource syncs, so a partial sync never reads as a clean bill. To bring that forward, run **Run a full sync…** twice from **Infrastructure → Clusters → *your cluster* → Settings → Kubernetes sync** (this needs `clusters.write`), letting the first finish before starting the second.

### Review an installed Helm release

Under **Infrastructure → Clusters → *your cluster* → Security**, open **Vulnerability reports for installed Helm releases** and choose the release by name and namespace. The Kubernetes release detail also links to its report. Releases installed by your own Helm pipeline can be investigated here.

**Deployment** shows the chart version, application version, and Helm revision when the cluster supplies them. Expand **Release history** to see when each revision was deployed. Several revisions can deploy the same chart version. **Chart advisories** shows catalogue evidence when it matches the installed release and chart version.

In **Runtime vulnerability report**, search a CVE, package, image, workload or container. Each row shows a scanner observation with the installed and published fixed package versions. Use **Copy finding details** to take the package versions, observed digest, workload, scan time and release link into an issue or pull request. Under a reported image, **See pods using this image in** *namespace* opens that image in its namespace. There, in **Image vulnerabilities** under **Vulnerabilities reported for this image**, select a column heading to sort the full result, including the installed and published fixed versions. Select the heading again to reverse the order. The report matches Helm ownership annotations and Kubernetes workload UIDs, including workloads outside the release namespace. **Other workloads** lists controllers in the release namespace whose ownership by this release is unconfirmed. Open one to inspect its own pods and container findings.

Choose **Compare a candidate image** beside a reported image and paste the SHA-256 digest from your registry. When both scans are available, the comparison shows introduced, remaining and removed findings. Share the URL to reproduce the comparison. A candidate comparison describes those image scans. Verifying a production repair requires a subsequent scan of the digest that rolled out.

### Find the vulnerabilities in a stack image

Open the cluster's **Security** page and select a stack under **Where the issues are**. **Running images** lists the containers the stack deploys, init containers included. Replicas with the same digest share one row. You can also open an add-on or manifest to see just its images. Search by image, pod, namespace or container name.

Choose an image to see its reported advisories, affected packages, installed versions and published fixes. Search by advisory ID or package name. Findings appear in severity order. Replicas with the same digest share an image report. Opening a finding keeps the stack, add-on or manifest in focus. **Containers running this image** lists the placements in the selected stack or source. Select a container to see the findings from its own matched report, or open the pod to inspect its other containers. When a digest is unavailable, the inventory shows the tag and leaves the image report unavailable.

### Trace a namespace vulnerability to a container

1. In **Security → Vulnerabilities**, focus on the cluster and namespace and open a finding. **Images with this vulnerability** shows the images in that namespace where the scanner observed the affected package.
2. Choose **View pods and image vulnerabilities** on an image. The pod list matches its exact digest in that namespace. The image findings below the list cover scans of that exact digest on the clusters of the current project.
3. Select a **pod** to see its containers together, or select a **container** to go straight to its advisories, affected packages, installed versions and available fixes. Use **All containers** to include the pod's other containers. From a finding, the **All vulnerabilities in** link returns to the container.

You can also start at **Resources**. Open a namespace and expand the container count beside a pod to see its images. A tag can identify several builds over time. Following a digest pins the investigation to one build. A missing or stale container scan is shown separately from a scan that found no active vulnerabilities.

### Acknowledge or accept the risk

Open a finding from **Security → Vulnerabilities**. Its page leads with what you can do about it. Where no fix is published, it says **No fix is published yet.** and offers **Acknowledge** and **Accept the risk**; elsewhere they are under **Not fixing it now?**

- **Acknowledge** (`security.triage`) records that your team has seen it. The issue stays open and stays counted.
- **Accept the risk** (`security.manage`) takes it off the open count until a **Review date**, from tomorrow and never more than a year out. An issue used by attackers warns: "Attackers use this issue somewhere. Accepting takes it off the open count without fixing it."

Both need a **Reason**. **What this decision covers** chooses the scope:

| Choice | Covers | Survives a rollout | Survives an image rebuild |
|---|---|---|---|
| **This add-on (*name*) on every cluster** | The add-on the occurrence belongs to, on every cluster | Yes | Yes |
| **Everything in namespace *name*** | Every workload in the occurrence's namespace, on that cluster | Yes | Yes |
| **This workload (*name*)** | The one workload it was seen in. For a Deployment's pods this is the Deployment | Yes | Yes |
| **This exact image (*digest*)** | The image digest, wherever it runs | Yes | No |

Images that belong to no add-on (your own applications, operator-created pods, plain manifests) cannot take the add-on scope; for your own application, the namespace is usually the right choice. The image scope stops matching when the image is rebuilt, so the finding returns for a fresh decision.

**Security → Accepted risks** lists every decision under **Needs review** (an accepted risk that expires soon, or an acknowledged issue that now has a fix) and **Accepted and acknowledged**. Nothing is extended silently: **Keep accepted** needs a reason, and **Reopen for fixing** returns the issue to open. Each decision is written with its event and an audit log entry in one transaction.

<Warning>
When a decision expires, or a fix becomes available for one set to end then, its findings are open again and can fire threshold alerts. A decision made in the portal ends when a fix becomes available, unless someone then chooses **Keep accepted** or **Keep acknowledged** and gives a reason. From the CLI, pass `--expire-when-fix-available`.
</Warning>

From the terminal, `ankra security dispositions preview`, `create`, `update` and `revoke` carry the same decisions, with `--scope namespace`, `workload` or `image`. See [`ankra security dispositions`](/reference/cli/security#ankra-security-dispositions). From chat or the MCP server the tools are `preview_security_disposition`, `create_security_disposition`, `update_security_disposition` and `revoke_security_disposition`; the writes are confirmed before they run.

## Used by attackers and chance of use

Severity says how bad an issue could be; it says nothing about whether anyone exploits it. Ankra joins every finding by CVE id against two public feeds:

- **Used by attackers**: CISA, the US cyber security agency, lists the issue in its Known Exploited Vulnerabilities catalogue as used in real attacks somewhere. It does not mean anyone attacked you. A listed issue shows CISA's remediation deadline, whether CISA links it to ransomware, and CISA's required action.
- **Chance of use**: EPSS, a public prediction that the issue is used somewhere in the next 30 days.

The join happens on the platform, using the CVE ids already in your scanners' reports. **Vulnerabilities** lists the issues used by attackers first, then by chance of use. Until the platform has read CISA's list, the counts say **How many are used by attackers is unknown** rather than zero.

## Advisory pages

Every finding with a CVE id links to an Ankra advisory page (**Read the advisory** on a finding, **About this CVE** in the Vulnerabilities list) at `/next/security/advisories/<cve-id>`. The platform reads the public record itself, from NVD and OSV, and shows it under two headings:

- **Where it is in your organisation**: one issue for each package that carries the CVE, with the workloads and clusters it runs on and whether a fixed version exists.
- **What the advisory says**: the description, CISA's entry when the CVE is listed, the severity, the affected and fixed versions, and the references. **Dates, scoring vector and sources** folds the detail.

A record the platform has not read yet says "The public advisory has been requested and is not held yet. Check again in a minute." A CVE neither source holds a record for says "The public sources hold no advisory text for this CVE." The same advisory is `ankra security advisory <cve>` on the CLI and `get_security_advisory` on the MCP server.

## Bills of materials

A bill of materials (SBOM) lists every package in a container image. Trivy Operator writes one per image only when the baseline input `trivy_sbom_generation_enabled` is `true`, because they are the largest objects it writes. Turn it on per cluster that has control-plane headroom; the next scan fills the inventory. **Where the issues are** and **Coverage** count the containers with and without one, and a container without one is a gap to close, never clean.

Open the inventory from **Security → Vulnerabilities** with **Images and packages (SBOM)** at the bottom of the list, or from **Security → Evidence**. In the portal each image downloads as CycloneDX JSON; `ankra security sbom export <image> --format csv` gives a CSV.

### Licence risk

Every package's licences are sorted into one of six tiers, by what they oblige of the code that links the package. An `OR` expression takes the least demanding alternative, an `AND` binds every term, and a package that names several licences is taken to be under all of them.

| Tier | Licences | What it means for a service you host |
|---|---|---|
| **Network copyleft** | AGPL, SSPL, EUPL, OSL, RPL, CAL | Serving it over a network counts as distribution: the source of every service that links it must be published |
| **Source-available** | BUSL, Elastic License, Redis Source Available, Commons Clause, PolyForm, non-commercial Creative Commons | Hosting it as part of a managed service needs a commercial licence from the author |
| **Copyleft** | GPL, GFDL, CeCILL, Sleepycat, CC-BY-SA | Safe behind a private backend; shipping it in a browser bundle, mobile app or CLI is distribution |
| **Weak copyleft** | LGPL, MPL, EPL, CDDL, CPL, and GPL with a linking or Classpath exception | Only changes to the component itself must be published |
| **Permissive** | MIT, Apache-2.0, BSD, ISC, Unlicense, CC0, Zlib, PostgreSQL, Python, Boost | No obligation on the surrounding code |
| **Unclassified** | Anything else, or `NOASSERTION` | Not a verdict: confirm the terms. An unclassified package never counts as permissive |

From the terminal, `ankra security sbom`, `sbom images`, `sbom image <image>`, `sbom component <name> --version <version> --type <ecosystem>`, `sbom containers` and `sbom export <image> [--format csv]` read the same inventory. See [`ankra security sbom`](/reference/cli/security#ankra-security-sbom).

## Which project a read covers

In an organisation with [projects](/concepts/projects), every Security read covers the project you act in. A finding, image or cluster of another project is left out of every list. In an organisation with projects off, a read covers the whole organisation.

- **In the portal**, an organisation-wide member sees **Show security for** with **This project** and **All projects** in the page header. **All projects** reads every project and offers no changes: to act on a finding, switch to the project it belongs to. A member limited to projects is not offered the choice; an address that asks for it shows **Not available with your access** with **Show this project**.
- **From the CLI**, `--all-projects` reads the whole organisation and the global `--project <name>` reads another project. `compliance`, `history` and `report-schedule` take no `--all-projects`.
- **On the API**, the `GET` routes under `/api/v1/org/security/...` take `project_id`: `all` for the whole organisation, or a project's id. Any other value is refused with `422 project_id must be a UUID or all`.

A pinned token and a member limited to projects read their own project only, and are refused `project_id=all` with `403 Pinned tokens cannot act outside their project` or `403 Members limited to projects cannot act outside their project`. The compliance framework scores and report are the organisation's, whichever project you act in; a pinned token and a member limited to projects are refused them with `403 Organisation compliance documents are not available to pinned tokens or members limited to projects`.

## From the CLI and MCP

The `ankra security` commands read and change everything above. The ones you reach for first:

```bash
ankra security overview                      # totals, coverage and the issues used by attackers
ankra security findings --known-exploited    # only the findings CISA lists as exploited
ankra security finding <finding-id>          # one finding with every place it occurs
ankra security advisory <cve>                # the advisory, CISA's guidance and your exposure
ankra security clusters --all-projects -o json   # per-cluster posture for reporting
ankra cluster baseline --cluster my-cluster  # the cluster's Ankra Baseline score, which includes its known-exploited issues
```

Per cluster, `ankra security stacks`, `stack <name>`, `namespaces`, `pods`, `pod <namespace> <pod>`, `addon <addon-name>`, `history`, `benchmarks` and `network-exposure` take `--cluster`. The portal has no view for the CIS benchmark controls of one cluster or for its NetworkPolicy exposure score; use `ankra security benchmarks --cluster my-cluster` and `ankra security network-exposure --cluster my-cluster`. Every command is in the [`ankra security` reference](/reference/cli/security), and every MCP tool is under [Security Center in MCP tools](/platform/mcp-tools#security-center).

### NetworkPolicy exposure score

`ankra security network-exposure --cluster my-cluster` scores how tightly the cluster's NetworkPolicies are written, ingress and egress separately, each from 0 to 100 (higher is tighter). Each score is the average of two halves: coverage, the share of workloads a policy selects in that direction, and tightness, the share of allow rules scoped to a named workload identity. The findings list every workload no policy selects (high severity on ingress, medium on egress, because egress default-deny is uncommon) and every rule broader than a named identity. From chat or the MCP server the tool is `get_cluster_network_policy_overprivilege`.

<Warning>
The score is computed from the policy objects, not from traffic. It does not check that your CNI enforces NetworkPolicy, it does not score ports, and it counts only Deployments, StatefulSets and DaemonSets: a direction with none of them reads `n/a (no workloads to score)`. A default-deny in every namespace with no allow rules scores 100 while it blocks every flow, so a high score means the policies are written tightly, not that traffic reaches where it should. Use it to find workloads nobody has scoped, never to decide that a policy change is safe.
</Warning>
