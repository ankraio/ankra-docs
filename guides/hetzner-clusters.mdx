Choose Hetzner when you want a multi-node Kubernetes cluster on Hetzner Cloud servers in Germany, Finland, the US or Singapore, in a project you own. Ankra creates the servers, private network and bastion in your Hetzner Cloud project, installs Kubernetes and the Hetzner cloud integration, and then operates the cluster for you - this is an **Ankra Managed** cluster. Hetzner bills you directly for the servers.

## Before you start

<Note>
**Add a payment method first.** Creating a Hetzner cluster needs a payment method on your Ankra organisation. Without one, the create is refused with "The cluster was not created ... Add a payment method". Save a card from [guided setup](/get-started/guided-setup) or **Billing** - see [Credit and payment method](/platform/billing#credit-and-payment-method). The free [playground](/guides/cluster-sandbox) is the only cluster that works without one.
</Note>

- A **payment method** on the organisation, as above.
- A **Hetzner Cloud API token** with **Read & Write** permissions, stored as a [Hetzner credential](/platform/credentials/hetzner): in the new Ankra portal, **Integrations & alerts → Credentials → Add credential → Hetzner Cloud**. No Hetzner account yet? [Sign up for Hetzner Cloud](https://www.hetzner.com/cloud).
- At least one **SSH key credential** - required for every Hetzner cluster. Add it at **Integrations & alerts → Credentials → Add credential → SSH key**: paste a public key, or generate a 4096-bit RSA key pair in the browser, which downloads the private key once. See [SSH Key Credentials](/platform/credentials/ssh-key).
- Room in your Hetzner project's limits for the servers, a network and the SSH keys. Check them in the [Hetzner Console](https://console.hetzner.cloud); Hetzner support raises them.

## Create the cluster

<Tabs>
  <Tab title="Dashboard">
    The new Ankra portal (`/next` on your portal's address, for example `https://platform.ankra.app/next/clusters/new?provider=hetzner`) walks you through one form:

    <Steps>
      <Step title="Open the Hetzner wizard">
        Go to **Infrastructure → Clusters**, click **Add a cluster** and pick **Hetzner**.
      </Step>
      <Step title="Name and purpose">
        Name the cluster and pick its purpose: **Production**, **Staging**, **Development**, **Testing** or **Local**.
      </Step>
      <Step title="Credential, SSH key and location">
        Pick the Hetzner credential, one or more SSH keys, and the location, for example `fsn1`, `nbg1` or `hel1`.
      </Step>
      <Step title="Control plane and servers">
        Choose **1** or **3** control plane nodes, the management (bastion) server type, and one or more node groups of workers. Pick server types the location can provision right now - the `cx` line is often unavailable; see [Server types](#server-types). A cheap set that works: `cpx12` for the management server, `cpx22` for the control plane and workers.
      </Step>
      <Step title="Kubernetes">
        Keep **kubeadm** (the default, with Cilium) or pick **k3s**, and optionally the version. See [Choices fixed at create time](/guides/operate-ankra-managed-clusters#choices-fixed-at-create-time) for the CNI and etcd options.
      </Step>
      <Step title="Git repository (optional)">
        Optionally connect a Git repository; Ankra commits the cluster's stacks to it. By default the cluster also gets the networking stack (Traefik, cert-manager and a Let's Encrypt ClusterIssuer, with Traefik behind a Hetzner Load Balancer) and a delegated subdomain on `ankra.cc` with external-dns wired, so an ingress hostname under it gets its DNS record and TLS certificate automatically.
      </Step>
      <Step title="Review and create">
        **Review** shows the choices and a cost estimate. Click **Create**. A progress view follows the network, bastion, servers, Kubernetes installation and Ankra Agent.
      </Step>
    </Steps>
  </Tab>
  <Tab title="CLI">
    <CliVersion since="0.9.0" />

    ```bash
    ankra credentials hetzner create --name my-hetzner-token   # prompts for the token
    ankra credentials hetzner ssh-key create --name my-ssh-key --generate

    # Check what the location can provision now; use rows with AVAILABLE=yes
    ankra cluster hetzner server-types --credential-id <hetzner-credential-id> --location fsn1

    ankra cluster hetzner create \
      --name my-cluster \
      --credential-id <hetzner-credential-id> \
      --ssh-key-credential-ids <key-id-1>,<key-id-2> \
      --location fsn1 \
      --control-plane-count 1 \
      --worker-count 2 \
      --bastion-server-type cpx12 \
      --control-plane-server-type cpx22 \
      --worker-server-type cpx22
    ```

    `cx` types are often unavailable in `fsn1` and other locations, so pick the `--bastion-server-type`, `--control-plane-server-type` and `--worker-server-type` values from the `AVAILABLE=yes` rows of `server-types` (`--available-only` hides the rest). Leave a flag out and Ankra picks a type for that role from what the location can provision at that moment (see [Server types](#server-types)). `ankra cluster hetzner locations` lists the locations your credential can use. `--distribution k3s`, `--etcd-topology external`, `--include-networking=false` and the `--gitops-*` flags cover the other choices.
  </Tab>

    ```bash
        "name": "my-cluster",
        "credential_id": "<hetzner-credential-id>",
        "ssh_key_credential_ids": ["<key-id-1>", "<key-id-2>"],
        "location": "fsn1",
        "control_plane_count": 1,
        "control_plane_server_type": "cpx32",
        "node_groups": [
          {"name": "default", "instance_type": "cpx32", "count": 2},
          {"name": "gpu-workers", "instance_type": "ccx33", "count": 1, "labels": {"gpu": "true"}, "taints": [{"key": "gpu", "value": "true", "effect": "NoSchedule"}]}
        ],
        "include_networking": true,
        "include_dns": true,
        "gitops_credential_name": "my-github-token",
        "gitops_repository": "my-org/my-repo",
        "gitops_branch": "main"
      }'
    ```

    The `gitops_*` fields are optional; with them, Ankra commits the hcloud stack (and the networking stack, when included) to the repository after creation. `worker_count` and `worker_server_type` are still accepted, and `node_groups` wins when both are given; the singular `ssh_key_credential_id` is merged with `ssh_key_credential_ids`. Leave out `bastion_server_type` (as here), `control_plane_server_type` or `worker_server_type` and Ankra picks one for that role; the response's `server_types` object names the type each role got. Every field and default is in the [Hetzner Reference](/reference/hetzner).

## Verify

1. The cluster moves from **Provisioning** to **Online** in the clusters list once the Ankra Agent has connected.
2. Point `kubectl` at it through Ankra (this needs a [Cluster Access](/guides/cluster-access) grant) and check the nodes:

   <CliVersion since="0.3.0" command="cluster kubeconfig add" />

   ```bash
   ankra cluster kubeconfig add my-cluster --use
   kubectl get nodes
   ```

   Every control plane and worker should be `Ready`. See [Accessing Clusters with kubectl](/guides/kubeconfig).

## What Ankra created in your project

- **A private network** that every server joins. Nodes have private addresses only.
- **A bastion** - the only server with a public IP. It is the SSH jump host and also the NAT gateway for all node egress, so stopping or deleting it cuts the nodes off from the internet.
- **Control plane and worker servers**, and your SSH keys registered in the project.
- **The hcloud stack** in the `hcloud` namespace: the Hetzner cloud controller manager (Load Balancers for `LoadBalancer` Services, node metadata) and the CSI driver (Hetzner Volumes through the `hcloud-volumes` StorageClass), both using your credential's token.

The [Hetzner Reference](/reference/hetzner#architecture) has the full layout and the CCM and CSI configuration.

## Server types

Hetzner's stock of a server type changes by location and by hour. The cost-optimised `cx` line is sold in limited quantities and is often unavailable altogether: on 2026-10-28 `fsn1` offered only `cpx`, `ccx` and `cax` types. `cpx12` for the bastion and `cpx22` for the control plane and workers is a cheap set that was available. A type that is out of stock is refused when you create the cluster, add a node group, or resize one, so check what a location sells right now with `ankra cluster hetzner server-types --credential-id <hetzner-credential-id> --location fsn1 --available-only` rather than relying on that example.

- **Leave a server type out** and Ankra picks it when the cluster is created, from what the location can provision at that moment: the cheapest x86 type with at least 2 vCPU and 4 GB for the bastion and workers, and at least 4 vCPU and 8 GB for the control plane and dedicated etcd nodes. Out-of-stock and deprecated types are skipped. The create response and the AI's create result name the type each role got.
- **Name a type** and Ankra checks it against the location first. If the location cannot provision it, the create is refused with the types of at least that size it can provision instead, cheapest first. The sizes above are only what Ankra picks by default, not a minimum for a type you name: `cpx22` (2 vCPU, 4 GB) runs a small control plane, and `cpx32` (4 vCPU, 8 GB) matches the default.
- **For a node group that autoscales**, pick a type the location sells reliably. Each scale-up orders a new server of the group's type, so a group on a type that goes out of stock cannot grow until it is back.

## Hetzner specifics

- **Disk growth is irreversible.** Moving a node group to a larger server type enlarges each server's disk, which Hetzner cannot shrink, so a group can never move back to a smaller type. Each node is powered off, resized and powered on, with brief downtime for its workloads. For smaller nodes, create a new group and delete the old one.
- **Restart** is a native reboot, falling back to a power cycle when the server does not respond.
- **SSH keys are shared by fingerprint.** Hetzner registers a public key once per project, so a key used on several Ankra Hetzner clusters is one Hetzner key object, and terminating any of those clusters deletes it. Running nodes keep working (their `authorized_keys` are already written), and the next key sync registers it again.
- **What a terminate touches.** Servers, the network and SSH keys are deleted by the IDs Ankra recorded - Ankra never lists your project and deletes what it finds. Just before the network is deleted, three scoped sweeps run: servers carrying this cluster's `ankra-cluster-id` label **and** attached to its network, volumes carrying that label, and Load Balancers attached to its network **or** carrying that label. That last filter is a union, so a Load Balancer you attached to the cluster's network by hand is removed too. Load Balancers are deleted on every terminate, because an attached one blocks the network delete. Your Hetzner API token is never touched.
- **Keeping a volume.** A Hetzner Volume labelled `ankra-retain` is kept when the cluster is terminated.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| Cluster stuck in provisioning | Check the token's permissions and your project limits in the [Hetzner Console](https://console.hetzner.cloud) |
| Invalid API token | Create a new read and write token and [rotate the credential](/platform/credentials/hetzner) |
| Server type unavailable | Run `ankra cluster hetzner server-types --credential-id <id> --location <location>` and pick a type marked available, often from the `cpx` line |
| "The cluster was not created ... Add a payment method" | Save a payment method on the organisation under **Billing**, then create the cluster again |
| `412: error during placement` | Hetzner has no capacity for that type at that location. Retry later or pick another server type |
| Cannot move a node group to a smaller type | Hetzner disks cannot shrink. Create a new node group and delete the old one |
| Node keeps the `uninitialized` taint | The CCM removes it once it has initialised the node. Check that the CCM pods run: `kubectl get pods -n hcloud` |
| `LoadBalancer` Service stuck in `Pending` | Check the CCM pods in `hcloud` and their logs for Hetzner API errors |
| PVCs stuck in `Pending` | Check the CSI pods in `hcloud` and that the `hcloud-volumes` StorageClass exists |
| CCM or CSI pods in `CrashLoopBackOff` | Check that the `hcloud-token` Secret in `hcloud` holds a valid token: `kubectl get secret -n hcloud hcloud-token -o yaml` |
| Ankra Agent pod `Pending` | The agent tolerates the `uninitialized` taint; if every node is unschedulable for another reason, check `kubectl describe nodes` |
