Reviewers should be able to open a link on a pull request and see the change running, instead of reading a diff and imagining it. Ankra deploys every pull request on a connected application to your organisation's staging cluster, keeps one status comment on the pull request up to date, and tears the preview down when the pull request closes.

A preview deploys an image that was already built for the pull request. Which image that is depends on how the application is built - see [Where the preview image comes from](#where-the-preview-image-comes-from) before you rely on previews.

---

## What you get

Once the pull request's image exists, a comment like this appears and keeps itself up to date:

> ### 🚀 Ankra Preview
>
> | Application | Status | Preview | Commit | Updated (UTC) |
> |:---|:---|:---|:---|:---|
> | **website** | ✅ Ready | **Visit Preview ↗** | `524ba32` | Aug 8, 2026, 10:26 PM |
>
> <sub>⏳ Expires Aug 9, 22:26 UTC · 🔁 Redeploys on every push</sub>

The preview runs in its own isolated namespace on the staging cluster, PodSecurity-hardened and quota-bounded, exactly like a manually launched [preview demo](/concepts/applications#preview-demos). When the Ankra GitHub App has the optional Deployments permission, the pull request also gets a GitHub deployment entry, so the preview shows up in the pull request's environments box.

## Prerequisites

<Steps>
  <Step title="Connect the repository as an application">
    The repository must be a [connected application](/concepts/applications) on GitHub.
  </Step>
  <Step title="Make sure pull requests produce an image">
    An application built with Ankra Pipelines already does: every pull request run builds the head commit. An application built with the generated GitHub Actions workflow does not, because that workflow pushes nothing for a pull request. See [Where the preview image comes from](#where-the-preview-image-comes-from).
  </Step>
  <Step title="Configure a staging cluster">
    An organisation admin chooses it under **Ankra AI → AI workspaces**, in **Where workspaces and previews run** → **Staging cluster**. Without it, pull requests deploy nothing however the switch below is set. The same page sets **How long a preview lives at first** (1 to 720 hours) and the longest each role may keep a preview running.

    From the CLI:

    <CliVersion since="0.71.0" command="application previews" />

    ```bash
    ankra org ai-environment set --staging-cluster my-staging-cluster
    ankra org ai-environment get
    ```

    Check: the application's **Ship → Previews** section shows a **Cluster online** badge beside the cluster's name.
  </Step>
  <Step title="Turn pull request previews on">
    Pull request previews are off on a new GitHub connection, and nothing is deployed until they are on. Turn them on for one application, or for the whole connection:

    <Tabs>
      <Tab title="Portal">
        For one application: go to **Applications → your application → Settings → Deploys**, and in the **Pull requests** card switch on **Preview every pull request**. This needs a role that can configure the application. It applies to that repository only, from the next pull request.

        For every repository of the connection: an admin goes to **Ankra AI → Gateway connections** and, in the GitHub installation's repository table, switches on **Pull request previews** on the **All repositories** row or on a rule for one repository. See [AI code review](/platform/ai-code-review#the-repository-table).
      </Tab>
      <Tab title="CLI">
        `ankra application previews enable` sets the rule for that application's repository, and `ankra application previews follow` removes the rule again, so the repository follows the connection's default:

        ```bash
        ankra application previews enable my-app
        ankra application previews follow my-app
        ```
      </Tab>
    </Tabs>

    Check: after you switch it on, the card says "Preview every pull request: on for this repository. It applies to the next pull request."
  </Step>
  <Step title="Optional: bring a preview domain for HTTPS">
    By default previews are served under the staging cluster's own Ankra DNS zone (`*.ankra.cc`, or the [Ankra domain your organisation selected](/concepts/applications#the-preview-url)). For your own hostnames, an admin sets a **Preview domain** with its **Ingress class** and **TLS secret** under **Ankra AI → AI workspaces → Domains for previews**.
  </Step>
</Steps>

## Where the preview image comes from

Ankra looks for the preview image in one of two ways, depending on what builds the application. The application's setup pull request decides that: a new application builds with Ankra Pipelines by default. [Ship Your App](/guides/deliver-your-app#where-the-image-is-built) compares the builders.

### Applications built with Ankra Pipelines

The preview deploys the image the pipeline's `build` step pushed for the pull request's head commit, by digest. Nothing else is needed: the pull request run that the push already starts is what produces it. Ankra never deploys a tag that could still point at an older commit.

While that run is still going, the preview waits and the comment says **Building**. When the run concludes, Ankra deploys straight away. If the run fails before it produces an image, the preview reports **Failed** with the reason, for example `Pipeline run #53 failed to build 524ba32: ...`. The next push, or a later successful run for the same commit, deploys it.

The pipeline needs its CI cluster and an approved definition before it runs at all - see [Before your first run](/guides/ankra-pipelines#before-your-first-run).

### Applications built by GitHub Actions

The preview deploys an image from the application's registry repository tagged with, in this order of preference:

1. `sha-<7>` - the first seven characters of the pull request's head commit,
2. `pr-<number>` - the pull request number,
3. the branch name, with every character other than letters, digits, `.`, `_` and `-` replaced by `-`.

<Warning>
The generated `build-and-publish.yml` workflow builds and scans the image on a pull request but never pushes it, so it produces none of these tags for a pull request. An application on the generated workflow therefore reports **Build unavailable** on every pull request. Previews work in this lane only when a workflow of your own pushes one of the tags above for pull requests, or after the application moves to [Ankra Pipelines](/guides/migrate-from-github-actions#migrate-an-existing-application-with-one-call).
</Warning>

Ankra prefers the head's own `sha-<7>` tag because a `pr-<number>` or branch tag can still hold an earlier push's image.

## The status comment

One marker-tagged comment per pull request, updated in place - never a stream of new comments.

| Status | Meaning |
|---|---|
| 🔄 **Building** | No image exists for this head yet. Ankra checks again for a few minutes and updates the comment when it arrives; a later completed build for the same head also re-triggers it. The footer says what the preview is waiting for: the pipeline run's `build` step for a pipeline-built application, or a `pr-<number>` or `sha-<7>` tag for every other application. |
| ⏳ **Deploying** | The image was found and the preview is starting on the staging cluster. |
| ✅ **Ready** | Deployed. The **Visit Preview** link opens the running pull request build; the **Commit** column shows the deployed head SHA. |
| ⚠️ **Build unavailable** | Ankra stopped waiting and found no image for this head. See [Troubleshooting](#troubleshooting). |
| ❌ **Failed** | The deploy failed, or the pipeline run failed to build the head. The reason appears in a caution callout under the table. |
| ⚪ **Stopped** | The pull request was closed or merged and the preview namespace was deleted. |

Lifecycle:

- **On open**: the preview deploys as soon as the pull request's image exists.
- **On every push**: the preview redeploys with the new head; the comment's Commit and Updated cells refresh.
- **On close or merge**: the namespace is torn down immediately and the comment flips to ⚪ Stopped.
- **On expiry**: previews are time-limited (the organisation's **How long a preview lives at first**, 24 hours by default) and removed automatically; pushing again deploys a fresh one.

The application's **Ship → Previews** section lists every running preview, a pull request preview with its **Pull request** number linked to GitHub. **Stop preview** removes one before its time.

## Configuration and data

Automatic previews start from the application's preview defaults under **Applications → your application → Settings → Deploys**: **Preview defaults** (preview variables, **Preview database**, **Preview login**) and **What a preview starts with** (a stack profile, shared services, a migration command). [Set what every preview starts with](/guides/branch-demos#set-what-every-preview-starts-with) explains each one. If your app needs configuration to boot, set the defaults once and every pull request preview gets them. The defaults apply to new previews; a preview already running keeps what it was launched with.

## Troubleshooting

| Symptom | What to check |
|---|---|
| No comment appears on a new pull request | Is **Preview every pull request** on for that repository, is the repository a connected application, and is the staging cluster set? If all three hold, push a new commit (or close and reopen the pull request) - either re-triggers the preview. |
| Stuck on 🔄 Building, pipeline-built application | Find the pull request's run with `ankra pipeline list --application <application> --head-sha <full-sha>`, or under **Applications → your application → Pipelines**. No run at all usually means the organisation's CI cluster has no CI workers or no cluster is set - see [Before your first run](/guides/ankra-pipelines#before-your-first-run). |
| ⚠️ Build unavailable, application on the generated workflow | Expected: that workflow pushes no image for a pull request. Push a `sha-<7>` or `pr-<number>` tag from your own CI, or [move the application to Ankra Pipelines](/guides/migrate-from-github-actions#migrate-an-existing-application-with-one-call). |
| ⚠️ Build unavailable, your own workflow | The workflow did not push any of the tags [listed above](#applications-built-by-github-actions) to the application's registry repository for this head. Check the workflow run and the tags it pushed. |
| No preview for a pull request from a fork | Forks get no preview image in either lane. A fork's pipeline build is restricted and pushes nothing, and GitHub does not give a fork's workflow the secrets it would need to push. |
| ❌ Failed with a pipeline run named | The pull request's pipeline run failed before its `build` step produced an image. Open the run named in the callout, fix it, and push again. |
| ✅ Ready but the URL errors or 503s | The preview runs *your pull request's container* - a crash on boot is application-side, not platform-side. Read its logs with `ankra application demo logs <application-id> <workspace-id>` (`ankra application demo list <application-id>` gives the workspace id). When the preview card shows an error, **See its pods** opens its pods on the staging cluster. A config file change that breaks the container's server is the usual cause. |
| The preview URL does not resolve | The staging cluster's DNS zone must be active (or a **Preview domain** configured). If it resolves publicly but not on your machine, a stale negative DNS cache is usually to blame - retry against another resolver. |
| The card reads **No public address yet.** | The card links only an HTTPS address. Read the preview's address from `ankra application demo list <application-id> -o json`, or set a **Preview domain** with a **TLS secret** for HTTPS. |
