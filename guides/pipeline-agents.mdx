Your CI already has the schedule, the secrets and the logs. What it lacks is an answer to "what will this change do to the live cluster?" or "why did that deploy fail?". The [Ankra CLI](/integrations/ankra-cli) gives a CI job two commands for that: `ankra chat` asks Ankra's AI a question with your clusters as context and prints the answer, and `ankra cluster apply --wait` applies a cluster definition and waits for the result. This page shows one working job for each of three uses.

## Prerequisites

- A CI system that can run a shell step. The examples use GitHub Actions; the commands are the same anywhere.
- A [service token](/guides/service-tokens) stored as the CI secret `ANKRA_API_TOKEN`, with the narrowest role the job needs - see [Keep CI jobs read-only](#keep-ci-jobs-read-only).
- The CLI installed in the job:

  ```bash
  bash <(curl -sL https://github.com/ankraio/ankra-cli/releases/latest/download/install.sh)
  ```

`ankra chat` prints the answer on standard output and the conversation ID on standard error, so redirecting standard output captures only the answer.

## Comment a review of a cluster change on the pull request

When a pull request changes a cluster definition, pass the diff to `ankra chat` and post the answer as a comment. Ankra's AI compares the change with the live cluster.

<CliVersion since="0.9.0" />

```yaml
# .github/workflows/ankra-review.yml
name: Ankra review
on:
  pull_request:
    paths:
      - "cluster.yaml"
permissions:
  contents: read
  pull-requests: write
jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: Install Ankra CLI
        run: bash <(curl -sL https://github.com/ankraio/ankra-cli/releases/latest/download/install.sh)
      - name: Review the change against the live cluster
        env:
          ANKRA_API_TOKEN: ${{ secrets.ANKRA_API_TOKEN }}
          BASE_SHA: ${{ github.event.pull_request.base.sha }}
        run: |
          change=$(git diff "$BASE_SHA" HEAD -- cluster.yaml | head -c 20000)
          ankra chat --cluster my-cluster --mode ask \
            "This pull request changes the definition of this cluster. Compare it with the live cluster, \
             summarise what will change, and flag any capacity or quota risk. The diff: $change" \
            > review.md
      - name: Comment on the pull request
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs')
            await github.rest.issues.createComment({
              ...context.repo,
              issue_number: context.issue.number,
              body: fs.readFileSync('review.md', 'utf8'),
            })
```

Replace `cluster.yaml` with the path of your cluster definition and `my-cluster` with the cluster's name.

## Explain a failed deploy in Slack

After a merge, apply the cluster definition and wait for Ankra to accept it. If the apply fails, ask why and post the answer to Slack, so the channel gets a cause instead of a red cross.

```bash
set -euo pipefail

if ankra cluster apply -f cluster.yaml --wait --timeout 15m; then
  echo "Configuration applied"
else
  summary=$(ankra chat --cluster my-cluster --mode ask \
    "The last apply to this cluster failed. Give the root cause and the exact fix.")
  curl -sS -X POST "$SLACK_WEBHOOK_URL" \
    -H 'Content-Type: application/json' \
    -d "$(jq -n --arg text ":rotating_light: Deploy failed on my-cluster: $summary" '{text: $text}')"
  exit 1
fi
```

`ankra cluster apply --wait` exits with code `5` when `--timeout` expires, so you can treat a slow apply differently from a hard failure. `--wait` covers the configuration write only: add-on deploys are dispatched afterwards, so check them with `ankra cluster operations list` before calling a rollout healthy. The CLI's other [exit codes](/reference/cli) let a job treat `3` (not found) as success for idempotent steps and re-authenticate on `6`.

## Post a scheduled health check

Run every 30 minutes, stay silent while everything is healthy, and post to Slack only when something is degraded.

```yaml
# .github/workflows/ankra-health.yml
name: Ankra health check
on:
  schedule:
    - cron: "*/30 * * * *"
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - run: bash <(curl -sL https://github.com/ankraio/ankra-cli/releases/latest/download/install.sh)
      - name: Check every cluster
        env:
          ANKRA_API_TOKEN: ${{ secrets.ANKRA_API_TOKEN }}
          SLACK_WEBHOOK_URL: ${{ secrets.SLACK_WEBHOOK_URL }}
        run: |
          report=$(ankra chat --mode ask \
            "Check every cluster. Reply with the single word OK if all are healthy, \
             otherwise a short summary of what is degraded and why.")
          if [ "$(echo "$report" | tr -d '[:space:]')" != "OK" ]; then
            curl -sS -X POST "$SLACK_WEBHOOK_URL" -H 'Content-Type: application/json' \
              -d "$(jq -n --arg t ":warning: $report" '{text: $t}')"
          fi
```

Without `--cluster`, `ankra chat` answers across the whole organisation.

## GitLab CI and other runners

The commands are the same in any CI. In GitLab CI, run the review job on `rules: - if: $CI_PIPELINE_SOURCE == "merge_request_event"` and diff against `$CI_MERGE_REQUEST_DIFF_BASE_SHA`, and run the health check from a scheduled pipeline with `rules: - if: $CI_PIPELINE_SOURCE == "schedule"`.

## Keep CI jobs read-only

- The review and health check jobs only read. Give them a service token with the `viewer` role, which includes ask-mode AI. Token `--scopes` only choose MCP access (`mcp:read`, `mcp:write`), so the role is what limits a CLI token.
- Only the deploy job writes. Give it a separate service token with a role that can deploy Stacks, such as `member`.
- Run `ankra chat` with `--mode ask`: ask mode investigates and may make safe creations, but does not change what is already running. Never pass `--mode agent` in CI; make changes through `ankra cluster apply` and your GitOps repository.
