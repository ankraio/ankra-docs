The same flow runs from the console, the terminal and an AI coding assistant, because all three drive the same platform: connect a repository, get a setup pull request, test, build and scan, let the gate block a critical vulnerability, have Ankra AI fix it with your approval, merge, deploy to staging with Postgres and HTTPS, promote to production as a person, and hear about a real failure in Slack.

<YouTube id="zED1slvEvU0" title="From prompt and code to production, three ways: console, CLI and Claude Code" />

Pick your surface below. The [flow parity matrix](/reference/flow-parity) has every step on each surface side by side, including where a surface does not have a step yet.

<Warning>
**Pull request previews have an open bug.** On a default new cluster on Ankra Cloud a preview may not come up: its database can stop on a quota error and its hostname may not answer over IPv4. Previews are the one step of this flow we are not asking you to rely on yet. Everything else on this page does not depend on them.
</Warning>

## Before you start

- A GitHub repository with an application in it. A prompt-built or hand-written one both work.
- Two clusters in one organisation, one for staging and one for production, and a cluster to run CI on. Staging can be your CI cluster. See [Ankra CI](/get-started/ankra-ci).
- A person who can manage pipelines (an owner, administrator or operator) nearby, once. Approving what a pipeline may do needs that permission.

## The flow

<Tabs>
  <Tab title="UI">
    <Steps>
      <Step title="Connect GitHub">
        Under **Ankra AI** → **Gateway connections**, in the **GitHub** section, choose **Install the GitHub App** and install it on the account that owns the repository. See [GitHub](/integrations/github).
      </Step>
      <Step title="Register the repository">
        Open **Applications** → **New application**, find the repository and choose **Connect and prepare**. Ankra analyses it and opens a setup pull request with what it needs to build and run. **Ship** → **Go live** shows it.
      </Step>
      <Step title="Approve the pipeline's authority">
        Open a run under **Pipelines** on the application, choose **Review authority for approval**, then **Approve for future runs**. When you add the application in the portal yourself, Ankra already records your approval of the pipeline it generated. Until a person approves a changed definition, a run uses the last approved authority, or none.
      </Step>
      <Step title="Read the gate, and fix what it blocks">
        **Pipelines** shows the run and **Protect** shows its findings. Where the image gate blocks a fixable vulnerability, **Fix with Ankra** opens Ankra AI with the request written. Send it, and Ankra AI proposes the change on the pull request's branch. It writes nothing until you approve it.
      </Step>
      <Step title="Merge">
        Merge the pull request on GitHub, with **Merge** on a fix Ankra opened under **Protect**, or turn on **Merge when green** on the GitHub connection. See [merge when green](/pipelines/ai-in-pull-requests).
      </Step>
      <Step title="Deploy to staging">
        Use **Ship** → **Deploy a version**, choose the staging cluster, a version and a public hostname, review, and confirm. A Postgres database the setup declares comes up with it.
      </Step>
      <Step title="Promote to production">
        Use **Ship** → **Promote a version** to move the tag staging proved. A person does this; production does not follow merges unless you tell it to.
      </Step>
      <Step title="Hear about failures">
        Connect Slack with **Add to Slack** under **Ankra AI** → **Gateway connections**, add a notification destination for the channel, then choose **Add rule** under **Organisation** → **Notification routes**. See [Notification routing](/guides/notification-routing).
      </Step>
    </Steps>
  </Tab>
  <Tab title="CLI">
    <Steps>
      <Step title="Connect GitHub in the portal">
        Installing the GitHub App is a browser consent, and the CLI has no verb that starts it yet. Do it under **Ankra AI** → **Gateway connections** in the portal, then log in:

        ```bash
        ankra login
        ankra org ci-settings pool add <ci-cluster>
        ```
      </Step>
      <Step title="Ship from your checkout">
        Run this in a checkout whose `origin` is the repository. It registers the application, waits for setup and the first build, and deploys:

        ```bash
        ankra application ship . --cluster <staging-cluster> --set-up-database
        ```

        Re-running it is safe, and it carries on from where the flow stands.
      </Step>
      <Step title="Approve the pipeline's authority">
        A person with the `pipelines.manage` permission (owners, administrators and operators) does this, once per definition:

        ```bash
        ankra pipeline definitions approve <definition-id>
        ```
      </Step>
      <Step title="Read the gate, and fix what it blocks">
        ```bash
        ankra pipeline get --application <application> --latest --wait --exit-code
        ankra pipeline findings <run> --application <application>
        ```

        Ask Ankra AI for the fix, then confirm the write it proposes:

        ```bash
        ankra chat --mode agent "Fix the finding that blocked run <run> of <application>, on the pull request's branch, with its lockfile"
        ankra chat actions confirm <action-id>
        ```

        An AI fix that runs the package manager needs a sandbox on the workspace's cluster. See [what Ankra refuses](#what-ankra-refuses-and-why).
      </Step>
      <Step title="Merge">
        The CLI has no merge verb yet, so merge the pull request on GitHub, or add it to the [merge train](/pipelines/merge-train) where the repository has one:

        ```bash
        ankra pipeline train add <pull-request>
        ```

        The first `ship` stops at the setup pull request. Once it is merged, run `ankra application ship . --cluster <staging-cluster> --set-up-database` again: it carries on and deploys to staging.
      </Step>
      <Step title="Promote to production">
        There is no separate promote verb: a deploy of the tag staging proved is the promotion.

        ```bash
        ankra application deploy <application> \
          --cluster <production-cluster> \
          --set image_tag=sha-<the-tag-that-passed> \
          --set ingress_enabled=true \
          --set ingress_host=app.example.com
        ```
      </Step>
      <Step title="Hear about failures">
        Connect Slack in the portal, then route pipeline failures to the channel:

        ```bash
        ankra alerts destinations channels
        ankra alerts destinations create --name team-slack --channel-id <channel-id>
        ankra alerts routes create --destination-id <destination-id> --kinds pipeline_run_failed,image_gate_blocked
        ```
      </Step>
    </Steps>
  </Tab>
  <Tab title="Claude Code">
    <Steps>
      <Step title="Connect Claude Code">
        Install the skills and add the [MCP server](/platform/mcp-server), then run `/mcp` in Claude Code and sign in:

        ```bash
        ankra skills install --client claude-code --with-hooks
        claude mcp add --transport http ankra https://platform.ankra.app/api/v1/mcp
        ```

        Connect GitHub in the portal first: Ankra never creates a credential over MCP.
      </Step>
      <Step title="Ask for the flow">
        Give it the whole job and the rules. For example:

        ```
        Register this repository as an application in Ankra and read me the setup pull
        request. Watch its pipeline run. If the image gate blocks, tell me the finding
        and fix it on the pull request's branch, with the lockfile. Then deploy to
        <staging-cluster> with its Postgres and a public address, and stop. Do not touch
        production.
        ```

        It works through `create_application`, `get_application_setup_proposal`, `watch_pipeline_run`, `list_security_findings`, `scm_create_pull_request` and `deploy_application`, and the [MCP tool reference](/platform/mcp-tools) lists the rest. On a cluster with no Postgres operator, run `ankra application ship . --set-up-database` once first, because MCP cannot install the operator yet.
      </Step>
      <Step title="Approve what only you can">
        Claude Code cannot approve a pipeline's authority: run `ankra pipeline definitions approve <definition-id>` yourself, or approve it in the portal.
      </Step>
      <Step title="Merge">
        `scm_merge_pull_request` asks Ankra to merge once everything is green. It needs an `mcp:write` token, and it is refused unless the GitHub connection is in Agent mode with merge when green on, which an organisation administrator can turn on with `enable_merge_when_green`. A pull request from a fork is never merged. It never merges at once.
      </Step>
      <Step title="Promote, as a person">
        Ask for `promote_application` from staging to production: it deploys what staging runs. Keep this step to yourself: read the evidence before you say yes.
      </Step>
      <Step title="Hear about failures">
        Connect Slack in the portal, because the install is a browser consent. Then `create_alert_destination` and `create_notification_route` route failures to the channel.
      </Step>
    </Steps>
  </Tab>
</Tabs>

## What Ankra refuses, and why

These hold on the console, the CLI and MCP alike. A prompt does not change them.

| Ankra refuses | When | Why | What to do |
| --- | --- | --- | --- |
| **To publish an image** | The [image gate](/guides/ankra-pipelines) finds a fixable CRITICAL or HIGH vulnerability in the image, at the default `ci_image_gate` of `app` | What passed the gate is the only thing that reaches your registry tag and your clusters | Fix the finding, or change the organisation's policy deliberately |
| **To run an AI fix without a sandbox** | Ankra AI chose a command to run in a workspace, and the workspace has no gVisor or Kata runtime, or Ankra cannot tell | A command such as a package manager runs a repository's install scripts, which are untrusted code | On an Ankra-built kubeadm cluster, give the CI cluster a sandboxed node group, then recreate the workspace, for example `ankra cluster node-group add <cluster> --name sandbox --labels ankra.cloud/sandbox-runtime=gvisor` |
| **To let an AI approve a pipeline** | A service token or an AI agent tries to approve a definition's authority. There is deliberately no MCP tool for it | Approving grants the secrets, credentials and network the definition declares | A person with the `pipelines.manage` permission approves it |
| **To apply most AI changes you have not confirmed** | Ankra AI proposes a write in chat. Some run straight away: opening a pull request in Agent mode, and writes your organisation's autonomy setting, a trusted action or an approved plan already allows. Over MCP your client asks you, and the token's scope is Ankra's approval | You see what it will do before it does it | Confirm or reject it in the portal, or with `ankra chat actions` |
| **To merge at once from MCP** | `scm_merge_pull_request` is called | The merge waits for a green run, a passed gate and approved authority, with nothing requesting changes | Put the GitHub connection in Agent mode with merge when green on, or merge it yourself. A pull request from a fork is never merged |
| **To take a secret through a tool call** | An MCP call asks to create a credential, or a mutating call's arguments look like a live credential | A tool argument passes through the model and its logs | Use the portal, the CLI, or an [organisation secret slot](/reference/cli/secrets). `set_application_env_secret` stores a value you pass, and refuses one that looks like a live credential |
| **To move production on a merge** | Production is not the first environment you deployed, and has no branch rule | The first environment you deploy follows the application's push switch; every later one does not. A person moves production | Deploy staging first, then promote what staging proved |

Every resolved MCP tool call, refused calls included, is written to the organisation's audit log. See [MCP Server](/platform/mcp-server).
