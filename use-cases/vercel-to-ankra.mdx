Vercel builds and serves your project from its own platform. Ankra builds the same GitHub repository and runs it on your own cluster, behind HTTPS, with every change built and scanned first.

You keep pushing to the same repository. Ankra builds every commit.

---

## What moves, and what it becomes

| On Vercel | On Ankra |
|---|---|
| Next.js build | One container image. When `next.config` sets `output: 'standalone'`, the image carries only the standalone server, its static assets and `public/`. Otherwise it runs `next start` |
| API routes, route handlers, middleware, edge routes | Served by the Next.js server in that container. Nothing to split out |
| `vercel.json` crons | One Kubernetes CronJob per cron entry. It calls the same route on the same UTC schedule, with the `vercel-cron/1.0` user agent and `Authorization: Bearer <CRON_SECRET>` when the app has a `CRON_SECRET` secret, so a route that checks it keeps working |
| `vercel.json` rewrites, redirects and headers | Listed in the setup pull request. Vercel applied them at its edge; on Ankra your own server serves every request, so move them into `next.config` (`rewrites()`, `redirects()`, `headers()`) before you move traffic |
| Project environment variables | The application's environment secrets. Bring them over with the extension (below) or enter them in Ankra |
| Preview deployments | [Preview demos](/concepts/applications#preview-demos) on a preview address. The proof run of the setup pull request is compared with Vercel's preview of the same commit ([below](#compared-with-your-vercel-preview)) |
| Your domain | Your own domain with its certificate on the cluster ([Applications](/concepts/applications)) |

The setup pull request contains the Dockerfile, the Kubernetes manifests, the CronJobs, the deploy options (`.ankra/ankra.yaml`) and the build pipeline (`.ankra/pipeline.yaml`). Ankra's AI writes it when you add the repository. You review and merge it.

## Vercel storage in the Launch Plan

Ankra reads which Vercel storage the code uses and puts one card per service in the project's Launch Plan. Each card shows how locked in the service is and which choice applies by default. You can change the choice.

| Vercel service | Default | What you can choose instead |
|---|---|---|
| Vercel Postgres (`@vercel/postgres`) | Keep it: `POSTGRES_URL` stays an environment secret | A portability pull request switches to a plain Postgres driver on one connection string, then Ankra runs CloudNativePG in your cluster |
| Vercel KV (`@vercel/kv`) | Keep it | A portability pull request moves to a Redis client on `REDIS_URL`, backed by Valkey in your cluster |
| Vercel Blob (`@vercel/blob`) | Keep it | A portability pull request moves uploads to the S3 API, backed by object storage in your cluster |
| Edge Config (`@vercel/edge-config`) | Keep it | A portability pull request reads the same keys from environment variables, delivered as a ConfigMap |

A portability pull request is opt-in. It adds the open-protocol path beside Vercel's, and the app keeps using Vercel until you set the new variables. Data is copied only when you start a [data migration](#moving-your-data-closed-beta).

## Moving your data (Closed Beta)

<Warning>
**Closed beta.** Data migration is in closed beta. Where Ankra cannot yet carry out a step for a service, the run stops before anything at the vendor changes, or rolls back, and gives the reason. [Contact support](/platform/support) before relying on it for a production move.
</Warning>

When you choose to move a service into your cluster, the Launch Plan carries a data migration for it. The migration plans the move in steps, and one plan-level approval covers all of them.

Every service moves before one cutover:

1. Ankra copies the data in while your app keeps running on Vercel.
2. It makes each vendor source read-only.
3. It copies what changed since the first copy and checks counts and checksums.
4. It switches your app's variables to the services in your cluster in one change.

The vendor sources then stay read-only for a rollback window, seven days by default. In that window, one command puts the previous variables back and makes the sources writable again. Ankra never deletes data at the vendor. When the window closes, you get a checklist of what to remove there yourself.

| Service | How the data moves |
|---|---|
| Postgres | Ankra reads the source with the connection string you stored, to choose how it moves. It dumps the read-only source into one of your [backup vaults](/guides/backups) and restores the dump into CloudNativePG, then compares row counts and sequences |
| S3-compatible object storage | Every object is copied with its checksum checked, then copied again right before the cutover |

<CliVersion since="0.46.0" command="application data-migration" />

```bash
# follow the runs, and roll one back inside its window
ankra application data-migration list <application>
ankra application data-migration get <application> <run-id>
ankra application data-migration rollback <application> <run-id>
```

Vercel Blob is not S3-compatible, so its data is not copied yet.

## Compared with your Vercel preview

Before you merge the setup pull request, Ankra's proof run deploys it to an ankra.cc preview and requests its health routes and its home page. For a Vercel project, the proof then requests the same routes on the preview Vercel deployed of the same commit, and compares the two answers.

The comparison looks at the shape of each answer, not its exact bytes:

- the status code
- the content type
- for JSON, the keys two levels deep
- for an HTML page, its title and which of `header`, `nav`, `main` and `footer` it has
- the size, which counts as different only when one answer is more than twice the other

Build ids, nonces and timestamps differ between any two deployments, so they are not compared.

Each route gets one of three results on the proof card in the pull request:

| Result | Meaning |
|---|---|
| **match** | Both previews answered with the same shape |
| **differs** | Both answered, differently. The card names the first difference, for example a different status or page title |
| **unknown** | The routes were not compared. The card says why, for example: Vercel deployed no preview of the commit, the preview was still building, the preview is protected, or a request timed out |

An unknown route is never counted as a match.

A difference is a warning. It does not fail the proof and does not block the pull request. A Vercel preview can differ for good reasons, such as variables set only for previews. Check each difference before you move your domain.

Ankra finds the Vercel preview from the deployment status Vercel's GitHub integration posts on the commit, so the GitHub App Ankra uses must be able to read the repository's deployments. Ankra sends no credential to the Vercel preview. If the preview is protected by Vercel Authentication, its routes show as unknown.

## Start from the Vercel project page

The **Ankra — Chat & Deploy** extension for Chrome puts an **Ask Ankra** button on your Vercel project page, and also on Lovable, Claude Design and GitHub repository pages. See [install the extension](/use-cases/lovable-to-ankra#install-the-extension-without-the-chrome-web-store).

<Steps>
  <Step title="See where the project stands">
    The button carries a status pill for the project's repository: **Not connected**, **Analysing**, **N decisions**, **Ready to approve**, **Proving**, **Proof failed** or **Live**. The same pill appears on the repository's GitHub pages.
  </Step>
  <Step title="Review the Launch Plan">
    Open **Deploy project**. The extension fills in the GitHub repository the Vercel project builds and its branch. The **Launch Plan** panel lists:

    - the decisions only you can make, with their defaults
    - per external service, what stays at Vercel and what Ankra runs open source
    - the result of the proof run of the setup pull request

    To change a decision, use **Change decisions in Ankra**. All configuration stays in Ankra.
  </Step>
  <Step title="Bring your variables">
    Under **Bring variables from Vercel**, paste a Vercel access token for the project's team and choose **Read variables**. The token is used from your browser only and is not stored or sent to Ankra.

    By default you get the names of the project's production variables, marked by whether Ankra already has each one. Tick the box to copy the values into the application's encrypted secrets. Values Ankra already holds are never overwritten. Variables marked sensitive on Vercel cannot be read back, so enter those in Ankra.

    Values can be copied once Ankra has registered the application, which happens on the first deploy.
  </Step>
  <Step title="Approve">
    Click **Approve and deploy**. Ankra registers the application, opens the setup pull request, builds and scans the image, and deploys it with the plan's choices. If the setup pull request or the first build is still pending, the request waits and is sent when Ankra is ready.

    The approval covers exactly the actions the panel lists, for one hour. When Ankra AI works on the launch in your chat or in an agent run that carries the approval, it runs those actions without asking you again. Anything outside the list still asks first. If the plan changes after you approve, nothing runs under the old approval: read the new plan and approve it.
  </Step>
</Steps>

<Note>
Test on the Ankra address before you move your domain. Check every route the proof card shows as differing or unknown, the cron routes, the rewrites you moved into `next.config`, and every variable your app reads.
</Note>

## From the CLI

```bash
ankra application add . --branch main
ankra chat "show me the Launch Plan of <application>" --mode ask
```

Run the first command in a local checkout of the repository.

See [Applications](/concepts/applications) and [Lovable to Ankra](/use-cases/lovable-to-ankra) for the rest of the flow, from the setup pull request to automatic deploys.
