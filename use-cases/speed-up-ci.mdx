Most CI time goes on work a change did not need: the backend tests for a frontend fix, a full rebuild of a commit that was already built and tested on its pull request, a whole pipeline for a README edit. Ankra Pipelines lets you skip that work with a few lines of `.ankra/pipeline.yaml`, and it never skips anything it cannot prove the change left alone.

This page shows each technique with a complete pipeline you can paste, says which one to use when, and explains why a skipped stage never turns a run green by mistake.

## Which technique to use

| You want to | Use | What happens to the stages after it |
|---|---|---|
| Run nothing for changes that only touch documentation | [`on.<event>.paths`](#skip-runs-that-only-touch-documentation) | No stage runs, and the run is recorded as skipped |
| Check only what a pull request touches, and run everything on main | [`when.pull_request`](#check-only-what-a-pull-request-touches) | Skipped too, unless they list the stage in `skippable_needs` |
| Skip a component's tests on every event when its files did not change | [`paths:` on the stage](#skip-tests-for-components-a-change-did-not-touch) | They still run: the skipped stage counts as satisfied |
| Run a stage on a condition that a path list cannot express | [`if:`](#keep-later-stages-running-and-write-your-own-conditions) | Skipped, unless their own `if:` calls a status function such as `always()` |
| Stop building and testing a commit again after its pull request already did | [`promote_from`](#build-once-and-promote-on-merge) | The push runs `publish` only |
| Test each pull request on top of the latest main without testing it twice | [The merge train](#test-each-pull-request-as-it-will-merge) | Merge publishes the tested image |
| Run slow suites less often | [`on.schedule`](#move-slow-suites-to-a-nightly-run) | Only the listed stages run |
| Stop spending time on commits nobody will look at | [`cancel_in_progress`](#move-slow-suites-to-a-nightly-run) | The older run is cancelled and shown as superseded |

The techniques combine. A typical setup is pull-request-only filters on the expensive test stages, `promote_from` on `publish`, the merge train on the default branch, and a nightly run for the slowest suite.

## Skip runs that only touch documentation

Give a trigger a `paths` list, and an event whose changed files all fall outside it runs no stage: the run is recorded as skipped. A list that starts with `!` means "everything except", so this pipeline runs for every change except documentation, root Markdown files and GitHub workflow files:

```yaml
apiVersion: ankra.io/v1
kind: Pipeline
metadata:
  name: shop
on:
  push:
    branches: [main]
    paths: ["!docs/**", "!*.md", "!.github/**"]
  pull_request:
    branches: [main]
    paths: ["!docs/**", "!*.md", "!.github/**"]
defaults:
  network: egress-https
stages:
  - name: checkout
    kind: checkout
  - name: test
    kind: run
    image: golang:1.26
    run: go test ./...
    needs: [checkout]
```

A pull request that changes only `docs/intro.md` and `README.md` runs no stage. Its run is recorded as skipped, with the reason "Every file this event changed falls outside the paths this pipeline's trigger declares." A pull request that also changes `api/README.md` runs, because `*.md` matches Markdown files at the repository root only.

<Warning>
Exclude a file type everywhere (`**/*.md`) only when nothing your build or tests read has that type. Code that embeds Markdown, such as prompt files or templates, needs its tests to run when those files change.
</Warning>

<AccordionGroup>
  <Accordion title="How path patterns match">
    - Patterns are matched against file paths from the repository root: `api/**`, never `./api/**` or `/api/**`.
    - `*` matches any characters except `/`. `**` matches any characters, `/` included. `?` matches one character.
    - A pattern matches whole file names, so `docs/` matches nothing. Write `docs/**`.
    - `!` in front of a pattern removes what it matches. The last pattern that matches a file decides, so `["web/**", "!web/**/*.md"]` means the web directory except its Markdown files.
    - Matching is case-sensitive.
    - `ankra pipeline validate` warns about a pattern that can match no file, such as one starting with `./` or `/`, ending in `/`, or containing a backslash, and names the pattern to write instead.
  </Accordion>
</AccordionGroup>

## Check only what a pull request touches

A monorepo usually wants a pull request to run the checks of the components it changes, while every push to main runs everything. Give each expensive stage an event-scoped `when` block: the `pull_request` block filters on paths, and an empty `push` block means pushes are not filtered.

```yaml
apiVersion: ankra.io/v1
kind: Pipeline
metadata:
  name: shop
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
defaults:
  network: egress-https
stages:
  - name: checkout
    kind: checkout
  - name: backend-test
    kind: run
    image: golang:1.26
    run: go test ./...
    working_directory: backend
    needs: [checkout]
    when:
      pull_request:
        paths: ["backend/**"]
      push: {}
  - name: frontend-test
    kind: run
    image: node:24
    run: corepack enable && pnpm install --frozen-lockfile && pnpm run test
    working_directory: frontend
    needs: [checkout]
    when:
      pull_request:
        paths: ["frontend/**"]
      push: {}
```

A pull request that changes only `frontend/src/app.tsx` runs `checkout` and `frontend-test`, and records `backend-test` as skipped with reason `path_filter`. Every push to main runs all three, so main keeps a full test run after every merge.

This is the technique behind the "About 3 minutes instead of 19" example above. It is the safest place to start: nothing is skipped on main.

## Skip tests for components a change did not touch

When a component's tests should be skipped on every event, pushes included, give the stage `paths:`. A stage with `paths:` is **affected-only**: when no changed file matches, it is skipped, and the stages that need it still run: each waits on what the skipped stage waited on. That lets a monorepo skip the tests of untouched components and still build, scan, gate and publish.

```yaml
apiVersion: ankra.io/v1
kind: Pipeline
metadata:
  name: shop
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
defaults:
  network: egress-https
stages:
  - name: checkout
    kind: checkout
  - name: test-web
    kind: run
    image: node:24
    run: corepack enable && pnpm install --frozen-lockfile && pnpm -C web run test
    needs: [checkout]
    paths: ["web/**", "packages/ui/**"]
  - name: test-api
    kind: run
    image: golang:1.26
    run: go test ./...
    working_directory: api
    needs: [checkout]
    paths: ["api/**", "go.work"]
  - name: build
    kind: build
    needs: [test-web, test-api]
    build:
      dockerfile: Dockerfile
  - name: scan
    kind: scan
    needs: [build]
    scan:
      scanners: [semgrep, trivy]
  - name: gate
    kind: gate
    needs: [scan]
  - name: publish
    kind: publish
    needs: [gate]
    when:
      events: [push]
```

A push that changes `web/app.ts` skips `test-api` and runs every other stage. `build` waits for `test-web`, and for `checkout` in place of the skipped `test-api`.

Use `paths:` only on stages whose absence holds nothing back. `ankra pipeline validate` refuses an affected-only stage when skipping it would be unsafe:

- a stage whose outputs another stage reads
- a `build` that another stage needs, because what needs a build reads its image
- a `checkout`, `gate` or `approval` stage
- a scan that a gate judges, whether the gate names it in `require_stages`, pairs with it by name (`gate-api` with `scan-api`), or judges every scan in the run
- a stage that a release bundle build depends on, because the bundle packs what that stage left in the workspace

It also warns when an affected-only stage that another stage needs declares `artifacts:`.

## Keep later stages running, and write your own conditions

A stage filtered by `when` paths normally takes the stages that need it with it. To keep a later stage running, name the filtered stage in `skippable_needs`: when the filtered stage is skipped for its paths, the later stage waits on what that stage waited on instead. When the filtered stage runs, it is an ordinary need.

For a rule that a path list cannot express, give the stage an `if:` condition. `event.changed_files` is the run's list of changed files, and `event.kind` is the event.

```yaml
apiVersion: ankra.io/v1
kind: Pipeline
metadata:
  name: shop
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
defaults:
  network: egress-https
stages:
  - name: checkout
    kind: checkout
  - name: frontend-test
    kind: run
    image: node:24
    run: corepack enable && pnpm install --frozen-lockfile && pnpm run test
    working_directory: frontend
    needs: [checkout]
    when:
      pull_request:
        paths: ["frontend/**"]
      push: {}
  - name: e2e
    kind: run
    image: mcr.microsoft.com/playwright:v1.56.0-noble
    run: corepack enable && pnpm install --frozen-lockfile && pnpm run e2e
    working_directory: frontend
    needs: [checkout, frontend-test]
    skippable_needs: [frontend-test]
  - name: migrations-check
    kind: run
    image: golang:1.26
    run: go run ./cmd/migrate --dry-run
    needs: [checkout]
    if: "event.kind == 'push' || event.changed_files.exists(f, f.startsWith('db/migrations/'))"
```

A pull request that changes only `backend/main.go` skips `frontend-test` (`path_filter`) and `migrations-check` (`condition_false`), and still runs `e2e`. A pull request that adds `db/migrations/0042_add.sql` runs `migrations-check`. Every push runs everything.

An `if:` that calls a status function, such as `always()`, also keeps a stage running when a need was skipped: its condition decides, and `needs.<stage>.result` reads `skipped`.

## Build once and promote on merge

Without promotion, a merge to main builds, scans and tests the merged commit again, although its pull request run already did all of that. With `publish.promote_from: pull_request`, a push whose files are exactly the files a pull request run tested publishes that run's image instead:

```yaml
apiVersion: ankra.io/v1
kind: Pipeline
metadata:
  name: shop
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
defaults:
  network: egress-https
stages:
  - name: checkout
    kind: checkout
  - name: test
    kind: run
    image: golang:1.26
    run: go test ./...
    needs: [checkout]
  - name: build
    kind: build
    needs: [test]
    build:
      dockerfile: Dockerfile
  - name: scan
    kind: scan
    needs: [build]
    scan:
      scanners: [semgrep, trivy]
  - name: gate
    kind: gate
    needs: [scan]
  - name: publish
    kind: publish
    needs: [gate]
    when:
      events: [push]
    publish:
      promote_from: pull_request
```

A promoted push runs `publish` alone: it re-tags the digest the pull request run's gate approved as the push's own `sha-<7>` tag, and push-to-deploy rolls it out as after a full run. Every other stage shows as skipped with reason `promoted`, naming the run that passed it. This is the "15 seconds from merge to published" example above.

- **When it applies.** The pushed commit has the same git tree as a pull request run that passed every stage `publish` needs, under the same approved pipeline authority, within the last 72 hours, from a branch in the repository itself. A squash merge of a pull request that was up to date with main has that tree. Anything else builds and tests in full, and the run records why.
- **Combined with pull-request-only filters.** A stage the pull request run skipped did not pass, so the push builds and tests in full. That is the point of pull-request-only filters: main still runs everything that a pull request left out.
- **Approval.** `promote_from` is a protected section. An administrator approves it with the rest of the default branch's definition, and a pull request cannot turn it on for itself.
- **New applications.** Pipelines Ankra generates for an application declare `promote_from` whenever the pipeline's shape allows it.

A publish that meets a registry timeout or an outage status is retried for up to five minutes before the step fails, so a short registry problem does not leave a merge undeployed.

## Test each pull request as it will merge

A pull request that is behind main merges as a tree nobody tested, and its push then has nothing to promote from. Turn on the merge train, and Ankra tests each pull request squashed onto the latest main, then merges it through GitHub's own merge when that run passes. The merged tree is exactly the tree the train tested, so `promote_from` publishes the train's image on the merge.

<CliVersion since="0.30.0" />

```bash
ankra pipeline train enable --application my-app
ankra pipeline train add 412 --application my-app
ankra pipeline train list --application my-app
```

- A train run is planned as a pull request run with the pull request's own list of changed files, so the same filters apply. A train run with nothing left to run passes, as the pull request's own skipped check does. Such a run is never a source for promotion, so its merge builds in full or promotes from another passing run of the same tree.
- `--max-cars 3` on `enable` tests three pull requests at once, each on top of the ones ahead of it. When one fails, it leaves the train and the cars behind it are tested again without it.
- Make the **Ankra merge train** check required on main, and every merge goes through the train.

The merge train runs on GitHub repositories. [The merge train](/guides/ankra-pipelines#the-merge-train-test-every-pull-request-as-it-will-merge) explains what happens when main moves, a car fails or a pull request is pushed to.

## Move slow suites to a nightly run

A suite that is too slow for every pull request can run once a night. A schedule entry's `stages` list restricts that run to the stages it names, and `when.events: [schedule]` keeps the suite out of push and pull request runs. `concurrency` with `cancel_in_progress` cancels a branch's older run when a newer commit arrives, so you do not wait for a run of a commit that is already out of date.

```yaml
apiVersion: ankra.io/v1
kind: Pipeline
metadata:
  name: shop
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  schedule:
    - cron: "0 3 * * *"
      branch: main
      stages: [checkout, e2e-all-browsers]
concurrency:
  group: "${{ ankra.repository.name }}-${{ ankra.ref }}"
  cancel_in_progress: true
defaults:
  network: egress-https
stages:
  - name: checkout
    kind: checkout
  - name: test
    kind: run
    image: node:24
    run: corepack enable && pnpm install --frozen-lockfile && pnpm run test
    needs: [checkout]
  - name: e2e-all-browsers
    kind: run
    image: mcr.microsoft.com/playwright:v1.56.0-noble
    run: corepack enable && pnpm install --frozen-lockfile && pnpm run e2e --project=all
    needs: [checkout]
    when:
      events: [schedule]
```

Name every stage the subset needs, `checkout` included: a stage whose need is left out of the subset is skipped. A cancelled older run is shown as **Superseded** in grey, with a neutral commit status and no failure notification.

## Why a skip never hides a failure

A path filter only leaves a stage out when Ankra has the complete list of files the change touched. Whenever it cannot be sure, the stage runs, and the run's `paths_unverified` says why.

| Situation | What Ankra does |
|---|---|
| The provider could not be read, or the event has no file list | Nothing is skipped for its paths (`provider_error`, `unsupported_provider`) |
| More than 300 files changed | Nothing is skipped for its paths (`truncated`) |
| The push created the branch | Nothing is skipped for its paths (`branch_created`), so a new release branch runs its tests |
| The push rewrote the branch's history | Nothing is skipped for its paths (`forced_push`) |
| An earlier push to the branch was cancelled or failed | On GitHub, a push's files are counted from the last push run on that branch that succeeded within 30 days, so the earlier push's files are still in the list |
| The change edits `.ankra/pipeline.yaml` | Every path filter is set aside and every stage runs, because the edit can change what a filter guards (`plan_definition_changed`) |
| A pull request is retargeted to another base branch | It is planned again against the new base, and the new check replaces the old one |
| An `if:` condition can only be decided when its step starts | It reads the run's stored file list. When that list is incomplete, the stage runs unless the answer does not depend on the list |
| A merge train run | It carries the pull request's file list. A train run with nothing to run passes, and is never promoted from |
| A push asks to promote | Only an identical tree, tested under the same approved authority, with the gate's own digest, within 72 hours and never from a fork. Anything else builds in full |

On GitLab, a push's file list is the files its own commits touched, including after a force push. On Bitbucket Cloud, a push carries no file list, so path filters skip nothing on pushes there. Pull requests are filtered on every provider, up to 300 changed files.

## Preview a change before you commit it

`ankra pipeline validate` plans your pipeline for a push and a pull request without running anything. Add `--changed-file` for each file a change would touch, and the path filters decide for real:

```bash
ankra pipeline validate --application my-app \
  --spec-file .ankra/pipeline.yaml \
  --changed-file web/app.ts
```

For the affected-only pipeline above, the end of the output is a table of every stage against every event:

```text
╭──────────┬───────────────────┬────────────────────╮
│ STAGE    │ PUSH              │ PULL_REQUEST       │
├──────────┼───────────────────┼────────────────────┤
│ checkout │ run               │ run                │
│ test-web │ run               │ run                │
│ build    │ run               │ run                │
│ scan     │ run               │ run                │
│ gate     │ run               │ run                │
│ publish  │ run               │ skip: event_filter │
│ test-api │ skip: path_filter │ skip: path_filter  │
╰──────────┴───────────────────┴────────────────────╯
```

The command also reports every refusal and warning from the sections above, such as a pattern that can match no file or an affected-only stage that would be unsafe, and exits non-zero only when the pipeline cannot be planned. Run it with a few typical changes, a documentation edit, one component, two components, before you commit a new filter.
