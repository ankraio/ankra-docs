Connect a code host and Ankra AI reviews your pull requests: it reads the diff, posts a verdict with its findings, pins each finding to the line it is about, and answers when somebody mentions it in a comment.

Everything is set up on one page: **Ankra AI → Gateway connections** (`/next/ai/settings/gateway`), in its **GitHub**, **GitLab** and **Bitbucket** sections. What the reviews said afterwards is on **Ankra AI → Code reviews** - see [Read what the reviews found](#read-what-the-reviews-found).

<Info>
**Nothing runs until you switch it on.** Every capability on a new connection is off. Installing the GitHub App, connecting a GitLab token, or authorising a Bitbucket workspace gives Ankra access, and nothing more: no review is posted, no mention is answered, and no preview is deployed until an owner or admin, or another role with the `ai.manage` permission, turns the switch on for that connection or for a single repository.
</Info>

## Before you start

- **A role that may manage Ankra AI.** The `owner` and `admin` roles hold the `ai.manage` permission, and a custom role can be given it. Members can open **Gateway connections** and read every setting, and the page says **Your role can look but not change. Owners and admins connect apps, choose AI modes and set review rules.**
- **To connect GitLab, a role that may write credentials.** Without it, the **Connect GitLab** card is not shown.
- **To read Code reviews, a role that can read the organisation.** Without it, the page reads **Your role cannot read code reviews**.

## Connect a provider

Each provider has its own section on **Gateway connections**.

<Tabs>
  <Tab title="GitHub">
    In the **GitHub** section, press **Install the GitHub App**. GitHub asks which account and which repositories the App may reach, then brings you back to **Gateway connections**.

    The installation now shows as a card in the **GitHub** section. One account can carry several installations, and each is configured separately; to add another, press **Install the GitHub App** at the top of the section. See the [GitHub integration](/integrations/github) for the permissions the App requests and how to change which repositories it covers.

    GitHub is the only provider that also offers [PR preview environments](/guides/pr-preview-environments).
  </Tab>
  <Tab title="GitLab">
    In the **GitLab** section, fill in the **Connect GitLab** card: an optional **Name**, the **GitLab address** (leave it empty for gitlab.com, fill it in for a GitLab you run yourself, like `https://gitlab.example.com`), and the **Access token**. Press **Connect GitLab**.

    The card asks for a token with the `read_api` and `read_repository` scopes, which is what Ankra validates against and enough to *read* your merge requests. Posting the review is a write, so use a token with the `api` scope unless you deliberately want a read-only connection.

    A dialog, **Copy the webhook secret now**, shows the **Webhook address** and the **Webhook secret**. This is the only time Ankra shows the secret. Add the webhook to each GitLab project, for merge request, comment and push events, then tick **I have put it in GitLab or stored it somewhere safe** and press **Done**. The [GitLab integration](/integrations/gitlab) walks through the webhook.

    The connection now shows as a card in the **GitLab** section, with its **GitLab webhook** address and the masked secret. **Regenerate the secret** stops the current secret at once; **Disconnect** stops AI reviews and GitOps sync through this token.
  </Tab>
  <Tab title="Bitbucket Cloud">
    In the **Bitbucket** section, press **Connect Bitbucket** (or **Connect a workspace** once one is connected) and authorise Ankra against your Bitbucket Cloud workspace. Bitbucket brings you back afterwards, and the workspace shows as a card in the section.

    Webhooks are registered for you: switching AI review or mention replies on registers one on every repository it covers - every repository the credential can see, for the **All repositories** row - and a repository found later gets its own within minutes. Switching a lane off leaves the webhook in place.

    The webhooks carry pull request events only when the credential grants Bitbucket's `pullrequest` scope. A credential connected before Ankra asked for it has to be reconnected; until then GitOps sync works and reviews and mentions receive nothing. See the [Bitbucket Cloud integration](/integrations/bitbucket-cloud#granting-the-pull-request-permission) for the OAuth scopes, their purpose, and reconnecting.
  </Tab>
</Tabs>

Each installation, credential or workspace is one card. Its subtitle says which lanes the default row runs (**AI review**, **Replies to mentions**, **Pull request previews**) and how many **repository rules** differ from it, so a card reading **Nothing is switched on** is doing exactly that. A card with nothing switched on opens folded; press **Show settings** to open it.

## AI mode: Ask or Agent

Every connection carries an **AI mode** that bounds what Ankra AI may do when it is talked to from that repository. It is separate from the capability switches: the switches decide *whether* Ankra AI answers, the mode decides *how far* the answer may go. Pick **Ask** or **Agent** at the top of the card.

| Mode | What Ankra AI may do |
|---|---|
| **Ask** | Read-only. It investigates and explains, and can start throwaway workspaces and pull request previews, but never changes existing infrastructure or opens a pull request. |
| **Agent** | It can act. It opens fix pull requests on its own, and the pull request is where you review it. Other changes that remove or replace something still ask first. |

A connection in Agent mode is marked **Can act**. Automatic review events themselves stay read-only whatever the mode: a review comments, and a proposed fix arrives as a separate pull request you review like any other.

On GitLab and Bitbucket Cloud, Ankra cannot open a pull request, so an Agent-mode reply proposes the fix with a branch name and a commit message instead of offering one.

### Merge when green

A GitHub installation also carries a **Merge when green** switch beside the mode. With it on, `@ankraai merge when green` in a pull request comment, the merge button in Ankra and the merge tool ask Ankra to merge a pull request once its pipeline passes, its reviews are clear and it is approved. A comment is acted on only when it comes from a member of your organisation who linked GitHub through Ankra, holds the `pipelines.operate` permission, and is the pull request's author, can write to the repository on GitHub or is an organisation administrator. A pull request from a fork is never merged this way. A `Depends-on` line in the description holds the merge until the pull request it names is merged.

<Warning>
**Merge when green** needs the **Agent** mode too. While the mode is **Ask**, the card says **This needs Agent mode: merge requests are refused while the AI mode is Ask.**
</Warning>

## The repository table

Each card opens on a **Repositories** table of every capability, with two kinds of row.

- **All repositories**, marked **Default**, is the first row. It carries the connection-wide values, and every repository with no rule of its own follows it.
- **A repository rule** is one row per repository that should differ. Under the table, choose the repository in **Repository** (or type its path, `owner/repository`, when Ankra cannot list the installation's repositories) and press **Add rule**. The new row starts as a copy of the default row. Press the **×** at the end of a row to remove its rule; the repository follows the default row again.

Every control saves the moment you change it. There is no separate save button on this table. Past eight rules, a **Search rules** field appears and the rest fold behind **Show all** *n* **rules**. **What each column does**, under the table, repeats the column help.

To manage rules from the terminal or a script instead, an organisation admin can use the CLI:

<CliVersion since="0.21.1" />

```bash
ankra org ai-review repos list
ankra org ai-review repos set my-org/my-repo --review --mentions --max-reviews-per-pr 3
ankra org ai-review repos unset my-org/my-repo
```

`set` changes only the switches you pass (`--review`, `--mentions`, `--previews`, `--model`, `--review-drafts`, `--max-reviews-per-pr`; turn one off with `=false`) and keeps the rest of the repository's rule, or the default row's values when the repository has no rule yet. The connection is found from the repository; when that is ambiguous, pass `--binding <provider>/<id>` as `list` shows it. `list --reachable` also lists the repositories each GitHub App installation can see, and `unset` removes the rule so the repository follows the default row again. Listing needs organisation membership; `set` and `unset` need an organisation admin.

Over the API, an organisation admin's [API token](/reference/tokens) can send `PUT /api/v1/org/ai-gateway/scm-bindings/{provider}/{binding_external_id}/repo-overrides` with `repo_full_name`, `ai_review`, `mention_replies` and `pr_previews` to add or change a rule, and `DELETE` on the same path with `?repo_full_name=<owner>/<repository>` to remove it. `GET /api/v1/org/ai-gateway/scm-bindings` lists each connection's `binding_external_id` and its current rules; the [API Reference](/api-reference/introduction) has the full request shape.

<Note>
Rules are keyed by the repository path, lowercased. For GitLab, use the full project path including subgroups, up to 20 levels deep - for example `my-group/my-subgroup/my-project`.
</Note>

### What each column means

| Column | What it does | Default |
|---|---|---|
| **AI review** | Reviews every opened or updated pull or merge request automatically, and posts what it finds as comments. | Off |
| **Review drafts** | Also reviews draft pull requests on every push. When off, a draft is skipped until it is marked ready. | Off |
| **Automatic reviews per pull request** | Caps how many automatic reviews one pull request receives over its whole life, requested ones included. Leave it empty for no limit (the field reads **No limit**); the highest cap is 100. See [The two budgets](#the-two-budgets). | 3 |
| **Replies to mentions** | Lets Ankra AI answer in the thread when somebody writes `@ankraai` in a pull request comment. | Off |
| **Pull request previews** | Deploys every pull request to a temporary [preview environment](/guides/pr-preview-environments) with its own address, updated on each push and removed when the pull request closes. GitHub only. | Off |
| **Review model** | Which model the review runs on: one from your organisation's [model list](/platform/ai-provider), or any exact model from the searchable list. The default row offers **Ankra’s default**; a repository row offers **Follow the default**, naming the default row's model. | **Ankra’s default** |

When nothing picks a review model - not the repository's [Application AI settings](/platform/application-ai), not a repository rule, not the default row - the review runs on your organisation's **AI code review** model under [Models for each AI feature](/platform/ai-provider#models-per-function). Unless an admin changes it, that follows the **Think** tier: Claude Haiku 5.5 on Ankra's provider, or your own Think model when the organisation runs on its own key. A model list an admin has edited keeps the Think model it was saved with. Every pull request gets that model, whatever the size of its diff.

<Tip>
The cap and the draft switch gate *automatic* reviews only. Asking for a review in a comment always runs one, though it still counts toward the cap - see [Talking to the review](#talking-to-the-review) below.
</Tip>

## Review instructions

The **Review instructions** section, below the code hosts on **Gateway connections**, lists each connected installation with the first line of its instructions, or **No instructions yet**. Press **Add instructions** (or **Edit** when it has some) to open **Review instructions for** *installation*. It is what the reviewer should keep in mind on this installation: which areas to weigh heavily, which conventions to enforce, what language to write in.

```text
Write review comments in Swedish.
Pay extra attention to Terraform and RBAC changes.
Our Helm values must never hardcode an image tag.
```

Press **Save instructions**. The row now shows the first line of what you wrote.

- Up to 4,000 characters per installation; the field counts them. Past the cap it says **Shorten it to 4000 characters or fewer to save.** and **Save instructions** stays disabled.
- The instructions steer what the review focuses on and how it is phrased. They cannot override Ankra's own rules or the review format.
- Every repository on the installation follows them. An application that customised its own **Pull request review** under [Application AI settings](/platform/application-ai) keeps the instructions set there instead, because customising an activity pins the whole activity.
- A row that reads **Ankra cannot keep instructions for this installation yet** has no **Add instructions** button: set the instructions on each application's settings instead.
- Only a role with the `ai.manage` permission, which owners and admins hold, can change them.

## What a review posts

One comment per pull request, updated in place on every re-review, never a stream of new ones. Where a pipeline, a preview, or a promotion is also running, they share that comment as separate sections.

The review section is laid out like this:

```markdown
## Ankra AI review

**Verdict: comments.**

<two to four sentences on the change as a whole>

### Findings

- **[high] <short title>** (`path/to/file.go:42`)
  <what is wrong, why it matters, and what to do instead>

---
_Reviewed commit abc1234. This review is read-only and advisory._
```

| Verdict | What it means |
|---|---|
| **looks good** | The change looks safe. |
| **no findings** | The review ran and surfaced nothing. |
| **comments** | Worth reading, but nothing the reviewer calls a probable defect. |
| **changes requested** | A probable bug or a security issue. |
| **unavailable** | The model's answer could not be read. Push again or mention Ankra to re-run it. |

Findings carry a severity of **high**, **medium**, or **low**, and a review keeps to the issues that matter - at most eight. A finding that names a line is also posted as a comment pinned to that line, so it is read where the decision is made. Each inline comment carries an invisible fingerprint of its file and title, so re-reviewing a pull request never restates a finding it has already pinned, even if the line has drifted or the wording changed.

### How the review reads a change

- **Machine-written files are dropped before the diff is measured.** Lockfiles, minified bundles, source maps, and generated protobuf never reach the model. Beyond keeping the cost down, this is what stops a large lockfile from crowding the real change out of the review. Set **Ignore paths** per repository under [Application AI settings](/platform/application-ai) to drop more.
- **Uncertain findings are settled, not guessed.** When a finding rests on something the diff does not show, Ankra reads the file and either restates the finding as a definite defect or drops it. Where that check cannot run, the finding is posted with its uncertainty visible.
- **A truncated answer says so.** If the model runs out of output budget mid-answer, what arrived is posted under an explicit incomplete-review notice rather than as a finished review that found nothing.
- **The diff is treated as text, never as instructions.** An instruction planted in a diff or a pull request description asking the reviewer to act, change role, or reveal data is refused.

## What the review reads beyond the diff

Before it answers, the review also reads the code a change can break outside its diff: other callers of what changed in the same repository, files in related repositories that still use a name the change removes, and the companion pull request that carries the other half of a cross-repository change. A `Depends-on:` line in the description declares which pull request has to merge first.

On GitHub, when the diff changes a container build file (`Dockerfile`, `Dockerfile.*`, `*.dockerfile`, `Containerfile` or `Containerfile.*`), the review also reads the workflows under `.github/workflows` that build an image, at the reviewed commit. It compares what they copy into the image and the environment variables they set with the changed file, and searches the code for the items the changed file no longer provides. The comparison is textual, so an item may still arrive another way, such as a volume or a download at startup.

How each of those works, how to relate two repositories, and what an empty result does and does not mean are covered in [Cross-repository review](/platform/ai-code-review-cross-repo).

## Talking to the review

Mention `@ankraai` in a pull request or merge request comment and Ankra AI answers in the thread, with the change as context. This needs **Replies to mentions** on for that repository.

- **Ask a question.** "@ankraai does this handle the empty case?" gets an answer grounded in the diff, and a plain statement when the diff does not contain the answer.
- **Ask under an inline comment** and the question is read as being about that line.
- **Ask for a review.** A mention is a direct request from a human, so it is never filtered by draft state, branch scope, either review budget, or the documentation-only and dependency-bot skips. It runs even on a draft and even past the **Automatic reviews per pull request** cap, and it is counted against both budgets.

On GitHub and GitLab, Ankra reacts to your comment with 👀 as soon as it picks the mention up, so you can tell a slow review from one that never started. Bitbucket Cloud has no comment reactions, so there the reply itself is the first sign; it is posted as a reply to your comment.

<Note>
Only `@ankraai` summons the review. It is matched as a whole word, so `@ankraai-bot` and an address like `someone@ankraai.example.com` are ignored.
</Note>

## When a review does not run

A skipped review is normal and costs nothing. Ankra decides before any model call, in the order below, and stops at the first reason that applies. On GitHub the reason is written to the **Ankra AI review** check run on that commit: its title reads **Review skipped** followed by the reason, and its summary says what lifts it. The check run is the one place the decision is recorded.

| Check-run title | Why | What to change |
|---|---|---|
| **Review skipped - AI review is switched off for this repository** | **AI review** is off on the default row and on any rule covering the repository. | Turn the switch on, on the default row or on that repository's rule. |
| **Review skipped - draft pull request** | The pull request is a draft and **Review drafts** is off. | Turn **Review drafts** on, mark the pull request ready, or mention `@ankraai`. |
| **Review skipped - target branch out of scope** | The pull request review's branch patterns exclude the target branch. | Widen **Target branches** under [Application AI settings](/platform/application-ai), or mention `@ankraai`. |
| **Review skipped - head already reviewed** | A review of exactly this commit is already on the pull request. | Push a new commit. Nothing was lost. |
| **Review skipped - superseded by a newer push** | A later push replaced this commit before its review started. | Nothing. The newest head gets the review. |
| **Review skipped - daily review budget reached** | The repository has used its **Maximum runs per day** since midnight UTC, across every pull request. | Raise or clear **Maximum runs per day** under [Application AI settings](/platform/application-ai), or mention `@ankraai`. |
| **Review skipped - per-pull-request review budget reached** | This pull request has used its **Automatic reviews per pull request** allowance over its lifetime. | Raise or clear **Automatic reviews per pull request** on the repository table, or mention `@ankraai`. |
| **Review skipped - nothing to review** | Every file the pull request changes is documentation (Markdown, or under `docs/`), a dependency lockfile, generated code, or a path the review ignores. | Mention `@ankraai` to have it reviewed anyway. |
| **Review skipped - dependency update by a bot** | A dependency-update bot such as Dependabot or Renovate opened the pull request, and it changes only dependency manifests and lockfiles. | Mention `@ankraai` to have it reviewed anyway. |

A skipped head is not retried. Nothing on Ankra's side re-queues a commit it declined; the next push is a new head, judged afresh against the same switches and counts. So once a pull request is over its budget, every later push to it is skipped until the budget changes.

### The two budgets

Two counters can decline a review, and they are set in different places.

| Budget | **Automatic reviews per pull request** | **Maximum runs per day** |
|---|---|---|
| Counts | Reviews of one pull request over its whole life, keyed by the pull request number. A re-cut pull request starts at zero. | Reviews of the whole repository since midnight UTC, across every pull request. A brand-new pull request can be declined on its first push. |
| Default | 3 | 200 a day |
| No cap | Leave the field empty, or `0` | `0` |
| Where | The repository table on **Gateway connections**, per repository or on the default row. Owners and admins only. | The **Pull request review** activity under [Application AI settings](/platform/application-ai). |
| Applies | From the next push. | From the next push. |

The daily budget is checked first, so a repository over both reads **daily review budget reached** on its check run. Both counters include reviews somebody asked for with `@ankraai`: a requested review runs past either budget, and it is still counted against both.

A completed review of a commit replaces any earlier **Review skipped** on that commit's check run, so a review requested with `@ankraai` clears a check that a budget had concluded.

## Read what the reviews found

**Ankra AI → Code reviews** (`/next/ai/code-reviews`) shows what Ankra AI said on every pull request it reviewed, and what the authors did about it. **Review settings**, at the top, opens **Gateway connections**.

1. Narrow the view with the **Repository** list (**Every repository** by default), the period (**Last 7 days**, **Last 30 days**, **Last 90 days** or **All time**; **Last 30 days** by default) and the verdict chips (**Every verdict**, **Approved**, **Commented**, **Changes requested**). The address keeps the view, so you can share it.
2. Read the **Summary**: **Pull requests reviewed**, **Findings raised**, **Acted on** (the share of judged findings whose code changed) and **Repositories covered**. With more than one repository in view, **By repository** lists each one; press a repository to narrow the page to it.
3. In **Reviews**, newest first, each row shows the **Pull request**, its **Verdict**, its **Findings** and when it was **Reviewed**. Press **Show more reviews** for older ones. Open a row to read that review.

A review's page shows the verdict, **What Ankra AI said**, each finding with its severity, the file and line it points at, and what became of it, then **Details**: the **Repository**, the **Code host**, the **Commit reviewed** and the **Model**. **Open pull request** opens it on the code host.

| What became of a finding | What it means |
|---|---|
| **Acted on** | The code it pointed at changed before the pull request merged. |
| **Left as is** | The code it pointed at was unchanged when the pull request merged. |
| **Could not tell** | Ankra could not tell whether the code changed. |
| **Closed without merging** | The pull request closed without merging, so the finding was not judged. |
| **Not judged yet** | Judged when the pull request merges. Findings not pinned to a line are not judged. |

When nothing was reviewed over **All time**, the page reads **Ankra AI has not reviewed a pull request yet** and offers **Turn on AI review**, which opens **Gateway connections**.

## Per-application overrides

The repository table on **Gateway connections** sets your organisation's defaults. An [application](/concepts/applications) connected to a repository can override them under **Applications → &lt;your application&gt; → Settings → Who runs it**, in **On your pull requests**, which also sets target branches, ignore paths, the daily budget and the input-character budget. Both surfaces read the same stored settings, so they never disagree. See [Application AI settings](/platform/application-ai).

## Cost

A review is a model completion, billed to your organisation like any other AI usage. Four things keep it bounded, and all four are yours to set:

1. **Every lane is off until you turn it on**, per connection or per repository.
2. **Automatic reviews per pull request** caps the reviews one pull request can accumulate.
3. **Review model** picks what a review costs. With nothing picked, the organisation's **AI code review** model applies.
4. **Ignore paths** and **Maximum input characters**, under [Application AI settings](/platform/application-ai), bound how much of a diff one review reads.

Reviews already spent appear in your AI usage - see [Usage and the free allowance](/platform/ai-provider#usage-and-the-free-allowance).

## Permissions

Connecting a provider, changing any switch or AI mode, and editing the review instructions need the `ai.manage` permission, which owners and admins hold. ## Troubleshooting

| Symptom | What to check |
|---|---|
| No review appears on a new pull request | Is **AI review** on for that repository - the default row *and* any rule covering it? A rule wins over the default row. Then read the **Ankra AI review** check run on the commit: its title names the [skip reason](#when-a-review-does-not-run). |
| The connection card says **Nothing is switched on** | Every lane is off on the default row and on every rule. Nothing will run for this installation until one is switched on. |
| A repository is missing from the **Repository** list under the table | The list holds what the installation can actually see. For GitHub, add the repository to the App installation. When Ankra cannot list the repositories, the field is a text box: type `owner/repository`. |
| Reviews run but mentions go unanswered | **Replies to mentions** is a separate switch from **AI review**, and mentions must spell `@ankraai`. |
| A pull request that only changes docs or lockfiles gets no review | That is the **nothing to review** skip. Mention `@ankraai` to have it reviewed anyway. |
| The review says **Verdict: unavailable** | The model's answer could not be read. Push a new commit or mention `@ankraai` to re-run it. A recurring one usually means the selected review model's output budget is too small; pick a larger model. |
| The review says it is incomplete | Same cause, caught mid-answer: the model stopped at its output ceiling. Re-run it, and consider a model with a larger output budget. |
| Findings repeat on every push | They should not: inline findings are fingerprinted and deduped. The summary comment does restate every finding in full by design, so a reader who only opens the conversation tab still sees the whole review. |
| GitLab reviews stop after a secret rotation | Regenerating the webhook secret invalidates the old one immediately. Update the hook in GitLab with the new secret. |
| Bitbucket pushes sync, but no review or mention reply ever runs | The credential does not grant Bitbucket's `pullrequest` scope, so its webhooks carry pushes only. Reconnect it - see [Granting the pull request permission](/integrations/bitbucket-cloud#granting-the-pull-request-permission). |
