<Note>
Cluster settings allow you to monitor connectivity, configure agent behaviour, perform maintenance operations, and manage the cluster lifecycle.
</Note>

## Accessing Cluster Settings

1. Navigate to your cluster from the sidebar.
2. Click **Settings** in the cluster navigation.
3. Select **General** to access connectivity, agent, and maintenance settings.

---

## Connectivity

Monitor the health of your cluster's connection to the Ankra platform.

### Agent Status

The Ankra Agent is a lightweight component deployed in your cluster that enables communication with the platform.

| Status | Description |
|--------|-------------|
| **Connected** | Agent is online and communicating normally |
| **Disconnected** | Agent is not responding. Check your cluster's network |
| **Outdated** | A newer agent version is available |
| **Error** | Agent encountered an issue. Check logs for details |

### Agent Version

View the currently installed agent version and check if updates are available.

<Steps>
  <Step title="Check Version">
    The **Connectivity** card shows your current agent version.
  </Step>
  <Step title="Upgrade if Available">
    If a newer version is available, click **Upgrade Agent** to update manually.
  </Step>
</Steps>

<Tip>
Enable auto-upgrade to automatically keep your agent up-to-date. See [Agent Settings](#agent-settings) below.
</Tip>

### Kubernetes Watch Status

The Watch service monitors Kubernetes resources and syncs state to the platform. The status indicator shows:

| Status | Description |
|--------|-------------|
| **Synced** | All resources are synchronized |
| **Syncing** | Synchronization in progress |
| **Error** | Sync failed. Click to view details |

## Agent Settings

Configure how the agent behaves on this specific cluster.

### Auto-upgrade Agent

Whether the platform upgrades this cluster's agent for you depends on two switches, and both must allow it:

- **Auto-upgrade Agents** in **Organisation Settings** → **General**. It is on by default for organisations created since 7 September 2026; older organisations turn it on there. While it is off, no cluster in the organisation is upgraded automatically.
- **Disable Auto-upgrade** in the cluster's **Settings** → **General**. Off by default; turn it on to keep this one cluster at its current agent version while the rest of the organisation upgrades.

## Maintenance

Perform maintenance operations on your cluster.

### Generate an installation command

Generate a fresh agent installation command, for example to reinstall the agent or move it to a new cluster token.

<Steps>
  <Step title="Access Maintenance">
    Go to cluster **Settings** → **General** and find the **Maintenance** card.
  </Step>
  <Step title="Generate the command">
    Click **Generate command**.
  </Step>
  <Step title="Run it">
    Copy the installation command it shows and run it against your cluster.
  </Step>
</Steps>

### Sync All Resources

Force a full synchronization of all Kubernetes resources from your cluster to the platform.

<Steps>
  <Step title="Access Maintenance">
    Go to cluster **Settings** → **General** and find the **Maintenance** card.
  </Step>
  <Step title="Trigger Sync">
    Click **Sync All Resources**.
  </Step>
  <Step title="Monitor Progress">
    Watch the Kubernetes Watch Status indicator for sync completion.
  </Step>
</Steps>

**When to sync manually:**

- After network issues that may have caused missed updates
- When resources appear out of sync in the platform
- After bulk changes to Kubernetes resources outside of Ankra

## Power schedules

The **Power schedules** card on **Settings** → **General** stops and starts the cluster automatically - one-off at a chosen time, or repeated on a cron expression, for example to park a development cluster on weekday evenings and bring it back each morning. It is shown for the same self-managed providers that support manual [Stop and Start](#stop-cluster).

See [Power Schedules](/platform/cluster-power-schedules) for the full walkthrough.

  <Step title="Connect Repository">

  </Step>

| Status | Description |

## Kubernetes Settings

Monitor Kubernetes resource synchronization status in detail.

### Accessing Kubernetes Settings

1. Navigate to your cluster → **Settings** → **Kubernetes**
2. View the resource sync status table

### Resource Sync Status Table

The sync status table shows synchronization details for each Kubernetes resource type:

| Column | Description |
|--------|-------------|
| **Resource Type** | The Kubernetes resource kind (Deployments, Services, etc.) |
| **Status** | Current sync state for this resource type |
| **Resource Count** | Number of resources of this type tracked |
| **Last Sync** | When this resource type was last synchronized |
| **Errors** | Number of sync errors (if any) |

### Sync Status Values

| Status | Description |
|--------|-------------|
| **Synced** | All resources of this type are synchronized |
| **Syncing** | Synchronization is currently in progress |
| **Stale** | Resources may be out of date. Sync pending |
| **Error** | Sync failed for some resources. Check error messages |
| **Disconnected** | Cluster is offline. Sync unavailable |
| **Initializing** | First-time sync in progress |

### Table Features

- **Auto-refresh**: The table updates automatically every 10 seconds
- **Filtering**: Filter by resource type or status
- **Sorting**: Click column headers to sort
- **Error Details**: Expand error rows to see specific error messages

### Offline Cluster Warning

When a cluster is offline, a warning banner appears indicating that Kubernetes settings are unavailable until the cluster reconnects.

### Refreshing Sync Status

Click **Refresh** to manually trigger a status update. This fetches the latest synchronization state from the cluster.

## Audit

The **Audit** tab in cluster **Settings** lists every manual action performed on this cluster - who did it, what it was, and when. It is the per-cluster view of the organisation [Audit Log](/guides/audit-log).

Recorded actions include:

- **Lifecycle** - create, import, start, stop, upgrade, and terminate
- **Scaling** - worker scaling, node group create / scale / edit / delete, autoscaling changes, control plane count and instance type, bastion resize
- **Nodes** - manual node restarts
- **Stacks** - deploy, update, redeploy, retry, and delete, including addon configuration and settings changes
- **Helm** - agent-side release upgrades and rollbacks

Each entry shows the acting member's email, the action, the resource it touched, the timestamp, and expandable structured details (for example the previous and requested worker counts of a scale).

When a stack or cluster edit results in a commit to the cluster's [GitOps repository](/concepts/gitops), the entry links straight to that commit, so the platform action and the exact repository change it produced sit side by side.

**View in organisation audit log** opens the organisation [Audit Log](/guides/audit-log) with this cluster already selected as its filter, where the same entries sit alongside the organisation-level events - sign-ins, invitations, role changes - that this tab does not show. Going the other way, each row of the organisation log names its cluster and links back here.

**Export CSV** and **Export JSON** download this cluster's entries, honouring the search on screen. The download is the organisation export narrowed to this cluster, so both views report the same entries.

Viewing the tab requires the audit read permission, held by **owners** and **admins** by default and grantable to [custom roles](/guides/roles-and-access). Entries are append-only and cannot be edited or deleted.

## Danger Zone

<Warning>
Actions in the Danger Zone are destructive. Some operations cannot be undone.
</Warning>

### Move to another organisation

Move the cluster into another organisation you administer. The cluster keeps its id, agent, executions, resources, security findings, insights, DNS records and variables; nothing on the cluster itself changes.

Only an **organisation admin** can do this, and you must be an admin of **both** the current organisation and the destination. The destination picker only lists organisations where you hold the admin or owner role.

Only **imported clusters** can be moved today. Ankra-provisioned and managed Kubernetes clusters use a provider credential that belongs to the organisation that created them, so the platform refuses to move them; the action is not offered for those kinds.

**What moves with the cluster:**

- The agent and its sessions, so the cluster stays connected
- Executions, stacks, add-ons and the resource history the engine drives
- Kubernetes resource cache, security findings, insights, cost and security snapshots
- DNS records, network identity, cluster variables and incidents

**What is detached from the current organisation** (recreate it in the destination if you need it):

- Cluster access grants, cluster-scoped role assignments and kube tokens issued to members of the current organisation
- Notification routes, mutes and subscriptions for the cluster
- Security report schedules and trusted AI actions
- Cluster group memberships, links to this organisation's platform resources (registries, credentials), AI context repositories and the GitOps repository connection

**What stays with the current organisation:** billing and usage accounting, the audit trail, recorded terminal sessions, chat conversations, AI tickets, applications deployed from its application registry, and support tickets.

<Steps>
  <Step title="Access Danger Zone">
    Go to cluster **Settings** → **General** and scroll to **Danger Zone**.
  </Step>
  <Step title="Move cluster">
    Click **Move cluster**, choose the destination organisation and type the cluster name to confirm.
  </Step>
  <Step title="Open the cluster in its new organisation">
    Choose **Open in &lt;organisation&gt;** to switch organisations and land on the cluster, or **Stay here**.
  </Step>
</Steps>

The move is refused while operations are running on the cluster, while the cluster is a member of a cluster mesh, while it has DNS zones bound to this organisation (a published cluster domain or custom DNS zones - remove them first; the destination can publish its own), for playground and sandbox clusters, for provisioned and managed clusters, and when the destination already has a cluster with the same name. The reason is shown in the dialog.

The same action is available from the cluster's **⋯** menu on the clusters list and the cluster overview (**Move to organisation**), from the CLI with `ankra cluster move <cluster> --organisation <id|slug|name>`, and from Ankra AI with the `move_cluster_to_organisation` tool, which asks for the same confirmation.

<Info>
Organisation-level credentials, Helm registries and git connections are not copied, and the cluster's links to them are removed. Deployed workloads keep running, but re-link registries and credentials, reconnect the GitOps repository, and reconnect any metrics or log sources in the destination organisation before the next deploy that needs them.
</Info>

### Disconnect Cluster

Remove the cluster from Ankra without affecting running workloads.

**What happens:**

- The cluster is removed from the Ankra platform
- Running workloads continue to run
- ArgoCD and other installed components remain
- GitOps synchronization stops

<Steps>
  <Step title="Access Danger Zone">
    Go to cluster **Settings** → **General** and scroll to **Danger Zone**.
  </Step>
  <Step title="Disconnect">
    Click **Disconnect Cluster**.
  </Step>
  <Step title="Confirm">
    Confirm the disconnection.
  </Step>
</Steps>

<Info>
You can reconnect a disconnected cluster by importing it again with a new token.
</Info>

### Stop cluster

Release the compute for a self-managed cloud cluster while keeping the cluster registered in Ankra. The cluster moves to a **stopped** state.

**What happens on Hetzner, OVHcloud, UpCloud, DigitalOcean, Proxmox VE and HPE Morpheus (k3s and kubeadm clusters):**

- Ankra first captures the cluster's state - an encrypted snapshot of etcd - and uploads it to your backup vault (or to the Ankra-managed default vault when you have registered none; the object is ciphertext only, and the key stays in Ankra's secret store)
- Only once the snapshot is stored are the virtual machines terminated at the provider
- Cloud block volumes behind PersistentVolumes are never deleted by a stop
- The cluster record, credentials, stacks and configuration history are preserved in Ankra
- The capture runs as a **Cluster State Snapshot** operation; if it fails, the cluster stays running and nothing is torn down

Untick **Preserve cluster state** in the dialog (or pass `preserve_state=false` on the API and `--preserve-state=false` on the CLI) to tear the cluster down without a snapshot. Everything stored in the cluster itself - Secrets, ConfigMaps, custom resources and the bindings between claims and volumes - is then lost, and only what Ankra deploys from its own configuration comes back. A stop with **Force** never captures.

**Pausing instead of tearing down (Hetzner, UpCloud and DigitalOcean, k3s clusters):**

Choose **Pause** in the stop dialog (API `mode=pause`, CLI `--mode pause`) to power the servers off and keep them with their disks instead of terminating them. Nothing leaves the machines: etcd, local data and the nodes' identities survive exactly as they are, and **Start cluster** powers the servers back on and resumes Kubernetes without reinstalling anything - the same way a Scaleway or AWS stop always works. Networks, SSH keys and firewalls stay in place too.

The price is that a powered-off server keeps billing at these providers (DigitalOcean at the full droplet rate). Pause when you want a short stop with everything intact - overnight, or while you change the control plane - and tear down when you want to stop paying for the machines. A pause takes no state snapshot (there is nothing to capture) and cannot be combined with **Force**; kubeadm clusters, OVHcloud, Proxmox VE and Morpheus do not offer it yet. While the cluster is paused its API record carries `stop_mode: "pause"`.

**What happens on Scaleway and AWS:**

- The servers are powered off and kept with their volumes, so etcd and the cluster's state survive on their own
- Retained storage, gateways and addresses remain billable while stopped

**What happens on Proxmox VE and HPE Morpheus:**

- The same as above: Ankra captures the state snapshot through the credential's jump host before the virtual machines are terminated.

**Starting again:**

Use **Start cluster** to re-provision the saved topology. You can restore the entire cluster or start only the control plane first. Ankra creates fresh virtual machines with new IPs and installs Kubernetes. Where a state snapshot was captured, the first control plane resets etcd from it instead of bootstrapping an empty cluster (a kubeadm control plane also gets its certificate authorities and service-account keys back, so every token and kubeconfig stays valid, and the other nodes join it afresh), then clears the Node and volume-attachment records of the machines that no longer exist: your Secrets, ConfigMaps, custom resources and persistent volume claims come back, and StatefulSets reattach their existing cloud disks. Untick **Restore the cluster state captured at stop** (API `restore_state=false`, CLI `--restore-state=false`) to start fresh instead.

Stacks and addons configured in Ankra are reconciled either way. A snapshot that was never restored is kept for 90 days; a restored one is kept for 7 more days and then swept.

Stop and Start can also run automatically on a timetable - see [Power Schedules](/platform/cluster-power-schedules).

Both actions are also available from the cluster's **⋯** menu, on the cluster overview and on the clusters list: **Stop cluster** while the cluster is running, **Start cluster** while it is stopped. The menu entries open the same confirmation dialogs as the Danger Zone.

<Note>
Stop and Start are available for self-managed Hetzner, OVHcloud, UpCloud, DigitalOcean, Scaleway, AWS EC2, Proxmox VE, and HPE Morpheus clusters. An AWS cluster stops its instances rather than terminating them, so it keeps its private IPs and root volumes and starts again without a rebuild - see [AWS clusters](/guides/aws-clusters#stopping-and-starting-a-cluster); Hetzner, UpCloud and DigitalOcean k3s clusters get the same behaviour with the **Pause** mode described above.
</Note>

<Tip>
You no longer need to stop a cluster to add control planes: growing from 1 to 3 (or 3 to 5 on Proxmox VE) happens live, and a cluster with three controllers changes its instance type live too. Reducing the count still applies at the next start - see [Control plane](/platform/cluster-nodes#control-plane).
</Tip>

### Terminate Cluster

Permanently remove the cluster and all its cloud resources from Ankra. The cluster cannot be recovered.

<Warning>
This action cannot be undone. All cloud infrastructure will be destroyed and the cluster record will be permanently removed.
</Warning>

**Considerations before terminating:**

- Ensure no active operations are running
- Clean up cloud-provider-managed resources (Load Balancers, Volumes) that Ankra does not track
- Back up stack configurations if needed
- Inform team members who use this cluster

#### Persistent volumes

On Hetzner, OVHcloud, UpCloud, DigitalOcean, Scaleway and AWS EC2, terminating a cluster also deletes its persistent volumes - the cloud volumes the cluster's CSI driver provisioned for its `PersistentVolumeClaim`s - and the data on them. Ankra deletes them only when you accept that, whichever way you delete the cluster:

- **Dashboard.** The **Terminate** and **Delete cluster** dialogs list the volumes by claim and size, and the delete button stays disabled until you tick *I understand that these volumes and their data are deleted*.
- **CLI.** `ankra cluster deprovision` names the volumes and asks `[y/N]` on a terminal. In a script, pass `--accept-volume-data-loss`; `--yes` skips the teardown confirmation but never this one, so without the flag the command stops with exit code 2 and names the volumes. A CLI older than 0.19.0 cannot send the acknowledgement: its deprovision of a cluster with volumes gets the API's `409`, so upgrade it, or delete from the dashboard.
- **API.** `GET /api/v1/clusters/{provider}/{cluster_id}/deprovision-volumes` lists what a delete would remove. `DELETE /api/v1/clusters/{provider}/{cluster_id}?accept_volume_data_loss=true` deletes them with the cluster; without the parameter the delete answers `409` naming the volumes.
- **AI assistant and MCP.** The `delete_cluster` tool is refused until the user has agreed; it names the volumes and asks you first.

This holds forced or not: `--force` (`?force=true`) tolerates unreachable infrastructure and deletes the cluster's load balancers, and never stands in for the acknowledgement.

A cluster with no persistent volumes needs no acknowledgement. When Ankra cannot list a cluster's volumes - it was never connected, or its inventory could not be read - it asks anyway, because any volume the cluster created is still deleted.

A cluster whose `retention_policy` is `retain` (AWS EC2 and Scaleway; `retain` is the default there) keeps its volumes on every terminate, forced or not, and needs no acknowledgement: the dialog and the CLI say which volumes stay in your cloud account, where they keep billing until you delete them. Volumes Ankra cannot show belong to this cluster - attached to a machine it does not own, delete-protected, or labelled `ankra-retain` on Hetzner - are kept and reported too.

<CliVersion since="0.19.0" command="cluster deprovision --accept-volume-data-loss" />

```bash
ankra cluster deprovision <cluster>                            # names the volumes and asks
ankra cluster deprovision <cluster> --accept-volume-data-loss  # for scripts
```
