A cluster's settings are one page each. Open **Infrastructure → Clusters → &lt;your cluster&gt; → Settings** (`/next/clusters/<cluster-id>/settings`): the menu switches to the settings pages, with **Terminate or remove** at the bottom under **Danger zone**. Each page below gives its address, what it changes, the permission it needs and the CLI equivalent.

Some cluster pages are not settings and sit in the cluster's own menu: **Kubectl access** (who may reach the cluster with kubectl, see [Cluster access](/guides/cluster-access) and [Kubeconfig](/guides/kubeconfig)), **Audit log** (who changed what on this cluster, see [Audit log](/guides/audit-log)) and the nodes (see [Manage Nodes and Node Groups](/platform/cluster-nodes)).

## At a glance

<CliVersion since="0.66.0" />

| Page | Address | What it changes | Permission to change | CLI |
|---|---|---|---|---|
| [General](#general) | `settings` | What the cluster is used for, its label and its project | `clusters.write`; `projects.manage` for the project | See [General](#general) |
| [Agent](#agent) | `settings/agent` | Agent upgrades for this cluster | `clusters.write`; `agents.manage` to upgrade now | `ankra cluster agent` |
| [Stop, start and schedules](#stop-start-and-schedules) | `settings/power` | Stopping, starting and power schedules | `clusters.operate`; `clusters.write` for schedules | `ankra cluster <provider> stop`, `ankra cluster power-schedules` |
| [Upgrades and maintenance](#upgrades-and-maintenance) | `settings/maintenance` | Kubernetes version, agent install command, full sync, archive, deployment engine | `clusters.operate` to upgrade and to sync all resources; `agents.manage` for the install command; `clusters.write` for the rest | `ankra cluster upgrade`, `ankra cluster reconcile` |
| [GitOps](#gitops) | `settings/gitops` | The cluster's Git repository, syncs and conflicts | `clusters.write` | `ankra cluster gitops` |
| [Kubernetes sync](#kubernetes-sync) | `settings/kubernetes-sync` | Ankra's copy of the cluster's resources | `clusters.write` | None |
| [Network](#network) | `settings/network` | Internet gateway and the Gateway API | `clusters.write` | `ankra cluster gateway-api` |
| [SSH access](#ssh-access) | `settings/ssh` | SSH keys on the cluster's servers | `clusters.write` | `ankra cluster ssh-keys` |
| [Ankra AI](#ankra-ai) | `settings/ai` | Insights, alert fixes and the code Ankra AI reads | `clusters.write`; `ai.manage` for alert fixes | None |
| [Logs and data](#logs-and-data) | `settings/logs` | Hosted logs and the data policy | `clusters.write` | None |
| [Integrations](#integrations) | `settings/integrations` | Metrics, log store, log viewer, vulnerability scanning, cost estimates | `clusters.write`; also `stacks.write` and `stacks.delete` to save a source | None |
| [Variables](#variables) | `settings/variables` | Cluster variables | `variables.write` | `ankra cluster variables` |
| [Credentials](#credentials) | `settings/credentials` | Nothing; lists the credentials the cluster uses | None | `ankra credentials` |
| [Terminate or remove](#terminate-or-remove) | `settings/terminate` | Deletes, disconnects or removes the cluster | `clusters.delete` | `ankra delete cluster` (imported), `ankra cluster deprovision` (built by Ankra), `ankra cluster managed delete` (managed), `ankra cluster playground destroy` (playground) |

Built-in roles: `clusters.write` and `variables.write` are held by Member, Operator, Admin and Owner; `clusters.operate` by Operator, Admin and Owner; `clusters.delete`, `agents.manage`, `ai.manage` and `projects.manage` by Admin and Owner. Every page tells you when your role cannot change it, for example "Your role cannot sync this cluster. That needs the clusters.write permission." See [Roles and access](/guides/roles-and-access).

## General

`/next/clusters/<cluster-id>/settings`

**Name and use** shows the cluster's **Name**, **Description**, **Used for** and, where it differs, its **Label**. The name and description are set when the cluster is created or imported, and are not changed here.

- **Change what it's used for** opens a dialog with **Used for**: **Production**, **Staging**, **Development** or **Disposable**. Under **Change its label** you can set a **Label**, which Cost budgets and Security use to group clusters. Click **Review change**, then **Save**. Insight grading, notifications and AI remediation follow what a cluster is used for.
- **Confirm it is &lt;purpose&gt;** appears when nobody has chosen the value yet. Confirming records that you chose it; from then on Ankra suggests stopping the cluster at night only if it is not production and is quiet at night.
- **Project** shows the project the cluster is in and moves it to another one. It needs `projects.manage` and appears only when the organisation has projects; see [Set up projects](/guides/set-up-projects).

The portal cannot move a cluster to another organisation. Use `ankra cluster move`:

<CliVersion since="0.73.0" command="cluster move" />

```bash
ankra cluster move my-cluster --organisation <organisation-id-or-slug>
```

You must be an administrator of both organisations. See the [CLI reference](/reference/cli/cluster#ankra-cluster-move) for what moves with the cluster and what is detached.

### Rename the cluster

<CliVersion since="0.78.0" command="cluster rename" />

A cluster can be renamed in place with `ankra cluster rename <cluster> <new-name>`, without rebuilding it. Server and node names, the DNS zone and the GitOps directory keep the old name. A cluster synced with a connected GitOps repository and an Ankra Cloud cluster cannot be renamed: the platform refuses and changes nothing. [Rename a Cluster](/guides/rename-cluster) says what changes and what to update afterwards.

### Power schedules

Stops and starts the cluster on a timetable, on the providers that support stop and start. See [Stop, Start and Power Schedules](/platform/cluster-power-schedules).

## Agent

`/next/clusters/<cluster-id>/settings/agent`

Shows the agent's **Connection**, **Version** (with **Upgrade agent** when a newer one is available), **Last check-in** and **Automatic upgrades**.

- **Turn automatic upgrades off** keeps this cluster's agent on its version until someone upgrades it by hand; **Turn automatic upgrades on** lets the platform roll new versions to it. The organisation setting **Upgrade cluster agents automatically** (`/next/organisation/pipelines`) must also be on.
- **Upgrade agent** upgrades it now. It needs `agents.manage`.
- **Create an agent install command** links to the command on [Upgrades and maintenance](#upgrades-and-maintenance).

When no agent has registered yet, the page says so: on a cluster you imported, the agent registers once its install command has run. See [Cluster agent](/concepts/cluster-agent).

```bash
ankra cluster agent status
ankra cluster agent upgrade
ankra cluster agent auto-upgrade disable
```

## Stop, start and schedules

`/next/clusters/<cluster-id>/settings/power`

**Stop or start now** stops the cluster's servers or starts them again, and **Schedules** does it on a timetable. Only clusters Ankra built or runs at a cloud provider can be stopped. See [Stop, Start and Power Schedules](/platform/cluster-power-schedules).

## Upgrades and maintenance

`/next/clusters/<cluster-id>/settings/maintenance`

| Section | What it does | Permission |
|---|---|---|
| **Kubernetes version** | Choose **Version to upgrade to**, read **Before you upgrade**, then **Review upgrade**. See [Upgrade Kubernetes on a Cluster](/guides/kubernetes-upgrades). | `clusters.operate` |
| **Agent install command** | **Create install command** makes a new agent token and the command that installs the agent again or reconnects it. Commands created before it stop working. | `agents.manage` |
| **Sync all resources** | Applies every stack, add-on and resource Ankra has recorded for the cluster again. Resources that already match stay as they are. | `clusters.operate` |
| **Archive** | **Archive cluster** stops offline notifications and alerts for a cluster you expect to be offline and leaves it out of fleet health. The cluster stays connected. **Unarchive cluster** reverses it. | `clusters.write` |
| **Deployment engine** | On a cluster that deploys with ArgoCD, makes Ankra's own engine the default for new stacks and add-ons ("This cannot be switched back to ArgoCD."), and **Move add-ons off ArgoCD** moves the existing ones. See [Deployment engines](/concepts/deployment-engines). | `clusters.write` |

Automatic patch upgrades of Kubernetes are off by default, and neither the portal nor the CLI has a switch for them.

```bash
ankra cluster upgrade my-cluster <version>
ankra cluster reconcile my-cluster
```

## GitOps

`/next/clusters/<cluster-id>/settings/gitops`

- **Repository** - the Git repository that holds the cluster's definition. **Connect a repository** or **Change repository**.
- **Sync** - whether the cluster matches its repository. Ankra syncs when the branch changes; **Sync now** checks right away.
- **Merge conflicts** - resources changed both in Git and in Ankra since the last sync. Ankra does not sync them until you choose which version to keep.
- **Sync history** - every sync between the cluster and its repository.
- **Needs you** appears when GitOps is not working, for example "Install the Ankra GitHub App", with what to do.

See [GitOps](/concepts/gitops).

```bash
ankra cluster gitops status
ankra cluster gitops conflicts list
```

## Kubernetes sync

`/next/clusters/<cluster-id>/settings/kubernetes-sync`

Ankra keeps a copy of the cluster's Kubernetes resources so its pages load quickly. **Sync status** says whether that copy is up to date, and **Resource types** lists each type Ankra copies. **Run a full sync…** reads every resource from the cluster again and removes resources from the copy that no longer exist; nothing on the cluster changes. The cluster must be connected.

## Network

`/next/clusters/<cluster-id>/settings/network`

- On a cluster Ankra builds on UpCloud or OVHcloud, choose the internet gateway and change its size (**Change NAT gateway plan**, **Change load balancer plan** or **Change gateway size**). A gateway change can cut the cluster's internet access for several minutes, and the dialog says so.
- On a cluster Ankra built on a cloud provider, **Turn the Gateway API on**. See [Gateway API](/guides/gateway-api).

Other clusters have nothing to set here.

```bash
ankra cluster gateway-api status
ankra cluster gateway-api enable
```

## SSH access

`/next/clusters/<cluster-id>/settings/ssh`

**Connect with SSH** lists the cluster's servers and the commands to **Open a shell on the control plane** and **Reach the Kubernetes API on your computer**. **SSH keys** lists the keys on the servers and changes them. Where SSH is not offered, the page says "SSH access is not offered for this kind of cluster".

A key change writes every running server and the bastion. A server the cluster's stop or pause powered off gets the new keys when the cluster starts, and the change stays open until then. If the provider no longer has that server, Ankra removes its record and names it in the change instead of waiting.

```bash
ankra cluster ssh-keys get my-cluster
```

## Ankra AI

`/next/clusters/<cluster-id>/settings/ai`

| Section | What it does | Permission |
|---|---|---|
| **Ankra AI insights** | **Turn Ankra AI insights off** or **on**: whether Ankra AI watches this cluster for problems. See [AI insights](/platform/ai-insights). | `clusters.write` |
| **Alert fixes** | **Let Ankra AI fix alerts on this cluster?** What it may do on its own, and who approves the rest, is set for the whole organisation. | `ai.manage` |
| **Code for Ankra AI** | **Add a repository** (GitHub connection, **Repository**, **Branch**, **Why it matters here**). When Ankra AI looks into a problem here it sees this list with your notes, and can read and search the code. The same list feeds [AI code review](/platform/ai-code-review). | `clusters.write` |

## Logs and data

`/next/clusters/<cluster-id>/settings/logs`

- **Ankra hosted logs** - whether this cluster sends the log lines of its running containers to Ankra, who can read them and who can change the setting. See [Hosted logs](/guides/hosted-logs).
- **Data policy** - the data policy managed services on this cluster follow.

To connect a log store you already run (Grafana Loki, Elasticsearch or OpenSearch), use [Integrations](#integrations).

## Integrations

`/next/clusters/<cluster-id>/settings/integrations`

- **Your metrics and logs** - **Metrics** (your own Prometheus, see [Prometheus](/integrations/prometheus)), **Log store** (**Connect a log store**, see [Log sources](/integrations/log-sources)) and **External log viewer**. Each connection can be tested and disconnected.
- **Security and cost reporting** - **Vulnerability scanning** and **Cloud cost estimates**.

Ankra built-in metrics need none of these; see [Cluster metrics](/platform/cluster-metrics#ankra-built-in-metrics). SOPS encryption is set for the whole organisation, not per cluster; see [SOPS](/guides/sops).

## Variables

`/next/clusters/<cluster-id>/settings/variables`

Values the stacks on this cluster can refer to, such as a domain name or a replica count. Reading them needs `variables.read`; adding, changing and deleting them needs `variables.write`. See [Variables](/concepts/variables).

```bash
ankra cluster variables list
ankra cluster variables set domain example.com
```

## Credentials

`/next/clusters/<cluster-id>/settings/credentials`

**Credentials this cluster uses** lists the credentials the cluster's definition names: the Git repository it syncs with, its metrics and log sources and the registries its add-ons install from. Open one to check, rotate or replace it. See [Credentials](/platform/credentials).

## Terminate or remove

`/next/clusters/<cluster-id>/settings/terminate`

What the page offers depends on the cluster. Every action asks you to type the cluster's name, and needs `clusters.delete`: "Your role cannot do this. That needs the clusters.delete permission."

| Cluster | Action | What happens |
|---|---|---|
| Built by Ankra | **Terminate cluster** | Deletes every server, network and SSH key the cluster has at its provider and removes the cluster from Ankra. Its workloads and the data on its servers are lost. |
| Built by Ankra | **Force terminate cluster** | Deletes the cluster at its provider and removes its records even when normal cleanup cannot finish. A quieter button under **Terminate cluster**, offered while the cluster is stopped, offline or archived, for when terminating fails or gets stuck. |
| Managed Kubernetes | **Disconnect cluster** (under **Disconnect from Ankra**) | Removes the cluster from Ankra. It keeps running at the provider, and the provider keeps charging for it. |
| Managed Kubernetes | **Delete at &lt;provider&gt;** | The provider deletes the control plane and node pools, then Ankra removes the cluster. Its workloads and their data are lost. |
| Imported | **Disconnect cluster** | Ankra stops managing the cluster and removes it from Ankra. The cluster and everything running on it are not deleted, and the Ankra agent stays installed in the cluster until you remove it yourself. |
| Sandbox | **Remove sandbox** | Removes the sandbox and all its demo data. |

Disconnecting an imported cluster works while its agent is offline, and leaves its stacks and add-ons running in the cluster. From the command line it is `ankra delete cluster <name>`. Ask Ankra and MCP clients disconnect one with the `disconnect_cluster` tool; `delete_cluster` terminates only a cluster built by Ankra and refuses an imported one.

<Warning>
Terminating cannot be undone. When the cluster's persistent volumes will be deleted, the dialog lists them under **Persistent volumes** and asks you to type `DELETE VOLUME DATA` as well as the cluster's name. Volumes kept by the provider's retention policy keep billing at the provider after the cluster is gone.
</Warning>

To keep the cluster but stop paying for its servers, stop it instead on [Stop, start and schedules](#stop-start-and-schedules). While the cluster is running, the terminate card links there as **Stop the cluster instead**.

<CliVersion since="0.19.0" command="cluster deprovision --accept-volume-data-loss" />

```bash
ankra cluster deprovision my-cluster                            # names the volumes and asks
ankra cluster deprovision my-cluster --accept-volume-data-loss  # for scripts
```

In a script, `--yes` never stands in for `--accept-volume-data-loss`; without it the command stops. See [Operate an Ankra Managed Cluster](/guides/operate-ankra-managed-clusters#terminate-a-cluster) and, for managed Kubernetes, [Managed Kubernetes](/guides/managed-kubernetes).
