An AI agent is a standing job for Ankra AI. Each one has a goal, a trigger that starts it, the tools it may use, how far it may act on its own, and a budget. Every time an agent starts, Ankra records an **agent run**: what it read, what it did and what it reported.

In the portal, agents appear through their work. Every run is under **Ankra AI → Activity**, and each run names its agent as **Ankra agent**. The portal has no page that lists, creates or changes agents. Use `ankra ai tasks` in the CLI, or the MCP tools below.

## Where agents show up

| Where | What you see | Read more |
| --- | --- | --- |
| **Ankra AI → Activity** (`/next/ai/agent-runs`) | **Agent runs**: every run, its status, environment, duration and linked ticket. A run's page shows its activity and, while it is going, **Stop run** | [Follow, steer and stop an agent run](/guides/agent-runs) |
| **Ankra AI → Work** (`/next/ai/tickets`) | Tickets the Ankra agent investigates, plans and carries out | [Set up the ticket desk](/guides/ticket-desk) |
| **Ankra AI → Watching** (`/next/ai/watching`) | A watch that investigates when it fires runs an agent | [Watch for a problem](/guides/ai-watching) |
| Pull request comments, check runs and notifications | A link to `/next/ai/agent-tasks/<task-id>`, which opens the agent's newest run. Until the agent has run, the page reads **This agent task has not run yet** and checks again every few seconds | [Follow, steer and stop an agent run](/guides/agent-runs) |

## The default team

Every organisation starts with six agents, one per role:

| Agent | Template | What it does |
| --- | --- | --- |
| **AI Team Lead** | `ai_team_lead` | Your first point of contact. Triages requests, decides which specialist or board flow fits, and files tickets for deep work instead of doing it inline |
| **Developer** | `developer` | Application delivery: Helm charts and values, application deploys, CI/CD workflows and pull-request demos |
| **Database Admin** | `database_admin` | Stateful workloads: StatefulSets, volumes, database operators and backup hygiene. Checks backups before any step that touches data |
| **SRE** | `sre` | Reliability: alert triage, Prometheus queries, golden signals and incident write-ups. Backs every claim with a read |
| **DevOps** | `devops` | The platform: clusters, node pools, add-ons and Stacks, GitOps drift and infrastructure-as-code export. One reversible step at a time |
| **DevSecOps** | `devsecops` | Security findings: maps every vulnerable image to what deployed it and fixes critical and high CVEs at the source |

All six start the same way: started by hand only (the scheduler never runs them), autonomy `propose` so every change waits for a person, and the `quick` model rung. They use no tokens until one of them runs.

Ankra adds the team the first time your organisation's agents are read. Each role is added once: an agent you delete stays deleted, and a role that joins the team later is added once to every organisation. To bring a deleted role back, hire it again from the catalogue (see [Hire, create and change agents](#hire-create-and-change-agents)).

### The DevSecOps agent

The DevSecOps agent turns one cluster's security report into fixes, in this order:

1. **Reads the security report** for the cluster, the same findings the [Security Center](/guides/cluster-security) shows, filtered to critical and high. It quotes the CVEs, their fixed versions and the workloads each one runs in.
2. **Maps each vulnerable image to what deployed it**: a [connected application](/concepts/applications) deployed to that cluster, matched by namespace and image repository, or the add-on the report attributes the image to.
3. **Fixes applications at the source.** It bumps the base image or the vulnerable package in the application's repository and opens one pull request per application, listing every CVE it clears. It never commits to the default branch.
4. **Proposes add-on upgrades** for images that belong to an add-on: the chart version that ships the fix, with the current version as the rollback.
5. **Verifies** after the pull request merges and the image is rebuilt, by reading the report again and quoting the counts before and after.

Known-exploited CVEs ([CISA KEV](/guides/cluster-security#used-by-attackers-and-chance-of-use)) come first, then criticals, then highs; fixable before unfixable; production clusters before the rest. A CVE with no published fix is reported, and accepting the risk stays a decision for a person. The agent is refused `delete_resource`, `delete_application`, `delete_stack` and `uninstall_addon_from_stack` whatever its autonomy, so it never makes a finding disappear by removing what runs.

It needs a cluster to work on: an agent scoped to one cluster, or a ticket whose cluster is set. To open pull requests it needs a connected application whose repository Ankra can write to.

Unlike the other five, the DevSecOps agent acts as your organisation's **board identity**, so it can propose changes and open pull requests from its first run. Ankra creates that identity once per organisation, with the `operator` role, when it adds the team. `ankra ai board-identity revoke` stands it down, and Ankra never creates it again after that. Its autonomy stays `propose`: every change to a cluster still waits for a person, and each pull request is reviewed like any other.

## What an agent is made of

| Part | What it decides | Values | Set with |
| --- | --- | --- | --- |
| **Trigger** | What starts a run | `manual` (by hand), `cron` (a schedule, with a time zone), `alert` (an alert fires), `mission` | `--trigger`, with `--cron`, `--timezone` or `--alert` |
| **Tool profile** | Which tools it may call | `read_only` (the default for a new agent), `standard`, `admin` | `--tool-profile` |
| **Autonomy** | How far it acts on its own | `read_only`: never changes anything. `propose`: suggests changes, a person approves each one. `auto`: acts on its own within its limits | `--autonomy-level` |
| **Model** | The model its turns run on | `auto` (Ankra picks on every turn), `quick`, `think`, `expert`, or an entry in your [model catalogue](/platform/ai-provider) | `--model-mode` |
| **Cluster** | The one cluster it works on, if any | A cluster name or id. Set when the agent is created or hired, and cannot be changed afterwards | `--cluster` |
| **Budget** | The hard stop for its work | See below | `-f` with a YAML or JSON file |

Whatever an agent's autonomy, the actions Ankra AI always asks a person about still wait for one. See [What it can change without asking](/platform/ai-overview#what-it-can-change-without-asking).

### Budget

| Member | What it caps |
| --- | --- |
| `max_tool_calls` | Tool calls in one turn, reads included |
| `max_write_actions` | Changes in one run |
| `max_turns` | Turns in one run |
| `max_runtime_minutes` | Minutes one run may last |
| `max_runs_per_day` | Runs in one day |
| `max_tokens_per_day` | Tokens the agent uses in one UTC day, across all its runs, cached prompt reads included. Between 1,000 and 1,000,000,000. No value means no limit |

The DevSecOps agent ships with a `max_tokens_per_day` of 2,000,000. When an agent reaches its daily token limit, Ankra does not start it again that UTC day, brings a turn that crosses the limit to a close, and sends one notification for that agent that day. It runs again the next UTC day, or once someone raises the limit.

## Hire, create and change agents

<CliVersion since="0.74.0" />

Reading agents needs the `ai.use` permission. Every change needs `ai.manage`, which the built-in `admin` and `owner` roles hold, as does any custom role that grants it. Without it, Ankra refuses the change with a message such as `Only organisation admins can create agent tasks.`

```bash
# The organisation's agents
ankra ai tasks list

# The built-in roles, and whether each is hired
ankra ai tasks templates list

# Hire a role, optionally scoped to one cluster
ankra ai tasks templates hire sre --cluster my-cluster

# Write your own
ankra ai tasks create --name "Nightly cost review" --goal "Review yesterday's spend" \
    --trigger cron --cron "0 6 * * *" --timezone Europe/Stockholm

# Change only what you name
ankra ai tasks update "Nightly cost review" --autonomy-level propose
```

**You should see** the agent in `ankra ai tasks list`, with its trigger, tools, autonomy and next run. `ankra ai tasks get "<agent name>" -o json` prints its whole definition, the budget included.

`ankra ai tasks templates list` names every role you can hire: the six above, plus **Incident Responder**, **Gap Scanner**, **Reviewer** and **Nightly Auditor**. Hiring a role that is already hired is refused with 409.

| Command | What it does |
| --- | --- |
| `ankra ai tasks run <task>` | Queues an enabled agent to run now. Nothing happens when a run is already live |
| `ankra ai tasks runs <task>` | The agent's recent runs, newest first |
| `ankra ai tasks pause <task>` | Stops scheduling it. A live run finishes its current turn |
| `ankra ai tasks resume <task>` | Turns it back on and restores its schedule |
| `ankra ai tasks stop <task>` | Pauses it and cancels its live run in one step |
| `ankra ai tasks delete <task>` | Deletes it. Its past runs stay readable with `ankra agents runs` |
| `ankra ai tasks reapply-template <task>` | Brings a hired role up to the goal, tools, autonomy and budget the role ships with today. An agent someone changed is left alone unless you add `--force` |

`<task>` is the agent's id or its exact name. The full list of flags is in the [`ankra ai` reference](/reference/cli/ai#ankra-ai-tasks).

From an MCP client, `list_agent_tasks` lists the agents with a `can_work_board` verdict, and `designate_board_worker` makes an agent a board worker or removes that. See [MCP tools](/platform/mcp-tools).

## Agents that work tickets

An agent works tickets on **Work** when it is a **board worker** and can act. On the ticket desk (**Ankra AI → Settings → Configure work routing**) this shows as one **Ankra agent** with a status:

- **Available for automatic staffing** - at least one board worker can take tickets.
- **No eligible agent reported** - no board worker can. **Ask Ankra to check ticket staffing** asks Ankra AI what to change.

The portal cannot change which agents work tickets or the identity they act as. Use `designate_board_worker` over MCP for the first, and `ankra ai board-identity` for the second:

```bash
ankra ai board-identity status
ankra ai board-identity provision --role operator
ankra ai board-identity revoke
```

The board identity is what agents Ankra created act as, because they have no user account of their own. It cannot sign in and has no token. Without it, a board worker hands every ticket to a person instead of working it. See [Set up the ticket desk](/guides/ticket-desk).
