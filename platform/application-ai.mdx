title: Application AI Settings
description: Choose per application what Ankra AI does on its repository's pull requests - which activities run, on which model, and within which branches and daily budget.
---

Every [application](/concepts/applications) decides what Ankra AI does when its repository gets a pull request. Open **Applications → &lt;your application&gt; → Settings → Who runs it** (`/next/applications/<application-id>?view=settings&section=ai`); the **On your pull requests** section lists each activity.

Each activity follows your organisation's settings until you change it here. The section is a view onto the same per-repository settings the reviews read when a pull request event arrives, so what you set here and what your organisation's [source-control connection](/platform/ai-connections) sets can never disagree.

## Before you start

- **A role that may change the application.** Without it, **Configure** is greyed out and the section reads **Your role can’t change what Ankra does on pull requests.**
- **A repository connected through the Ankra GitHub App.** Without one, the section says why instead of listing activities: the application has no repository, the App is not installed for the repository's owner, or the repository is on a provider these activities cannot use. Install the App under **Ankra AI → Gateway connections → GitHub → Install the GitHub App**. See [GitHub](/integrations/github).

## The activities

| Activity | What it does | Runs when |
|---|---|---|
| **Pull request review** | Ankra reviews each pull request and comments on what it finds, as one comment that updates in place | A pull request is opened or updated |
| **Your organisation’s review rules** | Ankra also checks each pull request against the [skills](/platform/ai-skills) your organisation wrote, in the same comment | Alongside the pull request review |
| **Preview URLs** | Not set here: this is the **Preview every pull request** switch under **Settings → Deploys**, in the **Pull requests** card. It starts a [preview](/guides/pr-preview-environments) of each pull request and posts its address | A pull request is opened or updated |

Each row reads **On** or **Off**, then **Follows your organisation** or **Set for this application**, and **Your organisation has turned this off** when the organisation's switch is off.

Every activity is off for a repository nobody has configured. A fresh source-control connection never starts reviewing, replying or deploying on its own, so each activity is switched on deliberately - here, or for the whole connection under [AI code review](/platform/ai-code-review).

The platform also lists a code review of pushed branches and a review of failed workflow runs. Neither runs, so the section does not show them.

## Change an activity

<Steps>
  <Step title="Open its settings">
    Press **Configure** on the activity's row.
  </Step>
  <Step title="Choose where its settings come from">
    Under the settings source, pick **Follow organisation defaults** or **Customise for this application**.

    With **Follow organisation defaults**, the dialog says **This activity uses the organisation’s current settings, including future changes to those defaults.**
  </Step>
  <Step title="Set its values">
    With **Customise for this application**, tick **Enable this activity for the application** and set the values in [What you can set](#what-you-can-set). If the organisation has turned the activity off, the dialog warns that saving an override will not enable it globally.
  </Step>
  <Step title="Review and save">
    Press **Review AI settings**. The **Save AI activity** step sums up the change, for example the model and the limits. Confirm it.

    The section shows **Application AI settings saved.**, and the row now reads **Set for this application**.
  </Step>
</Steps>

Customising an activity pins the whole activity: the values in the dialog when you save become this repository's settings for it, and later changes to the organisation default stop reaching it. To undo every customisation at once, press **Use organisation defaults for all activities** and confirm **Restore organisation AI defaults**. The button appears only while some activity is set for this application.

## What you can set

| Setting | Activities | What it does |
|---|---|---|
| **Model** | Every activity except **Preview URLs** | Which model from your organisation's catalogue the activity runs on. **Ankra default** lets Ankra choose. The catalogue's **Auto** routing is not offered here: an activity that changed model between runs would make its findings impossible to compare. |
| **Ignore paths** | Every activity except **Preview URLs** | One path pattern per line, for example `vendor/**`. Patterns are matched against each changed file's path after the change, and matching files leave the diff *before* the character budget is measured, so a lockfile or a generated bundle cannot crowd the real change out of a review. `**` crosses directory separators, `*` and `?` do not, and a pattern with no wildcard also matches everything beneath it - `vendor` covers `vendor/lib/thing.go`. |
| **Maximum runs per day** | Every activity except **Preview URLs** | A cap on the activity's runs for this repository per UTC day, across every pull request, requested reviews included. `0` sets no cap. On the pull request review it is checked before the per-pull-request cap, so a brand-new pull request can be declined on its first push once the repository is over it - see [the two budgets](/platform/ai-code-review#the-two-budgets). |
| **Maximum input characters** | Every activity except **Preview URLs** | The most characters of diff one run may read. The built-in budget is 120,000 characters. |
| **Target branches** | **Pull request review** | One branch pattern per line, with `*` and `?` wildcards. Leave it empty to review pull requests into any branch. |
| **Skip draft pull requests** | **Pull request review** | Draft pull requests are reviewed once they are marked ready. |
| **Review instructions** | **Pull request review** | Guide the review's focus and language, in up to 4,000 characters. Platform review rules still apply. |

The pull request review reports findings. It does not propose fixes on its own.

**Preview URLs** is not set in this section: the section says whether **Preview every pull request** is on and links to **Settings → Deploys**, where that switch is. What a preview deploys comes from the application's demo defaults; see [environment variables and a throwaway database](/concepts/applications#environment-variables-and-a-throwaway-database). Turning it off stops the automatic pull-request previews for this repository without touching manually launched [preview demos](/concepts/applications#preview-demos).

<Note>
Mentioning `@ankraai` in a pull request comment gets an answer whenever **Replies to mentions** is on for the repository: a mention reply is a direct request from a person, so it is never filtered by branch scope, draft state, or either review budget. The run still counts toward the budgets.
</Note>

## Which skills your organisation's review rules use

**Your organisation’s review rules** is a second pass that rides on the pull request review and appends an **Organisation skills** section to the same comment, so it runs only when **Pull request review** runs too. It judges the change against:

- every skill marked **Always in use: Ankra AI reads it in every conversation**, and
- the skills pinned in the activity's `skill_ids`.

Skills of every kind count: core, CI/CD and add-on alike. One review uses at most 12 skills, always-active ones first, with at most 24,000 characters of skill text. With no such skill, it posts nothing.

Only this activity reads `skill_ids` (the `skills` lane in [`ankra application ai-config`](/reference/cli/application)). The field also appears on the other activities in the CLI and API output, but no review reads it there. The portal has no skill picker: to put a skill in front of the review there, mark it **Always in use**, which also adds it to every Ankra AI conversation, or pin it with the CLI. See [AI Skills](/platform/ai-skills).

To steer the pull request review itself, use its review instructions: per connection under [AI code review](/platform/ai-code-review), or per repository as **Review instructions** on the pull request review (`custom_instructions` in the CLI). Customising it pins the whole activity, as described under [Change an activity](#change-an-activity).

## Settings are per repository, not per application

<Warning>
These settings are keyed by the repository, not by the application. Two applications connected to the same repository share one set of settings - turning an activity off on one turns it off for the other, and each application's section shows the other's edits as its own. **Preview URLs** also fires once per matching application, so such a repository collects one preview comment per application on every pull request. Keep one application per repository.
</Warning>
