A cluster's capacity comes from its node groups (node pools on managed Kubernetes), its control plane and, on clusters Ankra builds, a bastion. Two pages in the portal hold them:

- **Kubernetes → Nodes** lists every node Kubernetes reports, grouped by node group, with readiness, capacity and scheduling. Cordon and drain start here.
- **Node management** changes the infrastructure: node groups, the control plane and the provider machines. Open it with **Manage nodes and groups** on the Nodes page.

## Before you start

| Task | Permission on the cluster | Built-in roles that have it |
|---|---|---|
| Read nodes and node groups | `clusters.read` | Every role |
| Add a node group; change its count, autoscaling, instance type, labels or taints; change the control plane; resize the bastion | `clusters.write` | Member, Operator, Admin, Owner |
| Change the node count of a managed Kubernetes node pool | `clusters.operate` | Operator, Admin, Owner |
| Restart a machine; stop or start the cluster | `clusters.operate` | Operator, Admin, Owner |
| Delete a node group on a cluster Ankra builds | `clusters.delete` | Admin, Owner |
| Delete a managed Kubernetes node pool | `clusters.write` | Member, Operator, Admin, Owner |
| Cordon or uncordon a node | `kubernetes.write` | Operator, Admin, Owner |
| Drain a node | `kubernetes.write` and `kube_access.use` | Operator, Admin, Owner |

The portal says what is missing next to the control, for example "Editing infrastructure requires clusters.write for this cluster." or "Draining this node requires kubernetes.write and kube_access.use for this cluster." See [Roles and access](/guides/roles-and-access).

On a cluster you imported, Ankra does not run the machines. Node management reads "Infrastructure is managed outside Ankra." and you can still cordon and drain nodes.

## Find the nodes

Go to **Infrastructure → Clusters → &lt;your cluster&gt; → Kubernetes → Nodes** (`/next/clusters/<cluster-id>/kubernetes/nodes`). The tiles at the top read **Ready**, **vCPU**, **Memory** and **Node groups** (or **Node pools**). Below them each node group lists its nodes; a node that cannot take new pods carries **Cordoned**. A provider machine that has not registered with Kubernetes yet reads **Not joined**.

Click **Manage nodes and groups** to open **Node management** (`/next/clusters/<cluster-id>/node-groups`). It has three sections: **Node groups** (or **Node pools**), **Control plane** and **Provider machines**. Managed Kubernetes clusters show the node pools only; the provider runs their control plane.

Every change on Node management follows the same pattern: fill in the form, click **Review change**, check the **Review infrastructure change** dialog, then click **Confirm change**. The page then says "Request accepted. Follow Operations, then verify the actual infrastructure and affected workloads." Follow the change under **Operations** with **View Operations**.

## Add a node group

<CliVersion since="0.16.0" />

<Tabs>
<Tab title="Portal">

<Steps>
  <Step title="Open the form">
    On **Node management**, click **Add node group** (**Add node pool** on managed Kubernetes).
  </Step>
  <Step title="Describe the group">
    Enter a **Group name** (lowercase letters, numbers and hyphens; it cannot be changed later), choose the **Instance type** and set the **Node count** (0 to 100). Tick **Enable autoscaling** to give a **Minimum nodes** and **Maximum nodes** instead. Add **Labels** (one `key=value` per line) and **Taints** (one `key=value:effect` per line, with `NoSchedule`, `PreferNoSchedule` or `NoExecute`) if workloads should be placed on this group.
  </Step>
  <Step title="Confirm">
    Click **Review change**, then **Confirm change**.

    **Check:** the group appears under **Node groups** with "nodes requested", and its nodes appear on **Kubernetes → Nodes** once they join.
  </Step>
</Steps>

</Tab>
<Tab title="CLI">

```bash
ankra cluster node-group add my-cluster \
  --name workers-large \
  --instance-type <instance-type> \
  --count 2 \
  --labels "workload=batch"
```

On managed Kubernetes use `ankra cluster managed node-pool add`. See [Operate an Ankra Managed Cluster](/guides/operate-ankra-managed-clusters#node-groups) and the [CLI reference](/reference/cli/cluster#ankra-cluster-node-group-add).

</Tab>
</Tabs>

## Change a node group

<Tabs>
<Tab title="Portal">

<Steps>
  <Step title="Open the group">
    On **Node management**, click **Inspect and edit** on the group. **Current settings** shows the instance type, the requested and observed node counts, **Fixed size** or the autoscaling range, labels and taints.
  </Step>
  <Step title="Pick what to change">
    Choose a tab:

    - **Node count** - a fixed size from 0 to 100 (from 1 on managed Kubernetes). Turn autoscaling off first: "Disable autoscaling before changing the fixed count."
    - **Autoscaling** - tick **Enable autoscaling** and set **Minimum nodes** and **Maximum nodes**. See [Cluster autoscaling](/guides/cluster-autoscaling).
    - **Instance type** - move the group to another size.
    - **Labels** and **Taints** - the saved set replaces the group's set. An empty set removes them all.
    - **Pool settings** - on managed Kubernetes providers that support it: **Autohealing** and **Upgrade policy**.
    - **Delete** - type the group's name to confirm.
  </Step>
  <Step title="Confirm">
    Click **Review change**, read the risk note under the form, then click **Confirm change**.

    **Check:** under **Operations** the change runs to completion, and **Current settings** shows the new values after **Refresh**.
  </Step>
</Steps>

On managed Kubernetes the pool's instance type, labels and taints cannot be changed in place: "Add a replacement pool when those settings must change."

</Tab>
<Tab title="CLI">

```bash
ankra cluster node-group scale my-cluster workers 3
ankra cluster node-group autoscaling set my-cluster workers --enabled --min 1 --max 5
ankra cluster node-group upgrade my-cluster workers <instance-type>
ankra cluster node-group labels my-cluster workers --labels "workload=batch"
ankra cluster node-group taints my-cluster workers --taints "dedicated=batch:NoSchedule"
ankra cluster node-group delete my-cluster workers
```

`scale`, `upgrade` and `delete` take `--force-drain` to remove a node even when a PodDisruptionBudget refuses its drain. `ankra cluster node-group remove-node` removes one named node from a group; the portal has no control for it.

</Tab>
</Tabs>

<Warning>
Lowering the count or deleting a group removes nodes and can interrupt workloads. Changing the instance type may restart or replace machines and may not be reversible. Drain the nodes first or check their workloads on **Kubernetes → Nodes**.
</Warning>

## Change the control plane

On **Node management**, click **Inspect control-plane settings**. The page shows the number of control plane nodes and their instance type, and offers:

- **Change control-plane count** - choose the number under **Control-plane nodes**. When a change is not possible right now, the page gives the reason.
- **Resize control plane** - choose a new **Instance type**. When the cluster has a single controller that can be resized while running, the dialog is **Resize the only control plane**: "The Kubernetes API is unavailable for a few minutes while the control plane restarts." Confirm with **Resize with API downtime**.

Which changes run live, rolling or with the cluster stopped depends on the provider and the controller count. [Operate an Ankra Managed Cluster](/guides/operate-ankra-managed-clusters#control-plane) covers each mode and the CLI equivalents.

## Restart a machine or resize the bastion

<Tabs>
<Tab title="Portal">

<Steps>
  <Step title="Open the machine">
    On **Node management**, under **Provider machines**, click **Inspect machine**. **Machine details** shows the role, node group, instance type, provider status, power state and addresses.
  </Step>
  <Step title="Choose the action">
    Under **What do you want to change?**:

    - **Restart machine** restarts the server at the provider. It does not drain its workloads first. Type the machine's name to confirm. HPE Morpheus clusters have no restart.
    - **Resize bastion or gateway** appears on the bastion (and the public gateway on Scaleway). Choose the new size.
  </Step>
  <Step title="Confirm">
    Click **Review change**, then **Confirm change**.

    **Check:** **Inspect machine operations** lists the request; once it finishes, **Machine details** shows the new power state or instance type.
  </Step>
</Steps>

</Tab>
<Tab title="CLI">

The provider is part of the command (`hetzner`, `ovh`, `upcloud`, `digitalocean`, `scaleway`, `aws`, `ankracloud`, `proxmox`, `morpheus`):

```bash
ankra cluster hetzner nodes list my-cluster
ankra cluster hetzner nodes restart my-cluster <node-id>
ankra cluster hetzner bastion resize my-cluster <instance-type>
```

`nodes list` names the zone each machine runs in. It is the zone the provider reports for the instance, or on UpCloud, Scaleway and Ankra Cloud the machine's location, which there is one zone; where neither gives one, it is the node's `topology.kubernetes.io/zone` label. A zone followed by `*` is only the one that was asked for, and `-` means none is recorded. See [Availability Zones](/guides/ovh-clusters#see-which-zone-each-machine-runs-in) for OVH's three-zone regions.

</Tab>
</Tabs>

## Cordon and drain a node

Cordoning stops new pods from being scheduled on a node; its current pods keep running. Draining cordons the node and evicts its pods within their disruption budgets, which is what prepares a node for shutdown.

<Tabs>
<Tab title="Portal">

<Steps>
  <Step title="Open the node">
    On **Kubernetes → Nodes**, click the node.
  </Step>
  <Step title="Cordon or drain">
    Under **Scheduling**, click **Review cordon** and confirm with **Cordon node**. To drain, click **Review node drain** instead.

    **Check:** after a cordon the node carries **Cordoned**.
  </Step>
  <Step title="Review the drain">
    The **Drain** page reads the live node and lists **Pods on this node** and **Matching disruption budgets**. Accept each risk it lists, click **Review drain confirmation**, type the node's name, then click **Start drain**.

    **Check:** the receipt reads **Drain in progress** with **Remaining evictable pods**, and its title names the final state when the drain ends. **Cancel drain** stops it and keeps the node cordoned; **Resume drain** continues one that stopped.
  </Step>
  <Step title="Return the node to service">
    When the work on the node is done, open **Review node scheduling and uncordon when ready**, click **Review uncordon** and confirm with **Uncordon node**.
  </Step>
</Steps>

To cordon or uncordon several nodes, tick them on **Kubernetes → Nodes** and click **Review cordon** or **Review uncordon** (at most 20 nodes per review).

</Tab>
<Tab title="CLI">

```bash
ankra cluster select my-cluster
ankra cluster drain worker-3 --dry-run
ankra cluster drain worker-3
```

`--dry-run` prints the plan without changing anything; `--grace-period` sets the seconds each pod gets to shut down.

</Tab>
</Tabs>

## Stop and start the cluster

Stopping deletes or powers off the cluster's servers, depending on the provider, and starting brings them back. Both are on **Settings → Stop, start and schedules**; see [Power schedules](/platform/cluster-power-schedules).

## What the portal does not do

| Task | Where it works |
|---|---|
| Diagnose the bastion over SSH | `ankra cluster <provider> bastion diagnose my-cluster` |
| Read a node's cloud-init log or run a node diagnosis | `ankra cluster <provider> nodes cloud-init-log` and `ankra cluster <provider> nodes diagnose` |
| Resize a playground | `ankra cluster playground resize my-cluster --size <size>`, with sizes from `ankra cluster playground plans` |
| Standalone VMs on the cluster's network | The API only: `/api/v1/clusters/{provider}/{cluster_id}/vms` |
| The most nodes the cloud account still has room for | The API only: `/api/v1/clusters/{provider}/{cluster_id}/quotas` |

## What can go wrong

| Message | What to do |
|---|---|
| "Disable autoscaling before changing the fixed count." | Open **Autoscaling**, untick **Enable autoscaling**, confirm, then set **Node count**. |
| "An external autoscaler owns this pool. Its settings cannot be changed here." | Change the pool where its autoscaler is configured. |
| "The group changed since you started editing." | Click **Reload data and reset edits**, then make the change again on the current settings. |
| "The request outcome is unknown. Check current infrastructure and Operations before trying again." | Check **Operations** before you send the change a second time. |
| "Cordon alone does not prepare a node for shutdown." | Drain the node before you restart, resize or remove it. |
