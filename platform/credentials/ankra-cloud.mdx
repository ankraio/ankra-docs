An Ankra Cloud credential stores an Ankra Cloud API token. One credential serves both cluster types on [Ankra Cloud](https://cloud.ankra.app): self-managed [Ankra Cloud clusters](/guides/ankra-cloud-clusters) and managed [Ankra Cloud Kubernetes](/guides/ankra-cloud-kubernetes).

<Warning>
**Closed beta.** Ankra Cloud as a cluster provider is in closed beta. The workflow is stable but the surface may still change, and it is enabled per organisation on request - until it is, Ankra Cloud is not offered as a credential provider. [Contact support](/platform/support) to have it turned on for your organisation.
</Warning>

The token is validated when you save it: Ankra lists the zones and plans of the account (`GET /v1/zones` and `GET /v1/plans`), so a rejected or mistyped token is refused immediately. The token never appears in an error message; on the credential's page only a role with `credentials.reveal` can show it, under **Stored values**.

## What Ankra Accesses

For self-managed clusters, Ankra provisions the infrastructure directly:

| Resource | Operations | Why it's used |
|----------|------------|---------------|
| Zones, plans, templates, storage tiers | read | The wizard's live catalog and pricing |
| The account (`GET /v1/account`) | read | [Which Ankra Cloud account a credential uses](#which-ankra-cloud-account-a-credential-uses) |
| Servers | create, read, start/stop/restart, delete | The cluster's nodes and bastion |
| Server firewalls | update | Per-server inbound rules |
| Private networks | create, read, delete | The cluster's private network |
| Routers | create, read, delete | NAT egress for the nodes |
| Storages | read, delete | Persistent volumes the in-cluster CSI driver creates. When you delete the cluster, Ankra deletes them or keeps them, following the cluster's storage retention policy |
| Load balancers | list, delete | The in-cluster cloud controller creates and removes them with the [runtime credential](#runtime-credential) as `LoadBalancer` Services come and go. When the cluster is deleted, Ankra lists the load balancers on the cluster's network and deletes the ones the cluster's cloud controller made |

When you delete a cluster, Ankra deletes a load balancer only if it is on the cluster's network **and** carries the cloud controller's cluster label with this cluster's name. Anything else on that network - made by hand, or by a cloud controller installed under another name - is left in place and reported on the delete operation, and it stays in your Ankra Cloud account, and is billed, until you delete it in the [Ankra Cloud console](https://cloud.ankra.app).

For [Ankra Cloud Kubernetes](/guides/ankra-cloud-kubernetes), Ankra uses the managed Kubernetes API instead:

| Resource | Operations | Why it's used |
|----------|------------|---------------|
| Kubernetes clusters | create, read, upgrade, delete | Cluster lifecycle |
| Node pools | create, read, update, delete | Scale and manage the cluster's node pools |
| Kubeconfig | read | Install Ankra's agent; fetched fresh each time and never stored |
| Private networks | create, read, delete | The network the cluster's nodes join |
| Versions, plans, zones | read | Available Kubernetes versions, plans and zones, and the production and development control planes with their fees |

## Before you start

- A role with `credentials.write` (the built-in `owner` and `admin` roles have it). See [Credentials](/platform/credentials#before-you-start).
- Ankra Cloud enabled for your organisation (see the closed beta note above). Until it is, **Ankra Cloud** is not offered under **Cloud providers**.

## Creating an Ankra Cloud credential

<Steps>
  <Step title="Create an Ankra Cloud API token">
    1. Sign in to the [Ankra Cloud console](https://cloud.ankra.app)
    2. Open **Settings** → **API tokens**
    3. Create a token with the operate scope, so Ankra can create servers and clusters, and copy it (it starts with `act_` and is shown once)

    A token that can only read passes the save-time check, which lists zones and plans, but fails when Ankra provisions.
  </Step>
  <Step title="Add it to Ankra">
    <Tabs>
      <Tab title="Portal">
        Go to **Integrations & alerts → Credentials**, click **Add credential**, and under **Cloud providers** choose **Ankra Cloud**. Fill in:

        - **Name**: 3 to 100 lowercase letters, digits and single hyphens (for example `ankra-cloud-prod`). It cannot change later.
        - **API token**: the `act_...` token from the previous step
        - **API endpoint**, under **Endpoint**: only for a private or development Ankra Cloud. It must be an `https://` address; leave it empty for the public Ankra Cloud.

        Click **Test the connection**. You see **The connection works**. Then click **Add credential**; the credential's page opens. You can also add the credential inline from either create-cluster wizard.
      </Tab>
      <Tab title="CLI">
        <CliVersion since="0.21.0" />

        The token is never taken from a flag. It is read from stdin with `--token-stdin`, else from the `ANKRA_CLOUD_API_TOKEN` environment variable, else from a masked prompt:

        ```bash
        ankra credentials ankracloud create --name ankra-cloud-prod
        cat token.txt | ankra credentials ankracloud create --name ankra-cloud-prod --token-stdin
        ankra credentials ankracloud list
        ```

        `--endpoint` names a non-default Ankra Cloud installation (https only).
      </Tab>
    </Tabs>
  </Step>
</Steps>

For self-managed clusters you also need an [SSH key credential](/platform/credentials/ssh-key). Ankra Cloud Kubernetes needs none.

<Note>
You can replace the token later under **Settings & access → Replace the secret**, without recreating the credential (see [Replace the secret](/platform/credentials#replace-the-secret)). Ankra checks the new token with Ankra Cloud before it stores it.
</Note>

## Runtime credential

A self-managed cluster runs the Ankra Cloud cloud controller manager and CSI driver inside the cluster, and they need a token too. The create wizard's **Runtime credential** picks which Ankra Cloud credential they get: by default the provisioning credential, or a second, dedicated one. A dedicated runtime credential limits what a compromised workload in the cluster could reach through that token. Ankra stores it in the Secret `ankra-cloud` in `kube-system`, SOPS-encrypted when the stack is committed to Git.

## Listing Ankra Cloud credentials

```bash
ankra credentials ankracloud list
curl https://platform.ankra.app/api/v1/credentials/ankracloud \
  -H "Authorization: Bearer $ANKRA_API_TOKEN"
```

## Which Ankra Cloud account a credential uses

Ankra shows the Ankra Cloud account a credential's token belongs to, with the Ankra organisation that account is linked to. Ankra asks Ankra Cloud with the credential's own token each time you look (`GET /v1/account`), so the answer is the account the token acts in now, including for the organisation's built-in credential. Seeing it needs only `credentials.read`, the permission that lists credentials: the account is not a secret, so you do not need `credentials.reveal`.

In the portal, open **Integrations & alerts → Credentials**, choose the credential, and read **Connection details** on its **Overview**: **Ankra Cloud account** and **Ankra organisation of the account**.

<CliVersion since="0.88.0" />

```bash
ankra credentials get ankra-cloud
```

```text
Credential Details:
  ID:       54fb4515-0811-42a1-8c41-0d2270e7f465
  Name:     ankra-cloud
  Provider: ankracloud
  Created:  1 month ago
  Ankra Cloud account: demo (01a108f4-16f0-7ada-84bb-9ef22be40664)
  Ankra Cloud account organisation: demo (7b2fedb6-4d79-45fd-b71a-044a2cfddce7)
  Usable:   yes
```

`-o json` carries it as `ankra_cloud_account` (`id`, `name`, `organisation`, which is null for an account not linked to an Ankra organisation). When Ankra cannot read the account, because the token could not be read, Ankra Cloud refused it, or Ankra Cloud did not answer, the line reads `Ankra Cloud account: unknown (<why>)` and `-o json` carries `ankra_cloud_account_error` instead. That means the account is unknown, not that the credential has none. If your role cannot reveal the credential, `ankra credentials get` still shows its name, provider, whether it is usable and the account, and says that the stored settings need `credentials.reveal`.

Through the API, `GET /api/v1/org/credentials/{credential_id}/ankra-cloud-account` answers `account` (or `account_error`) with `credentials.read`; any other credential answers 404. The credential detail, `GET /api/v1/org/credentials/{credential_id}`, carries the same account as `ankra_cloud_account` and needs `credentials.reveal`.

## Troubleshooting

| Symptom | Cause | Solution |
|---------|-------|----------|
| **Test the connection** reads **Failed to authenticate with Ankra Cloud**, or the credential is refused on save | The token is invalid, revoked, or copied incompletely, or the endpoint is wrong | Create a new token and paste the full `act_...` value; check the endpoint if you gave one |
| The endpoint is refused | The endpoint is not an `https://` URL | Use `https://`, or leave it empty for `https://cloud.ankra.app` |
| The credential saves, but provisioning fails with a permissions error | The token lacks the operate scope | Create a token with the operate scope and replace it on the credential's page |
| Provisioning fails with a payment or suspension error | The Ankra Cloud account needs a payment method or is suspended | Resolve it in the Ankra Cloud console, then retry |
| `Ankra Cloud account: unknown (... rejected the API token.)` | The stored token was revoked or has expired | Create a new token and [replace the secret](/platform/credentials#replace-the-secret) |
