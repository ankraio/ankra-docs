Azure credentials store an Azure **service principal** used to provision and manage [Azure Kubernetes Service (AKS)](/guides/aks-clusters). Ankra authenticates with the client-credentials grant against Microsoft Entra ID and reads the subscription's locations, Kubernetes versions, VM SKUs, quota and virtual networks to build the catalogue, then creates and operates AKS clusters in the resource groups it owns or adopts.

## Least-privilege roles

Do not grant `Contributor` on the whole subscription. Scope the service principal to what Ankra does:

| Scope | Role | Why |
|-------|------|-----|
| Subscription | `Reader` | Locations, Kubernetes versions, VM SKUs and availability zones, compute quota, virtual network discovery |
| Resource group(s) Ankra will own or adopt | `Azure Kubernetes Service Contributor Role` | Create, upgrade, scale, stop, start and delete AKS clusters and node pools |
| Resource group(s) Ankra will own or adopt | `Network Contributor` | Attach node pools to your subnet (`vnet_subnet_id`) and let AKS manage load balancers and public IPs |
| Subscription (only when Ankra creates resource groups) | A custom role with `Microsoft.Resources/subscriptions/resourceGroups/write` and `.../delete` | Create the `ankra-<cluster-name>` resource group and delete it with the cluster |

Grant `Network Contributor` on the resource group of the virtual network too when the subnet lives elsewhere. If you would rather not grant resource-group creation at the subscription, create the group yourself and name it at cluster creation (`aks.resource_group`); Ankra adopts it and never deletes it.

<Warning>
The `Azure Kubernetes Service Contributor Role` lets the principal retrieve the cluster admin kubeconfig, which Ankra needs to install its agent. Scope it to the resource groups Ankra manages, not the subscription.
</Warning>

## Before you start

- A role in Ankra with `credentials.write` (the built-in `owner` and `admin` roles have it). See [Credentials](/platform/credentials#before-you-start).
- Permission in Microsoft Entra ID to create an application and assign roles on the subscription and resource groups.

## Creating an Azure credential

<Steps>
  <Step title="Create the service principal">
    ```bash
    az ad sp create-for-rbac --name ankra-aks --skip-assignment
    ```
    Note the `appId` (client ID), `password` (client secret) and `tenant`. The secret is shown once - store it in a secret manager, not in a shell history or a ticket.
  </Step>
  <Step title="Assign the roles">
    ```bash
    az role assignment create --assignee <app-id> --role Reader \
      --scope /subscriptions/<subscription-id>
    az role assignment create --assignee <app-id> \
      --role "Azure Kubernetes Service Contributor Role" \
      --scope /subscriptions/<subscription-id>/resourceGroups/<resource-group>
    az role assignment create --assignee <app-id> --role "Network Contributor" \
      --scope /subscriptions/<subscription-id>/resourceGroups/<resource-group>
    ```
    Repeat the resource-group assignments for every group Ankra will manage.
  </Step>
  <Step title="Store it in Ankra">
    <Tabs>
      <Tab title="Portal">
        Go to **Integrations & alerts → Credentials**, click **Add credential**, and under **Cloud providers** choose **Microsoft Azure**. Enter a **Name** (3 to 100 lowercase letters, digits and single hyphens; it cannot change later), the **Subscription ID**, **Tenant ID**, **Client ID** and **Client secret**.

        Click **Test the connection**. You see **The connection works**. Then click **Add credential**; Ankra validates the principal again before storing it, and the credential's page opens.
      </Tab>
      <Tab title="CLI">
        <CliVersion since="0.14.0" />

        ```bash
        export AZURE_CLIENT_SECRET='<client-secret>'   # or omit it and answer the masked prompt
        ankra credentials azure create \
          --name azure-production \
          --subscription-id <subscription-id> \
          --tenant-id <tenant-id> \
          --client-id <app-id>
        ankra credentials azure list
        ```

        The CLI never accepts the secret as a flag: set `AZURE_CLIENT_SECRET` for automation, or let the command prompt for it.
      </Tab>
    </Tabs>
  </Step>
</Steps>

## Rotating the secret

1. Create a new secret on the application in Microsoft Entra ID.
2. In Ankra, open the credential, click **Settings & access**, and under **Replace the secret** enter the **New client secret** (and the **New client ID** if you moved to another application; leave a field empty to keep it). Click **Check and replace**.
3. When you see **The secret is replaced**, delete the old secret in Entra ID.

Ankra checks the new secret with Microsoft Azure before it stores it, so a rejected secret leaves the working one in place. The client secret is write-only: **Stored values** never shows it. See [Replace the secret](/platform/credentials#replace-the-secret).
