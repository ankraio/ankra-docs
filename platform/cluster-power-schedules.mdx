A development or test cluster that runs all night and all weekend costs money while nobody uses it. You can stop it to release its compute, start it again when you need it, and let power schedules do both on a timetable, for example stop at 19:00 on weekdays and start again at 07:00.

Stop, start and power schedules are available for clusters Ankra provisions on Hetzner, OVHcloud, UpCloud, DigitalOcean, Scaleway, AWS EC2, Ankra Cloud, Proxmox VE and HPE Morpheus. A cluster you connected to Ankra cannot be stopped from Ankra: the page says "This cluster was connected to Ankra, so Ankra does not own its servers. Stop and start it where it runs." Managed Kubernetes clusters that support it stop and start at the provider, without schedules; see [Managed Kubernetes](/guides/managed-kubernetes#stopping-and-starting).

## Before you start

- Stopping and starting needs `clusters.operate` on the cluster (Operator, Admin or Owner). Without it the page says "Your role cannot stop or start this cluster. That needs the clusters.operate permission."
- Adding, changing and removing schedules needs `clusters.write` (Member, Operator, Admin or Owner). Without it the page says "Your role can see these schedules but cannot change them."
- Starting creates servers, so the organisation's billing must allow it. Otherwise the start is refused: "The organisation's billing does not allow starting servers right now. Check the plan and payment method, then try again." See [Billing](/platform/billing).

See [Roles and access](/guides/roles-and-access).

## Stop and start a cluster

Go to **Infrastructure → Clusters → &lt;your cluster&gt; → Settings → Stop, start and schedules** (`/next/clusters/<cluster-id>/settings/power`). **Stop or start now** shows the cluster's **State** and **Provider**, and offers **Stop cluster** while the cluster runs and **Start cluster** while it is stopped.

<Tabs>
<Tab title="Portal">

<Steps>
  <Step title="Stop the cluster">
    Click **Stop cluster**. On providers that capture the cluster state, leave **Keep cluster state (recommended)** ticked. Type the cluster's name and click **Stop &lt;cluster name&gt;**.

    **Check:** the page reports the stop with a **Follow the stop** link to its operation, and the state reads stopped once it finishes.
  </Step>
  <Step title="Start the cluster">
    Click **Start cluster**. Where the provider offers it, choose under **What to start**: **Everything** (the control plane and the worker nodes) or **Only the control plane** (workloads cannot run until worker nodes are added). Click **Start cluster**.

    **Check:** the page says Ankra is starting the cluster, with a **Follow the start** link. "Starting takes about 6 minutes, and stopping is offered again once it is running."
  </Step>
</Steps>

</Tab>
<Tab title="CLI">

Stop and start are per-provider commands:

```bash
ankra cluster hetzner stop my-cluster                      # capture state, then tear down
ankra cluster hetzner stop my-cluster --mode pause         # k3s: power off and keep the servers
ankra cluster hetzner start my-cluster                     # restore the captured state
ankra cluster hetzner start my-cluster --scope control_plane
```

The same commands exist under `ovh`, `upcloud`, `digitalocean`, `scaleway`, `aws`, `ankracloud`, `proxmox` and `morpheus`. See the [CLI reference](/reference/cli/cluster).

</Tab>
</Tabs>

### What a stop does

It depends on the provider:

| Provider | Stop | What survives |
|----------|------|---------------|
| Hetzner, OVHcloud, UpCloud, DigitalOcean, Proxmox VE, HPE Morpheus | Captures the cluster's state, then deletes the servers, networks and SSH keys | The state snapshot, the cloud block volumes (HPE Morpheus has none, see below), and everything Ankra holds (cluster record, credentials, stacks, configuration history) |
| Scaleway, AWS EC2 | Powers the servers off and keeps their disks | Everything on the servers; disks and other retained resources keep billing |
| Ankra Cloud | Powers the servers off and keeps their disks | Everything on the servers. Ankra Cloud keeps billing a stopped server, which keeps its disk and its addresses |

**The state snapshot.** On the providers that delete servers, Ankra first captures an encrypted etcd snapshot and stores it in your organisation's oldest ready [backup vault](/concepts/backup-vaults), or in an Ankra-managed default vault when you have none. The servers are deleted only once the snapshot is stored. The capture runs as a **Cluster State Snapshot** operation; if it fails, the cluster stays running and nothing is torn down.

Untick **Keep cluster state (recommended)** (CLI `--preserve-state=false`) to tear down without a snapshot: Secrets, ConfigMaps, custom resources and the bindings between claims and volumes are then lost, and only what Ankra deploys from its own configuration comes back. A forced stop (CLI `--force`) never captures. When the cluster is not reachable, the box cannot be ticked and the dialog says data kept only on the servers' disks is lost.

**Pause instead of tearing down.** On k3s clusters on Hetzner, UpCloud and DigitalOcean, `ankra cluster hetzner stop my-cluster --mode pause` (or the `upcloud` or `digitalocean` command) powers the servers off and keeps them with their disks, so etcd, local data and node identities survive, and a start powers them back on. These providers bill a powered-off server in full, so a pause saves no compute cost. Pause takes no snapshot and cannot be combined with `--force`. The portal has no pause choice; use the CLI.

A stop never deletes the cloud block volumes behind PersistentVolumes, forced or not; at a cloud provider they keep billing while the cluster is stopped. On Proxmox VE the kept disks stay on your own host. HPE Morpheus clusters have no cloud volumes: a disk goes with its server, so data kept only on the servers' disks is lost at a stop. Only deleting the cluster removes the kept volumes; see [Terminate or remove](/platform/cluster-settings#terminate-or-remove).

### What a start does

On the providers that delete servers, a start creates fresh servers with new IP addresses and installs Kubernetes. When a snapshot was captured, the first control plane resets etcd from it, so your Secrets, ConfigMaps, custom resources and persistent volume claims come back, and StatefulSets reattach their existing cloud disks. A kubeadm control plane also gets its certificate authorities back, so existing tokens and kubeconfigs stay valid. To start a fresh cluster instead, use `ankra cluster hetzner start my-cluster --restore-state=false` (or the command for your provider); the portal always restores a captured snapshot.

Stacks and add-ons configured in Ankra are reconciled either way. The snapshot is kept for as long as the cluster stays stopped. Once the cluster runs again, a restored snapshot is kept for 7 more days, and one that was never restored for 90 days from its capture. The [scheduled snapshots](/guides/kubernetes-upgrades#set-the-retention-window) Ankra takes while the cluster runs follow their own retention window.

On Scaleway, AWS EC2 and Ankra Cloud, and after a pause, a start powers the existing servers back on; see [AWS clusters](/guides/aws-clusters#stopping-and-starting).

## Schedule stops and starts

The **Schedules** section on the same page lists the cluster's schedules. A cluster holds at most 20.

### Park a cluster overnight

<Steps>
  <Step title="Open Park overnight">
    Under **Schedules**, click **Park overnight**.
  </Step>
  <Step title="Choose the days and times">
    Choose **Days** (**Monday to Friday** or **Every day**), **Stop at** and **Start at** (19:00 and 07:00 by default) and the **Timezone** (your browser's by default).
  </Step>
  <Step title="Add the pair">
    Click **Add both schedules**.

    **Check:** the table lists **Stop the cluster** and **Start the cluster**, each with its **Next time**.
  </Step>
</Steps>

If the stop schedule is added and the start schedule is not, the dialog says so; click **Add the start schedule** to add only the missing one.

### Add a schedule

<Tabs>
<Tab title="Portal">

<Steps>
  <Step title="Open the dialog">
    Under **Schedules**, click **Add a schedule**.
  </Step>
  <Step title="Choose the action">
    Under **What should happen**, pick **Stop** or **Start**. Each schedule does one thing; add a pair to stop and start the cluster.
  </Step>
  <Step title="Choose when">
    Under **When**, choose **On the same days every week** and set **Days** (**Every day**, **Monday to Friday** or **Saturday and Sunday**), **Time of day** and **Timezone**. To use a cron expression instead, open **Use a cron line instead** and enter a five-field **Cron line**, such as `0 19 * * 1-5`; it replaces the days and time.

    Or choose **Once, at a date and time** and set **Date and time**.
  </Step>
  <Step title="Save">
    Click **Add schedule**.

    **Check:** the new row shows the schedule under **When** and its next run under **Next time**.
  </Step>
</Steps>

A stop schedule added in the portal stops the cluster the way **Stop cluster** does. To schedule a stop that only removes the worker servers (`scale_to_zero`), use the CLI.

</Tab>
<Tab title="CLI">

`ankra cluster power-schedules` works on the active cluster (`ankra cluster select`):

```bash
# Park on weekday evenings, back before the morning
ankra cluster power-schedules create --action stop --cron '0 19 * * 1-5' --timezone Europe/Stockholm
ankra cluster power-schedules create --action start --cron '0 7 * * 1-5' --timezone Europe/Stockholm

# One-off stop that only removes the workers
ankra cluster power-schedules create --action stop --at 2026-01-02T19:00:00Z --stop-mode scale_to_zero
```

`--stop-mode scale_to_zero` deletes only the worker servers at every stop and creates new ones at the next start. The control plane, etcd, cloud volumes and addresses are kept and keep billing. Data on the workers' own disks is lost at every stop, so a cluster with volumes that keep data there (local-path, hostPath, local PVs) needs `--accept-node-local-data-loss` when you are not answering the prompt.

</Tab>
</Tabs>

Ankra AI, an MCP client or a service-account token can schedule or switch on a `scale_to_zero` stop only on a cluster a person has confirmed is not production; otherwise the write is refused and says why. A person confirms this under **Settings → General** with **Confirm it is &lt;purpose&gt;** or **Change what it's used for**; see [Cluster settings](/platform/cluster-settings#general). Schedules you create yourself in the portal, or with the CLI or API on your own token, are not checked.

### Change, pause or remove a schedule

Each row shows the action, **When**, **Next time** and **Last time** with the last outcome (**Ran**, **Skipped** or **Failed**). The row's options menu offers:

- **Change…** opens **Change the schedule**. Change the fields and click **Save schedule**. A stop schedule keeps its stop mode.
- **Pause** keeps the schedule but it never fires; **Resume** arms it for its next occurrence. A paused schedule reads **Paused** under **Next time**.
- **Remove…** asks "Remove this schedule?"; click **Remove**.

<Tabs>
<Tab title="Portal">

Use the row's options menu as above.

</Tab>
<Tab title="CLI">

```bash
ankra cluster power-schedules list
ankra cluster power-schedules update <schedule-id> --action stop --cron '0 20 * * 1-5' --timezone Europe/Stockholm --enabled=false
ankra cluster power-schedules delete <schedule-id>
```

`update` replaces the schedule's action, timing and enabled flag, so restate them; omitting `--stop-mode` or `--preserve-state` keeps the current choice.

</Tab>
</Tabs>

### How schedules run

- A scheduled stop behaves like **Stop cluster**, with the mode and state choice the schedule carries.
- A stop is skipped if the cluster is already stopped or being deprovisioned. A start fires only when the cluster is stopped.
- If the cluster is busy or the action fails transiently, the schedule retries every 5 minutes for up to 24 hours, then records a failure. A repeated schedule still fires at its next occurrence.
- A one-off schedule disarms itself after it fires and stays in the list as a record. A repeated schedule re-arms for its next occurrence.
- Pausing or changing a schedule always wins over a retry in flight.

## Verify

1. Open **Settings → Stop, start and schedules**. After a stop, **Start cluster** is offered; after a start, **Stop cluster** is offered.
2. Open **Operations** on the cluster. A stop on a provider that captures state shows a **Cluster State Snapshot** run.
3. After a scheduled run, the schedule's **Last time** shows when it ran and its outcome.

## What can go wrong

| Message | What to do |
|---|---|
| "Ankra could not check whether an operation is running on this cluster" | Click **Try again**. Stopping and starting are offered once that check succeeds. |
| "Stopping is offered again once it finishes." | An operation is running on the cluster. Follow it with **Follow the operation**, then stop the cluster. |
| "A cluster can have at most 20 schedules. Remove one to add another." | Remove a schedule you no longer need. |
| "The schedule was not added" | Read the reason in the alert, correct the time, timezone or cron line, and save again. |
| A schedule's last outcome reads **Failed** | The action did not succeed within 24 hours of retries. Open **Operations** for the reason; the schedule fires again at its next occurrence. |
