A cluster's **Metrics** page shows what the cluster uses over a window you choose, in tabs of readings and of the cluster's dashboards. The cards of readings work without any setup, because the Ankra agent sends the cluster's metrics to Ankra itself. These are Ankra built-in metrics, described below. A Prometheus you connect adds the readings Ankra built-in metrics do not have, such as disk operations, CPU held back by limits and GPUs.

## Ankra built-in metrics

Ankra built-in metrics are on for every cluster by default. There is nothing to install or connect.

| | |
|---|---|
| **What the agent sends** | A fixed set of about 35 metrics. For each node it sends readiness, pressure conditions, CPU and memory capacity and use, network throughput, root filesystem size and use, the number of running pods, and, from agent 2.1.1357 on, the CPU and memory the pods scheduled on it ask for. For each namespace it sends CPU and memory use, requests and limits, pods by phase, container restarts and out-of-memory kills. For the 200 workloads that use the most CPU, and any workload that is restarting, it sends CPU, memory, pods and restarts. With a Traefik ingress controller it also sends, for each namespace, the request rate, the rate of 5xx responses and the response times. |
| **Where it reads them** | The cluster's node and pod lists from the Kubernetes API, each node's kubelet, and Traefik's own metrics. |
| **What it does not send** | Your applications' own metrics, anything from your own metrics endpoints, kube-state-metrics, and figures per pod or per container. |
| **How often** | Every 30 seconds. |
| **How long Ankra keeps them** | 30 days. |
| **Where you see them** | An application's **Metrics** view, this page, [alert rules](/guides/alerts#watch-clusters) on a cluster metric or on metrics that stop arriving, and the [AI Assistant](/platform/ai-assistant). |
| **Where they are stored** | In Ankra's metrics store, which runs with the rest of the Ankra platform in Finland. See [Where it lives](/security/overview#where-it-lives). |
| **What they cost** | Included in every plan. Ankra does not charge for them. |

The product shows the same metrics under three other labels. The Metrics page calls them **Ankra's readings**, alert rules call them **Platform metrics**, and the [usage report](/platform/usage) lists them as **Hosted metrics**.

### Your own metrics and queries

Ankra built-in metrics are read through the views above. Over MCP, `query_prometheus` and `query_prometheus_range` also answer PromQL from them. Their series are named `ankra_*`, and a query that finds nothing there goes to a connected Prometheus. `ankra cluster metrics query` reads a connected Prometheus only. To chart your applications' own metrics, connect your own [Prometheus](/integrations/prometheus). You can also run VictoriaMetrics on your cluster as a [managed service](/concepts/managed-services) (closed beta) and send your metrics there.

### Turn them off for a cluster

Set `metrics_collect.enabled: false` in the cluster's [agent Helm values](/reference/agent-helm-values). This needs agent 2.1.1339 or later, and older agents ignore the value. The setting lives in the agent, so there is no switch for it in the portal. Once it takes effect, Ankra's readings stop arriving, so the Metrics page says **Late** (not **Off**, which is about where the cluster is connected), and its cards read a connected Prometheus when one answers.

## Before you start

- **A cluster connected to Ankra with its agent online.** The agent sends Ankra built-in metrics. Its connection is on **Settings → Agent** and on the cluster's [Health](/platform/cluster-overview-and-health) page.
- **Permission to read the cluster.** The page needs `clusters.read`. Cards read from a connected Prometheus also need `kubernetes.read`, and so does seeing that Prometheus's address. Every built-in role holds both; see [Roles and access](/guides/roles-and-access).
- **A connected Prometheus, for some cards only.** **Disk operations**, **CPU held back by limits** and the **GPUs** tab read only from a Prometheus. The GPUs also need the NVIDIA DCGM exporter in that Prometheus. To connect one, see [Prometheus](/integrations/prometheus).

## Open the Metrics page

Go to **Infrastructure → Clusters → &lt;your cluster&gt; → Metrics** (`/next/clusters/<cluster-id>/metrics`).

The page is headed **Metrics**, with "What *cluster* uses, over time" under it, and opens on its first tab, **Resources** unless **Edit tabs** put another first, for the last hour of the whole cluster.

## The tabs of Metrics

Each tab of readings opens with a row of numbers for the window, then its cards. A card's title says what it reads and its figure says the reading now, or at the end of the window. Every card has units, and a gap in a line is a moment with no reading, not a zero. Until a reading is in, and when one cannot be read, no card, number or table cell says what it is or that there was none; a number or a cell whose read failed says **Not read**, and one read with nothing in it says **No reading**, or **No requests** for the numbers on **Traffic**.

| Tab | Its numbers | Its cards |
|---|---|---|
| **Resources** | **CPU, at the busiest** and **Memory, at the busiest**, each with what pods ask for; **Fullest disk**; **Nodes ready** | **CPU** and **Memory**, each against all the cluster has and what pods ask for; **Disk, by node**; **Pods waiting** |
| **Nodes** | **Nodes ready**; **Most memory used**; **Fullest disk**; **Nodes, a month**, such as "6 nodes on Hetzner" | A table of the nodes, then **CPU, by node**; **Memory, by node**; **Nodes ready**; **Nodes short of memory or disk**; **Network in, by node**; **Disk operations** |
| **Namespaces** | **Most CPU**; **Most memory**; **Restarts**; **Asked for, not used** | **CPU, by namespace**; **Memory, by namespace**; **Restarts, by namespace**; **Stopped for memory**; **CPU held back by limits**; then what each namespace asks for and uses, below |
| **Traffic** | **Requests a second**; **Failed, at the worst**; **Response time p95** | **Requests a second**; **Requests that failed**; **Response time**; then **By application** |
| **GPUs** | How busy each of the first two GPUs was at its most, such as **gpu-0, busiest**; **GPU memory, most**, in GiB, against the memory each GPU has ("of 24 each"); **Power, most** | **GPU busy**; **GPU memory**; **GPU temperature**; **GPU power** |

**Traffic** is shown for a cluster with an ingress. **GPUs** is shown only when a connected Prometheus answers with readings from the NVIDIA DCGM exporter. A GPU is named by its index on the node and its model, such as `gpu-0 (NVIDIA L4)`, or by its UUID when the exporter sends no index.

The table on **Nodes** has a row per node: its role, whether it is **Ready**, **Not ready**, **Not answering**, or only **Answering** until Kubernetes' list of nodes is read, CPU and memory used against what its pods ask for, its disk, the pods it has room for, and what it costs **A month** on its provider, or **Not priced**. Press a node's name to narrow the page to that node, and press it again for the whole cluster.

**By application**, at the end of **Traffic**, links each application on the cluster to its own [Metrics](/platform/application-page#metrics), on the environment it runs in there and for the same window.

### Response time

**Response time** on **Traffic** draws **Half within**, **95 in 100 within** and **99 in 100 within**: the time half, 95 in 100, or 99 in 100 of the requests took at most, read over all the cluster's requests at once, from every namespace whose requests and response times Ankra read in full, or over one namespace's on a page narrowed to it. While the card reads your Prometheus instead, it takes every request that Prometheus holds, because a Prometheus does not record whether a namespace was read in full, and with both Traefik and ingress-nginx it draws the longer of their two lines. **Response time p95** in the tab's row of numbers is not read from these lines: it is the slowest namespace's, so a single slow namespace always shows there. **Spread** shows instead the share of requests answered within each band of time.

The ingress measures response time against a set of bounds, and its highest bound is as far as it measures. Where a percentile lies above that bound, Ankra knows only that it is over it, so the line is drawn dotted at the bound and named *more than*, and the **Response time p95** number reads, for example, "more than 5000 ms". The card then says "Dotted: longer than the ingress measures, drawn at its highest bound."

### Size namespaces against their requests

**Namespaces** ends with **Asked for, and used at the busiest**, a row per namespace:

| Column | What it shows |
|---|---|
| **Namespace** | The namespace |
| **CPU, used of asked** | The most CPU it used in the window against the CPU it asks for, in cores |
| **Memory, used of asked** | The most memory it used against the memory it asks for, in GiB |
| **Not used, a month** | What the room it asks for and did not use costs a month, or **Not priced** |

The heading row adds up what was not used, and **Cost** opens the cluster's [Cloud Cost](/platform/cloud-cost) page. The price splits what the cluster's nodes cost a month half for their cores and half for their memory. A namespace that uses far less than it asks for holds room other workloads cannot be scheduled onto. When the namespaces' use could not be read, every row says **Not read**; a namespace the source left out says **No reading**. Either way, what was not used is not added up.

## Choose what the charts show

One row of controls above the numbers serves every tab of readings:

| Control | Choices |
|---|---|
| **Whole cluster** | Narrow the page to one node or one namespace, picked from the cluster's own lists. **Show the whole cluster** (the cross beside it) goes back. Inside one namespace, **Namespaces** shows its workloads: **CPU**, **Memory**, **Restarts, by workload**, **Stopped for memory**, **Pods waiting** and **CPU held back by limits**. |
| Time range | The button shows the current window. Pick a quick range from **Last 5 minutes** to **Last 30 days**, or set **From** and **To** under **Absolute time range**. Ankra keeps its readings for 30 days, so a window cannot reach further back. |
| Compare | **No comparison**, or **Compare: the hour before** (for a window of another length, the window before it). The window before is drawn dotted on **CPU**, **Memory** and **Requests a second**. |
| Auto-refresh | **Auto-refresh: off** (the default), or every 10 seconds, 30 seconds, minute or 5 minutes. **Read again** reads every card once now. |
| **Back to the last hour** | Shown when the window does not end now. |

The page address keeps the tab, the window, the node or namespace, the comparison, the refresh and the events shown, so you can bookmark or share a view. Each tab is a link of its own.

### Events across the charts

On the tabs of readings, below the controls, the chips **Changes**, **Nodes**, **Alerts** and **Ankra's checks** say how many of each fell in the window, and they are drawn across the charts. **Changes** are deploys and the other operations on the cluster that are not work on its nodes, scaling workers and changing node groups included. Ankra's own background work is a change when it recorded that it changed something, failed or was cancelled, and otherwise it is one of **Ankra's checks**, which start hidden. **Nodes** are a node going not ready or becoming ready, a gap in the node readings, and work on nodes, such as a restart, a repair or a Kubernetes upgrade. **Alerts** mark where each alert firing began, and again where it resolved. A **Nodes** or **Alerts** chip without a count means Ankra could not read node readiness or alert firings this time. Press a chip to show or hide its kind. Point at a mark under a chart, or move between the marks with the arrow keys, and it says its kind, what happened, when, who started it when Ankra knows, and its status. Use them to tie a change in usage to what caused it. The cluster's operations, with their status, are on its [Operations](/platform/operations) page, which leaves out Ankra's finished checks.

### What changed

**What changed**, at the end of the events row, lists the window's events in a panel beside the charts. The number on it is how many events the panel opens with.

The panel lists the events by day in UTC, the newest first: when, what happened, its kind, who started it when Ankra knows, and how it ended, such as **Succeeded**, **Failed** or **Not ready**. Where an alert fired, it reads **Firing** while it fires and **Fired** once it has ended; where it ended is its own event, **Resolved**. It lists **Changes**, **Nodes** and **Alerts** whichever chips are pressed. **Show Ankra's own checks** adds Ankra's checks, and is on from the start when that chip is. Where an event is an operation, its name opens that operation, and **Open Operations** at the bottom opens the cluster's [Operations](/platform/operations) page.

A day lists its latest 40 events, and says how many there were when there were more. When the window holds more events than Ankra sends at once, the panel says so and its counts carry a plus sign. Pick a shorter time range to see the rest. When Ankra could not read the events, the alerts or whether the nodes were ready, the panel says that instead of "Nothing changed in this stretch."

### When something went wrong

When the window on **Resources**, **Nodes** or **Namespaces** holds a node that stopped answering, or pods the kernel stopped for memory, a card above the charts says what happened and when: from the first of them to the last, the node ready again, its readings stopped or the last pod stopped for memory. While a node is still away, the card says since when it stopped answering, or runs to the window's end when the window ends first. When Ankra could count the stops for memory only over the whole window, the card spans the window. It says **Over** once the readings show every node that stopped answering ready again, and no pod stopped for memory after. A card for pods stopped for memory alone never says **Over**, because the readings do not show when that ended. Its label says **Ankra's readings**, or **Ankra's readings and your Prometheus** when a figure on it was read by your Prometheus. Its figures come from the same readings as the charts below: how many times the kernel stopped a pod for memory, how many minutes the node was away (**so far** while it still is, **at least** when the window ends first, **then stopped reporting** when its readings stopped), or how many nodes were away when there were several, the most pods waiting at once, and the worst share of one namespace's requests that failed. A namespace's page leaves out the nodes, and a node's page counts only the minutes that node was away. **Ask Ankra what happened** asks Ankra in the chat about the same minutes, with those figures, for what happened in order, why, and what would stop it next time. It shows to a role that can use Ankra AI. No card shows when Ankra could not read the events.

## Dashboards of the cluster

After the readings, the tabs hold the cluster's dashboards shown as tabs, then **All dashboards**.

- **All dashboards** lists the cluster's dashboards, with **Show as a tab** or **Take off the tabs** beside each. Taking one off everyone's tabs is for a person who may change the cluster. **New dashboard** makes an empty one that only you see and opens it there, and you can ask Ankra for one.
- **Add a tab** offers the same, and a dashboard made with **New dashboard** there is put on your own tabs. Shown as a tab, a dashboard everyone can open goes on everyone's tabs when you may change the cluster; any other goes on your own tabs, after everyone's.
- **Edit tabs** sets the order of the tabs for everyone on the cluster, for a person who may change the cluster.

One dashboard shows who made it, when it was last saved, and who sees it, then the time range, **Edit layout**, **Add a card**, **Ask Ankra** and **More**: **Share**, **Versions**, the tab, and **Open on its own page**. **Edit layout** and **Add a card** are shown to a person who may change the dashboard, and **Ask Ankra** to one who may also use Ankra AI.

A card of one of this page's readings is drawn as on the tabs above, over the time the page shows, and while that time ends now it is read again as often as **Auto-refresh** says or, with it off, every minute, or every five minutes when it is longer than a day. Its **Alert**, where the card on the tabs has one, is not narrowed to a node or a namespace: on CPU and memory it starts on **Any one node**, and the other conditions watch the whole cluster. A dashboard that also holds other cards keeps all of them on one time range: the page's when the dashboard offers it, its own otherwise.

### Add a card

**Add a card** lists what Ankra measures on the cluster, charted as on the tabs above, under **Resources**, **Nodes**, **Namespaces** and **Traffic**. Search by name. **Add** puts the card last on the dashboard, reading this cluster, and saves it as a new version. A card already on the dashboard reads **On it**. A card drawn as lines marks the cluster's deployments and alerts, as the tabs do. When the cluster has no Prometheus of its own, **From your Prometheus** says so, with **Connect one**.

When it has one, **From your Prometheus** takes **A PromQL query**. It is asked of that Prometheus through the cluster's agent, and needs the right to read Kubernetes on the cluster. **Try it** draws what the query answers over the time the dashboard shows. If your Prometheus refuses the query, the panel says so, and quotes its reason when Ankra receives one. **Add this card** is offered once the query you see was tried and answered: it puts a line chart named by the query last on the dashboard, as a new version, or joins what you are arranging. A query is at most 2000 characters. A card draws at most 10 lines: when the query answers more, the 10 whose newest value is furthest from zero, and it says how many there were.

### Arrange a dashboard

**Edit layout** puts **Move up**, **Move down**, **Narrower**, **Wider** and **Take off** on each card. The cards follow their order, each a third, a half, two thirds or the whole row wide. A card you add meanwhile joins the rest, and is saved or dropped with them. When **Save layout** finds the dashboard was changed somewhere else meanwhile, **Add a card** waits until you choose which to keep. On a narrow window the cards stand one to a row, and can be arranged there too. **Save layout** saves the result as a new version for everyone who opens the dashboard, and only closes when nothing changed. **Cancel** asks before it drops your changes. A dashboard keeps one card at least.

### Ask Ankra for a dashboard

**Ask Ankra for a dashboard** asks what you want to see, and Ankra answers on the page: the dashboard it proposes, why, and its cards. **Make this dashboard** makes it, as one only you see, and opens it under **All dashboards**. On a dashboard, **Ask Ankra** asks what should change, and **Add these cards** adds the cards it does not hold yet as a new version. An answer without a dashboard, or one that asks you something back, goes on in the chat with **Continue in chat**. Either way the question and its answer are one of your chat conversations.

## Where a reading comes from

Each chart card of readings reads Ankra built-in metrics, and names its source only when it is not Ankra's own: such a card says **Your Prometheus**. The card for when something went wrong always names its source: **Ankra's readings**, or **Ankra's readings and your Prometheus**. A card reads your Prometheus when only a Prometheus has the reading (**Disk operations**, **CPU held back by limits** and the GPUs), or while Ankra's readings are late or off and a connected Prometheus answers. A stopped cluster's cards read Ankra's history, which ends where the cluster stopped, and each figure says the moment it stopped.

When the readings are not the usual ones, one line under the controls of a tab of readings says so:

| Badge | What it says |
|---|---|
| **Just connected** | The first readings arrive within 2 minutes. |
| **Late** | Ankra's readings have stopped arriving, and when the last one did. With a connected Prometheus that answers, the cards read it until Ankra's catch up. |
| **Stopped** | Since when the cluster is stopped. The lines end there. A window that starts after it stopped says so, and asks you to pick an earlier one. |
| **Off** | Ankra's readings are not offered where this cluster is connected, and whether the cards read your Prometheus. |
| **Prometheus** | Your Prometheus is not answering, so the cards that read it are empty. |

### About these readings

**About these readings**, at the bottom of every tab of readings, says:

| Row | What it says |
|---|---|
| **Ankra's readings** | How often they arrive and when the last one did, and that they are kept 30 days; or that they are late, not on for this cluster, or have not arrived yet |
| **Your Prometheus** | **None connected**, or its address and whether it is answering. The address is the scheme, host and path only, never a user name, password or query, and is shown only to a person with `kubernetes.read`. |
| **Times** | Every time is UTC, and each point is the average of the minutes it covers, so a spike between two points still counts in them. On a short window, a rate from your Prometheus covers the 5 minutes before its point, the least a rate needs. |

**Change your Prometheus** opens the cluster's **Settings → Integrations** page, where you connect or change one.

## Alert from a chart

**CPU**, **Memory**, **Disk, by node** (**Disk** on a page narrowed to a node or a namespace), **Pods waiting**, **Nodes ready**, **CPU, by node**, **Memory, by node**, **Restarts, by namespace** (**Restarts, by workload** inside a namespace), **Stopped for memory** and **Requests that failed** have an **Alert** button. **Requests that failed** has none on a page narrowed to a node. The button opens **Alert from this chart** with an alert on what the card reads:

| Field | What it sets |
|---|---|
| **Tell me when** | The condition, such as **Memory used is above** or **Pods waiting are more than**. |
| **Level, in percent** | The number it must pass. For a count it reads **Level, in pods**, or in nodes, times or restarts. |
| **Of** | CPU and memory only: **Any one node**, **The whole cluster**, or one node. The other conditions follow the page: narrowed to a node or a namespace, the alert watches it where the condition can. From a dashboard's card they watch the whole cluster. |
| **For at least** | **1 minute**, **5 minutes** (the default), **15 minutes** or **30 minutes**. |
| **Tell** | One of the organisation's [alert destinations](/guides/alerts#who-is-told) that is turned on. With none, it offers **Nobody yet: it is listed under Alert rules**: the alert tells no destination, and its firings show on the alert's own page. |

Below the fields, Ankra replays the alert over the last 7 days, a minute at a time, which is how often its rule evaluator reads, and says when it would have fired, with a chart of the readings and the level. Minutes it has no reading for are said, and not counted. **Create alert** makes the alert on this cluster, named after the cluster and the condition, such as **eu-production: Memory used above 85% on any one node**, and listed under **Integrations & alerts › Alert rules**. It takes the **alerts.manage** permission on the organisation.

The button shows only to someone who may manage alerts.

## From the CLI

The CLI reads live usage and runs PromQL against the connected Prometheus.

<CliVersion since="0.74.0" />

```bash
# Live CPU and memory per node and per pod, from metrics-server
ankra cluster top nodes --sort-by cpu
ankra cluster top pods --all-namespaces --sort-by memory

# The connected Prometheus: which source is registered, then a query
ankra cluster metrics source
ankra cluster metrics query 'up'
ankra cluster metrics query-range 'rate(node_cpu_seconds_total[5m])' --range 6h --step 5m
```

`ankra cluster top` needs metrics-server in the cluster, not Prometheus. `ankra cluster metrics query` and `query-range` need a connected Prometheus. Over MCP, the same reads are `get_node_usage`, `get_pod_usage`, `query_prometheus` and `query_prometheus_range` ([MCP tools](/platform/mcp-tools)). The two query tools also answer from Ankra built-in metrics, so they work without a connected Prometheus. Every flag is in the [CLI reference](/reference/cli/cluster#ankra-cluster-metrics).

## What can go wrong

**A card reads "Needs your Prometheus. Connect one".**
Only a Prometheus has this reading, and the cluster has none connected. **Connect one** opens the cluster's **Settings → Integrations** page; see [Prometheus](/integrations/prometheus).

**A card reads "Your Prometheus is not answering."**
Ankra reached the connected Prometheus and its queries failed, or its address cannot be read. Follow [what can go wrong with a Prometheus](/integrations/prometheus#what-can-go-wrong), then press **Read again**.

**A card reads "Ankra does not offer this reading here yet."**
The platform does not have this reading yet, whichever source the page reads, so there is nothing to draw.

**A card reads "Could not be read just now."**
The source did not answer, or answered in a way the page cannot read. A failed read is asked for once more first when that can help. Press **Read again**.

**A card reads "No reading yet."**
Ankra has not received a reading from the cluster yet. A cluster that has just connected sends its first within 2 minutes. If it stays like this, check the agent's connection on **Settings → Agent** or the **Cluster agent** check on the cluster's [Health](/platform/cluster-overview-and-health) page.

**The page says Late.**
The agent is not sending metrics: it is not connected, or metrics collection has been turned off in the agent. Check its connection as above. [Agent Helm values](/reference/agent-helm-values) describes the `metrics_collect.enabled` setting. While a connected Prometheus answers, the cards read it until Ankra's readings catch up.

**A card reads "Ankra's readings are not on for this cluster."**
Ankra built-in metrics are not offered where this cluster is connected, so the cards can read only a connected Prometheus. Connect one; see [Prometheus](/integrations/prometheus).

**A card reads "Your role may not read this."**
Your role does not hold the permission the reading needs: `kubernetes.read` for a reading from a connected Prometheus. See [Roles and access](/guides/roles-and-access).

**A card reads "Some lines are left out".**
The source sent only part of the card's lines, so the chart does not show all of them. Choose one node or namespace in **Whole cluster** to see the rest.

**The tabs read "The tabs of this cluster could not be read just now."**
Ankra could not read the order of the cluster's tabs. Until it can, the readings are shown in Ankra's order, the dashboards are under **All dashboards**, and **Edit tabs** is not offered. Press **Try again**.

**There is no GPUs tab.**
The tab is shown only when a connected Prometheus answers with GPU readings. Install the NVIDIA DCGM exporter in the cluster and have that Prometheus scrape it.

**A Traffic card reads "Counted by namespace, not node." or "Timed by namespace, not node."**
The page is narrowed to a node, and requests are counted per namespace. Choose **Whole cluster** or a namespace.
