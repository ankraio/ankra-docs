A cluster's **Metrics** page charts its resource usage and workload signals over a window you choose. The charts work without any setup, because the Ankra agent sends the cluster's metrics to Ankra itself. These are Ankra built-in metrics, described below. A Prometheus you connect adds the charts Ankra built-in metrics cannot draw, such as network drops, CPU throttling and GPU telemetry.

## Ankra built-in metrics

Ankra built-in metrics are on for every cluster by default. There is nothing to install or connect.

| | |
|---|---|
| **What the agent sends** | A fixed set of about 35 metrics. For each node it sends readiness, pressure conditions, CPU and memory capacity and use, network throughput, root filesystem size and use, and the number of running pods. For each namespace it sends CPU and memory use, requests and limits, pods by phase, container restarts and out-of-memory kills. For the 200 workloads that use the most CPU, and any workload that is restarting, it sends CPU, memory, pods and restarts. With a Traefik ingress controller it also sends, for each namespace, the request rate, the rate of 5xx responses and the response times. |
| **Where it reads them** | The cluster's node and pod lists from the Kubernetes API, each node's kubelet, and Traefik's own metrics. |
| **What it does not send** | Your applications' own metrics, anything from your own metrics endpoints, kube-state-metrics, and figures per pod or per container. |
| **How often** | Every 30 seconds. |
| **How long Ankra keeps them** | 30 days. |
| **Where you see them** | An application's **Metrics** view, this page, [alert rules](/guides/alerts#watch-clusters) on a cluster metric or on metrics that stop arriving, and the [AI Assistant](/platform/ai-assistant). |
| **Where they are stored** | In Ankra's metrics store, which runs with the rest of the Ankra platform in Finland. See [Where it lives](/security/overview#where-it-lives). |
| **What they cost** | Nothing is charged for them during the pilot. |

The product shows the same metrics under three other labels. This page's **Source** control calls them **Ankra metrics**, alert rules call them **Platform metrics**, and the [usage report](/platform/usage) lists them as **Hosted metrics**.

### Your own metrics and queries

Ankra built-in metrics are read through the views above. Over MCP, `query_prometheus` and `query_prometheus_range` also answer PromQL from them. Their series are named `ankra_*`, and a query that finds nothing there goes to a connected Prometheus. `ankra cluster metrics query` reads a connected Prometheus only. To chart your applications' own metrics or build dashboards, connect your own [Prometheus](/integrations/prometheus). You can also run VictoriaMetrics on your cluster as a [managed service](/concepts/managed-services) (closed beta) and send your metrics there.

### Turn them off for a cluster

Set `metrics_collect.enabled: false` in the cluster's [agent Helm values](/reference/agent-helm-values). This needs agent 2.1.1339 or later, and older agents ignore the value. The setting lives in the agent, so there is no switch for it in the portal. Once it takes effect, the **Ankra metrics** row on this page reads **Not receiving recent metrics**, and the charts can read only a connected Prometheus.

## Before you start

- **A cluster connected to Ankra with its agent online.** The agent sends Ankra built-in metrics. Its connection is on **Settings → Agent** and on the cluster's [Health](/platform/cluster-overview-and-health) page.
- **Permission to read the cluster.** The page needs `clusters.read`. Charts read from a connected Prometheus also need `kubernetes.read`. Every built-in role holds both; see [Roles and access](/guides/roles-and-access).
- **A connected Prometheus, for some charts only.** Network drops, Disk operations, CPU throttling and the GPU telemetry charts read only from a Prometheus. GPU telemetry also needs the NVIDIA DCGM exporter in that Prometheus. To connect one, see [Prometheus](/integrations/prometheus).

## Open the Metrics page

Go to **Infrastructure → Clusters → &lt;your cluster&gt; → Metrics** (`/next/clusters/<cluster-id>/metrics`).

The page is headed **Understand cluster usage** and opens on the **Resources** charts for the **Last 1 hour**.

## Choose the window and the charts

The **Metrics view** section at the top holds every control. The page address keeps the time range, chart group, source and filters, so you can bookmark or share a view.

| Control | Choices |
|---|---|
| Time range | The button shows the current window. Pick a quick range from **Last 5 minutes** to **Last 30 days**, or set **From** and **To** under **Absolute time range** and click **Apply time range**. A window covers at least a minute and at most 30 days, and cannot end in the future. |
| **Automatic refresh** | **Paused** (the default), **Every 30 seconds** or **Every minute**. **Refresh metrics** at the top of the page reads every chart again at once. |
| **Metrics** | The group of charts to show. The groups are listed in the next section. |
| **Source** | **Choose an available source** (the default), **Ankra metrics** or **Connected Prometheus**. |
| **Node filter** | An exact node name. Leave it empty for all nodes. |
| **Namespace filter** | An exact namespace. Leave it empty for all namespaces. |

Type a filter and click **Apply filters**; **Clear filters** empties both. The charts redraw for the new window, group, source or filter.

With **Choose an available source**, each chart reads Ankra built-in metrics when the cluster is sending them and they can draw that chart. Otherwise it reads the connected Prometheus.

## What each group charts

| Group | Charts | Drawn from Ankra built-in metrics |
|---|---|---|
| **Resources** | CPU usage, Memory usage, Filesystem usage, Node readiness | All four |
| **Network and disk** | Network throughput, Network drops, Disk operations | Network throughput only |
| **Workloads** | CPU by namespace, Memory by namespace, Pods by phase, Pod restarts, Out-of-memory events, CPU throttling | All except CPU throttling |
| **Ingress traffic** | HTTP requests; Successful HTTP responses; HTTP response time, p95; HTTP response time, p50; HTTP response time, p99; HTTP response time spread | All six, when the ingress controller is Traefik. The p50, p99 and spread charts are drawn from Ankra built-in metrics only: see [Response time in Ingress traffic](#response-time-in-ingress-traffic) |
| **GPU telemetry** | GPU utilisation, GPU memory used, GPU temperature, GPU power draw | None: needs a connected Prometheus with the DCGM exporter |
| **Namespace sizing** | A table of requests against usage per namespace, described below | Yes |

Under each chart, a line names the source that answered and when it was read. A chart with more than one series has a selector to show one series or **All series**. Operations recorded in the window are marked on the charts. Missing samples stay gaps in the line: a gap is not a zero.

### Response time in Ingress traffic

**HTTP response time, p50** and **HTTP response time, p99** have a line for each namespace: the time half, or 99 in 100, of its requests took at most. The ingress measures response time against a set of bounds, and the highest bound is as far as it measures. Where a percentile lies above that bound, Ankra knows only that it is over it: the line carries the bound and its name ends in **more than**, such as *namespace*, p99 more than.

**HTTP response time spread** has a line for each namespace and bound, such as *namespace*, within *bound*: the share of the namespace's requests that finished within that bound. The platform sends at most 20 of these lines, and the chart then says it left out the ones with the smallest share of requests. Set the **Namespace filter** to see more. When nothing came in, the chart reads **No requests measured**.

Only Ankra built-in metrics answer these three charts. When **Source** is **Connected Prometheus**, or **Choose an available source** finds Ankra built-in metrics not enabled or not arriving, they read "This metric is unavailable." with "Check the source and filters. This is not a zero measurement."

## Check where the metrics come from

Below the controls, three rows say what the page can read:

| Row | What it says |
|---|---|
| **Ankra metrics** | **Receiving metrics**, **Not receiving recent metrics** or **Not enabled** |
| **Connected Prometheus** | **Not configured**, **Connected and answering**, **Connected but failing**, **Configured without an endpoint** or **Connected, not checked yet** |
| **Last ingestion** | When Ankra last received Ankra built-in metrics from the cluster, or **Not recorded** |

**Configure a metrics source** opens the cluster's **Settings → Integrations** page, where you connect a Prometheus.

## Size namespaces against their requests

Choose **Namespace sizing** in **Metrics**. A table compares what each namespace requests with what it used over the most recent stretch of the selected window's length:

| Column | What it shows |
|---|---|
| **Namespace** | The namespace |
| **CPU used / requested** | Measured CPU against requested CPU, in cores |
| **Memory used / requested** | Measured memory against requested memory, in MiB |
| **Hourly cost** | The namespace's hourly cost in cents, or **Not reported** |

The table covers every namespace. The node and namespace filters apply to the charts, not to this table. A namespace that uses far less than it requests holds capacity other workloads cannot schedule onto.

## See the operations in the window

**Operations during this window**, at the bottom of the page, lists the platform operations recorded in the selected window with their **Operation**, **Time** and **Status**. Click an operation's name to open it. When nothing ran, the section reads "No operations were recorded in this window." Use it to tie a change in usage to a deploy or an upgrade. Operations are described on [Operations](/platform/operations).

## From the CLI

The CLI reads live usage and runs PromQL against the connected Prometheus.

<CliVersion since="0.74.0" />

```bash
# Live CPU and memory per node and per pod, from metrics-server
ankra cluster top nodes --sort-by cpu
ankra cluster top pods --all-namespaces --sort-by memory

# The connected Prometheus: which source is registered, then a query
ankra cluster metrics source
ankra cluster metrics query 'up'
ankra cluster metrics query-range 'rate(node_cpu_seconds_total[5m])' --range 6h --step 5m
```

`ankra cluster top` needs metrics-server in the cluster, not Prometheus. `ankra cluster metrics query` and `query-range` need a connected Prometheus. Over MCP, the same reads are `get_node_usage`, `get_pod_usage`, `query_prometheus` and `query_prometheus_range` ([MCP tools](/platform/mcp-tools)). The two query tools also answer from Ankra built-in metrics, so they work without a connected Prometheus. Every flag is in the [CLI reference](/reference/cli/cluster#ankra-cluster-metrics).

## What can go wrong

**A chart reads "This metric is unavailable." with "Choose Connected Prometheus for this metric."**
The chart is one Ankra built-in metrics cannot draw and **Source** is set to **Ankra metrics**. Set **Source** to **Connected Prometheus**, and connect one first if **Connected Prometheus** reads **Not configured**.

**A chart reads "This metric is unavailable." with "Check the source and filters. This is not a zero measurement."**
The source did not answer. Read the source rows: **Connected but failing** means Ankra reached the Prometheus and its queries failed; follow [what can go wrong with a Prometheus](/integrations/prometheus#what-can-go-wrong). Click **Try again** on the chart once the source answers.

**A chart reads "No samples returned".**
The source answered with nothing for this window. Filters match exact names only, so check the spelling of the node or namespace, or clear the filters. For a chart drawn from a connected Prometheus, the exporter behind it must run in the cluster: node-exporter for Network drops, the kubelet's cAdvisor metrics for Disk operations and CPU throttling, and the DCGM exporter for GPU telemetry.

**Ankra metrics reads "Not receiving recent metrics".**
The agent is not sending metrics: it is not connected, or metrics collection has been turned off in the agent. Check its connection on **Settings → Agent** or the **Cluster agent** check on the cluster's [Health](/platform/cluster-overview-and-health) page. [Agent Helm values](/reference/agent-helm-values) describes the `metrics_collect.enabled` setting.

**Ankra metrics reads "Not enabled".**
Ankra built-in metrics are not offered where this cluster is connected, so the charts can read only a connected Prometheus. Connect one; see [Prometheus](/integrations/prometheus).

**The source rows read "The source status could not be read. Charts report their own results."**
Ankra could not read the cluster's metrics sources. Each chart still reports whether it could be drawn. Click **Refresh metrics** to read them again.
