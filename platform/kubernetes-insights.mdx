You need to see what is really running in a cluster, and fix it, without switching kubectl contexts or handing out kubeconfigs. Every cluster connected to Ankra has a **Kubernetes** menu that lists the resources the Ankra Agent reports, and lets you act on them within your organisation permissions.

This page covers what Ankra adds on top of the Kubernetes objects and where each one lives in the menu. For what a Deployment or a PersistentVolume is, see the [Kubernetes documentation](https://kubernetes.io/docs/concepts/).

## Where Everything Is

Open **Infrastructure → Clusters → &lt;your cluster&gt; → Technical details → Kubernetes** (`/next/clusters/<cluster-id>/kubernetes`). The side menu switches to the Kubernetes menu; the cluster's name at its top takes you back to the cluster.

| Menu entry | What it holds |
|------------|---------------|
| **All resources** | Every resource type, grouped as below, with a search box. Pick a type to open its list. |
| **Cluster logs** | Logs across the whole cluster, live or from history. See [Logs](/platform/logs). |
| **Workloads** | Pods, Deployments, StatefulSets, DaemonSets, ReplicaSets, Jobs, CronJobs, Horizontal Pod Autoscalers, Pod Disruption Budgets |
| **Networking** | Services, Ingresses, Ingress Classes |
| **Storage** | Persistent Volumes, Persistent Volume Claims, Storage Classes, CSI Drivers |
| **Configuration** | ConfigMaps, Secrets |
| **Access & policies** | Roles, Role Bindings, Cluster Roles, Cluster Role Bindings, Service Accounts, Network Policies |
| **Cluster** | Nodes, Namespaces, Events, Custom resource definitions |
| **Helm** | Helm releases |

Pod Disruption Budgets are under **Workloads**, and Network Policies under **Access & policies**. On **All resources** the access group is headed **RBAC**. Endpoints, LimitRanges, CSINodes and VolumeAttachments have no menu entry; read them with the CLI, which takes any kind:

<CliVersion since="0.2.1" />

```bash
ankra cluster get resources LimitRange -n my-namespace
ankra cluster get resources Endpoints -n my-namespace
```

## Resource Lists

Each list has a name search, a **Resource type** picker that jumps to another kind, and, for namespaced kinds, a **Namespace** field: type a namespace and click **Apply namespace**, or leave it on **All namespaces**. Click a column heading to sort. Long lists page with **Next page** and **First page**.

The name search, such as **Find secrets by name**, searches the whole list, not only the page shown, and the line under the list says how many resources match. Two lists match only what they have loaded: **Helm releases** (**Filter this page by name**) and **Nodes** (**Filter loaded nodes by name**). Sorting by a column orders only the page shown. **Events** from the platform's copy are listed newest first, by **Last seen**, until you sort a column; the line under the list says **Newest first** when they are.

Above the list a line says how fresh the data is, for example `Showing resources from the platform cache. Last sync was 12 seconds ago.` When the agent is not reporting it reads `The cluster is offline. These are previously recorded resources.` or `These resources may be out of date.`, and you see the last copy Ankra recorded. **Refresh** reads the list again.

To act on several resources at once, tick their checkboxes in the list. Only the checkbox selects a row: clicking a name or another cell leaves the selection as it is. Shift-click a second row to select every row between, tick the checkbox in the header to select every row shown, and press Escape to clear. A bar above the list says how many are selected, for example **2 of 14 deployments selected**, and offers **Delete…**, **Restart…** on Deployments, StatefulSets and DaemonSets, **Review actions** when one row is selected, and **Clear selection**. One review covers at most 20 resources and is the same as for one resource, below: type `DELETE 3 RESOURCES` or `RESTART 3 WORKLOADS` to confirm. Checkboxes show only while the list is read fresh, and not on **Helm releases**, which change one release at a time.

## What Every Resource Page Has

Click a resource to open its page. The tabs are:

| Tab | What it shows | On |
|-----|---------------|----|
| **Overview** | Status, the kind's key fields, an **Identity** card (name, scope, API, created, resource UID) and **Conditions** | Every resource |
| **Configuration** | Runtime settings and references Kubernetes reports. Environment values, annotations and Secret contents are not included. | Every resource except Helm releases |
| **Connections** | The resources this one declares a reference to, such as its owner, the volumes and claims it mounts, or the role a binding grants. Rows link to the other resource. A declared reference is not proof that traffic flows. | Every resource except Helm releases |
| **Pods** | The matching pods, each with its node and links to its **Logs**, **Metrics** and **Exec** | Deployments, StatefulSets, DaemonSets, ReplicaSets, Jobs, Services, Namespaces |
| **Events** | The Kubernetes events for this object | Every resource except Helm releases |
| **YAML** | The whole object as Kubernetes reports it, status included, without `managedFields`. Read only. | Every resource except Helm releases |

A namespace page also has **Browse this namespace**, with a link to each namespaced kind filtered to that namespace. The cluster-wide event list is **Cluster → Events**.

On the **YAML** tab, values that look like credentials, and every Secret value, are shown as `[protected]`.

### Change a resource

A resource's page has one button per action: **Restart…** on a Deployment, StatefulSet or DaemonSet, **Edit manifest…**, **Reveal values…** on a Secret, and **Delete…**. To delete or restart several, tick them in the list and use the bar above it. With one row ticked the bar also offers **Edit manifest…**, and **Reveal values…** on a Secret. The buttons appear while the list is live; on cached or offline data there is nothing to change.

Each button reads the object live from the cluster, then opens a window on that one action, titled for it, such as **Delete db-backup-29891640** or **Delete 3 jobs**. Its first sentence says where the object comes from, and for a delete a few lines say what deleting this kind does: for a Job, whether its CronJob keeps its schedule; for a StatefulSet, what happens to its volume claims; for a namespace, that everything in it goes too.

| Button | Does | Confirm with | Needs |
|--------|------|--------------|-------|
| **Edit manifest…** | Opens the manifest in an editor. The name, the namespace, ownership and what Kubernetes itself writes are fixed. | **Apply changes** | `kubernetes.write` |
| **Restart…** | A rolling restart: Kubernetes replaces the pods as the workload's rollout settings say. | **Restart deployment**, or **Restart 3 deployments** | `kubernetes.write` |
| **Delete…** | Deletes the object. | **Delete job**, or **Delete 3 jobs** | `kubernetes.write` |
| **Reveal values…** | Shows a Secret's values, see [Secrets](#secrets) | **Reveal values** | `kubernetes.secrets_reveal` |

An action on one object asks you to type its name in **Type &lt;name&gt; to confirm** before the confirm button turns on; on several, it asks for the count instead, such as `DELETE 3 JOBS` or `RESTART 3 DEPLOYMENTS`. **Copy** beside the name puts it on the clipboard and moves to the field, so the next key is paste. Every typed confirmation in Ankra has the same **Copy** button. If the object changes between the read and your confirm, nothing is done to it. When Kubernetes takes the change the window shows **Deletion accepted**, **Restart accepted** or **Change accepted**; a finalizer can hold a deleted object for a while, and whether a workload is healthy afterwards shows on its **Overview** and **Events** tabs. An answer that never arrived reads **Not confirmed**: look at the object before trying again.

Where an object comes from decides what you can change on it here:

- **An object a [Stack](/concepts/stacks) declares** cannot be edited or deleted here, because the Stack would write it back the next time it deploys. The window says so and opens the Stack with **Open stack &lt;name&gt;**. **Restart…** still works on it. An object a Helm release installed is changed through the release, under **Open Helm releases**. A direct change is refused with `A stack, a Helm release or another object owns this object. Change it there.`
- **An object a controller created**, such as the Jobs of a CronJob or the ReplicaSets and pods of a Deployment, can be deleted, also when the controller comes from a Stack. The window names the controller, such as `CronJob db-backup created it, and stack backups deploys that CronJob.`, says what it does next, and links to it. An owner that Kubernetes lists without marking it as the controller is named as its owner, and the window says it is not known whether something creates the object again. Its manifest is not edited here: edit the controller.
- **Any other object** can be deleted here, and its manifest edited.

Several objects at once: the ones that cannot be changed here are listed apart with the reason, and the rest go ahead.

If your role cannot act, the window says so, such as **Your role cannot change this job**, and names the permission it needs.

## Workloads

**Workloads** holds the workload kinds and **Pods**. The pod list has the same name search and namespace filter, sorts by name, namespace, phase, restarts, ready containers or age, and each row has **View logs** and a menu (the three dots). With `kubernetes.write` on the cluster, tick pods (shift-click for a range) and click **Delete…** in the bar above the list to delete up to 20 at once after typing `DELETE 3 PODS`. Each pod is read live first and only the instance in the list is deleted; the review shows each pod's answer. On a pod that is not running, has unready containers or has restarted, the menu has one entry worded for what the row shows: **Explain &lt;phase&gt; status with Ankra**, **Investigate unready containers with Ankra** or **Investigate restarts with Ankra**. Choosing it asks Ankra AI at once why the pod is in that state. If you can read security findings, the menu also has **View security findings** for the pod.

A pod page has **Overview**, **Logs**, **Metrics**, **Exec** and **YAML** tabs. **Overview** shows the phase, containers ready, restarts, each container's state and requests and limits, the pod's conditions and its **Events**, newest first. **Delete pod** in the page header deletes the pod after you type its name; the dialog says whether its controller recreates it. A pod of a workload a Stack deploys can be deleted; a pod a Stack declares itself is removed in the Stack. The pod-level tools have their own pages:

- [Logs](/platform/logs) - follow a container's output, or search the cluster's logs.
- [Pod Terminal](/platform/pod-terminal) - a recorded shell in a running container, on the **Exec** tab.
- [Debug Pods](/platform/debug-pods) - a pod that impersonates this one under an image with the tools you need.
- [Cluster Metrics](/platform/cluster-metrics) - CPU and memory for nodes and pods.

## Networking

**Networking** holds Services, Ingresses and Ingress Classes. A Service page has a **Pods** tab listing the pods its selector matches, which is the quickest way to see why a Service has no backends. The Services list shows each Service's type, cluster IP and ports; the Ingresses list shows each Ingress's hosts and ingress class.

Clusters Ankra creates can include a networking stack at create time: Traefik as the ingress controller, cert-manager and the `letsencrypt-prod` ClusterIssuer. Network Policies are under **Access & policies**; [Cluster Security](/guides/cluster-security) scores how tightly they are scoped.

## Storage

**Storage** holds Persistent Volumes, Persistent Volume Claims, Storage Classes and CSI Drivers. The Persistent Volumes and Persistent Volume Claims lists show capacity, storage class and status, and the Storage Classes list shows each class's provisioner, **Reclaim policy** and volume binding mode.

<Warning>
**Changing a Stack can delete volume data.** Removing a manifest from a Stack, or renaming one, makes Ankra delete the objects in it, PersistentVolumeClaims included. Ankra keeps an object that another live manifest or application on the cluster also declares, or that the Git repository's head declares under another Stack; an object only this manifest declares is deleted. With a `Delete` reclaim policy, the default for most CSI drivers, the disk behind a deleted claim is destroyed too. Read [Protect Persistent Data Before Changing a Stack](/guides/protect-persistent-data) before you rename or remove a manifest that holds a namespace or a claim.
</Warning>

## Configuration

**Configuration** holds ConfigMaps and Secrets. The ConfigMaps list shows each one's key count and whether it is immutable; the Secrets list shows type, key count and immutability, never values.

### Secrets

A Secret's values stay hidden. On its **YAML** tab every value reads `[protected]`. To see the values:

1. Open the Secret and click **Review resource actions**.
2. Click **Reveal secret values**, type the Secret's name and click **Reveal secret**.

The values appear in their Kubernetes form (base64 under `data`). They hide again after 30 seconds, when the browser window loses focus, or when you click **Hide values**. **Reveal secret values** is only offered when your role holds the `kubernetes.secrets_reveal` permission, which the `owner`, `admin` and `operator` roles hold; `member` and `viewer` see key names only. Each reveal is checked and written to the [audit log](/guides/audit-log).

From the terminal, `ankra cluster get secrets` shows key names and a digest for each value. A digest (`hmac-sha256:` and 32 characters) changes when its value changes. It is keyed per cluster with a key only the platform holds, so it cannot be used to check a guessed value, and the same value on two clusters shows two different digests. To read one Secret's values, name it, give its namespace and add `--reveal`:

<CliVersion since="0.21.1" command="cluster get secrets --reveal" />

```bash
ankra cluster get secrets db-credentials -n default --reveal -o yaml
```

`--reveal` needs the same `kubernetes.secrets_reveal` permission, and each reveal is written to the audit log like one from the portal. It reads exactly one Secret, so it is refused on a listing: without a name, with `-A` or with `-l`. Values under `data` stay base64-encoded, as `kubectl` prints them. The command exits 7 when your role lacks the permission, 3 when the Secret does not exist, 1 when the platform cannot read live values, for example because the cluster is not connected, and 2 for a reveal on a listing.

To keep secrets out of plain text in Git, see [SOPS Secrets](/guides/sops). For values shared across clusters and stacks, use [Variables](/concepts/variables) instead of hand-edited ConfigMaps.

## Access & policies

**Access & policies** shows the Kubernetes RBAC objects inside the cluster: Roles and Cluster Roles with their rules, their bindings with role and subjects, Service Accounts, and Network Policies.

This is not where you give a teammate access. Ankra has its own access control:

- [Roles & Access](/guides/roles-and-access) decides what each member can do in Ankra, per organisation, cluster or cluster group.
- [Cluster Access](/guides/cluster-access) grants a member `kubectl` access to a cluster. Ankra turns each grant into a RoleBinding or ClusterRoleBinding, which then appears in this menu.

## Cluster and Helm

- **Nodes** - the Kubernetes Node objects. A node page shows its **Conditions**, the **Workloads** on it and **Scheduling**, with **Review cordon** and **Review node drain**. See [Kubernetes Nodes](/platform/kubernetes-nodes). To add, remove or resize the machines themselves, see [Cluster Nodes](/platform/cluster-nodes).
- **Namespaces** - each namespace's status; a namespace page lists its pods and links to every kind inside it.
- **Events** - every Kubernetes event in the cluster, with reason, object and message.
- **Custom resource definitions** - every CustomResourceDefinition, with its kind, group and scope.
- **Helm releases** - every Helm release, with chart, revision and status. A release page has **Overview**, **Resources** (the objects the release declares) and **History** (the latest 25 revisions) tabs, and three buttons:

  | Button | Dialog | Confirm with |
  |--------|--------|--------------|
  | **Review Helm upgrade** | **Upgrade &lt;release&gt;?** with **Chart reference**, **Chart repository URL**, **Pinned chart version** and **Complete release values**. Helm waits for the workloads to become ready and rolls a failed upgrade back by itself. | **Upgrade release** |
  | **Review Helm rollback** | **Roll back &lt;release&gt;?** with a **Restore revision** choice. Database and volume contents are not restored. | **Roll back release** |
  | **Review Helm uninstall** | **Uninstall &lt;release&gt;?** Persistent data may be deleted according to the chart and storage policies. | **Uninstall release** |

  Each asks you to type the release name. A release an Ankra add-on or Stack owns is changed in its Stack, because the Stack would re-apply its own version: the upgrade dialog links **Review changes in the owning stack**, and the rollback and uninstall dialogs say `This release belongs to an Ankra stack.` See the [Add-on catalog](/platform/addon-catalog). The CLI and the API refuse the same three on such a release, with status 409 and the reason. To remove it, uninstall the add-on with `ankra cluster addons uninstall <add-on>`. To clear a release that is stuck, redeploy its Stack with `ankra cluster stacks redeploy <stack>`. A release whose values hold passwords, tokens or keys says `This release contains protected values. Use its source of truth to preserve those values during an upgrade.` and offers no values editor.

  When Ankra refuses one of the three, the dialog says so under **Upgrade was refused**, **Rollback was refused** or **Uninstall was refused** and shows the reason as the platform gave it. Nothing was changed. The cluster's own agent is a Helm release too, `ankra-agent`. Its page shows none of the three buttons: it says that the release is the cluster's own Ankra agent and links to **Agent settings**. The CLI and the API refuse all three on it, because Ankra reaches the cluster through it. Upgrade the agent from [Cluster settings](/platform/cluster-settings#agent) or with `ankra cluster agent upgrade`. In the API, a release's detail marks the agent's release with `metadata.is_cluster_agent`.

## Next Steps

Start from a problem: open **Workloads → Pods**, sort by **Most restarts**, and choose **Investigate restarts with Ankra** on the pod that keeps restarting. Or open the pod, check **Events** on its **Overview** tab, then its **Logs**. Press `⌘J` (`Ctrl+J`) on any page to open [Ask Ankra](/platform/ai-assistant) about the cluster you are on. For the full order of checks when a cluster misbehaves, see [Troubleshoot a Cluster](/guides/troubleshoot-a-cluster).
