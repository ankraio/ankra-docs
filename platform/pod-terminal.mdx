A pod terminal is an interactive shell inside a running Kubernetes container, the same thing `kubectl exec -it` gives you. In Ankra you open one from the pod's **Exec** tab in the browser, or with `ankra cluster terminal` from your own shell, with no kubeconfig and no port-forward. Every session is recorded in the audit log.

## Before you start

- Your role needs `kubernetes.exec` on the cluster. The `owner`, `admin` and `operator` roles hold it; `member` and `viewer` do not. Without it the **Exec** tab says `You need kubernetes.exec permission on this cluster.` See [Roles & Access](/guides/roles-and-access).
- The cluster's agent must be connected, and the container must be running.
- The shell you pick must exist in the container image.

## Opening a Terminal

<Steps>
  <Step title="Open the pod">
    Go to **Clusters → &lt;your cluster&gt; → Technical details → Kubernetes → Workloads → Pods** and click a running pod.
  </Step>
  <Step title="Open the Exec tab">
    Click **Exec**. The **Exec into a container** section reads `Disconnected. Choose Connect to start a session.`
  </Step>
  <Step title="Pick the container and shell">
    Pick the container in **Container** and the shell in **Shell**: `/bin/sh` (the default), `/bin/bash`, `/bin/ash` or `/bin/zsh`.
  </Step>
  <Step title="Connect">
    Click **Connect**. The status line reads `Connected. Switching views or hiding this tab disconnects the session.` and the terminal takes your keystrokes.
  </Step>
</Steps>

**Ctrl+C** and **Tab** send those keys to the shell, for when the browser would catch them. **Disconnect** ends the session; **Connect** starts a new one. Opening another tab of the pod page, or hiding the browser tab, disconnects the session too.

### From the CLI

The same terminal is available from the shell you are already in, through the platform - no kubeconfig and no port-forward:

<CliVersion since="0.14.0" />

```bash
ankra cluster terminal api-6d8f9c7b5-x2kq9 --namespace payments
ankra cluster terminal api-6d8f9c7b5-x2kq9 --namespace payments --container sidecar --shell /bin/bash
```

The local terminal is put in raw mode, so every keystroke (Ctrl-C included) reaches the remote shell and window resizes follow your terminal; leave with `exit` or Ctrl-D. A pod with one container needs nothing more; one with several takes `--container`. The command needs `kubernetes.exec` on the cluster, and the session is recorded and audited exactly like a portal one (see [Recorded sessions](#recorded-sessions)). `ankra cluster debug create --attach` uses it to drop straight into a freshly created [debug pod](/platform/debug-pods).

### One-off commands

To run a single command rather than open a shell - a `psql -c` check, a `curl` from inside the pod, reading a config file - use `ankra cluster exec`. It runs the command, streams its output, and exits with the command's own exit code, so a script or CI job can branch on it:

<CliVersion since="0.20.0" />

```bash
ankra cluster exec cnpg-cluster-1 -n cnpg-database -c postgres -- psql -U postgres -d appdb -Atc 'select count(*) from users'
ankra cluster exec api-6d8f9c7b5-x2kq9 -n payments -- curl -sf localhost:8080/healthz
ankra cluster exec cnpg-cluster-1 -n cnpg-database -c postgres --stdin -- psql -U postgres -d appdb < query.sql
```

Everything after `--` is passed to the container exactly as given: no shell re-parses it, so quote once for your local shell and not again. For pipes, globs or variables, run a shell explicitly: `-- sh -c 'env | grep ^APP_'`. (`ankra cluster terminal --shell` names a shell binary and cannot carry arguments; `exec` is the way to run a command.)

| Option | Effect |
|--------|--------|
| `-c`, `--container` | The container to run in; needed only when the pod has several |
| `--stdin` | Forward your input to the command; it sees end-of-file when your input ends. Without it the command gets no input |
| `-o json` / `-o yaml` | Print one `{exit_code, stdout, stderr, stdout_truncated, stderr_truncated}` document when the command ends instead of streaming (each stream capped at 8 MiB) |

The command runs without a TTY. When it ran, `ankra cluster exec` exits with its exit code; otherwise with the CLI's usual codes (`6` for a refused credential, `7` without `kubernetes.exec`, `1` when the command could not be started, for example because the binary does not exist in the image).

`exec` goes through the same platform relay as the terminal: it needs `kubernetes.exec` on the cluster, and each run is [recorded](#recorded-sessions) with an `open_pod_terminal` audit row whose details carry the exact command (`command: [...]`) instead of a shell. It needs a cluster agent recent enough to run one-off commands; an older agent is refused with the version it needs and nothing is run - upgrade it with `ankra cluster agent upgrade`.

## Features

| Feature | Description |
|---------|-------------|
| **Container** | Pick any running container in the pod, sidecars included |
| **Shell** | Choose between `/bin/sh`, `/bin/bash`, `/bin/ash` and `/bin/zsh` |
| **Status line** | Says whether the session is disconnected, connecting or connected, or why it failed |
| **Ctrl+C** and **Tab** | Send those keys to the shell |
| **Connect** and **Disconnect** | Start a new session, or end the current one |

---

## Supported Shells

| Shell | Path | Notes |
|-------|------|-------|
| sh | `/bin/sh` | Available in virtually all containers (default) |
| bash | `/bin/bash` | Available in most full Linux-based images |
| zsh | `/bin/zsh` | Available if installed in the container |
| ash | `/bin/ash` | Common in Alpine-based images |

<Tip>
If the container uses an Alpine-based image, use `/bin/sh` or `/bin/ash`. Bash is not included in Alpine by default.
</Tip>

## Recorded sessions

Every terminal session opened through Ankra is recorded, and so is every `ankra cluster exec`. Opening a shell writes an `open_pod_terminal` row to the [audit log](/guides/audit-log) naming who opened it, into which container, with which shell (or, for `exec`, the command it ran); while the session runs, everything typed and everything the container answered is stored with it, up to 4 MiB per session (longer sessions are marked truncated).

Anyone with `audit.read` (the `owner` and `admin` roles) can review a session. Open **Clusters → &lt;your cluster&gt; → Technical details → Audit log**, open the `open_pod_terminal` row and click **Replay terminal recording**. The **Terminal recording** page shows the **Session** facts (pod, container, who opened it, when it started and ended, and whether the recording is complete) and the **Recorded output**: click **Play replay** to play it back, pick a **Replay speed**, and **Pause replay** to stop. From the CLI, `ankra org terminal-session <session-id> --transcript` prints the same recording.

<Note>
A recording contains whatever the shell printed, secrets included. Transcript access is gated on `audit.read`; the transcript itself never travels inside the audit row.
</Note>

If the recording store is unavailable when a session opens, the session still opens and the audit row says `recording_unavailable`; a session whose recording failed part-way through is marked as degraded.

Transcripts are kept for **90 days** by default, then pruned: the session's facts - who, where, when, how it ended, how much was recorded - stay with the audit row, and the replay says the transcript was pruned and when, rather than showing an empty recording.

## No shell in the image?

A distroless image has nothing to attach to. Spin up a [debug pod](/platform/debug-pods) instead: a pod that impersonates this one - same service account, node, volumes and environment - under an image that has the tools you need.

## Troubleshooting

| You see | What to do |
|---------|------------|
| `You need kubernetes.exec permission on this cluster.` | Ask an organisation admin for a role that holds `kubernetes.exec` |
| `Choose a running container to connect.` | The container is not running. Pick another container, or check the pod's **Overview** |
| `A fresh pod observation is required.` | The page shows a recorded copy of the pod. Click **Refresh** and wait for the cluster to report |
| `The terminal did not connect. Check the agent and try again.` | Check the cluster's agent is connected on the cluster's **Overview**, then click **Connect** |
| `Connection refused. Refresh the pod and check that you have exec access to its running container.` | The pod may have been replaced. Click **Refresh** on the pod page |
| Shell exits immediately | The shell may not exist in the image. Pick `/bin/sh`, or use a [debug pod](/platform/debug-pods) |
| Session ends unexpectedly | The pod may have been restarted or deleted, or you switched views. Check the pod's **Overview** and click **Connect** |
