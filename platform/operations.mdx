A Stack deploy or add-on upgrade failed and you need to know which part broke and whether it is safe to run again. Every change Ankra makes to a cluster runs as an **operation**, and each operation is split into **steps** - one per add-on install, manifest apply, GitOps sync and so on. The portal calls the steps **Jobs**. This guide shows how to find the failed step, read its error and retry the operation.

## Before you start

- **Access to the cluster** in the Ankra portal, or the [Ankra CLI](/integrations/ankra-cli) logged in to your organisation.
- **`executions.operate` on the cluster to retry or cancel.** Without it, the operation page says "Retry and cancellation require executions.operate for this cluster." See [Roles and access](/guides/roles-and-access).

## Find the failed operation

<Steps>
  <Step title="Open the cluster's operations">
    Go to **Clusters → &lt;your cluster&gt; → Technical details → Operations** (`/next/clusters/<cluster-id>/operations`). **Technical details** is a group in the cluster menu that folds away; open it if it is closed.

    The page lists everything the platform has run against the cluster, newest first, with how far each got and how it ended. Tick **Needs attention only** to keep the failures that still need someone, or pick a status in the status filter (**Running**, **Stopping**, **Success**, **Cleanup**, **Failed**, **Critical** or **Cancelled**). A **Live** badge means a run is in progress and the list refreshes while it goes.
  </Step>
  <Step title="Open the operation">
    Click the failed operation. Its page shows the status, a count of jobs by state, when it started and its last update, then the **Jobs** list in run order.

    Type in **Search jobs, targets or errors…** to find a job, or pick a lane in the job status filter. Switch between **List** and **Kanban**: the kanban sorts jobs into **Waiting**, **In progress**, **Needs attention** and **Finished** (and **Other statuses** when a job reports one of those). A failed job shows its error under its name.
  </Step>
  <Step title="Read the failed step">
    Under **Needs you** at the top of the page, click **Inspect failed step** (or click any job). The step page shows:

    - **Recorded result** - the step's status, when it started and ended, and its duration.
    - **Step output** - the output each task of the step recorded, and **Live output** while the step runs. Output Ankra treats as protected is withheld.
    - **Target and source** - the resource, kind, namespace, Stack, chart, registry and source path the step targeted.
    - **Status history** - every status the step went through, with its time.

    Use **← Previous step**, **Next step →** and **Back to operation** to move around. Jobs after a failure that did not run were held back by the earlier failure, not broken themselves, so read the first failed job.
  </Step>
  <Step title="Ask Ankra AI if the error is not obvious">
    Click **Investigate with Ankra** on the operation page. It opens [Ankra AI](/platform/ai-assistant) with a question about this operation filled in, ready for you to send.
  </Step>
</Steps>

Fix the cause first - a wrong value in the add-on configuration, a missing Secret, a namespace that does not exist - then retry.

## Retry or cancel

<Tabs>
  <Tab title="Portal">
    - **Review retry** appears on a failed, critical or cancelled operation. The dialog asks **Start a new attempt?**: the platform replays the operation as a new execution, and completed steps may run again. It is not a resume from the failed step. Click **Start new attempt**. The page opens the new operation, which says it is "A new attempt of the previous operation. The previous record is unchanged."
    - **Review cancellation** appears while an operation is running. The dialog asks **Cancel this operation?**: cancellation stops eligible work and cannot undo completed changes. Click **Request cancellation**. A step that is still running finishes first, and the page reads "Cancelling: a step is still running and finishes first. Retry becomes available once the run has stopped."
    - **Re-apply stack (force)** appears instead of **Review retry** when Kubernetes did not apply a resource because it was changed outside the Stack. Retrying without force meets the same conflict. The re-apply applies every manifest in the Stack again and takes back the fields changed outside it, as a new operation. It needs the `stacks.deploy` and `clusters.write` permissions.

    An upgrade operation has its own wording (**Resume upgrade**, **Cancel the upgrade?**); see [Kubernetes upgrades](/guides/kubernetes-upgrades).
  </Tab>
  <Tab title="CLI">
    <CliVersion since="0.16.0" />

    ```bash
    # List failed operations on the selected cluster that still need someone
    ankra cluster operations list --attention open

    # Show the steps of one operation
    ankra cluster operations steps <execution-id>

    # Retry a failed operation (starts a new one)
    ankra cluster operations retry <execution-id>

    # Cancel a running operation, or one step of it
    ankra cluster operations cancel <execution-id>
    ankra cluster operations cancel-step <execution-id> <step-id>
    ```
  </Tab>
</Tabs>

There is no pause or resume.

## Verify

Open **Operations** again. The retry appears as a new operation at the top; wait for it to read **Completed**. The original failed row keeps its failed status, and once the resources it failed on are healthy it carries **Resolved by a later run**. On the failed operation's page, **Open the resolving operation** links to the run that fixed it.

An operation's status says what ran, not whether the workloads are healthy now. To check them, click **Inspect workloads** under **Operation details**.

## What can go wrong

The retry dialog shows the platform's refusal when a retry cannot start:

| Message | What to do |
|---|---|
| "Execution is not in a retryable state" | Only a failed, critical or cancelled operation can be retried. Refresh the page with **Refresh operation**. |
| "Execution has no steps left to retry" | Nothing in the operation is left to run again. Start the change again from its Stack or add-on. |
| "Execution already has a retry in progress" | Follow the retry already running on **Operations** instead. |
| "Execution still has steps stopping; retry once they have finished" | Wait for the cancelled steps to stop, then retry. |
| "Execution would deploy an add-on, manifest or application of an uninstalled stack; install the stack to deploy it again" | The Stack was uninstalled after the operation ran. Install the Stack again to deploy it. |
| "Cluster operations are temporarily blocked by a recent force stop" | A force stop cancels every running operation and blocks new ones for 60 seconds. Retry after the minute has passed. |

If the page says "Ankra started a new run but could not confirm it yet.", look for the new run on **Operations** before you retry again.

## Failed history versus open problems

The operations list is an audit log, not a to-do list. A failed operation keeps its failed status for as long as the record is kept, and nothing acknowledges or deletes it, so a rollout that needed a few attempts leaves its failed attempts in the history for good.

What tells you whether a failure still needs someone is its attention state:

| State | Meaning |
|-------|---------|
| `none` | The operation did not fail |
| `open` | It failed, was critical or was cancelled, and nothing has fixed it since |
| `resolved` | Every resource its failed steps targeted has recovered - a later run on the same resource succeeded, the resource is up, or it was removed |

The state is worked out each time you read the list, so a successful retry resolves the operation it retried. In the portal a resolved failure carries **Resolved by a later run**, and **Needs attention only** hides it; in the CLI filter with `--attention open` or `--attention resolved`.

## Operations with no cluster

An application deploy, a managed service or a security fix can run for the organisation rather than on one cluster. Its operation opens at `/next/operations/<operation-id>`, the address notifications and check runs link to. That page shows the status, the jobs and each step's output, read only: **Inspect failed step** opens the failed step, and there is no retry or cancel. An operation that ran on a cluster opens on that cluster's operation page from the same address.

## Next step

If a retry keeps failing on the same step, open a [support ticket](/platform/support) with the operation link, or ask [Ankra AI](/platform/ai-assistant) about it.
