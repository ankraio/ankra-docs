title: Cloud Cost
description: Estimated cloud spend for every cluster and your whole fleet - compute, storage, network, and per-namespace allocation.
---

Cloud Cost gives you an estimated view of what your clusters cost to run, without wiring up a separate cost tool. Ankra combines the live node and volume inventory it already syncs from your cluster with public cloud pricing to produce per-cluster and fleet-wide estimates, broken down by category and allocated back to namespaces and stacks.

<Note>
All figures are **estimates**, derived from on-demand and spot pricing for the resources Ankra can see. They are designed for trend-watching, right-sizing, and chargeback - not for reconciling a cloud invoice to the cent.
</Note>

---

## Where it lives

**Cost** has its own place in the sidebar, between **Credentials** and **Security**, with six tabs:

- **Overview** - the dashboard: projected month end (with its pace against the run rate), month to date, run rate, priced-cluster coverage, the fleet cost trend, then the same money three ways - by provider, by credential, and by costliest cluster - each linking to the tab with the complete breakdown, plus a preview of the costliest workloads.
- **Clusters** - the whole fleet in one table: every cluster's run rate, month to date, projection, confidence and the credential that pays for it, with the unpriced ones marked instead of shown as free. Filter by provider; every row opens the cluster's [cost drill-down](#per-cluster-drill-down).
- **Credentials** - spend grouped the way the bill arrives: provider, then the credential that provisions the capacity (see [Spend by credential](#spend-by-credential)). Each credential opens its own page.
- **Workloads** - what the allocated money is actually running: namespace allocations across the analysed fleet with the stacks, addons and applications in them (see [Workloads](#workloads)).
- **Savings** - recommendations with an estimated monthly saving each, the organisation's orphaned-resource findings, and actions that change cluster configuration in one click (see [Savings](#savings)).
- **Settings** - the display currency, effective discount and network egress estimate behind every figure.

Every cluster links into its own **cost drill-down** (`/organisation/cost/clusters/<id>`) - the finest-grained view, with the measured evidence behind each recommendation (see [Per-cluster drill-down](#per-cluster-drill-down)).

The clusters list carries the same rollup as a collapsible strip above the table, and the fleet numbers also appear on the [Dashboard](/platform/dashboard).

## How it works

To estimate cost for a cluster, Ankra needs three things:

1. A **cloud credential** for the cluster's provider (for example AWS or GCP), so it can resolve instance and volume pricing. See [Credentials](/platform/credentials).
2. The cluster to be **online**, so the agent can sync the current nodes and volumes.
3. **Pricing** for the region and instance types in use.

A background inventory sync keeps the node and volume picture current per provider; cost is recomputed from that inventory plus your pricing settings.

### Readiness states

The per-cluster cost view reports a readiness state so you always know why an estimate is or isn't available:

| State | Meaning |
|-------|---------|
| `ready` | A cost estimate is available |
| `no_credential` | No cloud credential is attached for this provider |
| `unsupported_provider` | The cluster's provider isn't supported for cost estimation |
| `cluster_offline` | The cluster is offline, so inventory can't be synced |
| `awaiting_nodes` | Waiting for the first node inventory sync |
| `awaiting_pricing` | Nodes are known, pricing is still resolving |
| `estimate_pending` | Inventory and pricing are present; the first estimate is being computed |
| `no_rate_card` | Private capacity (Proxmox, VMware, imported hardware) that nobody has priced yet - see [Private capacity](#private-capacity-rate-cards) |

## Private capacity: rate cards

Public providers publish a price for every machine size, so Ankra can look
one up. Proxmox, VMware, Morpheus and clusters you imported from your own
hardware have no size anyone sells - so you state what the capacity costs
and Ankra multiplies it by what each cluster actually holds.

A **rate card** is three monthly rates in your own currency:

| Rate | Applied to |
|------|-----------|
| Per vCPU | Each node's CPU capacity |
| Per GB of memory | Each node's memory capacity |
| Per GB of storage | Each provisioned volume |

The card lives on the **credential** that provisions the capacity, so one
Proxmox datacentre is priced once and every cluster built from it inherits
those rates. Open **Credentials → your credential → Pricing** to set them.

**Proxmox ships with defaults** (EUR 3.00 per vCPU, 0.75 per GB of memory
and 0.02 per GB of storage per month) so a cluster reports a number the day
it is connected. The Cost page labels them **Ankra defaults** rather than
your own figures; saving the form makes them yours, and clearing it returns
to the defaults.

Other private providers ship no defaults on purpose: inventing a price for
hardware Ankra knows nothing about would be a confident wrong answer. Until
you state rates, those clusters are reported as **not priced** - never as
free - and their readiness state is `no_rate_card`.

Clusters you imported without any provider credential fall back to the
organisation's own card, if you set one.

<Note>
Rates feed the same pipeline as a public provider's catalogue: the hourly
snapshot, the month-to-date and projected figures, the namespace
allocation, and the savings recommendations. Changing a rate applies from
the next hourly metering pass; it does not rewrite past snapshots.
</Note>

## Per-cluster cost

Open a cluster and select the **Cost** view to see its estimate. It includes:

- **Summary** - hourly cost, estimated monthly cost, month-to-date, and a projected month-end total, with a confidence level.
- **Breakdown** - compute split into on-demand and spot, plus storage, network, and control-plane cost, along with idle and unallocated portions.
- **Coverage** - how many nodes and volumes were priced. If some couldn't be priced, the estimate is flagged as `coverage_incomplete` so you know it understates the true figure.
- **Per-namespace allocation** - cost allocated to each namespace (and the owning stack, where known) by CPU and memory share, so you can attribute spend to teams or workloads.
- **Trend** - a daily series of the monthly cost estimate so you can spot changes over time.

```bash
GET /org/clusters/{cluster_id}/cost
```

## Fleet summary

The organisation-wide rollup aggregates every cluster's estimate into a single number, with breakdowns by provider and a list of your top-spending clusters:

```bash
GET /org/cloud-cost/summary
```

It returns estimated monthly cost, month-to-date, and projected month-end totals - in your configured display currency - overall, per provider, **per credential** (`by_credential`), and for every analysed cluster (`clusters`, each carrying the `credential_id` / `credential_name` it resolves to; `top_clusters` stays the ranked slice). This is the same rollup shown on the **Cost** page, the clusters list strip, and the [Dashboard](/platform/dashboard).

## Spend by credential

A cloud bill arrives per account, and an account is what a credential holds - so the **Credentials** tab regroups the fleet the way finance will read it: provider, then credential, then the clusters each credential provisions. Ankra resolves the credential from each cluster's own resource graph (the same lookup provisioning uses), so the attribution is what actually built the cluster, not a guess:

- A **live credential** links to its own page - `/organisation/cost/credentials/<id>` - with its figures, its clusters, and (for private capacity) the rate card pricing it, badged with where the rates come from and an edit path.
- A credential **deleted after its clusters were built** keeps its name in the listing - its clusters still cost money - but has no page to open.
- Clusters that name **no credential** (imported clusters, torn-down graphs) collect into one honest *No credential recorded* bucket per provider, so the totals always account for the whole fleet.

## Workloads

The **Workloads** tab answers "where does the money actually run" with names you recognise, not namespace strings. For every analysed cluster it takes the namespace allocation at the latest snapshot and joins in what lives there:

- the **stack** the namespace belongs to,
- the **addons** placed in it,
- the **applications** installed into it (each linking to its application page).

Rows are ranked by allocated monthly cost across the whole fleet, searchable and filterable by cluster, with the compute/storage split behind each figure. The same enrichment appears on each cluster's drill-down beside the namespace allocation donut.

```bash
GET /org/cloud-cost/workloads
```

The read is capped at the 500 costliest rows and says so when it truncates. On an installation older than this feature the tab says the backend does not serve workload allocations yet - never "nothing runs".

## Settings

Currency resolves in two layers. The **organisation default** is what everyone gets out of the box; each member can set **their own display currency** on top (Cost → Settings → *Your display currency*), and every cost figure the platform shows them - fleet, clusters, credentials, workloads, savings, drill-downs - renders in it. Provider quotes in the cluster-create wizards convert too: UpCloud quotes arrive in US dollars, Hetzner and OVHcloud in euros, and the wizard converts them into your display currency at the latest exchange rate (keeping the provider's own currency, honestly labelled, when no rate is known).

Organisation admins tune the defaults and estimation behaviour under cost settings:

| Setting | Description |
|---------|-------------|
| `currency` | The organisation's default display currency: `eur` (the default), `usd`, `gbp`, `sek`, `nok`, `dkk`, `chf`, `pln`, `czk`, `jpy`, `cad`, `aud` or `inr` |
| `effective_discount_pct` | A flat discount (0-100) applied to list pricing, to approximate committed-use or enterprise agreements |
| `include_network_egress_estimate` | Whether to add an estimated network egress component |

The settings read also answers `display_currency` (the currency effective for the caller) and `fx_rates`; the personal preference itself lives on `PATCH /org/me/preferences` as `display_currency` (empty clears it back to the organisation default).

```bash
GET /org/cloud-cost/settings
PUT /org/cloud-cost/settings   # organisation admins only
```

<Warning>
Only organisation admins can change cost settings. The discount must be between 0 and 100, and the currency must be one of the supported display currencies listed above.
</Warning>

## Savings

The **Savings** section turns the same data into actions:

- **Right-size idle capacity** - when a meaningful share of a cluster's run rate sits idle, one click opens Ankra AI's cost optimisation for that cluster; the scaling updates it proposes (`scale_workers`, `update_node_group`) apply to the cluster after your confirmation.
- **Stop non-production clusters off-hours** - a non-production cluster on a provider with [power schedule](/platform/cluster-power-schedules) support, running around the clock, gets a one-click schedule: weekdays 19:00 UTC the workers scale to zero, 07:00 UTC they come back, and weekends stay down - roughly 64% of its compute off the bill. The exact pair is spelled out before anything is written, and both schedules stay editable under the cluster's power schedules. A cluster with an unknown environment label is never offered a shutdown.
- **Reduce unallocated spend** - when a quarter or more of a cluster's run rate is not allocated to any workload.

Each cluster lane links into its [drill-down page](#per-cluster-drill-down), and **Costliest namespaces** lists the workload dependencies fleet-wide, each with its monthly cost and its share of the cluster. A cluster whose cost could not be read is counted as unanalysed and makes the savings total an explicit lower bound - it is never read as "no savings".

### Orphaned & idle resources

A six-hourly waste scan finds resources that bill money while doing no work and lists them on the Savings page (and, narrowed, on each cluster's drill-down):

| Finding | What it means |
|---------|---------------|
| Stopped server (still billed) | A Hetzner server with `status: off` - Hetzner bills a stopped server fully as long as it exists |
| Unattached volume | A block volume attached to no server |
| Unassigned IP address | A primary IPv4 or floating IP assigned to nothing (unassigned primary IPv6 is free and not reported) |
| Load balancer with no targets | A load balancer forwarding to nothing |
| Released persistent volume | A Kubernetes PV stuck in phase `Released` - its disk keeps billing while no claim can bind it again |

Every finding carries its estimated monthly cost (or "price unknown" - never a fabricated zero) and a one-click **Resolve with AI** that opens a chat naming the exact resource. The section is honest about its own limits: it says when the first scan is still pending, when a credential could not be listed (a partial scan, not "no waste"), and how long ago the last scan ran. The provider-side scan covers Hetzner accounts today; the released-PV check covers every cluster.

```bash
GET /org/cloud-cost/waste            # organisation-wide findings
GET /org/cloud-cost/waste?cluster_id=<id>
```

## Per-cluster drill-down

Clicking a cluster in Savings (or a costliest-cluster row on the Overview) opens its cost drill-down - the page to use when you want to know **what exactly to adjust, and why it is safe**:

- **Cost trend** - the daily run-rate over the last 30 days, with the delta over the window.
- **Where the money goes** - a donut of the itemised components (compute on-demand and spot, storage, network, control plane, Bastion & VMs), with idle and unallocated called out.
- **Node evidence** - the proof behind right-sizing: for every node, the measured **average, p95 and peak** CPU and memory usage over a selectable window (24h / 7d / 30d) against what the scheduler reserved, a derived monthly cost, and a verdict:
  - *underutilised* - even the busy moments (p95) fit well under the reservation on **both** CPU and memory, with the estimated saving from sizing to 1.5x the observed p95;
  - *spiky - keep headroom* - bursts make the average misleading, or p95 already approaches the reservation. A spiky node is never called safe to downsize, whatever its average;
  - *well sized*, or *no metrics* when the store has no series for the node - usage unknown, never "0% used".
- **Usage over time** - the per-node CPU and memory charts behind those numbers, so you can see the pattern (a nightly batch job, a business-hours curve) rather than trust a single statistic.
- **Recommendations** - the same recommendations Savings shows (one model, one set of thresholds), now with the measured evidence attached, and the same one-click resolves.
- **Namespace costs and efficiency** - the allocation donut next to requested-vs-used per namespace.
- **This cluster's waste findings.**

Node evidence needs the platform metrics pipeline; without it the page says so and keeps the recommendations request-based, and the endpoint answers:

```bash
GET /org/clusters/{cluster_id}/metrics/utilisation?range_seconds=604800
```

### What if the node groups changed?

Under the breakdown, the drill-down carries a **what-if draft**: the cluster's node groups as they run today - name, node count, vCPU, memory and disk per node - plus its load balancers, editable in place. Change a count, resize a group, add a group or drop one, add a load balancer, and the panel prices the draft and shows three figures side by side: **today's bill** (the metered run rate), the **predicted bill**, and the **change** between them. The draft is page state and nothing more: reload the page, or press *Discard draft*, and it is gone. Nothing is saved and nothing is applied to the cluster.

The prediction is honest about how it is built. It is today's bill plus the difference between the draft and the current configuration **priced the same way**, so the control plane, volumes and every other charge carry over unchanged, and only what you changed moves the number. Pricing comes from the same source the bill is metered from:

- **Public providers** (Hetzner, OVHcloud, UpCloud, Scaleway, and any size the cluster already runs) price from the price book. A group you resize is placed on the **cheapest published size that holds the requested vCPU and memory**, locked to the current size's CPU architecture (an ARM group never silently becomes x86) and preferring its current line (a dedicated group stays dedicated while a size in that line fits). The size it landed on is shown beside the price. Disk beyond what the size bundles is priced as volume storage; where a provider sells spot capacity the group can be priced as spot.
- **Private capacity** (Proxmox, VMware, Morpheus, MAAS, imported clusters) prices per vCPU, per GB of memory and per GB of disk from the [rate card](#private-capacity-rate-cards) that prices the cluster today - the credential's own, Ankra's Proxmox default, or the organisation fallback - and says which.

A group nothing can price - a shape no published size holds, a size the book has no price for, a private cluster without a rate card - reads *Not priced* with the reason, and the total shows *from* the priced part rather than a number that leaves the unknown out. If an unpriced part differs between the draft and today, the prediction is withheld rather than guessed. Every figure is an estimate in your display currency, after your organisation's discount.

The same estimate is served over the API for scripts and the CLI's `/api/v1` twin:

```bash
GET  /org/clusters/{cluster_id}/cost/estimate      # what runs today, priced - seeds a draft
POST /org/clusters/{cluster_id}/cost/estimate      # price a draft
```

```json
{
  "node_groups": [
    { "name": "workers", "count": 3, "vcpus": 4, "memory_gb": 8, "disk_gb": 100 },
    { "name": "batch", "count": 1, "vcpus": 2, "memory_gb": 4, "disk_gb": 0, "spot": true }
  ],
  "network": { "load_balancers": 2 }
}
```

The response carries the `baseline` and the `estimate` (one priced line per group with the size it was placed on, the network resources, and totals with a `coverage_incomplete` flag), `metered_monthly_cents`, `predicted_monthly_cents` and `delta_monthly_cents`, and a `pricing` block naming the mode (`catalog`, `rate_card` or `unavailable`), the source and the unit prices behind the figures. `network` may be omitted to keep today's resources.

## Prerequisites checklist

<Steps>
  <Step title="Attach a cloud credential, or price your own capacity">
    Add a credential for the cluster's provider under [Credentials](/platform/credentials). For Proxmox, VMware or
    imported hardware there is no catalogue to look up, so set a
    [rate card](#private-capacity-rate-cards) on that credential instead.
  </Step>
  <Step title="Bring the cluster online">
    Ensure the [agent](/concepts/cluster-agent) is connected so node and volume inventory can sync.
  </Step>
  <Step title="Set your currency and discount">
    As an org admin, set the display currency and any committed-use discount in cost settings.
  </Step>
  <Step title="Read the estimate">
    Open the cluster's Cost view, or the fleet rollup on the Dashboard.
  </Step>
</Steps>

## From the CLI and Ankra AI

The same surface is scriptable and conversational:

- **CLI** - `ankra cost summary`, `ankra cost cluster <name-or-id>`, and `ankra cost settings get|set` (`--currency`, `--discount`, `--include-egress`); every command takes `-o json`.
- **Ankra AI and MCP** - `get_fleet_cloud_cost` and `get_cost_settings` answer in chat and over `mcp:read` tokens; `update_cost_settings` changes the pricing settings (organisation admins, with confirmation, on `mcp:write`); `get_cluster_cost` and `get_stack_cost` cover a single cluster or stack.
