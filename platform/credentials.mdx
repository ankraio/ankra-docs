A credential is a named secret Ankra uses on your behalf: a cloud provider token to create servers and clusters, a Git connection to sync configuration, a registry login to pull private charts, or an SSH key for server access. Clusters and YAML refer to a credential by its name. The secret is kept in Ankra's secret store (HashiCorp Vault or OpenBao) and never shown in a list.

Credentials live at **Integrations & alerts → Credentials** (`/next/credentials`). This page holds the steps every credential shares. Each provider page below covers only what differs: what to create at the provider, the access it needs, the fields the form asks for, and the CLI command.

## Before you start

- **A role that may change credentials.** Every role can list and read credentials. Adding, renaming, checking and replacing a secret need `credentials.write`, deleting needs `credentials.delete`, and showing stored values needs `credentials.reveal`; the built-in `owner` and `admin` roles hold all three. See the [permission matrix](/guides/roles-and-access#permission-matrix). Without `credentials.write` the add page reads **Your role cannot add credentials.**
- **The secret from the provider.** Create it first, with only the access Ankra needs. The provider page says how.

## Add a credential

<Tabs>
  <Tab title="Portal">
    <Steps>
      <Step title="Open the add page">
        Go to **Integrations & alerts → Credentials** and click **Add credential**. The **Add a credential** page shows two groups: **Cloud providers** and **Git, registries and keys** (GitHub, Bitbucket Cloud, GitLab, Helm registry, SSH key, and AWS role (CloudFormation)).
      </Step>
      <Step title="Choose the provider">
        Click the provider. A cloud provider opens the form **New `<provider>` credential**. Git, registry, SSH key and AWS role connections open their own flow, described on their pages.
      </Step>
      <Step title="Name the credential">
        Enter a **Name**: 3 to 100 lowercase letters, digits and single hyphens, starting and ending with a letter or a digit. Clusters and YAML refer to the credential by this name, so it cannot change later. You can give it a friendlier label afterwards. Ankra checks the name is free as you type; a taken name shows the reason and, where it has one, a name to try.
      </Step>
      <Step title="Fill in the provider's fields">
        Enter the values the provider page lists. Some providers have an extra section you can open for optional settings (an endpoint, a jumphost, Tailscale).
      </Step>
      <Step title="Test the connection">
        Click **Test the connection**. Testing checks the values with the provider without saving them. You see **The connection works**, or **The connection did not work** with the provider's answer and a list of what to check.
      </Step>
      <Step title="Add it">
        Click **Add credential**. Ankra checks the values with the provider before it stores them and refuses them if the provider does (an HPE Morpheus appliance behind a jumphost is the one exception: test it first). The credential's page opens, and Ankra checks the connection again as soon as it is saved. The status next to the title reads **Connection works** once the provider accepts it.
      </Step>
    </Steps>
  </Tab>
  <Tab title="CLI">
    Each provider has its own create command, shown on its page. The secret is not a flag: the command asks for it, or reads it from stdin or an environment variable where the provider page says so.

    ```bash
    ankra credentials validate hetzner-production
    ankra credentials hetzner create --name hetzner-production
    ankra credentials list --provider hetzner
    ```
  </Tab>
</Tabs>

Ankra AI and MCP clients cannot create a credential, because that would mean passing the secret itself to a tool. See [AI and MCP access](#ai-and-mcp-access).

## Find a credential

**Integrations & alerts → Credentials** lists every credential with its provider, the account or address it points at, and its health. The counts above the list read **Credentials**, **Needs attention** (failed checks or unavailable connections), **Healthy connections** and **No recent check**.

- **Filter by name, account or provider…** searches the list.
- The provider filter starts at **All providers**; the health filter offers **All health states**, **Recorded issues**, **Last checks passed**, **No recent check**, **Not monitored** and **Other recorded states**.
- Credentials Ankra creates for the organisation, such as registry robot logins, are hidden until you tick **Show managed by Ankra**. They are marked **managed by Ankra** and cannot be changed.
- **Clear filters** resets the search and both filters. Past ten credentials the list pages, at 10, 25 or 50 per page.

<Tabs>
  <Tab title="Portal">
    Click a credential's name to open it.
  </Tab>
  <Tab title="CLI">
    ```bash
    ankra credentials list
    ankra credentials list --provider hetzner --sort created --order desc
    ankra credentials get hetzner-production
    ```
  </Tab>
  <Tab title="MCP">
    `list_credentials` lists every credential with availability and sync state; `get_credential` reads one, with secret fields redacted. See the [MCP Tool Reference](/platform/mcp-tools#credentials).
  </Tab>
</Tabs>

## The credential page

The header shows the credential's name, its provider and its health. The page has these tabs:

| Tab | Shown for | What it holds |
|---|---|---|
| **Overview** | Every credential | **Needs attention** when the last check found a problem, counts of **Recorded environments** (and **Recorded applications** for GitHub), **Connection details**, **Check the connection**, and links to the other tabs |
| **Connected resources** | Every credential except Git | The environments and applications in Ankra that use it |
| **Repositories & resources** | Git credentials | The repositories it can reach and their access, and what uses it |
| **Usage & limits** | Cloud provider credentials | Resources the credential can see at the provider, including resources outside Ankra |
| **Cost** | Cloud provider credentials, when cost reporting is enabled for the organisation | Daily costs and environment estimates for Ankra resources, not your provider's total bill |
| **Settings & access** | Every credential | **Display name**, **Replace the secret**, **Stored values**, **Delete this credential** and **Project**, as your role allows |

### Check the connection

On **Overview**, under **Check the connection**, click **Check now**. Ankra asks the provider whether it accepts the stored credential. You see **The provider accepted this credential just now.**, or the provider's answer and its error code. For an SSH key the section is **Validate the public key** and it checks only the stored key's format, not access to a server.

Git and registry credentials have no **Check now**. The CLI has no command that runs this check.

### Usage and limits

**Usage & limits** reads the provider's API with the credential each time you open it, so it counts everything in the account, including resources created outside Ankra.

| Provider | What it reports |
|---|---|
| Hetzner, Scaleway | Usage only: neither provider exposes its limits through its API |
| DigitalOcean, UpCloud, OVHcloud, Azure | Usage against the account's or project's limits |
| Proxmox VE | The cluster's physical node and storage capacity, not a quota |
| HPE Morpheus | Totals for each cloud on the appliance |

For any other cloud provider the tab reads **Provider capacity is unavailable**, with the reason.

## Rename a credential

The name is fixed. You can give the credential a **Display name** that the list and the page show instead.

1. Open the credential and click **Settings & access**.
2. Under **Display name**, enter a **Label** and click **Save label**. You see **The label is saved.** Clear the field and save to remove it.

## Replace the secret

The identity fields stay fixed, so a credential always points at the same account. What you replace is the secret.

1. Open the credential and click **Settings & access**.
2. Under **Replace the secret**, enter the new values. Where there are several fields, leave a field empty to keep what is stored for it.
3. Click **Check and replace**.

Ankra checks the new secret with the provider first and only stores it if the provider accepts it, so clusters using the credential keep working either way. You see **The secret is replaced** (**The new secret works and is now stored. Clusters using this credential use it from now on.**), or **The secret was not replaced** with the provider's answer and what to check. The provider page lists the fields each provider can replace; a provider with none has no **Replace the secret** section.

Before you revoke the old secret at the provider, check that every cluster serves the new one:

```bash
ankra credentials propagation hetzner-production
```

It names any cluster still on the old value and says when the old one is safe to revoke.

## Show stored values

A role with `credentials.reveal` can open **Settings & access → Stored values** and click **Show stored values** to see what Ankra holds for the credential and which environments use it. **Hide stored values** clears them from the page. Some secrets are write-only and read **Never shown: Ankra only uses it to connect.**: the Scaleway secret key, the Proxmox token secret, the Morpheus access token, the Google Cloud service account key and the Azure client secret.

<Warning>
Each look is recorded in the organisation's audit log.
</Warning>

## Delete a credential

<Warning>
Deleting cannot be undone. Anything that refers to the credential by name stops working until you add one with the same name. Ankra refuses to delete a credential a cluster still uses: **Credential is in use by a cluster and cannot be deleted**.
</Warning>

<Tabs>
  <Tab title="Portal">
    1. Open the credential and check **Connected resources** (or **Repositories & resources**) for what still uses it.
    2. Click **Settings & access**, then **Delete credential** under **Delete this credential**.
    3. Type the credential's name to confirm and click **Delete credential**. Ankra returns you to the list, where the credential is gone.

    Deleting a GitHub credential marks the connection for deletion; the GitHub App stays installed on GitHub until you remove it there.
  </Tab>
  <Tab title="CLI">
    ```bash
    ankra credentials get hetzner-production
    ankra credentials delete <credential-id>
    ```

    Add `--yes` to skip the confirmation prompt.
  </Tab>
  <Tab title="MCP">
    `delete_credential` deletes a credential that is not in use.
  </Tab>
</Tabs>

## See what a cluster uses

**Infrastructure → Clusters → &lt;your cluster&gt; → Settings → Credentials** lists **Credentials this cluster uses**: the credentials its definition names for the Git repository it syncs with, its metrics and log sources, and the registries its add-ons install from. Each row gives the **Name**, what it is **Used for** and its **Kind**; click a name to open the credential. A name that matches no stored credential reads **Not among your stored credentials**.

## AI and MCP access

Ankra AI and MCP clients can list and inspect credentials (secret fields are always redacted), validate names, delete unused credentials, and plan and apply a GitHub credential rotation. They can never **create** a credential, because that would mean passing the secret itself to the AI, which the platform refuses. See the [MCP Tool Reference](/platform/mcp-tools#credentials).

## Security

Credentials are stored in a dedicated secret store (HashiCorp Vault or OpenBao):
- Encrypted at rest
- Access controlled per organisation
- Every reveal of a secret value through the API is written to the organisation's audit log, as are checking, rotating, renaming and deleting a credential. Listing credentials, and the platform's own use of a credential when it provisions or deploys, are not written there.

## What can go wrong

| What you see | Why | What to do |
|---|---|---|
| **Your role cannot add credentials.** | Your role lacks `credentials.write` | Ask an organisation `owner` or `admin` |
| A name error such as **Use lowercase letters, digits and hyphens only.** or **Use single hyphens only.** | The name breaks the naming rules | Use 3 to 100 lowercase letters, digits and single hyphens |
| **The connection did not work** | The provider refused the values | Read the provider's answer and the list under it, fix the token's access at the provider, and test again |
| **The credential was not added** | The platform refused the create | Read the message in the alert; **This kind of credential cannot be added for this organisation.** means the provider is not enabled for your organisation |
| **The secret was not replaced** | The provider refused the new secret | Nothing changed; the stored secret still works. Fix the new secret and try again |
| **Credential is in use by a cluster and cannot be deleted** | A cluster still uses the credential | Open **Connected resources** to see which cluster, and take it off the credential before you delete |

For provider-specific errors, see the provider's page.

## API access

Manage credentials with the Ankra API:

```python
import requests

headers = {"Authorization": f"Bearer {TOKEN}"}

# List every credential in the organisation
response = requests.get(
    "https://platform.ankra.app/api/v1/org/credentials",
    headers=headers
)

# Create a credential: the path names the provider, the body carries
# what that provider needs (a Hetzner credential is an API token)
response = requests.post(
    "https://platform.ankra.app/api/v1/credentials/hetzner",
    headers=headers,
    json={
        "name": "hetzner-production",
        "api_token": "<your-hetzner-api-token>"
    }
)
```

Every provider has its own `POST /api/v1/credentials/{provider}` with the fields that provider needs; the API reference lists them.

See the [API Reference](/api-reference/introduction) for complete documentation.
