A pull request's own run tests its head. It does not test that head on top of everything that merged since the branch was cut. Two pull requests can both be green and still break `main` when they land together. That is how a default branch goes red with nobody to blame.

The merge train closes that gap. Ankra tests each pull request **as the commit its merge will produce**, on top of the base branch and every pull request ahead of it. It merges only after that exact commit passes. It does what GitLab's merge trains and GitHub's merge queue do, on any GitHub plan, inside your own CI cluster.

<Info>
The merge train works with **GitHub** repositories today, and merges with **squash**. It is off until you turn it on for a repository.
</Info>

## Why it is worth turning on

- **`main` stays green.** Nothing merges onto a base its car did not test, so a semantic conflict between two pull requests is caught before it lands, not after.
- **No bisection by hand.** Each car tests everything ahead of it. When a car tested alone fails, its pull request is the one that broke it. When a batch of cars fails, the train splits it in two and tests each half again until it finds the pull request that broke it.
- **One run for several pull requests.** With several cars, the train tests up to eight pull requests at once, each built on the ones ahead, with one pipeline run for all of them.
- **Merge to published is a re-tag.** The merge of a car tested alone, or of the last car in a batch, is exactly the tree its run tested, so a pipeline with [`promote_from`](#build-once-publish-the-tested-image) publishes that run's image instead of building and testing the same tree again.
- **Your rules still apply.** The train merges through GitHub's own merge API. Branch protection, required reviews and required checks hold exactly as for a person's merge. Ankra never pushes to or force-pushes the base branch.

## How a car is built

For each pull request in the train, Ankra writes a **car**: the pull request squashed onto the base branch, or onto the car ahead of it.

```mermaid
gitGraph
    commit id: "main A"
    commit id: "main B"
    branch car-412
    commit id: "B plus 412"
    branch car-415
    commit id: "B plus 412, 415"
    branch car-418
    commit id: "B plus 412, 415, 418"
    checkout main
    merge car-412 id: "squash 412"
```

1. The car's branch, `ankra-merge-train/<entry id>`, starts at its base: the base branch head for the first car, or the car ahead for every other car.
2. The pull request's pinned head is merged in, using the same merge GitHub's squash merge computes.
3. A single-parent commit with that tree is written. It is exactly the squash commit the merge will create, titled `<title> (#<number>)`.
4. A pipeline run tests that commit. When several cars are tested at once, only the last one gets a run, and it tests every car ahead of it (see [Several cars at once](#several-cars-at-once)). The run records the car's tree, which is what lets the merge publish without a rebuild.

**How the car's run is planned.** A car run is planned as a pull request into the base branch, under the base branch's approved [authority](/pipelines/how-it-works#logic-is-open-authority-is-closed):

- It runs only when the pipeline declares `on.pull_request` with `branches` that match the base branch.
- `when.events: [pull_request]` stages run. Push-only `publish` and deploy stages do not.
- It never joins the pull request's own concurrency group, and a push to an `ankra-merge-train/*` branch never starts a run of its own.
- A `[skip ci]` marker never skips a car.

## The life of a pull request in the train

```mermaid
stateDiagram-v2
    direction LR
    [*] --> queued: added (CLI, label, merge when green)
    queued --> building: a car slot is free
    building --> testing: car commit written
    testing --> passed: car run succeeded
    passed --> merging: first car, base unchanged
    merging --> merged: squash-merged through GitHub
    testing --> evicted: run failed or cancelled
    building --> evicted: merge conflict
    passed --> evicted: GitHub kept declining the merge
    queued --> cancelled: removed, closed, train off
    testing --> queued: base moved, car ahead changed or batch failed
    passed --> queued: base moved or car ahead changed
    merged --> [*]
    evicted --> [*]
    cancelled --> [*]
```

| Status | What it means |
|---|---|
| `queued` | Waiting for a car. Just added, or sent back to be rebuilt |
| `building` | The car branch is being written |
| `testing` | The car commit exists and a pipeline run is testing it: its own, or the run of the last car in its batch |
| `passed` | The run that tested it passed. It waits to be the first car with an unchanged base |
| `merging` | The merge is in progress |
| `merged` | The train merged the pull request |
| `evicted` | The train removed it: its car failed, it could not merge, or it changed under the train |
| `cancelled` | A person removed it, the train was switched off, or the pull request was closed or merged elsewhere |

A car whose run concludes **skipped** counts as passing. For example, every changed file is outside `on.pull_request.paths`. A skipped car is never a promotion source, though.

## Several cars at once

With `--max-cars 3`, the train tests three pull requests as one batch. Each car is built on the ones ahead, and one pipeline run, on the last car, tests all three.

```mermaid
flowchart LR
    Main[(main)] --> C1[Car 1<br/>main + 412<br/>rides]
    C1 --> C2[Car 2<br/>main + 412 + 415<br/>rides]
    C2 --> C3[Car 3<br/>main + 412 + 415 + 418<br/>one run tests all three]
    C3 -.-> Q[PR 421 queued]

    C3 -. run fails .-> S[Batch split in two<br/>412 + 415, then 418]
```

- Only the **first** car merges. It merges once the run that tested it passed and the base branch head, re-read just before the merge, is still the head it was built on. When a batch passes, its cars merge in order, one per pass.
- **When a batch's run fails**, nothing says which pull request broke it. Every car of the batch goes back to `queued` and the batch is split in two (`batch_split`, `batch_failed`). Each half is tested again, and a half that fails is split again.
- **When a car tested alone fails**, its pull request leaves the train with the failing run linked. Every car behind it included the failed change, so they are rebuilt without it (`predecessor_changed`).
- **When a car's run never tested the change**, because a step was never placed on a CI node, the car's commit could not be fetched, or Ankra failed, the car is rebuilt (`run_infrastructure`). After three such runs, a car tested alone leaves the train as `run_untested`, which says nothing against the pull request, and a batch is split.
- **When someone merges around the train**, every built car goes back to `queued` with `base_moved` and is rebuilt on the new head.
- **When you lower `max_cars`**, cars beyond the new limit are requeued with `train_shortened`.

Ankra builds one car per pass, because the next car needs the commit this one writes. Each car is still one pull request, and each merge is one squash commit. What is batched is the testing: one run for each window of `max_cars` pull requests instead of one run per car. A car that rides in a batch has no run of its own. Its check on GitHub reads `Waiting to be tested with the pull requests behind it`, then `Tested with #418 in run #<n>` with a link to that run once the last car's run is queued.

<Tip>
**Picking `max_cars`.** Start with `1` (one pull request at a time on the latest base) and raise it when pull requests wait in the queue. More cars means fewer runs per pull request, and more rounds of testing when a batch fails, because a failed batch is split and tested again. A high merge rate with a reliable test suite is the case for 3 to 8.
</Tip>

## Turn it on

<Steps>
  <Step title="Make sure the pipeline tests pull requests into the base branch">
    The car run is a pull request run, so the pipeline needs:

    ```yaml
    on:
      pull_request:
        branches: ["main"]
    ```

    Without it, a car is evicted with `pipeline_not_triggered`.
  </Step>
  <Step title="Enable the train">
    <CliVersion since="0.30.0" />

    ```bash
    ankra pipeline train enable --max-cars 2
    ```

    Run it from inside the repository's checkout, or name it with `--application <name>` or `--repository <id>`. This needs `pipelines.manage`. `--max-cars` takes 1 to 8 and defaults to 1.
  </Step>
  <Step title="Require the train's check on the base branch">
    Ankra posts an **Ankra merge train** check on every pull request it holds, and concludes it `success` only immediately before it merges. In GitHub's branch protection, require that check, pinned to the Ankra GitHub App rather than any source. Every merge then goes through the train. A pull request outside the train shows the check as expected and waiting, and cannot merge.
  </Step>
  <Step title="Optionally, publish the tested image on merge">
    Add `promote_from: pull_request` to your `publish` stage, so a train merge publishes the car's image instead of rebuilding it. See [Build once, publish the tested image](#build-once-publish-the-tested-image).
  </Step>
</Steps>

## Put a pull request on the train

There are three ways in, and they all lead to the same queue.

<Tabs>
  <Tab title="CLI">
    ```bash
    ankra pipeline train add 412                     # put #412 at the end of the train
    ankra pipeline train add 412 --head-sha 9f2c1e7  # pin the exact commit you reviewed
    ankra pipeline train list                        # the train in order, and what recently left it
    ```
  </Tab>
  <Tab title="Label">
    Add the `ankra:merge-train` label to the pull request, in any letter case. Removing the label only removes an entry the label put there.
  </Tab>
  <Tab title="Merge when green">
    Comment **`@ankraai merge when green`**, press the button in the portal, or ask Ankra AI. On a repository with the train on, the request enters the train instead of merging directly. See [AI in pull requests](/pipelines/ai-in-pull-requests#merge-when-green).
  </Tab>
</Tabs>

**Who may add a pull request.** You need `pipelines.operate` and must be a person, not a service token. You also need one of these: organisation administrator, the pull request's author, or write access to the repository on GitHub through your verified GitHub identity. You can always remove an entry you added yourself. When GitHub cannot be asked, nothing changes and the command says so.

**Pushing to a pull request in the train takes it out** (`head_changed`). The train merges the head a person put in it, never one that arrived later. Push your fix, then add it again.

## Stacked pull requests

A pull request based on another pull request's branch, rather than on the base branch, is stacked on it. The train takes a stack and can land it in one batch.

<CliVersion since="0.51.0" command="pipeline train list" />

```bash
ankra pipeline train add 74     # the bottom of the stack first
ankra pipeline train add 75     # based on #74's branch: stacked on it
ankra pipeline train list       # shows #75 as "(on #74)"
```

- **Add the bottom first.** A pull request enters stacked only while the pull request whose branch it is based on is in the train. Otherwise the add is refused with `409`: "Its base #74 is not in the merge train; add #74 first." When Ankra cannot find that pull request, the refusal names the branch instead. If no pull request in the train matches and one has not had its branch read yet, the answer is a `409` that says to try again shortly.
- **It is tested on top of the pull request below it.** Its car is built on the cars ahead of it, so it is tested with its parent's changes, as the two will land. A stack inside one window rides in one batch, tested by one run.
- **The train retargets it just before merging it.** Once the pull request below it has merged and it is the first car, Ankra changes its base to the base branch and squash-merges it. That retarget starts no new Ankra pipeline run on the pull request, and neither does GitHub's own retarget when the branch below is deleted: the run that tested its car already tested that head on top of the pull request below it.
- **Its base can be its parent's branch or the base branch.** Any other base takes it out (`base_branch_changed`). A pull request based on the base branch that is retargeted onto the branch of a pull request ahead of it is stacked on that one instead, and is not taken out.
- **When the pull request below leaves without merging**, every pull request stacked on it leaves with it as `parent_left`, and so does every pull request stacked on those. A parent someone merged by hand counts as merged.
- **To move a stack to the front**, move its bottom pull request: the whole stack moves with it, in order. Moving a pull request whose parent is still in the train is refused with `409`.
- **Forks never stack.** A pull request from a fork is never merged by the train.

`ankra pipeline train list` shows a stacked pull request with `(on #74)` after its title. Over the API, and in `train list -o json`, every entry carries `pull_request_head_branch`, `parent_entry_id` and `parent_pull_request_number`. The last two are null for a pull request based on the base branch. A riding car's entry names the run testing it in `tested_by_entry_id`, `tested_by_pull_request_number` and `tested_by_run_id`; `train list` shows `-` in its RUN column and does not show these yet.

## Merges GitHub declines

The train merges through GitHub's merge API, so GitHub can say no, usually because one of the pull request's own required reviews or checks has not arrived.

```mermaid
flowchart LR
    P[Car passed] --> M{GitHub merge}
    M -->|merged| OK[merged]
    M -->|declined| W[Stays passed,<br/>retried every pass]
    W --> M
    W -->|failing required check<br/>for 15 minutes| E1[evicted: merge_declined]
    W -->|any other reason<br/>for 3 hours| E2[evicted: merge_declined]
    W -.-> Behind[Cars behind keep<br/>building and testing]
```

- The car stays `passed` and the merge is retried on every pass, with GitHub's message shown as the reason.
- **Cars behind it keep building and testing meanwhile.** The train does not freeze behind one stuck merge.
- When GitHub says a required status check **is failing**, the car is evicted after **15 minutes**. A failed check does not turn green by waiting, so re-run it and add the pull request again.
- For any other reason, such as a review that has not arrived yet, the car waits up to **3 hours** before it is evicted.

## Why a pull request left the train

`ankra pipeline train list` shows what recently left the train and why. The same sentence is on the pull request's check run.

| Reason | Status | What it means and what to do |
|---|---|---|
| `run_failed` | evicted | The car's run did not pass. Open the linked run, fix, and add it again |
| `run_untested` | evicted | Three of its car's runs ended without testing it: a step never got a CI node, the car's commit could not be fetched, or Ankra failed. Nothing failed against the pull request. Add it again |
| `run_cancelled` | evicted | The car's run was cancelled |
| `merge_conflict` | evicted | It does not merge cleanly onto the base and the pull requests ahead. Rebase or merge `main` in, then add it again |
| `head_changed` | evicted | Pushed to after it entered the train. Add it again to test the new head |
| `base_branch_changed` | evicted | The pull request now targets a branch that is neither the base branch nor the branch of the pull request it is stacked on, or the repository's default branch changed |
| `parent_left` | evicted | The pull request it is [stacked on](#stacked-pull-requests) left the train without merging. The detail names it and why, such as `#74: run_failed`. Add it again once that pull request is back in the train |
| `stack_out_of_order` | evicted | The pull request it is stacked on stands behind it in the train. Add it again behind that pull request |
| `merge_declined` | evicted | GitHub kept declining the merge (above) |
| `pipeline_not_triggered` | evicted | The pipeline has no `on.pull_request` trigger matching the base branch |
| `fork` | evicted | Pull requests from forks are never merged automatically |
| `host_unavailable` | evicted | GitHub could not be reached for this pull request for over three hours |
| `pull_request_run_red` | evicted | [Auto-admit](/reference/cli/pipeline#ankra-pipeline-train-enable) put it in before its own run had passed, and that run failed at the head the train holds. Fix it and push, or re-run the run |
| `nothing_to_merge` | evicted | The base branch already contains the change |
| `pull_request_closed` | cancelled | The pull request was closed |
| `merged_outside_train` | cancelled | Someone merged it outside the train |
| `dequeued` | cancelled | Someone removed it |
| `train_disabled` | cancelled | The train was switched off |

A car sent back to be rebuilt shows `queued (<reason>)`: `base_moved`, `predecessor_changed`, `train_shortened`, `run_missing`, `run_replaced`, `run_infrastructure`, `batch_failed`, `batch_split` or `batch_broken`. That is normal train motion, not a failure.

After every merge, the train compares the merge commit's tree with the car's tree. The **TESTED AS MERGED** column of `train list` is that comparison: it is the proof that what merged is what was tested. A car that rode in a batch was tested as part of the last car's tree, with the pull requests behind it on top.

## Build once, publish the tested image

Without the train, a merge to `main` builds, scans, tests and gates the merged commit again, even when the pull request run already did the same work. With the train, the merge commit's tree is exactly the tree the car tested, so that second build is pure waste.

```mermaid
sequenceDiagram
    participant Car as Car run (merge_train)
    participant GH as GitHub
    participant Push as Push run on main
    participant Reg as Registry

    Car->>Car: checkout, test, build, scan, gate
    Note over Car: records tree T and<br/>gate-approved digest D
    Car->>GH: squash-merge (tree T)
    GH->>Push: push webhook for the merge commit
    Push->>Push: tree T was tested by car run, same authority, under 72h
    Push->>Reg: publish: re-tag digest D as sha-<merge commit>
    Note over Push: every other stage shows<br/>"already passed for exactly this tree"
```

Declare it on the `publish` stage:

```yaml
- name: publish
  kind: publish
  needs: [gate]
  when:
    events: [push]
  publish:
    promote_from: pull_request
```

The push is promoted only when all of these hold. Otherwise it builds in full, and the run records why:

- Every `publish` stage declares `promote_from`, under approved authority. It is a protected section, so a pull request cannot turn it on for itself.
- The push's plan is only `publish` and the stages it needs.
- A pull request or car run tested the same git tree, under the same approved authority, within the last 72 hours.
- Every stage `publish` needs passed in that run on its newest attempt. A stage that run skipped as [not affected](/pipelines/fast-ci#run-only-what-a-change-touches) counts too.
- That run's `gate` judged exactly the digest its `build` reported.
- The run was not from a fork, and was not a skipped car.

The run's detail says `Promotion: promoted (from run #N)`, or names the reason it fell back, such as `no_tested_run`, `source_inputs_differ` or `source_too_old`.

In a batch, only the last pull request's merge is a tree the batch's run tested, so the merges of the pull requests that rode with it cannot promote from the batch's run. Once the last one's push has promoted from that run, their push runs that are still waiting to publish stop as superseded by it, so only the tested tree publishes. A rider's push that already promoted from a run of its own tree, or that runs a stage the batch's run did not, is left to run.

## Commands

<CliVersion since="0.30.0" />

| Command | What it does | Needs |
|---|---|---|
| `ankra pipeline train enable [--max-cars 1-8]` | Turn the train on, or change how many cars test at once | `pipelines.manage` |
| `ankra pipeline train disable` | Turn it off. The train empties on the next pass | `pipelines.manage` |
| `ankra pipeline train add <pr> [--head-sha <sha>]` | Put a pull request at the end of the train. A stacked one needs the pull request below it in the train | `pipelines.operate`, and author, writer or admin |
| `ankra pipeline train list` | The train in order: pull request (a stacked one shows `(on #N)`, CLI 0.51.0+), status, attempt, car, run (`-` for a car tested by the run of the last car in its batch), entry id. Then what recently left, with why | Membership |
| `ankra pipeline train remove <entry-id>` | Take one entry out | `pipelines.operate` |
| `ankra pipeline train front <pr or entry-id>` (CLI 0.47.0+) | Move a pull request ahead of every car still queued, building or testing. Cars it passes are rebuilt. The bottom of a stack moves with the whole stack, in order; a pull request whose parent is still in the train is refused | Organisation administrator with `pipelines.operate` |

Every command takes `--application <name>` or `--repository <id>`, or infers the repository from your checkout's `origin`. Add `-o json` for scripts. `merge-train` is an alias for `train`. Over the [MCP server](/pipelines/cli-and-mcp), a coding agent enters a pull request through merge when green (`scm_merge_pull_request`), which joins the train on a repository that has one, and follows the car's run with `watch_pipeline_run`.
