<Note>
GitLab connects with an access token rather than an app: you paste a token, Ankra shows you a webhook URL and secret, and you register the hook in GitLab yourself. GitLab.com and self-managed instances work the same way.
</Note>

## What a GitLab connection powers

- **[AI code review](/platform/ai-code-review)** on merge requests, and replies when somebody mentions `@ankraai` in a merge request comment.
- **[Ankra Pipelines](/guides/ankra-pipelines)** runs on pushes, tags and merge requests. Cluster [GitOps](/concepts/gitops) sync supports GitHub and Bitbucket Cloud only, so a cluster's repository cannot live on GitLab.

Both ride the same credential and the same webhook. Every AI capability is off until an organisation owner or admin, or another role with `ai.manage`, turns it on. [Git Providers](/integrations/git-providers) compares what GitLab supports with GitHub and Bitbucket Cloud.

---

## Prerequisites

You need:

- A GitLab access token. A personal, group, or project access token all work.
- Permission to add a webhook to each project Ankra should watch, or to the group containing them.
- To switch on AI review or mention replies: the `ai.manage` permission in Ankra, which the organisation owner and admin roles hold.

### Token scopes

| Scope | Why |
|---|---|
| `read_api` | The minimum Ankra validates the token against, and enough to read merge requests and diffs. |
| `read_repository` | Read file contents when a review needs more than the diff. |
| `api` | Required for Ankra to **post** anything: the review comment and mention replies are writes, and `read_api` cannot make them. |

<Warning>
`read_api` is read-only. A token carrying only `read_api` and `read_repository` connects successfully and reads your merge requests, but every attempt to post a review comment fails. Use `api` unless you deliberately want a read-only connection.
</Warning>

A group access token scoped to the group that owns your projects is usually the least fiddly choice: one token, one webhook per project, and it survives people leaving.

The **Connect GitLab** form in Ankra names only `read_api` and `read_repository`. That is enough to connect and read, not to post reviews: give the token `api` as well.

## Connect GitLab

<Steps>
  <Step title="Open the GitLab connection form">
    In Ankra, go to **Ankra AI → Gateway connections** (`/next/ai/settings/gateway`) and scroll to the **GitLab** section. The **Connect GitLab** card is at its end.

    **Integrations & alerts → Credentials → Add credential → GitLab** opens the same form.
  </Step>
  <Step title="Fill in the form">
    - **Name** - optional, and worth setting when you connect more than one instance.
    - **GitLab address** - leave it empty for gitlab.com, or give the base URL of your self-managed instance, for example `https://gitlab.example.com`.
    - **Access token** - the token from above.

    Click **Connect GitLab**. Ankra validates the token against the instance before storing it, so a rejected token fails here, under **GitLab was not connected**, rather than silently later.
  </Step>
  <Step title="Copy the webhook address and secret">
    The **Copy the webhook secret now** dialog shows the **Webhook address**, of the form `https://platform.ankra.app/webhooks/gitlab/<credential-id>`, and the **Webhook secret**.

    <Warning>
    This is the only time Ankra shows the secret. Copy it, tick **I have put it in GitLab or stored it somewhere safe**, then click **Done**. If you lose it, regenerate it - you cannot read it back.
    </Warning>

    The instance now has its own card in the **GitLab** section. **Show settings** on it shows the **GitLab webhook** address again, with the secret masked.
  </Step>
  <Step title="Register the webhook in GitLab">
    In the GitLab project, go to **Settings** → **Webhooks** → **Add new webhook**:

    - **URL** - the webhook URL you copied.
    - **Secret token** - the secret you copied.
    - **Trigger** - tick **Merge request events**, **Comments**, **Push events**, and **Tag push events**.

    Save, then press **Test** → **Merge request events**. A `200` means Ankra accepted the delivery.

    Repeat per project, or add the hook once at group level under **Settings** → **Webhooks** to cover every project in the group.
  </Step>
  <Step title="Turn on what you want">
    A fresh connection does nothing. On the instance's card, click **Show settings**, then under **Repositories** switch on **AI review** and **Replies to mentions** on the **All repositories** row, or click **Add rule** for one project. See [AI code review](/platform/ai-code-review) for what each switch does.
  </Step>
</Steps>

## Which events do what

| GitLab event | What Ankra does with it |
|---|---|
| **Merge request events** | Runs the AI review when a merge request is opened or updated, and starts merge-request-triggered [Ankra Pipelines](/guides/ankra-pipelines) runs. |
| **Comments** | Answers a comment that mentions `@ankraai`. |
| **Push events** | Starts push-triggered [Ankra Pipelines](/guides/ankra-pipelines) runs. |
| **Tag push events** | Starts tag-triggered [Ankra Pipelines](/guides/ankra-pipelines) runs. A tag syncs no cluster. |

Every delivery is authenticated by comparing the `X-Gitlab-Token` header against the credential's stored secret. A delivery with the wrong secret is rejected with `401`; an event kind Ankra does not use is answered `200` so GitLab keeps the hook enabled.

---

## Rotate the webhook secret

On the instance's card in **Ankra AI → Gateway connections**, click **Show settings**, then **Regenerate the secret** under **GitLab webhook**, and confirm with **Regenerate secret**. Ankra shows the new secret once, in **Copy the webhook secret now**.

<Warning>
The old secret stops working immediately. GitLab keeps delivering with it until you update the hook, and those deliveries are rejected, so update the webhook in GitLab straight away.
</Warning>

## Repository paths and subgroups

Repository rules key on the project's full path, lowercased, including every subgroup - `my-group/my-subgroup/my-project`. Up to 20 levels of nesting are supported. The path is what appears in the project's URL after the instance host.

---

## Disconnect

**Disconnect** on the instance's card in **Ankra AI → Gateway connections** removes it, after you confirm. AI reviews, mention replies, and pipeline triggers through that credential all stop, and the webhook deliveries start being rejected. Remove the hook in GitLab too, so it stops retrying.

## Troubleshooting

| Symptom | What to check |
|---|---|
| **GitLab rejected the access token** on connect | The token is expired, revoked, or lacks `read_api`. For a self-managed instance, check the instance URL is the base URL with no path. |
| Webhook test returns `401` | The secret in GitLab does not match the credential's. Regenerate it in Ankra and paste the new one into the hook. |
| Webhook test returns `200` but no review appears | The delivery arrived and the capability is off. Turn **AI review** on for the instance or for that project, and check the [skip reasons](/platform/ai-code-review#when-a-review-does-not-run). |
| Reviews stopped after rotating the secret | The hook in GitLab still carries the old secret. Update it. |
| The review runs but nothing is posted | The token has `read_api` but not `api`, so Ankra can read the merge request and not comment on it. Replace the token with one carrying `api`. |
| Mentions go unanswered | **Replies to mentions** is a separate switch from **AI review**, the **Comments** trigger must be ticked on the webhook, and the comment must spell `@ankraai`. |
| Self-managed instance unreachable | Ankra calls your instance outbound over HTTPS. An instance behind a private network or an allow-list has to permit it. |
