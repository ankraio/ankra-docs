# Deprovision a Proxmox VE Cluster That Has Volumes

`ankra cluster deprovision` on a Proxmox VE cluster now names the persistent volumes it deletes, asks on a terminal, and sends `--accept-volume-data-loss`. # A Cluster Being Deprovisioned Says So

A command sent to a cluster that is being deprovisioned, such as deleting, patching or applying a resource, pod logs or a terminal, now prints the platform's reason: the cluster takes no new commands while its teardown is still running. <Update label="v0.52.0">
# Diagnose a Node over SSH, and See When an Answer Came from the Cache

`ankra cluster <provider> nodes diagnose <cluster> <node_id>` runs the read-only SSH diagnosis the Ankra assistant runs as `ssh_diagnose_node`. Over the platform's bastion lane it snapshots the node's Kubernetes service unit and journal, disk, memory, uptime, kernel log and firewall path to the API server, names the symptoms it finds and changes nothing on the node. It waits for the report (exit 5 when your `--timeout` runs out) and hands back the operation to poll when the job runs longer. It is offered on the providers with `nodes cloud-init-log` and needs the `clusters.operate` permission and a platform that serves the new route.

```bash
ankra cluster hetzner nodes diagnose my-cluster "$NODE_ID"
```

`ankra cluster get`, `cluster events` and `cluster describe` now print one line on stderr when an answer came from the agent's cache, with its age and, when the platform knows, why the cluster did not answer live. Standard output is unchanged, and `cache_metadata` in `-o json|yaml` also carries `stale`, `reconcile_pending` and, from platforms that send it, `cache_age_seconds`. `ankra cluster info` takes a cluster id as well as a name.

[Hetzner nodes diagnose reference →](/reference/cli/cluster#ankra-cluster-hetzner-nodes-diagnose)

</Update>

# Merge Train Auto-Admit from the Terminal, and Who Replied Last

`ankra pipeline train enable --auto-admit off|shadow|on` switches the merge train's auto-admit from the terminal: with `on` the train adds green pull requests by itself, `shadow` only records which ones it would add, and leaving the flag out keeps the current mode. `ankra pipeline train list` shows the auto-admit mode and who set it, its latest decisions with the reason a pull request was left out, and a pull request stacked on another one as `(on #N)`; `-o json` carries the auto-admit and stacking fields it used to drop.

```bash
ankra pipeline train enable --application my-app --auto-admit shadow
```

`ankra support list` gains `UPDATED` and `LAST REPLY` columns, `ankra support get` prints `Updated:` and `Last reply:` lines, and `-o json` carries `last_comment_at` and `last_comment_by`. `ankra credentials proxmox create` now waits up to five minutes for the platform to finish setting up Proxmox VE, where it gave up after 30 seconds and the credential was never saved.

# Grant a Role at Any Scope from the Terminal

`ankra org assign <member> --role <role> --scope organisation|cluster|cluster_group|project` grants a member a role at one scope. The member is named by email or user id, `--scope-id` names the cluster, cluster group or project (the global `--project` also works), and `--role` takes a built-in role or a custom role id. A grant the platform refuses, such as a duplicate or one above your own role, is shown with its reason.

```bash
ankra org assign dev@example.com --role operator --scope cluster --scope-id prod-eu
```

`ankra org member role <member> --role <role>` changes a member's organisation role, including `--role project --project <ref>` to make them project-only; it needs a platform that accepts this change from an API token and exits 3 until then. `ankra cost summary --by provider|credential|project` shows only that breakdown, `credential` being new. Fixed: `ankra cluster kube-token`, and so `kubectl`, finds a cluster in another project of your organisation without a `--project` pin, `org invite`, `org remove` and `org member role` always act in the organisation they name, `ankra cluster select` remembers the cluster's project when the platform reports it, and the bundled skills no longer steer Hetzner clusters onto server types the location cannot provision.

[Org assign reference →](/reference/cli/org#ankra-org-assign)

Fixed: `cluster apply` (`--confirm-removal`, `--prune`), `stack-profiles rollout` (multi-stack needs `--yes`) and `migrate restore` stop removing or overwriting what you did not name, and a refused request exits 7, not 6.

<Update label="v0.46.0">
# Organisation Secrets Without the Value on a Command Line

`ankra secrets` manages an organisation's secrets without the value passing through a command line, a file you commit or a model's context. `create <name>` stores a value from `--generate` (Ankra creates it and nobody sees it), `--from-file` or stdin, and prints its `${SECRET_SLOT:<id>}` sentinel, which a stack, add-on or application references and Ankra resolves at deploy time; a value given as an argument is refused with exit 2. `list` never shows a value, `set` and `rotate` replace one in place so the sentinel stays valid, and `delete` refuses a secret deployed resources still reference.

```bash
ankra secrets create db-password --generate
```

`ankra cluster ankracloud create` and `preflight` size and tier each server's root disk with `--bastion-disk-gib`, `--control-plane-disk-gib`, `--etcd-disk-gib`, `--worker-disk-gib` and the matching `--*-disk-tier` flags, and `ankra cluster node-group add` takes `--disk-gib` and `--disk-tier` for every server a node group creates. The agent skills now recommend `ankra secrets` for values that must not live in Git.

[Secrets reference →](/reference/cli/secrets#ankra-secrets)

</Update>

# Check a Managed Service's Connection Before You Publish It

`ankra services packages propose --profile <id> --demo <workspace-id>` reads a running demo of the stack profile on the staging cluster and proposes the connection blocks the package could declare, from its Services' ports and its Secrets' key names, never their values; `-f package.json` writes the best complete proposal into the file `init` made. `probe ... --wait` runs the protocol's readiness canary against the demo with that connection and exits 0 only when it passed, 1 when it failed or is unknown, and 5 when it is still running at `--timeout`.

```bash
ankra services packages propose --profile "$PROFILE_ID" --demo "$DEMO_ID" -f package.json
ankra services packages probe --profile "$PROFILE_ID" --demo "$DEMO_ID" -f package.json --wait
```

`ankra services packages init --addon` now has the platform build the chart's stack profile, and `--generate-secret <name>` with one `--generate-key` per key makes the profile generate the service's credentials in the cluster, where Ankra never sees a random value. `ankra cluster node-group`, `ssh-keys`, `scale` and `upgrade` on a cluster Ankra did not build, any `ankra cluster <provider>` command run against another provider's cluster, and `ankra delete cluster` on a cloud cluster now say so and exit 2, not 1.

`ankra cluster agent upgrade --version <release>` installs an exact agent release, and `--allow-downgrade` lets it be an older one: the rollback the platform's API already allowed. <Update label="v0.43.0">
# Propose a Change to the Kubernetes Access Policy

`ankra org access-policy set` proposes a change to the organisation's Kubernetes access policy, and an organisation owner or admin applies it, signed in: no token can change the policy itself. `set` takes only what should change (`--creator-role`, `--max-role`, `--elevated-max-ttl`, `--require-reason-from`) and a required `--reason`, then prints the policy before and after, the proposal id, its 7-day expiry and the link to apply it. Proposing needs the `kube_access.manage` permission (exit 7 without it).

```bash
ankra org access-policy set --max-role edit --reason "No standing admin" --wait
```

`--wait` blocks until the proposal is decided and exits 0 when it was applied, 4 when it was dismissed, 1 when it expired or a newer one replaced it, and 5 when `--timeout` runs out. `ankra org access-policy proposals` and `proposal <id>` read proposals, and `get` names a pending one and its link.

# Sign In from GitHub Actions Without a Stored Token, and Rotate Tokens

`ankra login --github-oidc` signs a GitHub Actions job in to Ankra with no stored token. # Variables, Live-Cluster SOPS, Dependency Parents, and Multi-Org

Rounds out stack CRUD from the CLI: template variables at every scope, SOPS encryption against live clusters, dependency-parent editing, read/delete commands, a global organisation override, and offline-installable Agent Skills.

## Variables (org / cluster / stack scopes)

Full CRUD for the template variables substituted into stack manifests and addon values at deploy time, at three scopes:

- `ankra org variables list|get|set|delete` - organisation-wide, available to every cluster.
- `ankra cluster variables list|get|set|delete [--cluster <name|id>]` - per cluster; shadows org variables on that cluster.
- `ankra cluster stacks variables list|get|set|delete <stack>` - per stack; the most specific scope.

`set` is an upsert (create or update). Values can be read from stdin with `-` for piping secrets, `list` / `get` support `-o json|yaml`, and `delete` prompts for confirmation (`--yes` to skip). Resolution at deploy time is **stack > cluster > organisation** - a more specific scope shadows less specific ones for the same name.

## SOPS encrypt/decrypt against live clusters

`ankra cluster encrypt` and `ankra cluster decrypt` now operate directly on a live cluster, with no local `cluster.yaml` required.

- `ankra cluster encrypt manifest <name> --key <key> [--cluster <name|id>]`
- `ankra cluster encrypt addon --name <addon> --key <key> [--cluster <name|id>] [--stack <stack>]`
- `ankra cluster decrypt manifest <name> [--cluster <name|id>]`
- `ankra cluster decrypt addon --name <addon> [--cluster <name|id>] [--stack <stack>]`

Cluster mode fetches the current content, runs it through the SOPS API, and (for encrypt) pushes the result back via the partial-stack PATCH with `encrypted_paths` updated. The `-f cluster.yaml` file mode is unchanged for GitOps workflows; the two modes are mutually exclusive and cluster mode is the default. `decrypt addon` is new, bringing the addon variant to parity with manifests.

## Dependency parents on upgrade

`ankra cluster addons upgrade` and `ankra cluster manifests upgrade` now edit the dependency parents that control deployment ordering inside a stack, without re-applying the whole `cluster.yaml`:

- `--add-parent name=<n>,kind=<manifest|addon>` - repeatable; `kind` defaults to `manifest`.
- `--remove-parent name=<n>,kind=<manifest|addon>` - repeatable; removing the last parent clears the link.
- `--set-parent name=<n>,kind=<manifest|addon>` - replaces ALL parents; mutually exclusive with `--add-parent` / `--remove-parent`.

## Read and delete

- `ankra cluster addons values <name>` - print an addon's current Helm values (decoded; `-o raw` for the base64 form).
- `ankra cluster manifests get <name>` - print a manifest's current YAML (decoded; `-o raw` for the base64 form).
- `ankra cluster manifests delete <name>` - disconnect a manifest from its stack and remove its resources; the owning stack is resolved automatically and a confirmation prompt protects the operation (`--yes` to skip, `--dry-run` to preview).

## Run a command against another organisation

A global `--org <name|id>` flag (or the `ANKRA_ORG` environment variable) runs a single command against any organisation you belong to, without changing your selected organisation:

```bash
ankra --org "Acme Corp" cluster list
export ANKRA_ORG="Acme Corp"   # scope a whole shell session
```

The override is per request and never changes the `ankra org switch` selection. You must be an active member of the target organisation.

## Install Ankra Agent Skills

`ankra skills` installs the curated Ankra Agent Skills into a Cursor/Claude skills directory. The skills are embedded in the binary, so installation works offline and is versioned with the release.

```bash
ankra skills list                  # list available skills (marks installed ones)
ankra skills install               # install all into ~/.cursor/skills (personal)
ankra skills install --project .   # install into ./.cursor/skills (project)
ankra skills install ankra-gitops  # install only named skills
ankra skills uninstall             # remove all Ankra skills
```

Use `--force` to overwrite existing skills and `--source <dir>` to install from a local directory instead of the embedded copy. This is separate from `ankra openclaw skill`, which generates a per-cluster SKILL.md.

# Surgical Addon and Manifest Upgrades

Two new subcommands for in-place updates that go through the same partial-stack endpoint as the UI. Atomic, locked, single git commit per invocation.

## Addon Upgrade

- `ankra cluster addons upgrade <addon> --chart-version <version>` - bump the chart version.
- `ankra cluster addons upgrade <addon> --set <key>=<value>` - mutate a single Helm values field (helm-style; supports dotted paths, `[idx]` indexing, and `[key=value]` list selectors such as `env[name=LOG_LEVEL].value`).
- `ankra cluster addons upgrade <addon> --values-from-file <path>` - replace the entire values document.
- `ankra cluster addons upgrade <addon> --registry-name`, `--registry-url`, `--registry-credential-name` - atomically retag the addon's registry.
- `ankra cluster addons upgrade <addon> --namespace <new>` - destructive Helm reinstall in a new namespace; requires `--yes` or an interactive confirmation.

`--set` and `--values-from-file` are mutually exclusive: `--set*` MUTATES the existing values document, `--values-from-file` REPLACES it. Use `--set-string` to force a value to remain a string, and `--set-file key=path` to load a value from a file.

## Manifest Upgrade

- `ankra cluster manifests upgrade <manifest> --from-file <path>` - replace the manifest content.
- `ankra cluster manifests upgrade <manifest> --manifest -` - read manifest YAML from stdin.
- `ankra cluster manifests upgrade <manifest> --set <key>=<value>` - mutate a single path in the manifest YAML (helm-style; supports dotted paths, `[idx]` indexing, and `[key=value]` list selectors such as `containers[name=app].image`).
- `ankra cluster manifests upgrade <manifest> --target-kind <kind> --target-name <name>` - with `--set`, pick which document to edit when the manifest holds multiple Kubernetes resources.
- `ankra cluster manifests upgrade <manifest> --namespace <new>` - change the manifest's namespace.

`--set*` MUTATE the existing manifest and are mutually exclusive with `--from-file` / `--manifest -`, which REPLACE it. Use `--set-string` to force a value to remain a string, and `--set-file key=path` to load a value from a file.

## Addon and manifest field selectors

Both `addons upgrade` and `manifests upgrade` `--set` paths can address a list item by a stable field instead of a numeric index - for example `env[name=LOG_LEVEL].value=debug` or `spec.template.spec.containers[name=app].image=nginx:1.27`. A selector that matches nothing fails with a clear error rather than guessing.

## Common Options

- `--cluster <name|id>` - defaults to the active selection.
- `--stack <name>` - addons only, required when the same addon name exists in multiple stacks. Manifest names are globally unique on a cluster, so `manifests upgrade` has no `--stack` flag.
- `--dry-run` - print before/after without writing.
- `-o json|yaml` - machine-readable output (the `--dry-run` envelope is `{before, after, notices}`).

## Example: bump `image.tag` for the website addon

```bash
ankra cluster addons upgrade website \
  --set image.tag=1.0.146 \
  --cluster website-demo
```

## Example: bump a Deployment image tag in a manifest

```bash
ankra cluster manifests upgrade web \
  --set 'spec.template.spec.containers[name=app].image=nginx:1.27' \
  --cluster website-demo
```
