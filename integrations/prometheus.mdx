Ankra charts a cluster's CPU, memory, network and workload usage without any setup: the Ankra agent sends those metrics itself (see [Cluster metrics](/platform/cluster-metrics)). Connect a Prometheus-compatible service you already run when you also want:

- the charts the built-in metrics cannot draw: **Network drops**, **Disk operations**, **CPU throttling** and **GPU telemetry** on the cluster's **Metrics** page,
- metrics in pod charts and in Ankra AI investigations,
- PromQL against the cluster from the CLI (`ankra cluster metrics query`) and MCP (`query_prometheus`).

## Before you start

- **Permissions on the cluster.** Saving a connection needs `clusters.write`, `stacks.write` and `stacks.delete`. With `clusters.write` alone you can test and disconnect, and the panel says "You can test and disconnect connections. Ask an administrator for the additional permissions needed to save a connection." See [Roles and access](/guides/roles-and-access).
- **An address the cluster can reach.** The Ankra agent queries the service from inside the cluster, so use an in-cluster service address, or an external one the cluster's network allows.
- **The cluster agent online.** Ankra tests the connection through the agent before it saves it.

## Kinds of service

| **Kind** in the dialog | For | Example address |
|---|---|---|
| **Prometheus** | A Prometheus you run in the cluster or one the cluster can reach, including Thanos Query | `http://prometheus.monitoring.svc.cluster.local:9090` |
| **Grafana Cloud or Mimir** | Grafana Cloud's Prometheus endpoint, or a Mimir you run, signed in with a token | `https://prometheus-prod-00-prod-eu-west-0.grafana.net/api/prom` |
| **VictoriaMetrics** | The Prometheus-compatible query address of a VictoriaMetrics | `https://victoriametrics.example.com/prometheus` |

Common in-cluster addresses for **Prometheus**:

```text
# kube-prometheus-stack
http://prometheus-operated.monitoring.svc.cluster.local:9090

# The prometheus community chart
http://prometheus-server.monitoring.svc.cluster.local:9090

# Prometheus Operator
http://prometheus-k8s.monitoring.svc.cluster.local:9090
```

## Connect a Prometheus

<Tabs>
  <Tab title="Portal">
    <Steps>
      <Step title="Open the cluster's integrations">
        Go to **Infrastructure → Clusters → &lt;your cluster&gt; → Settings → Integrations** (`/next/clusters/<cluster-id>/settings/integrations`). Under **Your metrics and logs**, the **Metrics** panel reads **Not connected**.
      </Step>
      <Step title="Open the dialog">
        Click **Connect a Prometheus**. The dialog **Connect a Prometheus** opens.
      </Step>
      <Step title="Pick the kind and enter the address">
        Under **Kind**, choose **Prometheus**, **Grafana Cloud or Mimir** or **VictoriaMetrics**, then type the address in **Prometheus address**, **Prometheus query address** or **VictoriaMetrics query address**. The address starts with `http://` or `https://`.

        For **Prometheus**, click **Find Prometheus in the cluster** to list the Prometheus services Ankra finds. **Answers** marks one that replied and **Best match** the one Ankra recommends; click **Use &lt;service&gt;** to fill in its address.
      </Step>
      <Step title="Choose how Ankra signs in">
        Under **How Ankra signs in**, choose **No sign-in**, **API token** (sent as a bearer token) or **User name and password** (sent as basic sign-in). For a token or a password, give it a **Credential name** - letters, numbers, dots, dashes and underscores, starting with a letter or number - and enter the secret. Ankra stores the secret under that name and never shows it again.
      </Step>
      <Step title="Test, then save">
        Click **Test connection**. A working connection reads **The connection works** with "Connected. The store answered with N series." Then click **Save**. Ankra tests the connection again before it saves it.
      </Step>
    </Steps>
  </Tab>
  <Tab title="Git">
    In a cluster connected to a GitOps repository, add `spec.prometheus_metrics` to the cluster document. See [Manage the connection in Git](#manage-the-connection-in-git).
  </Tab>
  <Tab title="MCP">
    `connect_metrics_source` connects the Prometheus-compatible source Ankra derived from the cluster's installed add-ons, as a `query_prometheus` refusal named it ([MCP tools](/platform/mcp-tools)).
  </Tab>
</Tabs>

**Check:** the **Metrics** panel shows the **Provider**, **Address**, **Credential** and **Last checked**, and its badge reads **Answering**. On the cluster's **Metrics** page, the **Connected Prometheus** row reads **Connected and answering**, and setting **Source** to **Connected Prometheus** draws the charts from it.

## Change or disconnect the connection

- **Change** on the **Metrics** panel opens **Change the Prometheus connection** with the kind and address filled in. When the stored address holds a password, token or query, the panel shows "Not shown: the stored address holds a password, token or query." and you enter the address again.
- **Disconnect** asks **Disconnect this Prometheus?**: Ankra stops reading metrics from it. The Prometheus itself is not changed, and you can connect it again.
- **Remove credential**, beside the credential's name, asks **Remove the credential &lt;name&gt;?**: Ankra deletes the stored token or password, and until you add another, reaches the Prometheus without signing in.

## Credentials

Ankra keeps its own copy of the secret and sends it with every query and with the health check that runs every five minutes. Changing the password or token on the Prometheus side does not change it in Ankra, and changing it in Ankra does not change Prometheus.

A stored credential cannot be edited. While one is stored, the dialog says "Ankra signs in with the stored credential &lt;name&gt; (...). To use a different one, remove this credential first, then add the new one here."

To rotate a secret in the portal:

1. Make the new secret live on the Prometheus side.
2. On the **Metrics** panel, click **Remove credential** and confirm.
3. Click **Change**, choose how Ankra signs in, enter the new secret under the same **Credential name**, click **Test connection**, then **Save**.

Queries fail with a 401 between step 1 and step 3, once Prometheus drops the old secret. To rotate without the portal, use the API below.

### Rotate by API

To rotate from a script, send the cluster's import request with only the new credential. The call replaces the saved metrics credential and leaves everything else on the cluster as it is - as long as the body carries no `stacks`, because a stack in the body replaces the saved stack of that name.

```bash
curl -sS -X POST "https://platform.ankra.app/api/v1/clusters/import?wait=true" \
  -H "Authorization: Bearer $ANKRA_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "<cluster-name>",
    "spec": {
      "prometheus_credential": {
        "name": "<credential-name>",
        "username": "<username>",
        "password": "<new-password>"
      }
    }
  }'
```

- **Use a REST token** - a [personal access token](/reference/tokens) created without `--scopes`, or a [service token](/guides/service-tokens) with no MCP scope, whose role can change the cluster. A token with `mcp:read` or `mcp:write` is refused with `403`.
- **Send the whole block.** `name`, `username` and `password` for basic auth, or `name` and `token` for bearer auth. An omitted `username` is saved as empty and basic auth stops working.
- **Keep the name** the **Metrics** panel shows, so the old secret is overwritten rather than left behind.
- **Use `wait=true`**, so the call answers with the outcome - check its `errors` list - instead of `202` before the work is done.
- **If the call answers `422 Failed to push changes to Git repository`**, the credential is already saved: Ankra had not synced your latest commit to the cluster's repository. Do not retry; check with the query below.

This call is the only scripted way to change the secret: `ankra cluster apply` and the Git sync both ignore a `prometheus_credential` block. To check the whole path afterwards - the saved credential, the agent and Prometheus - run `ankra cluster metrics query 'up'` against the cluster. Results are cached for ten seconds.

## Manage the connection in Git

If the cluster is connected to a [GitOps repository](/concepts/gitops), the metrics source is part of the cluster document at `clusters/<cluster-name>-<cluster-id>/<cluster-name>.yaml`. Adding or editing the `spec.prometheus_metrics` block connects and updates the source on the next sync, exactly as the settings page does:

```yaml
spec:
  prometheus_metrics:
    endpoint: http://prometheus-operated.monitoring.svc.cluster.local:9090
    flavor: self_hosted
    credential_name: prometheus-prod
```

`flavor` is `self_hosted` (**Prometheus**), `grafana_cloud` (**Grafana Cloud or Mimir**) or `victoria_metrics` (**VictoriaMetrics**). Accepted fields are `endpoint`, `credential_name`, `flavor`, `verify_ssl` and `tenant_id` - see the [ImportCluster schema](/reference/importcluster#spec-prometheus-metrics) for what each one means. Any other top-level field is refused with an error naming it, rather than ignored. A block without `credential_name` keeps using the credential already saved on the cluster, if there is one; the **Metrics** panel under **Settings → Integrations** shows which.

<Warning>
**Credentials never go in Git.** A `username`, `password`, `token` or `auth_scheme` inside the block is refused by name: silently ignoring it would leave a live secret in your repository while you believe it is in effect. Create the credential in the platform and reference it with `credential_name`.

**Removing the block does not disconnect Prometheus.** Git can create and update the source, never disconnect it - the source survives the sync and the block reappears the next time Ankra regenerates the file. Disconnect from **Settings → Integrations** instead.
</Warning>

## Verify

<CliVersion since="0.74.0" />

```bash
# The source Ankra has registered: provider, endpoint, state and latest health check
ankra cluster metrics source

# The whole path: the saved credential, the agent and Prometheus
ankra cluster metrics query 'up'
```

In the portal, the cluster's **Metrics** page with **Source** set to **Connected Prometheus** draws every chart from the connected service, and each chart names its source underneath.

## What can go wrong

A failed **Test connection** reads **The connection does not work** with one of these messages:

| Message | What to do |
|---|---|
| "The metrics store refused the credential. Check the token, key, or user name and password." | The secret is wrong or expired. Remove the credential and add the right one. |
| "The metrics store accepted the credential but does not let it read metrics." | Give the account or token read access to metrics on the Prometheus side. |
| "The cluster is offline. The Ankra agent must be connected to reach the store." | Bring the agent back online; check **Settings → Agent**. |
| "The metrics store did not answer in time. Check that the address can be reached from inside the cluster." | Check the address and port, and that the service exists (below). |
| "The metrics store answered, but not as a Prometheus does. Check the address." | The address points at something else, for example the Grafana UI instead of its Prometheus endpoint. |

A save that fails its test reads **The connection was not saved** with "Ankra tested the connection before saving it, and it did not work." and the reason.

To check that the service exists and runs, without a kubeconfig:

```bash
ankra cluster get services -n monitoring
ankra cluster get pods -n monitoring
```

**Charts stay empty or read "No samples returned".** The service answers, but has no series the chart needs. The Metrics page reads these exporters:

| Exporter | Metrics it reads | Charts |
|---|---|---|
| cAdvisor, in the kubelet | `container_cpu_usage_seconds_total`, `container_memory_working_set_bytes`, `container_network_receive_bytes_total`, `container_network_transmit_bytes_total`, `container_fs_reads_total`, `container_fs_writes_total`, `container_cpu_cfs_throttled_seconds_total`, `container_oom_events_total` | CPU, memory, network and disk operations, CPU throttling, out-of-memory events |
| node-exporter | `node_filesystem_avail_bytes`, `node_filesystem_size_bytes`, `node_network_receive_drop_total`, `node_network_transmit_drop_total`, `node_uname_info` | Filesystem usage, network drops |
| kube-state-metrics | `kube_node_status_condition`, `kube_pod_status_phase`, `kube_pod_container_status_restarts_total` | Node readiness, pods by phase, pod restarts |
| Traefik or ingress-nginx | `traefik_service_requests_total`, `traefik_service_request_duration_seconds_bucket`, `nginx_ingress_controller_request_duration_seconds_bucket` | Ingress traffic |
| NVIDIA DCGM exporter | `DCGM_FI_DEV_GPU_UTIL`, `DCGM_FI_DEV_FB_USED`, `DCGM_FI_DEV_GPU_TEMP`, `DCGM_FI_DEV_POWER_USAGE` | GPU telemetry |

kube-prometheus-stack scrapes cAdvisor, node-exporter and kube-state-metrics out of the box. Ingress and GPU charts need their own exporters scraped too.

**Queries are slow.** Narrow the time range on the Metrics page, add recording rules for the queries you run often, or give Prometheus more CPU and memory.
