## ankra security

Read the organisation's Security Center - the same data the portal shows,
for your own reporting and automation.

Every finding carries its exploitation intelligence: whether CISA lists the
CVE in its Known Exploited Vulnerabilities (KEV) catalog, with CISA's
remediation deadline and required action, and the FIRST EPSS probability
that it is exploited in the next 30 days. Findings sort by exploitability by
default - CISA listing first, then EPSS, then severity - so the top of the
list is what is actually being exploited, not what merely has the highest
CVSS score.

The reads cover the project you act in (see 'ankra project current'). Pass
`--all-projects` to read the whole organisation, or the global `--project` to read
another project. A pinned token or a member limited to projects cannot read past
their project, and `--all-projects` is refused for them. The compliance frameworks,
report and export are the organisation's whatever the project, so they do not
take the flag, and neither do 'history' and 'report-schedule'.

Pass -o json (or yaml) for the full API document.

## ankra security access

Evaluate one cluster's kube gateway grants and print every failed check,
most severe first: a grant whose identity the cluster verified can
impersonate, a standing cluster-wide admin or cluster-admin grant, a grant
the organisation's access policy would refuse today, and the creator's grant
left unchanged for 90 days on a GitOps cluster. Each finding names the grant,
the grantee, its role and scope, and the commands that fix it.

Checks that could not be evaluated are listed after the findings, so a short
list is never read as a clean one. A grant absent from both lists passed
every check. Grantee emails appear only when you hold kube_access.manage;
otherwise the grantee is shown by its Ankra user id. A service account,
which has no email, is shown as "service account &lt;name&gt;".

If the platform leaves the summary (or one of its always-sent counts), the
findings or the unknowns out of its answer, that part reads "not reported", whatever was reported is still
printed, and the command exits 1: an incomplete answer is never a pass.
-o json prints the document as sent, nulls included, and exits 0.

The same summary line is the Access column of 'ankra security clusters'.

```bash
ankra security access [flags]
```

## ankra security code-dispositions

A code disposition records a reviewed Semgrep or Checkov finding of a
pipeline repository as a false positive or an accepted risk. The Ankra
Pipelines image gate then stops blocking on that rule in that file, and names
the disposition on every run it lets through. A CRITICAL finding cannot be
disposed of. Container vulnerability dispositions are 'ankra security
dispositions'.

## ankra security code-dispositions create

Record a reviewed Semgrep or Checkov finding as a false_positive or an
accepted_risk. An accepted risk needs `--expires-at`, at most a year out. A
CRITICAL finding is refused, as is a second active disposition of the same
finding. See what it would cover first with 'preview'. It asks first; `--yes`
skips the question and is required when there is no terminal to ask on.

```bash
ankra security code-dispositions create --application <application> --tool semgrep|checkov --rule <rule-id> --path <file> --disposition <kind> --reason <why> [flags]
```

**Examples**

```bash
ankra security code-dispositions create --application shop --tool semgrep \
  --rule go.lang.security.audit.xss --path internal/web/render.go \
  --disposition false_positive --reason "Output is escaped by the template"
```

| Flag | Default | Description |
|------|---------|-------------|
| `--application` |   | The application whose pipeline repository holds the finding (name or id) |
| `--disposition` |   | false_positive or accepted_risk (required) |
| `--expires-at` |   | Review deadline as a date (2026-12-31) or RFC3339; required for accepted_risk |
| `-o`, `--output` |   | Output format: json or yaml (default: human-readable) |
| `--path` |   | The file the finding is in, relative to the repository root (required) |

## ankra security dispositions

List the organisation's vulnerability-disposition policies. A disposition
acknowledges a finding (it stays visible but leaves the actionable set) or
accepts its risk, for every occurrence its selector matches - one CVE and
package inside one add-on across the organisation, or pinned to one
namespace, one workload or one image digest when no add-on owns the image.

Each policy has a lifecycle status: active, expiring (the review deadline
is near), fix_available (a fixed version exists, so the acceptance should be
revisited), mitigated (nothing matches any more), unmatched (nothing ever
matched), expired or revoked.

Examples:

```bash
ankra security dispositions --status expiring --status fix_available
ankra security dispositions --disposition accepted_risk --sort expires_at --order asc
```

## ankra security dispositions create

Write a disposition anchored on one occurrence: acknowledged keeps the
finding visible but out of the actionable set; accepted_risk records a
decision to live with it, which needs the security.manage permission.

The preview prints first and the write asks for confirmation; `--yes` skips
the prompt. Give a `--reason`: it is what an auditor reads. `--expires-at` sets
a review deadline; `--expire-when-fix-available` ends the disposition the
moment a fixed version appears. `--allow-unmatched` stores a policy whose
anchor no longer matches anything.

`--scope` chooses what the policy is pinned to: organisation_addon (the
default) for the add-on that owns the occurrence, or, when no add-on owns
the image, namespace (every workload in the namespace on its cluster,
surviving rollouts and rebuilds), workload (one workload; a Deployment
survives rollouts) or image (one digest; lapses on the next build).

Examples:

```bash
ankra security dispositions create --occurrence 4f1c... --disposition acknowledged --reason "tracked in PLA-812" --expires-at 2026-10-31
ankra security dispositions create --occurrence 4f1c... --scope workload --disposition accepted_risk --reason "operator-managed, not reachable from outside the cluster"
ankra security dispositions create --occurrence 4f1c... --scope namespace --disposition accepted_risk --reason "transitive via crewai, feature unused" --expires-at 2026-12-31
```

```bash
ankra security dispositions create [flags]
```

**Flags**

| Flag | Default | Description |
|------|---------|-------------|
| `--allow-unmatched` | `false` | Store the policy even when its anchor no longer matches any occurrence |
| `--disposition` |   | acknowledged or accepted_risk |
| `--expire-when-fix-available` | `false` | End the disposition the moment a fixed version appears |
| `--expires-at` |   | Review deadline as a date (2026-12-31) or RFC3339 timestamp |
| `--occurrence` |   | Occurrence id to anchor the disposition on (from 'ankra security finding &lt;id&gt;') |
| `-o`, `--output` |   | Output format: json or yaml (default: human-readable) |
| `--reason` |   | Why the finding is acknowledged or its risk accepted (kept for audit) |
| `--scope` | `organisation_addon` | Selector scope: organisation_addon, namespace, workload or image; use namespace (survives rollouts and rebuilds), workload or image when no add-on owns the occurrence's image |
| `-y`, `--yes` | `false` | Skip the confirmation prompt |

## ankra security dispositions preview

## ankra security evidence

Security evidence is a bounded snapshot of what the Security Center knows: a
compliance framework's report when one is asked for, and the SBOM image
inventory with known-exploited vulnerabilities first.

A destination is where evidence goes: a Vanta document, a Wazuh relay or a
webhook that receives signed requests. A delivery is one snapshot sent to one
destination. For Vanta, the upload and the submission are separate steps: a
delivery reads "uploaded" until 'deliveries submit' submits the document.


## ankra security stack

## ankra security stacks

## ankra security workloads

List the fleet's scanned workload containers, riskiest first. Each row
carries the observed and actionable severity counts, what is acknowledged
or accepted, the fixable severe count and how many of its CVEs CISA lists
as exploited.

The filters are the findings list's. `--sort` defaults to risk_score.

Examples:

```bash
ankra security workloads --known-exploited
ankra security workloads --cluster production --namespace payments
ankra security workloads --addon ingress-nginx --sort last_scan --order asc
```

```bash
ankra security workloads [flags]
```

**Flags**

| Flag | Default | Description |
|------|---------|-------------|
| `--addon` |   | Only workloads attributed to one add-on (slug) |
| `--all-projects` | `false` | Read the whole organisation instead of the project you act in |
| `--cluster` |   | Only workloads observed on one cluster (name or id) |
| `--fixable` | `any` | Fix availability: true, false or any |
| `--known-exploited` | `false` | Only CVEs CISA lists as exploited in the wild (KEV) |
| `--namespace` |   | Only workloads observed in one namespace |
| `--order` | `desc` | Sort order: asc or desc |
| `-o`, `--output` |   | Output format: json or yaml (default: human-readable) |
| `--page` | `1` | Page number |
| `--page-size` | `25` | workloads per page (max 100) |
| `--search` |   | Match CVE id, package name or title |
| `--severity` | `[]` | Severity filter, repeatable: critical, high, medium, low, unknown |
| `--sort` | `risk_score` | Sort key: risk_score, priority, severity, known_exploited, observed, actionable, fixable_severe, last_scan, workload_name, image_ref, cluster_name, addon_attribution |
| `--status` | `[open,acknowledged]` | Status filter, repeatable: open, acknowledged, accepted_risk, resolved, or any |
