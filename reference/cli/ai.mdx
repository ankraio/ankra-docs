## ankra ai

Configure the organisation's AI provider, credentials, custom
OpenAI-compatible endpoints, and the model catalog the chat picker offers.

Mutations require the ai.manage permission (organisation admins by default);
the provider status and the model listing are available to every member.

Your own Anthropic or OpenRouter API keys, for the chats and pull request
reviews you start, are under 'ankra ai keys'; adding them needs no extra
permission.

## ankra ai autonomy

Read and operate the organisation-wide AI kill switch.

Engaging it stops all AI for everyone in the organisation: running sessions
and agent runs are cancelled, and chat is refused until it is released. Reach
for it during an incident, not to tighten a policy - a narrower stop lives in
the auto-remediation policy, which 'ankra ai remediation policy' reads.

## ankra ai autonomy pause

Pause autonomous actions across the organisation.

Chat, diagnosis and read-only investigation keep working; what stops is the
AI changing anything without a person approving it first. It switches off
auto-remediation and pauses every enabled agent, and records exactly what it
switched off - so resuming restores that and nothing else, from any
terminal or browser, by any administrator.

To stop AI entirely during an incident, use "ankra ai autonomy stop-all".

```bash
ankra ai autonomy pause [flags]
```

## ankra ai board-identity

Manage the organisation's board agent identity.

Agents the platform created - the preloaded team - have no user account of
their own, so their headless runs cannot change anything. The board identity
gives them one, with its own role, so their work is attributable to the agent
rather than to whoever set it up. It cannot sign in and has no token.

Without it, a designated board worker is escalated to a human on every ticket
instead of working it.

## ankra ai keys

Add your own Anthropic or OpenRouter API keys to your profile. The chats you
send and the reviews of your GitHub and Bitbucket Cloud pull requests then run
on your keys, in the order you choose, and your provider bills your account
instead of your organisation's. GitLab reviews, background work, scheduled runs
and alert analysis keep running on the organisation's AI.

Your keys are yours alone: they never serve another member's work, and after
you add a key Ankra only ever shows its last four characters. You can keep up
to 10 keys.

Only API keys are accepted: a Claude Console API key (it starts with
sk-ant-) or an OpenRouter key (it starts with sk-or-). Claude subscription
tokens (sk-ant-oat...) and Anthropic admin keys are refused, because
Anthropic does not allow other services to store them.

Ankra tries your keys from the top. A key that runs out of credit is tried
again an hour later; a key the provider rejects is not used until
'ankra ai keys test' passes.

An organisation administrator can turn members' own keys off for the
organisation ('ankra ai keys policy disable'). Your keys then stay on your
profile, but are not in use there.

You can also manage your keys in the Ankra portal: Profile, Connected
accounts, Your AI keys.

## ankra ai keys add

Add an Anthropic or OpenRouter API key to your profile. Ankra checks the key
with the provider before saving it, so a mistyped or revoked key is refused
straight away, and adds it to the end of your order.

The key is never a flag: a flag value lands in your shell history and in the
process list. Run the command in a terminal and paste the key when asked (the
input is hidden), or pipe it in with `--key-stdin`.

The provider is worked out from the key: a Claude Console API key (it starts
with sk-ant-) is Anthropic and sk-or-... is OpenRouter. `--provider` is only
needed to check that the key is the kind you meant. A Claude subscription
token (sk-ant-oat...) or an Anthropic admin key is refused before anything is
sent.

Only the key's masked preview is ever printed.

```bash
ankra ai keys add [flags]
```

**Examples**

```bash
# Paste the key when asked; the input is hidden.
ankra ai keys add --label "Personal Max plan"

# Pipe it in, for example from a password manager.
op read op://Private/anthropic/credential | ankra ai keys add --key-stdin --label work
```

**Flags**

| Flag | Default | Description |
|------|---------|-------------|
| `--key-stdin` | `false` | Read the API key from stdin instead of asking for it (the key is never taken as a flag) |
| `--label` |   | Your name for the key, shown beside it (at most 100 characters) |
| `-o`, `--output` |   | Output format: json or yaml (default: human-readable) |
| `--provider` |   | anthropic or openrouter; worked out from the key when left out |

## ankra ai tasks

Define, hire and control the organisation's agent tasks: the AI agents that
run on a schedule, on an alert or on demand, each with a goal, a tool profile,
an autonomy level and a budget.

'ankra agents' reads the runs these agents produce; the commands here manage
the agents themselves. A task is named by its id or by its exact name.
Reading needs ai.use; every change needs ai.manage and an organisation admin.

## ankra ai tasks create

Create an agent task. `--name`, `--goal` and `--trigger` are required, as flags or
as the name, goal_prompt and trigger members of the -f document; a flag wins
over the document. The tool profile defaults to read_only.

The budget, capabilities and the other members of the definition are set
through -f, which takes the platform's body as YAML or JSON (- reads stdin).

```bash
ankra ai tasks create [flags]
```

**Examples**

```bash
ankra ai tasks create --name "Nightly cost review" --goal "Review yesterday's spend" \
    --trigger cron --cron "0 6 * * *" --timezone Europe/Stockholm
ankra ai tasks create -f task.yaml
```

**Flags**

| Flag | Default | Description |
|------|---------|-------------|
| `--alert` |   | Alert id of an alert trigger |
| `--autonomy-level` |   | How far the agent acts alone: read_only, propose or auto |
| `--cluster` |   | Cluster name or id the agent is scoped to |
| `--cron` |   | Cron expression of a cron trigger |
| `--enabled` | `true` | Whether the agent is scheduled |
| `-f`, `--file` |   | YAML or JSON file with the task definition (- reads stdin) |
| `--goal` |   | What the agent is asked to do on every run |
| `--model-mode` |   | Model mode the agent runs on |
| `--name` |   | The agent's name |
| `-o`, `--output` |   | Output format: json or yaml (default: human-readable) |
| `--timezone` |   | Time zone the cron expression is read in |
| `--tool-profile` |   | Tools the agent may use: read_only, standard or admin |
| `--trigger` |   | What starts a run: mission, cron, alert or manual |
