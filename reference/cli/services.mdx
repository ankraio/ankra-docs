## ankra services

Set up, inspect and retire managed services: PostgreSQL, Valkey, OpenSearch,
VictoriaMetrics, VictoriaLogs and the other engines in the service catalogue,
run on your own cluster as reviewed, health-checked platform services.

A service is set up in three steps:

1. Pick a package from the catalogue:   ankra services packages list
2. Bind the application namespace that
   will use the service:                 ankra services consumers bind `--application` &lt;a&gt; `--cluster` &lt;c&gt; `--namespace` &lt;ns&gt;
3. Review and confirm the setup:         ankra services setup &lt;name&gt; `--package` postgresql `--cluster` &lt;c&gt; `--consumer` &lt;id&gt;

Declaring where a cluster is ('ankra services policy set') is optional: do it
when services must keep data within a data boundary.

Setup, retirement and disconnecting an application are two-step on the
platform. A review is prepared first: the platform resolves a plan, stores it
with a digest for ten minutes, and changes nothing. The plan is shown, and
only confirming it by its digest sets the service up, removes it or
disconnects the application. Every confirmation asks first; `--yes` skips the
question for scripts. Retiring a service deletes its data, so delete also
needs `--acknowledge-data-loss`. 'ankra services disconnect' takes one
application off a service that keeps running for the others, and deletes
nothing.

An application namespace on the service's own cluster receives the connection
once the service is running: a &lt;service&gt;-connection Secret in its namespace,
copied inside the cluster, which its workloads read as environment variables
(DATABASE_URL, REDIS_URL, NATS_URL, ...). While none of the application's
running pods reads the Secret, Ankra writes it without a redeploy; otherwise
Ankra leaves it to the application's next deploy, which rolls the pods that
read it together. Workloads deployed before the service was connected usually read
it after their next deploy; 'ankra services get' says when they do not. An
application on another cluster is not connected for you.

'ankra services list' and 'ankra services get &lt;name&gt;' show each service's
deployment state, health, readiness (a consumer-path canary connects with the
generated credentials, for every engine) and connection: its endpoints, the
Secret holding its credentials, and how each consumer receives them.
Credential values are never shown; they stay in the cluster.

**Examples**

```bash
ankra services packages list
ankra services setup orders-db --package postgresql --cluster prod --consumer 5b1f0c7e-...
ankra services list
ankra services get orders-db
ankra services disconnect orders-db --application storefront
ankra services delete orders-db --acknowledge-data-loss
```

## ankra services consumers

Bind, list and unbind consumers: the application namespaces a service is set up for.

A consumer is one application's namespace on one cluster, with a stable id.
Setup takes one or more consumer ids (`--consumer`), and the plan records each
with the cluster policy it was resolved against. A binding normally resolves
to the application's installation on that cluster; `--allow-planned` binds a
namespace the application is not installed in yet. A binding a service still
uses cannot be unbound: disconnect the application from the service first
('ankra services disconnect &lt;service&gt; `--consumer` &lt;id&gt;'), or retire the service.

## ankra services consumers bind

Bind an application's namespace on a cluster as a service consumer and print
its consumer id, which 'ankra services setup `--consumer`' takes.

The application must be installed in that namespace unless `--allow-planned`
is given. A binding is created once per application, cluster and namespace;
changing an existing one needs `--revision` with its current revision
('ankra services consumers list `--application` &lt;app&gt;' shows it); a setting
not given on the command line keeps the binding's current value. Binding
deploys nothing. Once a service set up for this consumer is running on the
same cluster, Ankra delivers its connection: without a redeploy while none of
the application's running pods reads it, otherwise it is left to the
application's next deploy. 'ankra services get &lt;service&gt;' shows its pickup.

```bash
ankra services consumers bind [flags]
```

**Examples**

```bash
ankra services consumers bind --application orders --cluster prod --namespace orders
ankra services consumers bind --application orders --cluster prod --namespace orders --allow-planned
```

**Flags**

| Flag | Default | Description |
|------|---------|-------------|
| `--allow-planned` | `false` | Bind even though the application is not installed in the namespace yet |
| `--application` |   | The application that will consume the service (name or id) |
| `--cluster` |   | The cluster the application runs on (name or id; default: the selected cluster) |
| `--local-only` | `false` | The consumer may only use a service on its own cluster |
| `--namespace` |   | The application's namespace on that cluster |
| `-o`, `--output` |   | Output format: json or yaml (default: human-readable) |
| `--revision` | `0` | The current revision of the binding being changed (omit to create one) |

## ankra services consumers unbind

Remove a consumer binding: the application namespace stops being a consumer
services can be set up for. Nothing is deployed or removed on any cluster.

A binding a service still uses is kept. Disconnect the application from the
service first ('ankra services disconnect &lt;service&gt; `--consumer` &lt;id&gt;'), or
retire the service ('ankra services delete'); then unbind it. A setup review
still pending that names the binding can no longer be confirmed.

The platform removes a binding only at the revision you last read. Without
`--revision` the current one is read from the binding. A binding whose
application or cluster has since been removed can still be unbound, but it can
no longer be read by id: pass `--revision` with the revision 'ankra services
consumers list `--application` &lt;application&gt;' shows. Asks first; `--yes` skips the
question.

```bash
ankra services consumers unbind <consumer-id> [flags]
```

**Examples**

```bash
ankra services consumers unbind 5b1f0c7e-0d7a-4c55-a6f4-2f1f4a9b1c11
ankra services consumers unbind 5b1f0c7e-0d7a-4c55-a6f4-2f1f4a9b1c11 --revision 3 --yes
```

**Flags**

| Flag | Default | Description |
|------|---------|-------------|
| `-o`, `--output` |   | Output format: json or yaml (default: human-readable) |
| `--revision` | `0` | The binding's current revision (default: read from the binding) |
| `-y`, `--yes` | `false` | Remove without asking |

## ankra services credentials

The registry of credentials a managed service can be given as an input, for
example the password of a database you already run.

A family is one named credential. Its values are immutable versions, and one
of them is active: storing a new value rotates the family, which retires the
previous value, revokes its grants and issues replacements. A grant is a
reference to a value for one input of one package version, and each grant is
revoked on its own.

No command here shows a value: the platform stores it and returns metadata
only. This registry does not connect or restart a workload.

**Examples**

```bash
ankra services credentials create orders-db-password
cat password.txt | ankra services credentials values add orders-db-password --first --value-stdin
ankra services credentials grants issue orders-db-password --package-digest sha256:... --input-name DATABASE_PASSWORD --mode existing
```

## ankra services credentials grants issue

Issue a grant: a reference to one of the family's values, bound to one input of
one package version. `--package-digest` is the package version's digest
(sha256:...), `--input-name` the input the credential is for (upper case, as the
package declares it) and `--mode` how the service is run: hosted, customer or
existing.

The grant references the family's active value unless `--value-id` names a
retained one. Each grant is revoked on its own, and a family holds at most 128
active grants.

```bash

```

**Examples**

## ankra services credentials values add

Store a new value in a credential family. The value becomes the family's active
value; the previous one is retired, its grants are revoked and replacement
grants are issued, which the command lists.

Say what you expect the family to hold, so a repeated or stale command cannot
replace a newer value:

```text
--first                   the family has no active value yet
--expected-value-id <id>  the active value you are replacing, as
                          'ankra services credentials get <family>' shows it
```

The platform refuses (409) when the family's state is not what you named.

The value is never taken as an argument. Pipe it on stdin with `--value-stdin`,
or run in a terminal to be asked for it with the input hidden. It is stored by
the platform and never shown again.

```bash
ankra services credentials values add <family> --first | --expected-value-id <id> [flags]
```

**Examples**

```bash

cat new-password.txt | ankra services credentials values add orders-db-password \
  --expected-value-id 5b1f0c7e-3a55-4d0b-9a57-0d5f3c1a2b3c --value-stdin
```

## ankra services delete

Retire a managed service, in two steps, deleting its data.

First a retirement review is prepared: the platform resolves what retiring
removes and keeps - the service's stack and its members, its namespace with
everything in it (objects it did not create are listed), every volume claim
with the reclaim policy that decides its data, the consumers it is
disconnected from and the shared operators it keeps - and stores that plan
with a digest for ten minutes. Preparing changes nothing on the cluster. The
plan is shown, and the service is retired only when you confirm it: at the
prompt, or with `--yes`.

Retiring deletes the namespace, its volume claims and its Secrets, generated
credentials included, and no export is offered; restore points stay in their
backup vault under its retention. A volume whose reclaim policy is Retain
keeps its data until someone removes it, and the settled retirement names it.
So delete always needs `--acknowledge-data-loss`, before anything is prepared.

A retirement review you prepared earlier that is still open (for example one
whose answer was lost) is resumed instead of preparing another; `--new-review`
prepares a fresh one. `--review-only` stops after the review and prints the
command that confirms it. `--wait` follows the retirement until it settles.

```bash
ankra services delete <service> [flags]
```

**Examples**

```bash
ankra services delete orders-db --acknowledge-data-loss
ankra services delete orders-db --acknowledge-data-loss --review-only
ankra services delete orders-db --cluster prod --acknowledge-data-loss --yes --wait
```

**Flags**

| Flag | Default | Description |
|------|---------|-------------|
| `--acknowledge-data-loss` | `false` | Acknowledge that retiring deletes the service's data (required) |
| `--cluster` |   | The cluster the service runs on, when its name is not unique (name or id) |
| `--new-review` | `false` | Prepare a new retirement review even if one of yours is still open |
| `-o`, `--output` |   | Output format: json or yaml (default: human-readable) |
| `--review-only` | `false` | Prepare and show the retirement review, but do not confirm it |
| `--timeout` | `30m0s` | How long `--wait` follows the retirement |
| `--wait` | `false` | Follow the retirement until it settles; exit non-zero unless it settled retired |
| `-y`, `--yes` | `false` | Confirm the reviewed retirement without asking |

## ankra services disconnect

Disconnect one application environment from a managed service. The service
keeps running for its other applications, and nothing is deleted: the service,
its data and its credentials stay.

It is two steps on the platform. First a disconnection review is prepared: the
platform works out what disconnecting does and stores that plan with a digest
for ten minutes. Preparing changes nothing. The review is shown in the
platform's own words:

```text
Variables         the variables the application stops receiving (DATABASE_URL,
                  ...) and, when another service of the same kind is
                  connected, who gives the conventional names from now on
Credential        every application of a service shares one credential
                  today, so it is not revoked: the application keeps the
                  password it has. What that cannot guarantee, and how to
                  make sure the application can no longer authenticate
                  (rotate the password, for every application)
Secret            the connection Secret in the application's namespace,
                  which Ankra keeps until no pod reads it
Workloads         the deployed workloads that read it: those Ankra attached
                  it to roll on the next deploy, those that refer to it by
                  hand must be changed by a person
Network           whether the namespace loses access to the service's port
                  (--keep-network-access keeps it)
Timing            the application keeps working until it is deployed again
What stays        what is left in place afterwards
```

The application is disconnected only when you confirm the review: at the
prompt, or with `--yes`. Without a terminal to ask on, `--yes` is required.
`--review-only` shows the review and confirms nothing.

`--application` names the application, and `--environment` the environment when
the application uses the service from more than one. `--consumer` names one
consumer by its id instead ('ankra services get &lt;service&gt;' lists them), for
example a namespace no environment is deployed to.

When the service gives the application its conventional connection names
(DATABASE_URL, REDIS_URL, ...) and another service of the same kind is
connected too, the review asks who gives them from now on. `--names-from`
&lt;service&gt; chooses that service and `--names-from` none chooses nobody; without it
the review is shown and nothing is confirmed.

'ankra services get &lt;service&gt;' shows the disconnection until it has finished.

```bash
ankra services disconnect <service> [flags]
```

**Examples**

```bash
ankra services disconnect orders-db --application storefront
ankra services disconnect orders-db --application storefront --environment staging --review-only
ankra services disconnect orders-db --application storefront --names-from orders-db-v2 --yes
ankra services disconnect orders-db --consumer 5b1f0c7e-0d7a-4c55-a6f4-2f1f4a9b1c11 --keep-network-access -o json --yes
```

**Flags**

| Flag | Default | Description |
|------|---------|-------------|
| `--application` |   | The application to disconnect (name or id) |
| `--cluster` |   | The cluster the service runs on, when its name is not unique (name or id) |
| `--consumer` |   | The consumer to disconnect, by id ('ankra services get' lists them), instead of `--application` |
| `--environment` |   | The application's environment, when it uses the service from more than one (name or id) |
| `--keep-network-access` | `false` | Keep the application's namespace allowed on the service's port |
| `--names-from` |   | When the review asks: the connected service (name or id) that gives the conventional connection names (DATABASE_URL, ...) from now on, or none |
| `-o`, `--output` |   | Output format: json or yaml (default: human-readable) |
| `--review-only` | `false` | Prepare and show the disconnection review, but do not confirm it |
| `-y`, `--yes` | `false` | Confirm the reviewed disconnection without asking |

## ankra services get

Show one managed service by name or id: its package, cluster and location, its
deployment state, health and readiness with the evidence behind each, how it
is reached (endpoints and the Secret holding its credentials), the consumers
it was set up for with how each receives the connection, the applications
being disconnected from it, and the latest retirement if one was confirmed.

A consumer on the service's cluster receives the connection as a
&lt;service&gt;-connection Secret in its namespace, read as environment variables,
whose names are listed. Its delivery reads delivered, pending (not delivered
yet; Pickup says what it waits for), unsupported (for example a consumer on
another cluster, which needs the values set by hand) or unknown.

Pickup says how far the application is from running with the connection:

```text
waiting_for_service  the service has no credentials yet; Ankra delivers the
                     connection once it has
delivering           no running pod reads it, so Ankra is writing it without
                     a redeploy or restart
holder_gone          waits for you to choose which service provides the
                     standard names (DATABASE_URL, ...)
redeploy_needed      Ankra leaves it to a deploy; a deploy usually writes
                     it and connects the workloads to it, but not always
                     (the delivery reason says what is needed)
restart_needed       running pods started before it arrived; restart them
                     to pick it up (Ankra does not restart them)
in_use               every running pod that reads it has it
```

A value not listed here comes from a newer platform and is shown as sent.
"Defined twice" lists the connection's variables that the application's
workloads also get from another source. Ankra holds back a connection that
is not delivered yet until that is resolved; the delivery reason says how.

An application being disconnected ('ankra services disconnect') is no longer
one of the consumers; until the disconnection finishes it is listed under
Disconnecting, with its phase:

```text
draining   Ankra keeps the connection Secret until no pod and no deployed
           workload reads it; a deploy of the application rolls the
           workloads Ankra attached it to
removing   the connection Secret is being removed
revoking   the namespace's access to the service's port is being removed,
           where the review said it would be
```

A phase not listed here comes from a newer platform and is shown as sent.

The connection names the Secret and its keys only. Credential values are never
shown here; they stay in the cluster.

A name that runs on more than one cluster needs `--cluster`.

```bash
ankra services get <service> [flags]
```

**Examples**

```bash
ankra services get orders-db
ankra services get orders-db --cluster prod -o json
```

**Flags**

| Flag | Default | Description |
|------|---------|-------------|
| `--cluster` |   | The cluster the service runs on, when its name is not unique (name or id) |
| `-o`, `--output` |   | Output format: json or yaml (default: human-readable) |

## ankra services list

List the organisation's managed services: each with its cluster, package,
deployment state, health and readiness.

Deployment state is the recorded operation progress (accepted, deploying,
verification_pending, deployment_failed, ...), not current health. Health is
what the platform last observed from the cluster (serving, progressing,
degraded, unknown). Readiness says whether a consumer can use the service: a
canary connects with the generated credentials (ready, verifying, degraded,
stale); a service no canary covers, or whose cluster's agent is too old to
run one, reads unverified.

`--application` keeps the services an application uses: those whose reviewed
plan names one of the application's namespaces as a consumer. The
application is given by name or id, and a Used by column says which of its
environments each service serves (or the namespace, where the application is
not deployed yet).

Retired services keep their record; `--include-released` lists them too.

```bash
ankra services list [flags]
```

**Examples**

```bash

```

**Flags**

## ankra services packages collisions

## ankra services packages init

Write a service package (contract schema 2) for one version of a stack profile
this organisation owns, so the services it deploys can be set up from the
catalogue and connected to applications like Ankra's own.

The skeleton pins the profile version and names the protocol consumers speak
(nats, opensearch, postgres, redis, s3, victorialogs, victoriametrics). Before publishing, fill in
what only you know about the engine the profile deploys:

```text
connection.endpoints[0].service  the Service consumers connect to
connection.endpoints[0].port     its port
connection.secret_name           the Secret holding its credentials
connection.fields                which key of that Secret holds each field
```

Publication refuses the package until these are filled in.

To make a service from one Helm chart rather than a stack profile, pass
`--addon` with `--registry` and `--chart-version` instead of `--profile` and
`--profile-version`: init first creates a stack profile holding that chart
alone (installed into a namespace named after each service), then writes the
package pinned to it.

With `--generate-secret`, that profile also generates the service's
credentials: a Secret of that name in each service's namespace, created on
the first install and kept unchanged across upgrades. Name its keys with
`--generate-key`: "password" for a random value, "password:48" for a random
value of 48 characters. Random values are generated in the cluster and Ankra
never sees them. "username=app" sets a fixed value, which is stored in the
profile and visible on the command line, so use it only for names (a user or
database name), never for a password. Point the chart at the Secret in
`--values` (most charts take an existing-secret setting); the package's
connection names it already.

```bash
ankra services packages init [flags]
```

**Examples**

```bash
ankra services packages init --profile <profile-id> --profile-version <version-id> \
  --name dragonfly-cache --protocol redis -f dragonfly-cache.json
ankra services packages init --addon dragonfly --registry dragonfly --chart-version 1.2.0 \
  --values dragonfly-values.yaml --name dragonfly-cache --protocol redis -f dragonfly-cache.json
ankra services packages init --addon postgresql --registry bitnami --chart-version 16.4.2 \
  --generate-secret orders-db-auth --generate-key username=app --generate-key password \
  --values orders-db-values.yaml --name orders-db --protocol postgres -f orders-db.json
ankra services packages publish -f dragonfly-cache.json
```

**Flags**

| Flag | Default | Description |
|------|---------|-------------|
| `--addon` |   | make the service from this Helm chart instead of a stack profile |
| `--capability` |   | what the package provides (defaults to the protocol's usual one) |
| `--chart-version` |   | the chart version `--addon` pins |
| `-f`, `--file` |   | write the skeleton to this file instead of standard output |
| `--generate-key` | `[]` | a key of `--generate-secret`: key (random), key:length (random of that length) or key=value (a fixed, non-secret name such as a user); repeatable |
| `--generate-secret` |   | with `--addon`, a Secret of this name the profile generates in each service's namespace |
| `--name` |   | package name (a DNS label, for example dragonfly-cache) |
| `--profile` |   | id of the stack profile the package deploys |
| `--profile-version` |   | id of the profile version to pin |
| `--protocol` |   | wire protocol consumers speak: nats, opensearch, postgres, redis, s3, victorialogs, victoriametrics |
| `--registry` |   | the Helm registry `--addon` comes from (as named in Ankra) |
| `--values` |   | a values file for the `--addon` chart |
| `--version` | `1.0.0` | package version (semantic version) |

## ankra services packages probe

Probe the connection a package file declares against a running demo of its
stack profile, before publishing: Ankra runs the protocol's readiness canary
in the demo's namespace, the same one that verifies a published package.

Without `--wait` the probe is only queued. With `--wait` the command follows it
and exits 0 only when the verdict is passed; failed and unknown (the canary
could not run, or the demo stopped) exit 1 with the reason, and a probe still
running when `--timeout` ends exits 5.

```bash
ankra services packages probe [flags]
```

**Examples**

```bash
ankra services packages probe --profile <profile-id> --demo <workspace-id> -f dragonfly-cache.json --wait
```

**Flags**

| Flag | Default | Description |
|------|---------|-------------|
| `--demo` |   | id of the running demo (its workspace id) |
| `-f`, `--file` |   | package file whose connection is probed (- for standard input) |
| `-o`, `--output` |   | Output format: json or yaml (default: human-readable) |
| `--profile` |   | id of the stack profile the demo runs |
| `--timeout` | `10m0s` | how long `--wait` follows the probe |
| `--wait` | `false` | follow the probe to its verdict; exit 0 only if it passed |

## ankra services packages propose

Read a running demo of a stack profile on the organisation's staging cluster
and propose the connection blocks a service package made from that profile
could declare: one per Service port speaking a protocol Ankra connects
applications to, each field mapped to a key of the Secret that holds the most
of the credentials. Only Service ports and Secret key names are read, never
Secret values, and nothing is tried: probe a proposal with
'ankra services packages probe' before publishing.

With -f, the best complete proposal is written into that package file (made
by 'ankra services packages init'), replacing its connection.

A demo whose namespace could not be observed exits 1 with the reason, so an
unobserved namespace is never read as one with nothing to propose.

```bash
ankra services packages propose [flags]
```

**Examples**

```bash
ankra services packages propose --profile <profile-id> --demo <workspace-id>
ankra services packages propose --profile <profile-id> --demo <workspace-id> -f dragonfly-cache.json
```

**Flags**

| Flag | Default | Description |
|------|---------|-------------|
| `--demo` |   | id of the running demo (its workspace id) |
| `-f`, `--file` |   | write the best complete proposal into this package file |
| `-o`, `--output` |   | Output format: json or yaml (default: human-readable) |
| `--profile` |   | id of the stack profile the demo runs |

## ankra services setup

Set up a managed service on a cluster, in two steps.

First a review is prepared: the platform resolves the package, the cluster's
placement policy and every consumer, and stores the plan with a digest for ten
minutes. Preparing changes nothing. The plan is shown, and the service is set
up only when you confirm it: at the prompt, or with `--yes`. The confirmation
carries the digest of the plan you saw, so a plan that changed in between is
refused rather than deployed.

`--review-only` stops after the review and prints the command that confirms it
('ankra services reviews confirm &lt;id&gt; `--digest` &lt;digest&gt;'), for a person or a
pipeline that approves separately.

The name becomes the service's namespace on the cluster: lower-case letters,
digits and single hyphens, starting with a letter. Ankra's engines also need
it to be at most 36 characters and not a system namespace (default, kube-*,
ankra*, cert-manager, ...); the platform refuses any other name when the
review is prepared, before anything is stored.

Every setup needs at least one consumer (`--consumer`, from 'ankra services
consumers bind'). The region and data boundary default to the cluster's
placement policy. Parameters (`--param`) default to the package's defaults;
'ankra services packages get &lt;package&gt;' lists them with their bounds.

Confirming starts the deployment; it is not proof that the service is ready.
Follow it with 'ankra services get &lt;name&gt;'.

```bash
ankra services setup <name> [flags]
```

**Examples**

```bash
ankra services setup orders-db --package postgresql --cluster prod --consumer 5b1f0c7e-0d7a-4c55-a6f4-2f1f4a9b1c11
ankra services setup orders-db --package postgresql@1.0.0 --consumer <id> --param storage_gib=20 --param instances=3
ankra services setup orders-db --package postgresql --consumer <id> --review-only
ankra services setup orders-db --package postgresql --consumer <id> --yes -o json
```

**Flags**

| Flag | Default | Description |
|------|---------|-------------|
| `--cluster` |   | The cluster to run the service on (name or id; default: the selected cluster) |
| `--consumer` | `[]` | Consumer binding id the service is for (repeatable; 'ankra services consumers bind') |
| `--data-boundary` |   | Data boundary (default: the cluster's placement policy) |
| `--mode` | `customer` | Operating mode: customer (runs on your cluster) or existing |
| `-o`, `--output` |   | Output format: json or yaml (default: human-readable) |
| `--package` |   | The package to set up: name, name@version or id ('ankra services packages list') |
| `--param` | `[]` | Package parameter as name=value (repeatable) |
| `--region` |   | Physical region (default: the cluster's placement policy) |
| `--review-only` | `false` | Prepare and show the review, but do not confirm it |
| `--secret-reference` | `[]` | Secret input as name=&lt;credential grant id&gt; (repeatable); values are never accepted |
| `-y`, `--yes` | `false` | Confirm the reviewed plan without asking |
