## ankra chat

AI-powered chat for troubleshooting and assistance.

If a message is provided, sends a one-shot question and prints the
conversation id so a follow-up can continue it with `--conversation`.
If no message is provided, enters interactive chat mode.

Use `--cluster` to provide cluster context for better answers; without it the
persisted 'ankra cluster select' applies, and with neither the chat reads
across the whole organisation.

A one-shot question takes -o json (or -o yaml) for scripts and CI jobs: the
answer is printed once, when the turn ends, as one document carrying the
answer text, the conversation id, the safety mode the turn ran in, the
cluster it was scoped to, the tools the model ran and any write left
awaiting confirmation. A turn that starts and then fails still prints the
document, with its "error" member set, and exits non-zero; a question the
platform refuses to start (a rejected token, an unknown cluster) prints
nothing on stdout and exits with that error's code. The one exception is
AI paused by the organisation's billing standing: that refusal prints the
document with "error_code" BILLING_RESTRICTED and the platform's sentence in
"detail", whether it came before the turn or on it, so a job can tell it
from a failed answer. Interactive mode has no structured output.

A one-shot question can end before the conversation does, because the agent
paused on a condition and the platform resumes it by itself. That is not a
finished answer: the command exits 9, and the document's "state" reads
"waiting". Pass `--wait` to follow the conversation through its pauses instead;
it exits 5 if a pause outlasts `--wait-timeout`, with the conversation still
running. "state" is otherwise "completed", "failed", or "awaiting_user" for a
turn that needs a confirmation or an answer, which exits 0.

```bash
ankra chat [message] [flags]
```

**Examples**

```bash
# Ask once, scoped to a cluster
ankra chat --cluster prod "why is the payments pod restarting?"

# The same, parsed in a CI job
ankra chat --cluster prod --mode ask -o json "summarise failing pods" | jq -r .answer

# Continue the conversation a previous answer named
ankra chat --conversation <id> "and the one before that?"

# Follow the agent through a pause, up to 30 minutes
ankra chat --wait --wait-timeout 30m "upgrade the addon and check it came up"
```

**Flags**

| Flag | Default | Description |
|------|---------|-------------|
| `--cluster` |   | Cluster name for context |
| `--conversation` |   | Continue an existing conversation (id from 'ankra chat history' or a previous answer) |
| `--mode` |   | Safety mode: 'ask' (read-only + safe creations) or 'agent' (can act). Defaults to the server default. |
| `-o`, `--output` |   | Output format: json or yaml (default: human-readable) |
| `--wait` | `false` | With a one-shot question, follow the conversation through the agent's pauses instead of exiting 9 at the first one |
| `--wait-timeout` | `4h0m0s` | How long `--wait` follows a paused conversation before exiting 5 |

## ankra chat actions

Agent-mode chat halts before every write and proposes it as a pending
action. Confirm the action to run it, or reject it to discard it.

Pending actions expire, so confirm promptly. If the cluster changed since the
action was proposed, confirming answers a drift conflict; re-run with `--force`
to apply it against the changed state anyway.

## ankra chat actions confirm

Confirm a pending action proposed by agent-mode chat.

The platform re-checks the action against live cluster state before running
it. If the state drifted since the proposal, the command reports the drift and
exits without running anything; pass `--force` to run it anyway.

```bash
ankra chat actions confirm <action_id> [flags]
```

**Examples**

```bash
# Confirm the action id printed by the chat stream
ankra chat actions confirm 6f1c2f9e-6d5a-4a1e-9f0b-6d4c2b8a1e77

# Apply it even though the cluster drifted since it was proposed
ankra chat actions confirm 6f1c2f9e-6d5a-4a1e-9f0b-6d4c2b8a1e77 --force \
  --force-reason "drift is an unrelated label change"
```

**Flags**

| Flag | Default | Description |
|------|---------|-------------|
| `--force` | `false` | Confirm even though cluster state drifted since the action was proposed |
| `--force-reason` |   | Why the drift is acceptable (recorded in the audit trail, max 280 characters) |
| `-o`, `--output` |   | Output format: json or yaml (default: human-readable) |

## ankra chat plans

A chat conversation that needs several writes proposes them as one plan and
halts. Approving the plan runs its steps in order; rejecting it discards them.

Plans expire, so decide promptly. A plan with high-risk or irreversible steps
is only approved when each of those steps is named with `--acknowledge`.

## ankra chat plans approve

Approve a proposed plan and follow its steps as they run.

Approving is the decision: there is no further prompt, exactly as with
'ankra chat actions confirm'. Read the plan first with
'ankra chat plans get &lt;plan_id&gt;'. A plan with high-risk or irreversible steps
is refused, with nothing run, until each of those steps is named with
`--acknowledge` &lt;step-order&gt;; the refusal lists them. It needs the ai.execute
permission.

Exit codes: 0 when every step completed (or the plan was handed to the chat
session that proposed it, which runs the steps), 8 when steps still need
`--acknowledge`, 3 when the plan is not found, 1 when the plan could not be
approved or a step failed.

```bash
ankra chat plans approve <plan_id> [flags]
```

**Examples**

```bash
ankra chat plans approve 6f1c2f9e-6d5a-4a1e-9f0b-6d4c2b8a1e77

# Accept the two steps the refusal named as high-risk or irreversible
ankra chat plans approve 6f1c2f9e-6d5a-4a1e-9f0b-6d4c2b8a1e77 --acknowledge 2,4
```

**Flags**

| Flag | Default | Description |
|------|---------|-------------|
| `--acknowledge` | `[]` | Step order of a high-risk or irreversible step you accept; repeat or separate with commas |
| `-o`, `--output` |   | Output format: json or yaml (default: human-readable) |
