Most of the work in an audit is not deciding what your controls are - it is proving they were in effect on a given date. Ankra produces that proof for the part of your estate it manages: benchmark results, policy state, vulnerability posture over time, and an attestation of the organisation controls that are switched on.

This page covers what you can generate, what each piece proves, and where the limits are.

---

## The compliance report

The organisation compliance report is a single export that gathers the evidence an assessor usually asks for in one document. Generate it from **Organisation** &rarr; **Security**, or pull it via the API for a scheduled evidence job:

```bash
curl -sS \
  -H "Authorization: Bearer <your-token>" \
  "https://platform.ankra.app/org/security/compliance-report?format=json&start_date=2026-07-01&end_date=2026-07-31" \
  -o compliance-report-july.json
```

Both `json` (default) and `csv` are supported, and the date range bounds the audit-activity section.

### What it contains

| Section | What it proves |
|---------|----------------|
| **Posture** | Each cluster's latest daily security snapshot, so you can show the state on a specific date rather than only today |
| **Findings** | Open vulnerability findings by severity, with a count of severe findings that have a fix available |
| **Dispositions** | The vulnerability dispositions currently in effect - what was acknowledged or accepted as risk, by whom, and until when |
| **Audit summary** | A summary of administrative actions over the requested window |
| **Attestation** | Organisation control state: whether MFA is required, whether SOPS is initialised, whether the security baseline is enabled, and which clusters have the scanner installed |
| **Compliance** | Live benchmark rollup per cluster, with pass and fail totals per benchmark |

<Note>
The report requires **both** the security read and audit read permissions. A caller holding only one receives a `403` naming the permission they are missing, which is deliberate: the report combines security posture with audit activity, so it should not be obtainable with half the access.
</Note>

## Benchmark compliance

When [Trivy Operator](/guides/cluster-security) runs in a cluster, Ankra ingests its cluster compliance reports and rolls them up per cluster on the **Compliance** tab. Three benchmark specifications are covered:

| Benchmark | What it checks |
|-----------|----------------|
| CIS Kubernetes Benchmark | Control plane, kubelet, etcd and workload configuration against the CIS baseline |
| NSA/CISA Kubernetes Hardening Guidance | The NSA and CISA hardening recommendations |
| Kubernetes Pod Security Standards | Pod-level security posture against the PSS levels |

Each cluster reports pass and fail totals per benchmark, and the per-cluster view lists the failed checks with their remediation. Scanning runs inside your cluster and only findings metadata reaches the platform - no image contents leave.

A cluster without the scanner installed reports an explicit **not available** status rather than silently counting as passing. That distinction matters in an audit: an unscanned cluster is a coverage gap, not a clean result.

## Policy enforcement

The security baseline installs Kyverno with the Pod Security Standards baseline policy set. Policy results aggregate onto the **Policies** tab per cluster, so you can show which workloads violate the baseline.

Policies install in **audit** mode, reporting violations without blocking deployments. When you are ready to enforce, switch the mode from the cluster's security view. Enforcement rejects non-conforming workloads at admission.

<Warning>
Switching from audit to enforce blocks deployments that violate the baseline. Review the current violations on the Policies tab and fix or exempt them before switching, otherwise the next deploy of a non-conforming workload fails.
</Warning>

Running in audit mode still produces evidence - you can demonstrate that the control exists and that violations are monitored, which satisfies many configuration-management criteria even before enforcement.

## Posture over time

Daily snapshots build a trend, which is what distinguishes a real programme from a point-in-time cleanup. Most frameworks care that posture is managed continuously, and a trend line showing findings closing over a period is stronger evidence than a single clean scan on audit day.

Scheduled [security reports](/guides/security-reports) deliver the same posture by email on a cadence, which doubles as evidence that review actually happens.

## Turning this into an audit response

<Steps>
  <Step title="Establish coverage">
    Show which clusters are managed and which have the scanner installed. The attestation section lists both. Coverage gaps are the first thing an assessor looks for.
  </Step>
  <Step title="Show the control is configured">
    Point at the attestation flags - MFA required, security baseline enabled, SOPS initialised - and at the benchmark and policy results per cluster.
  </Step>
  <Step title="Show the control operated over the period">
    Attach posture snapshots across the audit window and the [audit export](/security/audit-export) for the same window. Configuration proves design; the trail proves operation.
  </Step>
  <Step title="Show exceptions were governed">
    The dispositions section records what was accepted as risk, by whom, and when it expires. An accepted risk with an owner and a review date is a managed exception. An unexplained open finding is not.
  </Step>
</Steps>

## Limits worth stating up front

- **Ankra evidences the clusters it manages.** Clusters outside Ankra are outside this evidence, and an assessor will ask about them.
- **Benchmark results come from the scanner, not from Ankra.** Ankra ingests, aggregates and retains Trivy Operator's output. The authority for a given check is the benchmark specification, and a cluster without the scanner produces no result at all.
- **The report is input to your programme, not the programme.** It does not assert that your controls are effective, and it does not replace your risk assessment, policy set or management review.
- **Nothing here certifies your environment.** The platform produces evidence; your assessor draws the conclusion.

## Ankra's own compliance posture

Everything above is evidence about **your** environment. A separate question comes up in procurement: what is Ankra's own certification status?

Ankra runs an internal information security management system covering the platform, and the current, honest state of that work - which certifications are held, which controls are implemented, and what is still in progress - is published at [ankra.ai/trust](https://ankra.ai/trust), alongside the sub-processor and hosting list.

<Warning>
Take Ankra's certification status from [ankra.ai/trust](https://ankra.ai/trust) or from us directly, never from this documentation. That page is the single source of truth and it changes as the programme progresses. Documentation lags; the trust page does not.
</Warning>

For how Ankra's posture does and does not affect the scope of your own certification, see [Shared Responsibility](/security/shared-responsibility).
